# Matt Pocock Skills — 面向真正工程师的 AI 编程技能库

> **一句话概括：** TypeScript 大神 Matt Pocock 开源的个人 Claude Code 技能库，把 AI 放进成熟的软件工程约束里，120K+ GitHub Star。

## 项目背景

**Matt Pocock** 是 TypeScript 社区知名专家，**Total TypeScript** 创始人。他开源的 [mattpocock/skills](https://github.com/mattpocock/skills) 是他的个人 Claude Code 配置，GitHub 上获得 **120K+ Star**。

> ⚠️ 本文档基于 **2026-07 最新版本**（GitHub API 实时核对），只包含当前存在的命令。

### 核心理念

> **不要把 AI 当成"自动驾驶"，把它当成一个需要约束的初级工程师。**

- AI 写代码很快，但容易跑偏、产生幻觉、在长对话中迷失
- 解决方法是**用工程流程约束 AI**，而不是让它自由发挥
- 每个 Skill 是独立可组合的 Markdown 指令文件，只负责一件事

### 两种调用方式

| 类型 | 含义 | 例子 |
|------|------|------|
| **用户主动调用**（User-invoked） | 只有你输入 `/命令` 才触发，负责编排流程 | `/grill-me`、`/wayfinder` |
| **模型自动调用**（Model-invoked） | 你可以主动输入，AI 也会在合适时机自动使用 | `/tdd`、`/code-review` |

> 规则：用户主动调用的技能可以调用模型自动技能，但不会调用另一个用户主动技能。

## 快速上手

```bash
# 安装（二选一，不要都装）
# 方式一：Claude Code 插件（自动更新）
/plugin install mattpocock-skills

# 方式二：复制到你项目里（可自由修改）
npx skills@latest add mattpocock/skills

# 每个仓库运行一次初始化
/setup-matt-pocock-skills
```

`/setup-matt-pocock-skills` 会问你三个问题：
1. 用哪个 Issue 追踪器（GitHub / Linear / 本地文件）
2. 打什么标签（`/triage` 会用）
3. 文档保存到哪里

## 技能详解（带使用示例）

> 示例中 `你:` 是你要输入的内容，`→` 后面是 AI 会做的事。标注 `(模型)` 的技能 AI 也会自动调用。

---

### 🛠️ 工程类（Engineering）— 用户主动调用

#### `/ask-matt` — 技能路由器

> 当你不知道用什么技能时，先问它。它像一个路由器，根据你的情况推荐合适的技能或流程。

```
你: /ask-matt 我想给项目加个搜索功能，该用什么流程？

→ AI 分析你的情况：
   "建议先 /wayfinder 理清范围，再 /to-spec 写规范，
    然后 /to-tickets 拆任务，最后 /implement 实现。"
```

**结果：** 不用记全部命令，让 Matt 帮你选。

---

#### `/wayfinder` — 大项目路线图规划

> 当任务大到超过一次 AI 会话能承载时，用它把工作拆成一张"决策地图"，在 Issue 追踪器上逐个解决决策点，直到路线清晰。产出 `wayfinder:map` 标签的地图 Issue。

```
你: /wayfinder 我要重构整个支付系统（跨 20 个模块）

→ AI 在 Issue 追踪器上创建一张地图：
   ├── Map: 重构支付系统（标签 wayfinder:map）
   │   ├── 决策票1: 选哪个支付网关？
   │   ├── 决策票2: 数据库怎么迁移？
   │   ├── 决策票3: 旧接口怎么兼容？
   │   └── ...
→ 你逐个解决决策票，每解决一个路线就清晰一分
→ 所有决策都定了，路线清晰，交给 /to-spec
```

**结果：** 一个超大任务被拆成一张可逐步推进的决策地图，不会淹没在一次会话里。

---

#### `/to-spec` — 生成技术规范

> 把当前对话内容直接转化为一份 spec（类似 PRD），发布到 Issue 追踪器。**不会追问你**——只综合你已经讨论过的内容。

```
你: /to-spec
     （前提：项目已初始化，你对方案已经讨论过了）

→ AI 探索代码库，理解现状
→ AI 起草测试接缝（在哪里测这个功能）
→ 和你确认接缝是否合理
→ AI 生成 spec，包含：问题描述、解决方案、接缝设计
→ 发布到 Issue 追踪器，打上 ready-for-agent 标签
```

**结果：** 一份可以直接交给 AI 实现的技术规范文档。

---

#### `/to-tickets` — 拆解任务

> 把 spec、计划或对话拆成一组"曳光弹"垂直切片任务（tickets），每个都声明它被谁阻塞。发布到 Issue 追踪器。

```
你: /to-tickets
     （前提：项目里有 spec）

→ AI 读取 spec
→ AI 拆成一组垂直切片任务：
   ├── Ticket 1: 搭建脚手架（阻塞：无）
   ├── Ticket 2: 上传接口（阻塞：Ticket 1）
   ├── Ticket 3: 简历解析（阻塞：Ticket 2）
   └── ...
→ 发布到追踪器，标注每个 ticket 的阻塞关系
```

**结果：** 一份带依赖关系的任务清单，可以按顺序逐个实现。

---

#### `/implement` — 实现任务

> 根据 spec 或一组 tickets 实现代码。在约定的接缝处驱动 `/tdd`，完成后自动用 `/code-review` 审查，然后提交。

```
你: /implement
     （前提：项目里有 spec 或 tickets）

→ AI 按 spec 实现代码
→ 在每个接缝处用 /tdd（先写测试再写实现）
→ 定期跑类型检查、单个测试
→ 最后跑完整测试套件
→ 用 /code-review 审查
→ 提交到当前分支
```

**结果：** 一个从 spec 到提交的完整实现流程，不用你手动指挥每一步。

---

#### `/triage` — Issue 分类

> 把 Issue 追踪器上的新 Issue 按状态机分类处理：分类（bug/增强）→ 验证 → 需要时追问 → 写成 AI 可执行的简报。

```
你: /triage

→ AI 处理追踪器上的新 Issue：
   ├── Issue #42: "登录报错" → 分类为 bug
   ├── Issue #43: "想要深色模式" → 分类为 enhancement
   └── 每个都验证、必要时追问、写成 agent 简报
```

**结果：** 一堆乱糟糟的 Issue 被整理成清晰的待办队列。

---

#### `/grill-with-docs` — 追问并固化文档

> 一次"拷问式"需求澄清，同时建立项目的领域模型——澄清术语、更新 `CONTEXT.md`、把难做的决策写进 ADR。

```
你: /grill-with-docs 我们打算用 PostgreSQL 换掉 MongoDB

→ AI 轮流追问："迁移期间数据一致性怎么保证？""团队熟悉 SQL 吗？"
→ 你回答后，AI 自动：
   ├── 更新 CONTEXT.md（统一术语）
   └── 新增 docs/adr/XXX（记录决策理由）
```

**结果：** 需求被拷问清楚，术语和决策也固化成了文档。Matt 本人说这可能是全仓库最强大的技能。

---

#### `/improve-codebase-architecture` — 架构体检

> 扫描代码库找"加深机会"（把浅层模块变成深层模块），产出可视化 HTML 报告，然后针对你选的改进点继续追问。

```
你: /improve-codebase-architecture

→ AI 扫描代码库，生成 HTML 报告：
   ├── 问题1: 4 个日志工具该合并成 1 个（推荐强度: 强）
   ├── 问题2: 用户模块和订单模块耦合过紧（推荐强度: 值得探索）
   └── 每个都带：涉及文件、解决方案、收益、前后对比图
→ 你挑一个，AI 深入追问直到方案清晰
```

**结果：** 一份可视化架构体检报告 + 针对选定问题的深度讨论。建议每几天跑一次。

### 🛠️ 工程类（Engineering）— 模型自动调用

#### `/tdd` — 测试驱动开发 `(模型)`

> 强制 RED→GREEN→REFACTOR 循环，一次一个垂直切片构建功能或修 bug。

```
你: /tdd 帮我实现计算购物车总价的函数

→ Step 1 (RED): 先写 test('2件商品总价100') → 运行失败
→ Step 2 (GREEN): 写最少代码让测试通过 → 通过
→ Step 3 (REFACTOR): 优化 → 测试依然通过
```

**结果：** 每段代码都有测试兜底。

---

#### `/diagnosing-bugs` — 系统化调试 `(模型)`

> 有纪律的调试循环：复现 → 最小化 → 假设 → 插桩 → 修复 → 回归测试。适用于难缠 bug 和性能回退。

```
你: /diagnosing-bugs 用户登录偶尔报 500

→ AI 按循环走：
   1. 复现：什么条件触发？
   2. 最小化：缩小到最小复现案例
   3. 假设：token 过期？连接池耗尽？
   4. 插桩：加日志确认
   5. 修复
   6. 回归测试：确认没引入新问题
```

**结果：** 找到根因，不是瞎猜。

---

#### `/research` — 网络调研 `(模型)`

> 针对问题调研高可信度的一手资料，把结论写成带引用的 Markdown 存到仓库，作为后台代理运行。

```
你: /research React Query 和 SWR 哪个适合我们的项目？

→ AI 后台搜索一手资料
→ 产出带引用的调研文档存到仓库
→ 给出对比结论和建议
```

**结果：** 一份带引用来源的调研报告。

---

#### `/code-review` — 代码审查 `(模型)`

> 从两个维度并行审查 diff：**规范**（是否遵守编码规范 + Fowler 坏味道基线）和 **Spec**（是否忠实实现了源 Issue/PRD）。用并行子代理跑，互不污染。

```
你: /code-review
     （前提：有未提交的改动）

→ AI 并行两个子代理：
   ├── 子代理1: 检查编码规范、坏味道
   └── 子代理2: 对照 spec 检查实现是否忠实
→ 汇总两份报告
```

**结果：** 一份双维度审查报告。

---

#### `/domain-modeling` — 领域建模 `(模型)`

> 主动构建和打磨项目的领域模型——用边界场景挑战术语、对照术语表检查，内联更新 `CONTEXT.md` 和 ADR。

```
你: （在讨论业务逻辑时，AI 自动触发）
→ AI 检查：你用的"结账"一词和 CONTEXT.md 里的定义一致吗？
→ 发现矛盾 → 讨论澄清 → 更新 CONTEXT.md
```

**结果：** 项目术语始终一致，代码命名也跟着统一。

---

#### `/codebase-design` — 代码库设计 `(模型)`

> 设计深层模块的共享纪律和词汇：大量行为藏在简单接口后面，放在干净的接缝处，通过接口可测试。

```
你: /codebase-design 帮我设计一个文件上传模块

→ AI 按深层模块原则设计：
   ├── 接口：upload(file) → UploadResult（简单）
   ├── 内部：校验、分片、重试、进度回调（丰富）
   └── 接缝清晰，可单独测试
```

**结果：** 一个接口简单但功能强大的模块设计。

---

#### `/resolving-merge-conflicts` — 解决合并冲突 `(模型)`

> 逐块处理进行中的 git merge/rebase 冲突，根据每一侧的源头追溯解决意图，然后完成操作——**永不 `--abort`**。

```
你: /resolving-merge-conflicts
     （前提：正在 merge/rebase 中）

→ AI 逐 hunk 处理冲突
→ 每个冲突：追溯两边意图 → 决定保留哪边
→ 全部解决 → 完成 merge/rebase
```

**结果：** 冲突被有意图地解决，而不是粗暴放弃。

---

#### `/prototype` — 原型验证 `(模型)`

> 构建一次性原型来回答设计问题——状态/逻辑问题用可运行的终端应用，UI 问题用多个差异很大的页面变体，从单一路由切换。

```
你: /prototype 验证一下支付流程的状态机设计

→ AI 构建一个可运行的终端原型
→ 你操作体验：下单→支付→退款，各状态流转是否合理
→ 确认后丢弃原型，正式实现
```

**结果：** 花最小代价验证设计，不浪费正式代码。

### ⚡ 效率类（Productivity）— 用户主动调用

#### `/grill-me` — 方案压力测试

> 被 AI 不停地拷问你的计划/设计，直到决策树的每个分支都被解决。**不写代码，只问问题**。

```
你: /grill-me 我打算做个人记账 App

→ AI 轮流追问：
   "目标用户是谁？"
   "和随手记的区别是什么？"
   "用户懒得记账怎么办？"
   "免费还是收费？怎么活？"
   ...
→ 你回答到 AI 问无可问
```

**结果：** 方案漏洞被提前发现。这是 Matt 最受欢迎的技能，**每次做改动前都建议用**。

---

#### `/handoff` — 会话交接

> 把当前对话压缩成交接文档，让另一个 AI（或下一个会话）能继续工作。

```
你: /handoff
     （工作做到一半）

→ AI 生成交接文档：
   ├── 已完成：登录模块
   ├── 进行中：支付模块写到一半
   ├── 待办：退款功能
   ├── 已知问题：金额精度
   └── 下一步：从支付模块第3步继续
```

**结果：** 中断的工作不丢失，新会话无缝接续。

---

#### `/teach` — 多会话教学

> 用多个会话教你一个新技能/概念，用当前目录作为有状态的教学工作区。

```
你: /teach 教我用 Rust 的 trait

→ 会话1: 基础概念 + 第一个例子
→ 你练习，遇到问题回来
→ 会话2: 深入 + 进阶例子
→ 逐步推进直到掌握
```

**结果：** 分阶段学习，每次都有练习和反馈。

#### `/writing-great-skills` — 技能编写参考

> 教你如何写好技能——让技能可预测的词汇和原则。适合想自己写技能的进阶用户。

```
你: /writing-great-skills

→ AI 输出编写技能的原则：
   ├── description 怎么写才容易被触发
   ├── 指令要具体可预测
   └── 参考文件怎么组织
```

**结果：** 一份技能编写指南。

## 完整工作流（示例串联）

假设你要做"AI 简历筛选工具"：

```
1. /ask-matt "我该用什么流程？"      → 推荐路径
2. /wayfinder "做 AI 简历筛选"       → 理清范围，产出决策地图
3. /grill-with-docs "看看我的方案"    → 拷问需求 + 固化术语/决策
4. /to-spec                          → 生成技术规范（含接缝设计）
5. /to-tickets                       → 拆成带依赖的任务
6. /implement                        → 按 spec 实现（内部自动 /tdd + /code-review）
7. /diagnosing-bugs（如果出 bug）      → 系统化修 bug
8. /handoff（下班）                   → 交接文档
```

> 这是**工具箱**而非强制流水线——按需选用，不必每次从头走到尾。

## 核心哲学

> **"Skills for Real Engineers"——不是让 AI 接管你的开发流程，而是把 AI 放进你熟悉的软件工程约束里。**

每个 skill 独立可装：可以只装 `/grill-me` 验证想法，也可以装全套覆盖整个开发流程。
