# Superpowers — Claude Code 技能全家桶

> **一句话概括：** 一套让 Claude Code 从"随缘编程"变成"工程化开发"的 14 个强制技能——先思考、再计划、后编码、再审查，每一步都有章可循。

## 项目背景

**Superpowers** 由开发者 **Jesse Vincent (obra)** 创建，GitHub 上 **16,000+ Star**，是 Claude Code 生态中最流行的技能全家桶。它不是零散的提示词集合，而是一套**强制执行**的工程化工作流。

核心理念：**Process over Prompt（流程大于提示）**——靠流程保证质量，不靠提示词碰运气。

## 技能详解

### 1. using-superpowers｜元技能

> **元技能**——它是全家桶的"入口说明书"，确保你在做任何事之前先检查有没有技能可用。

#### 核心规则

- **1% 原则**：哪怕只有 1% 的概率某个技能能用，也必须先调用技能检查
- **技能优先于行动**：收到用户消息后，在任何回复（包括澄清问题）之前，先检查技能列表
- **指令优先级**：用户明确指令 > Superpowers 技能 > 默认系统提示

#### 警惕的"合理化借口"（Red Flags）

| 脑子里这么想 | 实际是 |
|-------------|--------|
| "这只是一个简单问题" | 问题也是任务，需要检查技能 |
| "让我先看看代码" | 技能会告诉你如何探索 |
| "我记得这个技能的内容" | 技能会更新，需要读最新版 |
| "这不需要正式技能" | 如果有技能存在，就用它 |

#### 工作流程

```
用户消息 → 检查是否有技能匹配 → 调用 Skill 工具
    → 宣告"使用 XX 技能来 XX"
    → 有清单？创建 TodoWrite
    → 按技能指示执行
    → 回复用户
```

### 2. brainstorming｜头脑风暴

> 在写任何代码之前，像苏格拉底一样**一次问一个问题**，把模糊想法变成清晰的设计文档。

#### 它解决了什么？

大多数问题在于：需求还没想清楚就开干，结果写出来的代码一遍遍改。Brainstorming 强制在"写代码之前"把需求聊透。

#### 工作流程

1. **探索项目上下文** — 了解已有代码、技术栈、文件结构
2. **逐一提问** — 一次只问一个问题，等用户回答后再问下一个（不是连珠炮）
3. **提出 2-3 种方案** — 每个方案说明权衡利弊
4. **分段确认** — 展示设计的关键部分，逐段获取用户批准
5. **输出设计文档** — 保存到 `docs/superpowers/specs/<日期>-<主题>-design.md`

#### 适用场景

| 场景 | 说明 |
|------|------|
| 一个新功能 | "我想加个用户头像上传" |
| 一个模糊的需求 | "代码库需要优化" → 具体怎么优化？ |
| 技术选型 | "用 A 库还是 B 库？" |
| 重构决策 | "这个模块要不要拆？" |

#### 典型追问节奏

```
AI: 头像上传的用户是谁？（只问这一个问题）
你: 所有注册用户
AI: 好。头像的尺寸限制和格式要求是什么？
你: 2MB 以内，支持 jpg/png
AI: 明白了。我有两个方案...
```

**实际体验参考**："前面花了两个小时被拷打需求，后面执行只用了 10 分钟，一遍过。"

### 3. writing-plans｜编写计划

> 把批准后的设计文档转换成**可执行的细粒度实现计划**，精确到文件路径和具体代码。

#### 核心要求

- ✅ **每个任务写清具体文件路径** — 不能模糊地说"修改相关文件"
- ✅ **尽量给出完整代码** — 禁止 TBD、TODO 占位符
- ✅ **细粒度步骤** — 每个步骤 2-5 分钟，默认按 TDD 拆
- ✅ **每个步骤包含验证命令** — 以及期望输出
- ✅ **自查** — 写完后检查覆盖度、占位符、类型一致性

#### 步骤粒度示例

```
1. 创建用户头像的测试文件 tests/UserAvatar.test.ts
   - 验证: npm test -- --testPathPattern=UserAvatar → 失败（RED）

2. 实现 UserAvatar 组件的最小代码 src/components/UserAvatar.tsx
   - 验证: npm test -- --testPathPattern=UserAvatar → 通过（GREEN）

3. 重构优化（提取常量、添加注释）
   - 验证: npm test → 全部通过

4. Git commit
```

#### 产出文档

`docs/superpowers/plans/<日期>-<功能>.md`

### 4. executing-plans｜执行计划

> 当不适合使用子代理时，按计划文档的顺序**逐个步骤执行**，遇到 blocker 才停。

#### 执行规则

1. **加载计划**后先审查一遍，有问题先问用户
2. **逐个执行**计划中的步骤，每步标记进度（in_progress → completed）
3. **持续执行**，遇到 blocker 才停（不同于旧版每三步一停）

#### 停止条件

遇到以下情况才停：
- **Blocker** — 依赖缺失、测试失败、指令不清晰
- **计划缺口** — 无法开始执行
- **不理解指令** — 需要澄清
- **验证反复失败** — 同一个步骤连续失败

#### 完成时

所有任务完成后，自动进入 `finishing-a-development-branch` 收尾流程。

> ⚠️ 如果平台支持子代理（Claude Code / Codex），官方推荐优先使用 `subagent-driven-development`，质量更高。

### 5. subagent-driven-development｜子代理驱动开发

> 把计划中的每个小任务派给**全新的子代理**执行，每个子代理有独立的上下文窗口，互不干扰。

#### 为什么更好？

- **上下文隔离** — 子代理干完活就消失，中间产生的"垃圾"不污染主会话
- **避免长上下文幻觉** — 每个子代理只看自己需要的文件，不会在长对话中"迷失"
- **并行执行** — 互不依赖的任务可以同时跑
- **可追溯** — 每个子代理的结果单独审查

#### 任务颗粒度

每个任务 2-5 分钟可以独立完成：

| 好例子（2-5 分钟） | 坏例子（太大） |
|-------------------|---------------|
| 创建一个组件文件 | 实现整个用户系统 |
| 写一个函数的测试 | 重构整个模块 |
| 修复一个类型错误 | 迁移数据库 |
| 提取一个常量 | 写一套 API |

#### 工作流程

```
writing-plans 产出计划
    ↓
AI 逐个取出步骤
    ↓
为每个步骤创建子代理执行
    ├── 任务 A: 创建测试文件 → 子代理 1
    ├── 任务 B: 写实现代码 → 子代理 2
    ├── 任务 C: 运行验证 → 子代理 3
    ↓
主代理收集结果，统一审查
    ↓
进入 requesting-code-review
```

### 6. dispatching-parallel-agents｜并行代理调度

> 一次性派发多个子代理，同时执行**互不依赖的独立任务**，总耗时 ≈ 最慢那个任务的时间。

#### 适用场景

| ✅ 适合并行 | ❌ 不适合 |
|-----------|----------|
| 同时调研多个技术方案 | 同一文件的密集修改 |
| 同时修复多个独立的 bug | 共享状态很多的任务 |
| 同时为多个模块写测试 | 根因高度相关的问题 |
| 并行编写数据库迁移和补测试 | 前后有依赖关系的步骤 |

#### 效果对比

```
串行: T1 → T2 → T3 → T4 = 总耗时 40 分钟
并行: T1, T2, T3, T4 同时跑 = 总耗时 ≈ 最慢那个（比如 12 分钟）
```

### 7. test-driven-development｜测试驱动开发

> 强制 RED → GREEN → REFACTOR 红绿重构循环：先写测试让它失败，再写代码让它通过，最后重构优化。

#### 三阶段循环

```
🔴 RED          → 写一个会失败的测试 → 确认它确实失败
🟢 GREEN        → 写最少代码让测试通过 → 确认测试通过
🟡 REFACTOR     → 重构代码，保持测试通过 → 确认测试仍然通过
```

#### 为什么强制？

- 防止"忘了写测试"
- 防止"测试通过了但其实没测到位"（先看到它失败，才能确认它有效）
- 每一步都有验证，出问题了能立刻知道是哪个步骤

### 8. systematic-debugging｜系统化调试

> 用**二分法**系统性定位 bug 根因，拒绝"print 加猜"的玄学调试。

#### 四阶段流程

| 阶段 | 做什么 |
|------|--------|
| ① **收集现象** | 复现 bug，记录精确的错误信息、输入、环境 |
| ② **构建假设** | 基于现象提出 2-3 个可能根因，排优先级 |
| ③ **针对性实验** | 逐个验证假设——"如果 X 是根因，那么做 Y 应该观察到 Z" |
| ④ **验证修复** | 修复后确认 bug 不再出现，且不引入新问题 |

#### 二分法定位

在 100 个可能的改动中找到根因，最多只需 7 次验证（log₂100 ≈ 7）。

比如：git bisect 自动在提交历史中二分查找，找到第一个引入 bug 的提交。

> **拒绝玄学三连**："加个 print 看看"、"好像好了"、"再跑一次试试"。

### 9. requesting-code-review｜请求代码审查

> 完成任务后，让 AI 代理审查你的代码，按严重程度分级，Critical 的必须立即修。

#### 触发时机（强制）

- 每个子代理任务完成后
- 完成主要功能后
- 合并到主分支前

#### 审查分级

| 等级 | 含义 | 行动 |
|------|------|------|
| 🔴 **Critical** | 安全漏洞、数据丢失、功能完全不可用 | **立即修复** |
| 🟠 **Important** | 性能问题、错误处理缺失、边界条件遗漏 | **修复后再继续** |
| 🟡 **Minor** | 命名不规范、注释不清晰、轻微冗余 | **记录稍后处理** |

#### 审查关注点

- **安全漏洞** — 注入、越权、敏感信息泄露
- **边界条件** — 空值、超大文件、并发竞争
- **代码可维护性** — 命名、结构、复杂度
- **简化机会** — 有没有更简单的写法

#### 工作原理

```
获取 git SHA 范围（BASE → HEAD）
    ↓
派发 code-reviewer 子代理
    ↓
生成结构化 Review Report
    ↓
Critical → 立即修复
Important → 修完再继续
Minor → 记下来
审查者错了 → 用技术理由反驳
```

### 10. receiving-code-review｜接收代码审查反馈

> 拿到同事或外部 Reviewer 的审查意见后，让 AI 帮你逐条理解、验证、修改。

#### 核心原则

- **先理解，再核验** — 不盲目接受审查意见
- **外部 Reviewer 不一定对** — 基于技术事实判断
- **不做表演式认同** — 不同意的意见要基于技术理由反驳（push back）

#### 它能省什么？

最费脑的循环：
```
看懂 Review 意见 → 找到对应代码 → 理解上下文
    → 修改 → 确认没有改错
    → （如果还有下一条，重复）
```

AI 帮你在几秒内走完这个循环。

### 11. verification-before-completion｜完成前验证

> **证据先于断言**——在说"做完了"、"修好了"、"测试通过了"之前，必须跑验证命令并看到实际输出。

#### 强制流程

1. **找出验证命令** — "用什么命令能证明这个说法？"
2. **运行完整命令** — 不是部分运行，不是"假设能通过"
3. **读取完整输出** — 看 exit code，看输出内容
4. **检查是否真通过** — 输出内容确实证明了说法，才算数
5. **然后才能说"做完了"**

#### 典型场景

| 说法 | 需要验证 |
|------|---------|
| "测试通过了" | 运行 `npm test`，看输出 |
| "bug 修好了" | 运行重现步骤，确认不出现 |
| "构建成功" | 运行 `npm run build`，看 exit code 0 |
| "类型检查通过" | 运行 `tsc --noEmit`，看输出 |

> **底线**：没有验证 = 没有完成。

### 12. finishing-a-development-branch｜完成开发分支

> 测试全部通过后，帮你决策：合并、提 PR、保留分支还是丢弃。

#### 前置条件

必须先跑完 `verification-before-completion`，确认所有测试通过。

#### 提供的选项

| 选项 | 做什么 |
|------|--------|
| 🔀 **Merge** | 合并到主分支，清理工作树 |
| 🚀 **Push + PR** | 推送并创建 Pull Request |
| 💾 **Keep** | 保留当前状态不动 |
| 🗑️ **Discard** | 丢弃所有改动 |

如果当前在 detached HEAD 状态，合并选项不可用（只有 3 个选项）。

#### 环境检测

自动检测当前环境：普通仓库 / Git Worktree / Detached HEAD，然后提供相应的选项。

### 13. using-git-worktrees｜Git Worktree 环境隔离

> 从同一个仓库创建多个**独立的工作目录**，每个目录可以在不同的分支上并行开发。

#### 为什么需要？

```
常规操作:
    切分支 → stash → 切回来 → 冲突 → 崩溃

Worktree:
    project/
    ├── main/       ← 在主分支上
    ├── feature-a/  ← 在 feature-a 分支上
    └── hotfix/     ← 在 hotfix 分支上
    可以同时开着，互不干扰
```

#### 安全机制

Superpowers 的 **来源追踪式清理**——`finishing-a-development-branch` 只会清理由 Superpowers 创建的 worktree（`.worktrees/` 目录下），不会动你自己创建的。

#### 适用场景

- 同时维护多个功能分支
- 紧急 hotfix 不中断当前工作
- 并行实验不同方案

### 14. writing-skills｜编写自定义技能

> 自己动手编写 SKILL.md 文件，把你的团队规范、项目模板、调试套路都变成可复用的技能。

#### 它能做什么？

- 📝 **封装团队代码规范** — 命名规则、文件结构、提交格式
- 🧩 **创建项目模板** — 新组件、新 API、新页面的标准模板
- 🔧 **固化调试套路** — 你常用的调试流程，变成一键执行
- 📚 **分享最佳实践** — 团队内部共享成熟的工作方式

#### 一个技能文件的样子

```markdown
---
name: my-team-standards
description: 团队代码规范和审查清单
---

## 命名规范
- 组件文件用 PascalCase: `UserProfile.tsx`
- 工具函数用 camelCase: `formatDate.ts`

## 组件模板
每次新建组件，至少包含：
1. TypeScript 接口定义
2. 组件主体
3. 单元测试文件
```

> **进阶用法**：编写技能时可以使用 Sub-agent 来测试技能效果——让 AI 先按技能干活，检查输出是否符合预期。

## 常见混淆与澄清

以下是在实际使用中最容易搞混的概念，逐个拆清楚。

---

### 混淆 ①：`/using-superpowers` 与 `/brainstorming` 该用哪个？

| | `/using-superpowers` | `/brainstorming` |
|---|---|---|
| **本质** | **元技能（说明书）** | **具体技能（干活用的）** |
| **能主动调用吗？** | ❌ 它不是一个给你"运行"的命令 | ✅ 是你主动输入的斜杠命令 |
| **做了什么** | 后台检查有没有匹配的技能 | 苏格拉底式追问，产出设计文档 |
| **生效方式** | 自动加载，不需要你手动输入 | 由你主动发起 |
| **类比** | 手机里的**用户手册** | 手机里的**计算器 App** |

#### 核心理解

**`using-superpowers` 不是一个可以"用"的技能，它只是一个在后台自动生效的说明书。** 它只在启动时做一件事：检查有没有匹配的具体技能，有就自动调用，没有就退回到默认行为。

所以你**不应该**主动输入 `/using-superpowers 我要做XX`。这就像拿着相机说明书喊"我要拍照"——正确做法是直接用人像模式（`/brainstorm`）。

| 你的需求 | 应该输入 |
|---------|---------|
| 有一个模糊的新功能想法 | **`/brainstorm` 我想做...** |
| 想检查有哪些技能可用 | 输入 `/` 看自动补全列表 |
| 主动调用 using-superpowers | **不需要，它已在后台自动运行** |

> **`using-superpowers` 是入口大门，`brainstorming` 是电梯按钮。你不会对着大门喊"我要去 10 楼"，先进大门（自动的），然后按电梯按钮。**

### 混淆 ②：`/executing-plans` 与 `/subagent-driven-dev` 的区别

| | `/executing-plans` | `/subagent-driven-dev` |
|---|---|---|
| **在哪执行** | 主对话里，一步一步走 | 派独立子代理，各干各的 |
| **并行** | ❌ 串行，一步等一步 | ✅ 互不依赖的任务可并行 |
| **上下文** | 越来越长，容易"迷失" | 每个子代理有干净的上下文 |
| **质量** | 步骤多了容易出幻觉 | ✅ 更可靠 |
| **推荐度** | ⚠️ 仅平台不支持子代理时使用 | ✅ **当前推荐方案** |

#### 怎么选？

| 情况 | 选哪个 |
|------|--------|
| 平台支持子代理（Claude Code ✅） | **`/subagent-driven-dev`** |
| 平台不支持子代理 | `/executing-plans` |
| 步骤之间有强依赖、需要连续上下文 | `/executing-plans` |
| 步骤相互独立、想快点搞完 | `/subagent-driven-dev` |
| 计划只有 2-3 步，很简单 | 区别不大 |
| 计划有 10+ 步 | **`/subagent-driven-dev`** 更好 |

### 混淆 ③：`/subagent-driven-dev` 与 `/dispatching-parallel-agents` 的区别

| | `/subagent-driven-dev` | `/dispatching-parallel-agents` |
|---|---|---|
| **处理什么** | **一个计划**里的多个步骤 | **多个不相关**的任务 |
| **来源** | 来自同一个 `writing-plans` 产出 | 来自任何地方（不同需求） |
| **目标** | 完成**一个功能** | 同时做**很多件事** |
| **关系** | 步骤之间可能有依赖 | 任务之间完全独立 |
| **粒度** | 细粒度（2-5 分钟/步） | 可粗可细 |

#### 对比示例

**`/subagent-driven-dev`**：一个功能"用户头像上传"拆出的 6 步，分配给不同子代理并行执行。

**`/dispatching-parallel-agents`**：三件不相关的事（调研 Cropper.js + 修支付 bug + 迁移 node-sass），一把派出去同时跑。

| 看到什么情况 | 用哪个 |
|-------------|--------|
| 我有一个计划，要把它执行完 | `subagent-driven-dev` |
| 我有几件不相干的事，想同时跑 | `dispatching-parallel-agents` |
| 做功能时遇到需要独立调研的子问题 | 前者里临时调后者 |
| **本质** | **把一件事拆细了并行** | **把很多事放一起并行** |

### 混淆 ④：TDD 和 subagent-driven-dev 是什么关系？

**它们不是二选一的关系，而是在不同层面上工作的互补组合：**

| | 层面 | 回答的问题 |
|---|---|---|
| **subagent-driven-dev** | **执行策略** | "任务怎么分配？谁来做？" |
| **TDD** | **编码方法** | "代码怎么写？先写测试还是先写实现？" |

#### 实际中的组合

```
subagent-driven-dev（决定：派子代理执行）
    │
    ├── 子代理 A：步骤 1（写测试文件）
    │   └── 在子代理内部：🔴 TDD 循环 → 先写测试
    │
    ├── 子代理 B：步骤 2（实现代码）
    │   └── 在子代理内部：🟢 TDD 循环 → 写最少代码让测试通过
    │
    ├── 子代理 C：步骤 3（纯重构，不需要 TDD）
    │   └── 直接改代码
    │
    └── ...
```

**TDD 是 subagent-driven-dev 每个子代理内部的默认编码方式。**

---

### 混淆 ⑤：writing-plans 之后，下一步到底该做什么？

很多人以为：`writing-plans` → 执行完了 → 不知道是再跑一次 `subagent-driven-dev` 还是进 `receiving-code-review`。

**正确答案：都不是。下一步是 `requesting-code-review`（自审）。**

#### 正确的工作流顺序

```
writing-plans（出计划）
    ↓
subagent-driven-dev（执行：派子代理实现所有步骤）
    ↓
requesting-code-review（自审：让 AI 代理审查刚写完的代码） ← 下一步在这里
    ↓
（如果有外部 Review 意见→ receiving-code-review）
    ↓
verification-before-completion（验证：跑命令确认一切正常）
    ↓
finishing-a-development-branch（收尾：合并/提 PR）
```

#### 为什么不能

| 你想做的 | 为什么不行 |
|---------|----------|
| 再跑一次 `subagent-driven-dev` | 计划已经执行完了，没有新步骤可以分派。除非发现新需求，那得重新 `brainstorming → writing-plans` |
| 直接跑 `receiving-code-review` | 那是处理**外部**Review 意见的（同事给你的 PR 评论）。你刚执行完计划，还没有人给你 Review，所以先自审 |

#### 那 `requesting-code-review` 可以多次执行吗？

**可以。** 修完 Critical 问题后、加了新代码后、提 PR 前，都可以再跑一次。审几次不是固定的，**审到没有 Critical 和 Important 问题为止**。

---

### 混淆 ⑥：`writing-plans` 为什么必须在 `brainstorming` 之后？

因为**先有设计，才有计划**。如果跳过 brainstorming，相当于没有需求文档就直接出排期表。

```
❌ 错误顺序：
    /write-plan "实现头像上传"
    → 没有设计稿，计划里的每一步都是猜的

✅ 正确顺序：
    /brainstorm "实现头像上传"  → 产出设计文档（spec）
        ↓
    /write-plan                 → 产出实现计划（plan）
```

> **Brainstorming 回答"做什么、为什么"，Writing Plans 回答"怎么做、按什么顺序"。**

## 完整工作流

```
┌─────────────────────────────────────────────────────┐
│                  using-superpowers                   │  ← 入口，确认技能就位
│                （全家桶使用说明书）                     │
└────────────────────────┬────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│                    brainstorming                     │  ← 需求阶段
│           （苏格拉底式追问，产出设计文档）                │  "我要做头像上传"
└────────────────────────┬────────────────────────────┘      ↓
                         ↓                           输出: docs/superpowers/specs/
┌─────────────────────────────────────────────────────┐
│                     writing-plans                    │  ← 规划阶段
│           （设计稿 → 细粒度实现计划）                    │  "拆成 6 步"
└────────────────────────┬────────────────────────────┘      ↓
                         ↓                           输出: docs/superpowers/plans/
┌─────────────────────────────────────────────────────┐
│                  executing-plans                     │  ← 执行入口
│              （按计划执行，遇 blocker 停）               │
└──────────┬──────────────┬──────────────┬─────────────┘
           ↓              ↓              ↓
   ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
   │ subagent-    │ │ dispatching- │ │     TDD      │
   │ driven-dev   │ │ parallel-    │ │  红绿重构     │
   │ 子代理开发    │ │ agents       │ │  循环        │
   │             │ │ 并行派发      │ │             │
   │ 后端任务1    │ │ 调研A库+     │ │ 先写测试     │
   │ 后端任务2    │ │ 迁移脚本+    │ │ 再写代码     │
   │ 前端组件     │ │ 补测试       │ │ 最后重构     │
   └──────────────┘ └──────────────┘ └──────────────┘
           ↓              ↓              ↓
┌─────────────────────────────────────────────────────┐
│               requesting-code-review                 │  ← 自审
│          （AI 代理审查代码，分级报告）                   │
└────────────────────────┬────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│               receiving-code-review                  │  ← 他审
│         （逐条处理外部 Review 意见）                    │
└────────────────────────┬────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│               systematic-debugging                   │  ← 修复
│        （测试挂了？二分法定位根因）                      │
└────────────────────────┬────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│           verification-before-completion              │  ← 验证
│          （证据先于断言——跑完验证才算完）                 │
└────────────────────────┬────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│         finishing-a-development-branch               │  ← 收尾
│       （合并 / PR / 保留 / 丢弃，打完收工）              │
└─────────────────────────────────────────────────────┘
```

## 实用建议

### 🎯 从哪个技能开始？

- **只想试试** → `/brainstorm` 拿一个真实需求走一遍
- **写代码总返工** → 完整流程走一遍 `brainstorming → writing-plans → executing-plans`
- **代码质量不稳** → 加进 TDD 和 code-review
- **觉得流程太重** → 先只加 `brainstorming` 和 `verification-before-completion` 两个

### 💡 技能组合拳推荐

| 场景 | 组合 |
|------|------|
| 最小可用 | brainstorming → executing-plans |
| 标准开发 | brainstorming → writing-plans → TDD → code-review → finish |
| 全流程 | 上图完整 14 步 |
| 紧急修 bug | systematic-debugging → verification-before-completion |

### 📌 关键哲学

> **Process over Prompt（流程大于提示）**
>
> 好的流程能把 60 分的 AI 用到 90 分；
> 没有流程，90 分的 AI 也会做出 60 分的结果。
