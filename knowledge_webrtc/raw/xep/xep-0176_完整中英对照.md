# XEP-0176 完整中英对照

> Jingle ICE-UDP 传输方法 - Jingle ICE-UDP Transport Method

---

## Abstract（摘要）

Jingle (XEP-0166)
> XEP-0166: Jingle <https://xmpp.org/extensions/xep-0166.html>.
defines a framework for negotiating and managing out-of-band data sessions over XMPP. In order to provide a flexible framework, the base Jingle specification defines neither data transport methods nor application formats, leaving that up to separate specifications.

Jingle (XEP-0166) 定义了一个通过 XMPP 协商和管理带外数据会话的框架。为了提供一个灵活的框架，基础 Jingle 规范既没有定义数据传输方法，也没有定义应用格式，这留给单独的规范来定义。

The current document defines a transport method for establishing and managing data exchanges between XMPP entities over the User Datagram Protocol (see RFC 768
> RFC 768: User Datagram Protocol <http://tools.ietf.org/html/rfc0768>.
), using the ICE methodology developed within the IETF and specified in RFC 5245
> RFC 5245: Interactive Connectivity Establishment (ICE) <http://tools.ietf.org/html/rfc5245>.
(hereafter referred to as ICE-CORE). Use of this "ice-udp" method results in a datagram transport suitable for media applications where some packet loss is tolerable (e.g., audio and video).

本文档定义了一种传输方法，用于在 XMPP 实体之间通过用户数据报协议（参见 RFC 768）建立和管理数据交换，使用 IETF 开发并在 RFC 5245（以下简称 ICE-CORE）中指定的 ICE 方法论。使用这种 "ice-udp" 方法会产生一个数据报传输，适用于可容忍一定丢包的媒体应用（例如音频和视频）。

Note: ICE-CORE has been approved for publication as an RFC but has not yet been published as an RFC. While every effort has been made to keep this document synchronized with ICE-CORE, the interested reader is referred to ICE-CORE for a detailed description of the ICE methodology.

注意：ICE-CORE 已获批作为 RFC 发布，但尚未正式发布为 RFC。虽然我们已尽一切努力使本文档与 ICE-CORE 保持同步，但感兴趣的读者应参考 ICE-CORE 以获取 ICE 方法论的详细描述。

The process for ICE negotiation is largely the same in Jingle as it is in ICE. There are several differences:
- Instead of using the Session Initiation Protocol (SIP) as the signalling channel, Jingle uses XMPP as the signalling channel.
- Syntax from the Session Description Protocol (see RFC 4566
> RFC 4566: SDP: Session Description Protocol <http://tools.ietf.org/html/rfc4566>.
) is mapped to an XML syntax suitable for sending over the XMPP signalling channel.
- In Jingle, lists of "preferred" candidates are typically sent in the Jingle session-initiate and session-accept messages, in a way that is consistent with the SDP offer / answer model described in RFC 3264
> RFC 3264: An Offer/Answer Model with the Session Description Protocol (SDP) <http://tools.ietf.org/html/rfc3264>.
and the process described in ICE-CORE.
- Candidates can also be sent in separate transport-info messages either before sending the session-accept message (to expedite negotiation) or after media begins to flow (to find modify existing candidates, find superior candidates, or adjust to changing network conditions).

在 Jingle 中，ICE 协商的过程与 ICE 基本相同。但存在以下几个差异：
- Jingle 使用 XMPP 作为信令通道，而不是使用会话发起协议（SIP）作为信令通道。
- 来自会话描述协议（参见 RFC 4566）的语法被映射为适合通过 XMPP 信令通道发送的 XML 语法。
- 在 Jingle 中，"优先"候选列表通常在 Jingle session-initiate 和 session-accept 消息中发送，这种方式与 RFC 3264 中描述的 SDP offer/answer 模型以及 ICE-CORE 中描述的过程一致。
- 候选也可以在单独的 transport-info 消息中发送，可以在发送 session-accept 消息之前（以加快协商），也可以在媒体开始流动之后（以修改现有候选、找到更优候选或适应变化的网络条件）。

## Requirements（需求）

The Jingle transport method defined herein is designed to meet the following requirements:
- Make it possible to establish and manage out-of-band connections between two XMPP entities, even if they are behind Network Address Translators (NATs) or firewalls.
- Enable use of UDP as the transport protocol.
- Make it relatively easy to implement support in standard Jabber/XMPP clients.
- Where communication with non-XMPP entities is needed, push as much complexity as possible onto server-side gateways between the XMPP network and the non-XMPP network.

本文定义的 Jingle 传输方法旨在满足以下需求：
- 使得在两个 XMPP 实体之间建立和管理带外连接成为可能，即使它们位于网络地址转换器（NAT）或防火墙之后。
- 支持使用 UDP 作为传输协议。
- 使标准 Jabber/XMPP 客户端能够相对容易地实现对它的支持。
- 当需要与非 XMPP 实体通信时，将尽可能多的复杂性推送到 XMPP 网络和非 XMPP 网络之间的服务器端网关上。

## Protocol Description（协议描述）

In accordance with Section 10 of Jingle (XEP-0166)
> XEP-0166: Jingle <https://xmpp.org/extensions/xep-0166.html>.
, this document specifies the following information related to the Jingle ice-udp transport method:
- The transport negotiation process is defined in the Protocol Description section of this document.
- The semantics of the &lt;transport/&gt; element are defined in the ICE Negotiation section of this document.
- Successful negotiation of the ice-udp method results in use of a datagram transport that is suitable for applications where some packet loss is tolerable, such as audio and video.
- If multiple components are to be communicated by the application type that uses the transport, the transport shall support those components and assign identifiers for them as described in the specification that defines the application type.

根据 Jingle (XEP-0166) 第 10 节，本文档指定了以下与 Jingle ice-udp 传输方法相关的信息：
- 传输协商过程在本文档的"协议描述"部分定义。
- &lt;transport/&gt; 元素的语义在本文档的"ICE 协商"部分定义。
- 成功协商 ice-udp 方法后，将使用一个数据报传输，适用于可容忍一定丢包的应用，例如音频和视频。
- 如果使用该传输的应用类型需要传递多个组件，则传输应支持这些组件并按照定义该应用类型的规范中所述为其分配标识符。

## Negotiation Flow（协商流程）

### Overall Protocol Flow（总体协议流程）

The overall protocol flow for negotiation of the Jingle ICE-UDP Transport Method is as follows (note: many of these events happen simultaneously, not in sequence).

Jingle ICE-UDP 传输方法的总体协议协商流程如下（注意：其中许多事件是同时发生的，而不是按顺序发生的）。

```
INITIATOR                               RESPONDER
|                                       |
|  Jingle session-initiate             |
|  (with candidates)                   |
|-------------------------------------->|
|                                       |
|  Jingle ack (XMPP IQ-result)         |
|<--------------------------------------|
|                                       |
|  multiple STUN Binding Requests      |
|  (connectivity checks)               |
|======================================>|
|                                       |
|  multiple STUN Binding Results       |
|<======================================|
|                                       |
|  Jingle session-accept               |
|  (with candidates)                   |
|<--------------------------------------|
|                                       |
|  Jingle ack (IQ-result)              |
|-------------------------------------->|
|                                       |
|  optional Jingle transport-info      |
|  stanzas (one candidate per stanza)  |
|<------------------------------------->|
|                                       |
|  MEDIA NOW CAN FLOW                  |
|======================================>|
|                                       |
```

Note: The examples in this document follow the scenario described in Section 17 of ICE-CORE, except that we substitute the Shakespearean characters "Romeo" and "Juliet" for the generic entities "L" and "R".

注意：本文档中的示例遵循 ICE-CORE 第 17 节描述的场景，不同之处在于我们将莎士比亚角色 "Romeo" 和 "Juliet" 替代了通用实体 "L" 和 "R"。

### Session Initiation（会话发起）

In order for the initiator in a Jingle exchange to start the negotiation, it sends a Jingle "session-initiate" stanza that includes at least one content type, as described in Jingle (XEP-0166)
> XEP-0166: Jingle <https://xmpp.org/extensions/xep-0166.html>.
. If the initiator wishes to negotiate the ice-udp transport method for an application format, it MUST include a &lt;transport/&gt; child element qualified by the 'urn:xmpp:jingle:transports:ice-udp:1' namespace (see Namespace Versioning regarding the possibility of incrementing the version number). This element SHOULD in turn contain one &lt;candidate/&gt; element for each of the initiator's higher-priority transport candidates as determined in accordance with the ICE methodology, but MAY instead be empty (with each candidate to be sent as the payload of a transport-info message).

为了让 Jingle 交换中的发起方开始协商，它发送一个 Jingle "session-initiate" 节，其中包含至少一种内容类型，如 Jingle (XEP-0166) 中所述。如果发起方希望为某种应用格式协商 ice-udp 传输方法，它必须包含一个由 'urn:xmpp:jingle:transports:ice-udp:1' 命名空间限定的 &lt;transport/&gt; 子元素（关于版本号递增的可能性，请参见命名空间版本控制）。该元素应依次为发起方根据 ICE 方法论确定的每个较高优先级传输候选包含一个 &lt;candidate/&gt; 元素，但也可以为空（每个候选作为 transport-info 消息的有效载荷发送）。

```xml
<iq from='romeo@montague.lit/orchard'
    id='h7ed2'
    to='juliet@capulet.lit/balcony'
    type='set'>
  <jingle xmlns='urn:xmpp:jingle:1'
          action='session-initiate'
          initiator='romeo@montague.lit/orchard'
          sid='vj3hs98y'>
    <content creator='initiator' name='this-is-the-audio-content'>
      <description xmlns='urn:xmpp:jingle:apps:rtp:1' media='audio'>
        <payload-type id='96' name='speex' clockrate='16000'/>
      </description>
      <transport xmlns='urn:xmpp:jingle:transports:ice-udp:1'
                 pwd='asd88fgpdd777uzjYhagZg'
                 ufrag='8hhy'>
        <candidate component='1'
                   foundation='1'
                   generation='0'
                   id='el0747fg11'
                   ip='192.0.2.3'
                   network='0'
                   port='45664'
                   priority='2130706431'
                   protocol='udp'
                   type='host'/>
        <candidate component='1'
                   foundation='2'
                   generation='0'
                   id='y3s2b30v3r'
                   ip='192.0.2.3'
                   network='0'
                   port='3478'
                   priority='2130706175'
                   protocol='udp'
                   rel-addr='10.0.1.1'
                   rel-port='8998'
                   type='srflx'/>
      </transport>
    </content>
  </jingle>
</iq>
```

### Session Acceptance（会话接受）

As described in Jingle (XEP-0166)
> XEP-0166: Jingle <https://xmpp.org/extensions/xep-0166.html>.
, to acknowledge receipt of the session initiation request, the responder immediately returns an IQ-result.

如 Jingle (XEP-0166) 中所述，为了确认收到会话发起请求，响应方立即返回一个 IQ-result。

```xml
<iq from='juliet@capulet.lit/balcony'
    id='h7ed2'
    to='romeo@montague.lit/orchard'
    type='result'/>
```

Depending on the application type, a user agent controlled by a human user might need to wait for the user to affirm a desire to proceed with the session before continuing. When the user agent has received such affirmation (or if the user agent can automatically proceed for any reason, e.g. because no human intervention is expected or because a human user has configured the user agent to automatically accept sessions with a given entity), it returns a Jingle session-accept message. This message MUST contain a &lt;transport/&gt; element qualified by the 'urn:xmpp:jingle:transports:ice-udp:1' namespace, which SHOULD in turn contain one &lt;candidate/&gt; element for each ICE-UDP candidate generated by or known to the responder, but MAY instead be empty (with each candidate to be sent as the payload of a transport-info message).

根据应用类型的不同，由人类用户控制的用户代理可能需要等待用户确认希望继续会话后才能继续。当用户代理收到此类确认后（或者如果用户代理由于任何原因可以自动继续，例如预期不需要人工干预，或者人类用户已将用户代理配置为自动接受来自给定实体的会话），它将返回一个 Jingle session-accept 消息。此消息必须包含一个由 'urn:xmpp:jingle:transports:ice-udp:1' 命名空间限定的 &lt;transport/&gt; 元素，该元素应依次为响应方生成或已知的每个 ICE-UDP 候选包含一个 &lt;candidate/&gt; 元素，但也可以为空（每个候选作为 transport-info 消息的有效载荷发送）。

Note: See the Security Considerations section of this document regarding the exposure of IP addresses by the responder's client.

注意：关于响应方客户端暴露 IP 地址的问题，请参见本文档的安全考虑部分。


### Exchanging Candidates（交换候选）

The initiator and responder negotiate connectivity over ICE by exchanging XML-formatted transport candidates for the channel. This negotiation proceeds immediately in order to maximize the possibility that connectivity can be established (and therefore media can be exchanged) as quickly as possible. In order to expedite session establishment, the initiator SHOULD include transport candidates in its session-initiate message but MAY also send additional transport candidates as soon as it learns of them, even before receiving acknowledgement of the session-initiate message (i.e., the initiator MUST consider the session to be live as soon as it sends the session-initiate message).

发起方和响应方通过交换 XML 格式的通道传输候选，在 ICE 上协商连接性。此协商立即进行，以最大限度地提高尽快建立连接性（从而能够交换媒体）的可能性。为了加快会话建立，发起方应在其 session-initiate 消息中包含传输候选，但也可以在获悉其他传输候选后立即发送它们，甚至在收到 session-initiate 消息的确认之前（即，发起方必须在发送 session-initiate 消息后立即将会话视为活跃状态）。

> Given in-order delivery as mandated by XMPP Core
> RFC 6120: Extensible Messaging and Presence Protocol (XMPP): Core <http://tools.ietf.org/html/rfc6120>.
, the responder will receive such transport-info messages after receiving the session-initiate message; if not, it is appropriate for the responder to return &lt;unknown-session/&gt; errors since according to its state machine the session does not exist.

> 鉴于 XMPP Core (RFC 6120) 要求的有序传递，响应方将在收到 session-initiate 消息之后收到此类 transport-info 消息；如果不是这样，响应方适合返回 &lt;unknown-session/&gt; 错误，因为根据其状态机，该会话不存在。

The first step in negotiating connectivity is for each party to send transport candidates to the other party.
> The fact that both parties send candidates means that Jingle requires each party to be a full implementation of ICE, not a lite implementation as specified in ICE-CORE.
These candidates SHOULD be gathered by following the procedure specified in Section 4.1.1 of ICE-CORE (typically by communicating with a standalone STUN server in order to discover the client's public IP address and port) and prioritized by following the procedure specified in Section 4.1.2 of ICE-CORE.

协商连接性的第一步是各方将传输候选发送给另一方。
> 双方都发送候选这一事实意味着 Jingle 要求每一方都是 ICE 的完整实现，而不是 ICE-CORE 中指定的 lite 实现。
这些候选应按照 ICE-CORE 第 4.1.1 节指定的过程进行收集（通常通过与独立的 STUN 服务器通信以发现客户端的公共 IP 地址和端口），并按照 ICE-CORE 第 4.1.2 节指定的过程进行优先级排序。

Each candidate shall be sent as a &lt;candidate/&gt; child of a &lt;transport/&gt; element qualified by the 'urn:xmpp:jingle:transports:ice-udp:1' namespace. The &lt;transport/&gt; element is sent via a Jingle message of type session-initiate, session-accept, or transport-info.

每个候选应作为由 'urn:xmpp:jingle:transports:ice-udp:1' 命名空间限定的 &lt;transport/&gt; 元素的 &lt;candidate/&gt; 子元素发送。&lt;transport/&gt; 元素通过 Jingle 消息发送，消息类型为 session-initiate、session-accept 或 transport-info。

Either party MAY include multiple &lt;candidate/&gt; elements in one &lt;transport/&gt; element, especially in the session-initiate and session-accept messages sent at the beginning of the session negotiation. Including multiple candidates in the session-initiate and session-accept messages can help to ensure interoperability with entities that implement the SDP offer/answer model described in RFC 3264
> RFC 3264: An Offer/Answer Model with the Session Description Protocol (SDP) <http://tools.ietf.org/html/rfc3264>.
; in particular, an entity SHOULD include multiple candidates in its session-initiate or session-accept message if the other party advertises support for the "urn:ietf:rfc:3264" service discovery feature as described in the SDP Offer / Answer Support section of this document. However, including one candidate per subsequent transport-info message typically results in a faster negotiation because the candidates most likely to succeed are sent first (in the session-info and session-accept messages) and it is not necessary to gather all candidates before beginning to send any candidates; furthermore, because certain candidates can be more "expensive" in terms of bandwidth or processing power, either party might not want to advertise the existence of such candidates unless it is necessary to do so after other candidates have failed.

任一方可在一个 &lt;transport/&gt; 元素中包含多个 &lt;candidate/&gt; 元素，特别是在会话协商开始时发送的 session-initiate 和 session-accept 消息中。在 session-initiate 和 session-accept 消息中包含多个候选有助于确保与实现 RFC 3264 中描述的 SDP offer/answer 模型的实体的互操作性；特别是，如果另一方通过广告支持 "urn:ietf:rfc:3264" 服务发现功能（如本文档的 SDP Offer/Answer 支持部分所述），则实体应在其 session-initiate 或 session-accept 消息中包含多个候选。然而，在后续的 transport-info 消息中每条消息包含一个候选通常会带来更快的协商，因为最有可能成功的候选会首先发送（在 session-initiate 和 session-accept 消息中），而且无需在开始发送任何候选之前收集所有候选；此外，由于某些候选在带宽或处理能力方面可能更"昂贵"，任一方可能不希望广告此类候选的存在，除非在其他候选失败后有必要这样做。

If the party that receives a candidate in a Jingle message can successfully process a given candidate or set of candidates, it returns an IQ-result (if not, for example because the candidate data is improperly formatted, it returns an IQ-error). At this point, the receiving entity is only indicating receipt of the candidate or set of candidates, not telling the other party that the candidate will be used.

如果收到 Jingle 消息中候选的一方能够成功处理给定的候选或候选集，它将返回 IQ-result（如果不能，例如由于候选数据格式不正确，则返回 IQ-error）。此时，接收实体仅表示收到候选或候选集，并不告诉另一方该候选将被使用。

The initiator can keep sending candidates (without stopping to receive an acknowledgement of receipt from the responder for each candidate) until it has exhausted its supply of possible or desirable transport candidates. The responder can also keep sending potential candidates, which the initiator will acknowledge.

发起方可以持续发送候选（无需停下来接收响应方对每个候选的接收确认），直到其耗尽所有可能或需要的传输候选。响应方也可以持续发送潜在的候选，发起方将对其进行确认。

### Connectivity Checks（连接性检查）

As the initiator and responder receive candidates, they probe the candidates for connectivity. In performing these connectivity checks, each party SHOULD follow the procedure specified in Section 7 of ICE-CORE. The following business rules apply:
- Each party sends a STUN Binding Request (see RFC 5389
> RFC 5389: Session Traversal Utilities for NAT (STUN) <http://tools.ietf.org/html/rfc5389>.
) from each local candidate it generated to each remote candidate it received.
- In accordance with ICE-CORE, the STUN Binding Requests MUST include the PRIORITY attribute (computed according to Section 7.1.1.1. of ICE-CORE).
- For the purposes of the Jingle ICE-UDP Transport Method, both parties are full ICE implementations and therefore the controlling role MUST be assumed by the initiator and the controlled role MUST be assumed by the responder.
- The STUN Binding Requests generated by the initiator MAY include the USE-CANDIDATE attribute to indicate that the initiator wishes to cease checks for this component.
- The STUN Binding Requests generated by the initiator MUST include the ICE-CONTROLLING attribute.
- The STUN Binding Requests generated by the responder MUST include the ICE-CONTROLLED attribute.
- The parties MUST use STUN short term credentials to authenticate requests and perform message integrity checks. As in ICE-CORE, the username in the STUN Binding Request is of the form "ufrag-of-peer:ufrag-of-sender" and the password is the value of the 'pwd' attribute provided by the peer.

当发起方和响应方收到候选时，它们会探测候选的连接性。在执行这些连接性检查时，各方应遵循 ICE-CORE 第 7 节中指定的程序。以下业务规则适用：
- 各方从它生成的每个本地候选向它收到的每个远程候选发送一个 STUN 绑定请求（参见 RFC 5389）。
- 根据 ICE-CORE，STUN 绑定请求必须包含 PRIORITY 属性（根据 ICE-CORE 第 7.1.1.1 节计算）。
- 对于 Jingle ICE-UDP 传输方法而言，双方都是完整的 ICE 实现，因此控制方角色必须由发起方承担，受控方角色必须由响应方承担。
- 发起方生成的 STUN 绑定请求可以包含 USE-CANDIDATE 属性，以表明发起方希望停止对该组件的检查。
- 发起方生成的 STUN 绑定请求必须包含 ICE-CONTROLLING 属性。
- 响应方生成的 STUN 绑定请求必须包含 ICE-CONTROLLED 属性。
- 双方必须使用 STUN 短期凭证来认证请求并执行消息完整性检查。与 ICE-CORE 中一样，STUN 绑定请求中的用户名的格式为 "对等方的ufrag:发送方的ufrag"，密码为对等方提供的 'pwd' 属性的值。

> Thus when Romeo sends a STUN Binding Request to Juliet the credentials will be STUN username "9uB6:8hhy" (ufrag provided by Juliet concatenated with ufrag provided by Romeo) and password "YH75Fviy6338Vbrhrlp8Yh" (pwd provided by Juliet) whereas when Juliet sends a STUN Binding Request to Romeo the credentials will be STUN username "8hhy:9uB6" (ufrag provided by Romeo concatenated with ufrag provided by Juliet) and password "asd88fgpdd777uzjYhagZg" (pwd provided by Romeo).

> 因此，当 Romeo 向 Juliet 发送 STUN 绑定请求时，凭证将是 STUN 用户名 "9uB6:8hhy"（由 Juliet 提供的 ufrag 与 Romeo 提供的 ufrag 拼接而成）和密码 "YH75Fviy6338Vbrhrlp8Yh"（由 Juliet 提供的 pwd），而当 Juliet 向 Romeo 发送 STUN 绑定请求时，凭证将是 STUN 用户名 "8hhy:9uB6"（由 Romeo 提供的 ufrag 与 Juliet 提供的 ufrag 拼接而成）和密码 "asd88fgpdd777uzjYhagZg"（由 Romeo 提供的 pwd）。

When it receives a STUN Binding Request, each party MUST return a STUN Binding Response, which indicates either an error case or the success case. As described in Section 7.1.2.2 of ICE-CORE, a connectivity check succeeds if _all_ of the following are true:
- The STUN transaction generated a success response.
- The source IP address and port of the response equals the destination IP address and port to which the Binding Request was sent.
- The destination IP address and port of the response match the source IP address and port from which the Binding Request was sent.

当收到 STUN 绑定请求时，各方必须返回 STUN 绑定响应，该响应指示错误情况或成功情况。如 ICE-CORE 第 7.1.2.2 节所述，如果满足以下_所有_条件，连接性检查成功：
- STUN 事务生成了成功响应。
- 响应的源 IP 地址和端口等于绑定请求发送到的目标 IP 地址和端口。
- 响应的目标 IP 地址和端口与发送绑定请求的源 IP 地址和端口匹配。

For the candidates exchanged in the previous section, the connectivity checks would be as follows (this diagram mirrors the example in ICE-CORE).

对于上一部分中交换的候选，连接性检查将如下所示（此图反映了 ICE-CORE 中的示例）。

```
  ROMEO (controlling)                     JULIET (controlled)
  |                                       |
  | STUN Binding Request                  |
  | from 192.0.2.3:45664                  |
  | to   192.0.2.1:3478                   |
  | USE-CANDIDATE                         |
  |======================================>|
  |                                       |
  | STUN Binding Response                 |
  | from 192.0.2.1:3478                   |
  | to   192.0.2.3:45664                  |

  |                                       |
  | STUN Binding Request                  |
  | from 192.0.2.1:3478                   |

  |<--------------------------------------|
```

Note: Here the initiator (controlling agent) is using "aggressive nomination" as described in Section 8.1.1.2 of ICE-CORE and therefore includes the USE-CANDIDATE attribute in the STUN Binding Requests it sends.

注意：在这里，发起方（控制方）使用了 ICE-CORE 第 8.1.1.2 节中描述的"激进出名"，因此在其发送的 STUN 绑定请求中包含了 USE-CANDIDATE 属性。

### Nomination（提名）

If, based on STUN connectivity checks, the parties determine that they will be able to exchange media between a given pair of local candidates and remote candidates (i.e., the pair is "nominated" and ICE processing is "completed"), they can then begin using that candidate pair to exchange media.

如果基于 STUN 连接性检查，双方确定它们能够在给定的本地候选和远程候选对之间交换媒体（即该对被"提名"且 ICE 处理已"完成"），则它们可以开始使用该候选对交换媒体。

Once the parties have connectivity and therefore the initiator has completed ICE as explained in ICE-CORE, the initiator MAY communicate the in-use candidate pair in the signalling channel by sending a transport-info message that contains a &lt;remote-candidate/&gt; element (this maps to the SDP "remote-candidates" attribute as described in Section B.6 of ICE-CORE, i.e., remote candidates are "the actual candidates at R that were selected by the offerer", of which there will be only one at this stage of the ICE-UDP negotiation).

一旦双方建立了连接性并且发起方已按照 ICE-CORE 的解释完成了 ICE，发起方可以通过发送包含 &lt;remote-candidate/&gt; 元素的 transport-info 消息，在信令通道中传达正在使用的候选对（这映射到 SDP 的 "remote-candidates" 属性，如 ICE-CORE 附录 B.6 所述，即远程候选是"在 R 处由 offerer 选择出来的实际候选"，在 ICE-UDP 协商的这个阶段只会有一个）。

```xml
<iq from='romeo@montague.lit/orchard'
    id='z8i4fs4z'
    to='juliet@capulet.lit/balcony'
    type='set'>
  <jingle xmlns='urn:xmpp:jingle:1'
          action='transport-info'
          initiator='romeo@montague.lit/orchard'
          sid='vj3hs98y'>
    <content creator='initiator' name='this-is-the-audio-content'>
      <transport xmlns='urn:xmpp:jingle:transports:ice-udp:1'>
        <remote-candidate component='1'
                          ip='192.0.2.1'
                          port='3478'/>
      </transport>
    </content>
  </jingle>
</iq>
```

(In accordance with Jingle core, the responder will also acknowledge the transport-info message.)

（根据 Jingle 核心规范，响应方也将确认 transport-info 消息。）

In the unlikely event that one of the parties determines that it cannot establish connectivity even after sending and checking lower-priority candidates, it SHOULD terminate the session as described in Jingle (XEP-0166)
> XEP-0166: Jingle <https://xmpp.org/extensions/xep-0166.html>.
.

在不太可能发生的情况下，如果一方即使在发送和检查较低优先级的候选之后仍确定无法建立连接性，则应按照 Jingle (XEP-0166) 的描述终止会话。

### Sending Additional Candidates（发送额外候选）

Even after media has begun to flow, either party MAY continue to send additional candidates to the other party (e.g., because the user agent has become aware of a new media proxy or network interface card). Such candidates are shared by sending a transport-info message.

即使在媒体开始流动之后，任一方也可以继续向另一方发送额外的候选（例如，因为用户代理已经发现新的媒体代理或网络接口卡）。此类候选通过发送 transport-info 消息来共享。

```xml
<iq from='romeo@montague.lit/orchard'
    id='a7b3c5d'
    to='juliet@capulet.lit/balcony'
    type='set'>
  <jingle xmlns='urn:xmpp:jingle:1'
          action='transport-info'
          initiator='romeo@montague.lit/orchard'
          sid='vj3hs98y'>
    <content creator='initiator' name='this-is-the-audio-content'>
      <transport xmlns='urn:xmpp:jingle:transports:ice-udp:1'>
        <candidate component='1'
                   foundation='2'
                   generation='0'
                   id='abc123def'
                   ip='192.0.2.7'
                   network='1'
                   port='45664'
                   priority='1694498815'
                   protocol='udp'
                   type='host'/>
      </transport>
    </content>
  </jingle>
</iq>
```

The receiving party MUST acknowledge receipt of the candidate.

接收方必须确认收到该候选。

```xml
<iq from='juliet@capulet.lit/balcony'
    id='a7b3c5d'
    to='romeo@montague.lit/orchard'
    type='result'/>
```

The parties would check the newly-offered candidate for connectivity, as described previously. If the parties determine that media can flow over the candidate, they MAY then use the new candidate in subsequent communications.

双方将检查新提供的候选的连接性，如前所述。如果双方确定媒体可以通过该候选流动，则可以在后续通信中使用新的候选。

### ICE Restarts（ICE 重启）

At any time, either party MAY restart the process of ICE negotiation by sending a candidate with a 'generation' value that is greater than the previous generation of candidates; when it does so, it MUST generate new values for the 'pwd' and 'ufrag' attributes, consistent with the definition of an ICE restart in Section 9.1.1.1 of ICE-CORE. As explained in ICE-CORE, typically the ICE negotiation would be restarted to change the media target (e.g., an IP address change for one of the parties) and certain third-party-call-control scenarios.

在任何时候，任一方可以通过发送一个 'generation' 值大于上一代候选的候选来重启 ICE 协商过程；当这样做时，它必须为 'pwd' 和 'ufrag' 属性生成新的值，与 ICE-CORE 第 9.1.1.1 节中 ICE 重启的定义一致。如 ICE-CORE 所解释的，通常 ICE 协商重启是为了更改媒体目标（例如一方的 IP 地址变更）以及某些第三方呼叫控制场景。

```xml
<iq from='juliet@capulet.lit/balcony'
    id='r4t5y6u'
    to='romeo@montague.lit/orchard'
    type='set'>
  <jingle xmlns='urn:xmpp:jingle:1'
          action='transport-info'
          initiator='romeo@montague.lit/orchard'
          sid='vj3hs98y'>
    <content creator='initiator' name='this-is-the-audio-content'>
      <transport xmlns='urn:xmpp:jingle:transports:ice-udp:1'
                 pwd='newPwdValue777'
                 ufrag='newFrag'>
        <candidate component='1'
                   foundation='1'
                   generation='1'
                   id='newCand01'
                   ip='192.0.2.99'
                   network='0'
                   port='45664'
                   priority='2130706431'
                   protocol='udp'
                   type='host'/>
      </transport>
    </content>
  </jingle>
</iq>
```

The recipient then acknowledges receipt.

然后接收方确认收到。

```xml
<iq from='romeo@montague.lit/orchard'
    id='r4t5y6u'
    to='juliet@capulet.lit/balcony'
    type='result'/>
```

The parties would then exchange new candidates to renegotiate connectivity and would check the new candidates for connectivity, as described previously. If the parties determine that media can flow over one of the new candidates, they can then use the successful candidate in subsequent communications. However, while ICE is being renegotiated the parties can continue to send media with the existing candidate-in-use.

然后双方将交换新的候选以重新协商连接性，并检查新候选的连接性，如前所述。如果双方确定媒体可以通过其中一个新候选流动，则可以在后续通信中使用成功的候选。然而，在 ICE 重新协商期间，双方可以继续使用现有的在用候选发送媒体。

## Fallback to Raw UDP Transport（回退到原始 UDP 传输）

It can happen that the responder does not support ICE, in which case it can be necessary to fall back to use of the Jingle Raw UDP Transport Method  (XEP-0177)
> XEP-0177: Jingle Raw UDP Transport Method <https://xmpp.org/extensions/xep-0177.html>.
. One typical scenario is communication between an ICE-aware Jingle endpoint and a non-ICE-aware SIP endpoint through a Jingle-to-SIP gateway, as follows:
- The Jingle endpoint sends a session-initiate request to the SIP endpoint, specifying a transport method of ICE-UDP.
- Based on capabilities information, the gateway knows that the SIP endpoint does not support ICE, so it enables the endpoints to use its media relay. It does this by:
  - Sending a transport-replace message to the Jingle endpoint on behalf of the SIP endpoint, specifying a transport method of Raw UDP and a candidate whose IP address and port are hosted at the gateway.
  - Sending SIP INVITE to the SIP endpoint on behalf of the Jingle endpoint, specifying an IP address and port at the gateway.

可能出现响应方不支持 ICE 的情况，此时可能需要回退到使用 Jingle 原始 UDP 传输方法 (XEP-0177)。一个典型的场景是通过 Jingle-to-SIP 网关在支持 ICE 的 Jingle 端点和不支持 ICE 的 SIP 端点之间通信，具体如下：
- Jingle 端点向 SIP 端点发送 session-initiate 请求，指定传输方法为 ICE-UDP。
- 基于能力信息，网关知道 SIP 端点不支持 ICE，因此它让端点使用它的媒体中继。它通过以下方式实现：
  - 代表 SIP 端点向 Jingle 端点发送 transport-replace 消息，指定传输方法为原始 UDP，并使用托管在网关上 IP 地址和端口的候选。
  - 代表 Jingle 端点向 SIP 端点发送 SIP INVITE，指定网关上的 IP 地址和端口。

The session flow is as follows.

```xml
                   ip='192.0.2.3'
                   port='45664'
                   type='host'/>
      </transport>
    </content>
  </jingle>
</iq>
```

The gateway then acknowledges the acceptance on behalf of Juliet.

然后网关代表 Juliet 确认接受。

```xml
<iq from='juliet@capulet.lit/balcony'
    id='gwAccpt1'
    to='romeo@montague.lit/orchard'
    type='result'/>
```

The responder then sends a session-accept through the gateway.

然后响应方通过网关发送 session-accept。

```xml
<iq from='juliet@capulet.lit/balcony'
    id='gwSessAc1'
    to='romeo@montague.lit/orchard'
    type='set'>
  <jingle xmlns='urn:xmpp:jingle:1'
          action='session-accept'
          initiator='romeo@montague.lit/orchard'
          responder='juliet@capulet.lit/balcony'
          sid='fallback01'>
    <content creator='initiator' name='audio'>
      <description xmlns='urn:xmpp:jingle:apps:rtp:1' media='audio'>
        <payload-type id='96' name='speex' clockrate='16000'/>
      </description>
      <transport xmlns='urn:xmpp:jingle:transports:raw-udp:1'>
        <candidate component='1'
                   generation='0'
                   id='juliet1'
                   ip='203.0.113.5'
                   port='50000'
                   type='relay'/>
      </transport>
    </content>
  </jingle>
</iq>
```

```xml
<iq from='romeo@montague.lit/orchard'
    id='gwSessAc1'
    to='juliet@capulet.lit/balcony'
    type='result'/>
```

The endpoints now begin to exchange session media, and can continue the session as long as desired.

端点现在开始交换会话媒体，并且可以根据需要继续会话。

## Implementation Notes（实现说明）

In order to speed the negotiation process so that media can flow as quickly as possible, the initiator SHOULD gather and prioritize candidates in advance, or as soon as the principal begins the process of initiating a session.

为了加快协商过程以便媒体能够尽快流动，发起方应提前或在主体开始发起会话的过程时立即收集候选并对其进行优先级排序。

> Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN) <http://tools.ietf.org/html/draft-ietf-behave-turn>. Work in progress.

## Security Considerations（安全考虑）

### Sharing of IP Addresses（IP 地址共享）

By definition, the exchange of transport candidates results in exposure of the sender's IP addresses, which comprise a form of personally identifying information. A Jingle client MUST enable a user to control which entities will be allowed to receive such information. If a human user explicitly accepts a session request, then the client SHOULD consider that action to imply approval of IP address sharing. However, waiting for a human user to explicitly accept the session request can result in delays during session setup, since it is more efficient to immediately begin sharing transport candidates. Therefore, it is RECOMMENDED for the client to immediately send transport candidates to a contact (without waiting for explicit user approval of the session request) in the following cases:
- The user has permanently and formally authorized the contact to view the user's presence information via a presence subscription as reflected in an XMPP roster item (see XMPP IM
> RFC 6121: Extensible Messaging and Presence Protocol (XMPP): Instant Messaging and Presence <http://tools.ietf.org/html/rfc6121>.
).
- The user has temporarily and dynamically shared presence with the contact via "directed presence" as described in RFC 3921
> RFC 3921: Extensible Messaging and Presence Protocol (XMPP): Instant Messaging and Presence <http://tools.ietf.org/html/rfc3921>.
.
- The user has explicitly added the contact to a list of entities who are allowed to access the user's personally-identifying information.

根据定义，传输候选的交换会导致发送方 IP 地址的暴露，这构成一种个人身份信息的形式。Jingle 客户端必须使用户能够控制允许哪些实体接收此类信息。如果人类用户明确接受会话请求，则客户端应将此操作视为暗示批准 IP 地址共享。然而，等待人类用户明确接受会话请求可能会导致会话建立过程中的延迟，因为立即开始共享传输候选更为高效。因此，建议客户端在以下情况下立即向联系人发送传输候选（无需等待用户对会话请求的明确批准）：
- 用户已通过反映在 XMPP 花名册项中的存在订阅（参见 XMPP IM, RFC 6121）永久并正式授权联系人查看用户的存在信息。
- 用户已通过 RFC 3921 中描述的"定向存在"临时且动态地与联系人共享存在信息。
- 用户已将联系人明确添加到允许访问用户个人身份信息的实体列表中。

### Encryption（加密）

A Jingle implementation SHOULD support security preconditions that are enforced before application media is allowed to flow over a UDP association, such as those described in Jingle XTLS
> Extensible Messaging and Presence Protocol (XMPP) End-to-End Encryption Using Transport Layer Security ("XTLS") <http://tools.ietf.org/html/draft-meyer-xmpp-e2e-encryption>.
.

Jingle 实现应支持在允许应用媒体通过 UDP 关联流动之前强制执行的安全前提条件，例如在 Jingle XTLS（使用传输层安全的 XMPP 端到端加密）中描述的那些。

Application types that use the Jingle ICE-UDP transport method MAY also define their own application-specific encryption methods, such as the Secure Real-time Transport Protocol (SRTP) for RTP exchanges as described in Jingle RTP Sessions (XEP-0167)
> XEP-0167: Jingle RTP Sessions <https://xmpp.org/extensions/xep-0167.html>.
.

使用 Jingle ICE-UDP 传输方法的应用类型也可以定义自己的应用特定加密方法，例如 Jingle RTP 会话 (XEP-0167) 中描述的用于 RTP 交换的安全实时传输协议 (SRTP)。
