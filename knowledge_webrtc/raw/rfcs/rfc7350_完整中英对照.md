# RFC 7350 - STUN over DTLS
## Datagram Transport Layer Security (DTLS) as Transport for Session Traversal Utilities for NAT (STUN)
## DTLS（数据报传输层安全）作为 NAT 会话遍历工具（STUN）的传输协议

**原文**: [[RFC 7350](./rfc7350)] - Standards Track

**更新**: RFCs 5389, 5928

## Abstract | 摘要

This document specifies the usage of Datagram Transport Layer Security (DTLS) as a transport protocol for Session Traversal Utilities for NAT (STUN). It provides guidance on when and how to use DTLS with the currently standardized STUN usages. It also specifies modifications to the STUN and Traversal Using Relay NAT (TURN) URIs and to the TURN resolution mechanism to facilitate the resolution of STUN and TURN URIs into the IP address and port of STUN and TURN servers supporting DTLS as a transport protocol. This document updates RFCs 5389 and 5928.

本文档指定了 DTLS（数据报传输层安全）作为 NAT 会话遍历工具（STUN）的传输协议的使用。它提供了关于何时以及如何将 DTLS 与当前标准化的 STUN 用法一起使用的指导。它还指定了对 STUN 和利用 NAT 中继遍历（TURN）URI 以及 TURN 解析机制的修改，以促进将 STUN 和 TURN URI 解析为支持 DTLS 作为传输协议的 STUN 和 TURN 服务器的 IP 地址和端口。本文档更新了 RFC 5389 和 5928。

## 1. Introduction | 1. 简介

STUN [[RFC5389](./rfc5389)] defines Transport Layer Security (TLS) over TCP (simply referred to as TLS [[RFC5246](./rfc5246)]) as the transport for STUN due to additional security advantages it offers over plain UDP or TCP transport. But, TCP (and thus TLS-over-TCP) is not an optimal transport when STUN is used for its originally intended purpose, which is to support multimedia sessions. This is a well documented and understood transport limitation for real-time communications.

STUN [[RFC5389](./rfc5389)] 定义了通过 TCP 的传输层安全（TLS）（简称为 TLS [[RFC5246](./rfc5246)]）作为 STUN 的传输，因为它提供的额外安全优势优于普通 UDP 或 TCP 传输。但是，当 STUN 用于其最初预期目的（即支持多媒体会话）时，TCP（因此 TLS-over-TCP）并非最佳传输。这是一个有据可查且被理解的实时通信传输限制。

---

DTLS-over-UDP (referred to in this document as simply DTLS [[RFC6347](./rfc6347)]) offers the same security advantages as TLS-over-TCP, but without the undesirable concerns.

DTLS-over-UDP（本文档中简称为 DTLS [[RFC6347](./rfc6347)]) 提供与 TLS-over-TCP 相同的安全优势，但没有那些不良问题。

---

## 3. DTLS as Transport for STUN | 3. DTLS 作为 STUN 的传输协议

STUN [[RFC5389](./rfc5389)] defines three transports: UDP, TCP, and TLS. This document adds DTLS as a valid transport for STUN.

STUN [[RFC5389](./rfc5389)] 定义了三种传输：UDP、TCP 和 TLS。本文档将 DTLS 添加为 STUN 的有效传输。

---

STUN over DTLS MUST use the same retransmission rules as STUN over UDP (as described in Section 7.2.1 of [[RFC5389](./rfc5389)]). It MUST also use the same rules that are described in Section 7.2.2 of [[RFC5389](./rfc5389)] to verify the server identity. Instead of TLS_RSA_WITH_AES_128_CBC_SHA, which is the default cipher suite for STUN over TLS, implementations of STUN over DTLS, and deployed clients and servers, MUST support TLS_DHE_RSA_WITH_AES_128_GCM_SHA256 and TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256, and MAY support other cipher suites. Perfect Forward Secrecy (PFS) cipher suites MUST be preferred over non-PFS cipher suites. Cipher suites with known weaknesses, such as those based on (single) DES and RC4, MUST NOT be used. Implementations MUST disable TLS-level compression. The same rules established in Section 7.2.2 of [[RFC5389](./rfc5389)] for keeping open and closing TCP/TLS connections MUST be used as well for DTLS associations.

通过 DTLS 的 STUN 必须使用与通过 UDP 的 STUN 相同的重传规则（如 [[RFC5389](./rfc5389)] 第 7.2.1 节中所述）。它还必须使用 [[RFC5389](./rfc5389)] 第 7.2.2 节中描述的相同规则来验证服务器身份。代替 TLS_RSA_WITH_AES_128_CBC_SHA（这是通过 TLS 的 STUN 的默认密码套件），STUN over DTLS 的实现以及已部署的客户端和服务器必须支持 TLS_DHE_RSA_WITH_AES_128_GCM_SHA256 和 TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256，并且可以支持其他密码套件。必须优先选择具有完美前向保密（PFS）的密码套件，而不是非 PFS 密码套件。不得使用具有已知弱点的密码套件，如基于（单个）DES 和 RC4 的密码套件。实现必须禁用 TLS 级压缩。[[RFC5389](./rfc5389)] 第 7.2.2 节中建立的用于保持打开和关闭 TCP/TLS 连接的相同规则也必须用于 DTLS 关联。

---

In addition to the path MTU rules described in Section 7.1 of [[RFC5389](./rfc5389)], if the path MTU is unknown, the actual STUN message needs to be adjusted to take into account the size of the (13-byte) DTLS Record header, the MAC size, and the padding size.

除了 [[RFC5389](./rfc5389)] 第 7.1 节中描述的路径 MTU 规则外，如果路径 MTU 未知，则需要调整实际 STUN 消息以考虑（13 字节）DTLS 记录头、MAC 大小和填充大小的大小。

---

By default, STUN over DTLS MUST use port 5349, the same port number as STUN over TLS. However, the Service Record (SRV) procedures can be implemented to use a different port (as described in Section 9 of [[RFC5389](./rfc5389)]). When using SRV records, the service name MUST be set to "stuns" and the protocol name to "udp".

默认情况下，通过 DTLS 的 STUN 必须使用端口 5349，与通过 TLS 的 STUN 相同。但是，可以实现服务记录（SRV）程序来使用不同的端口（如 [[RFC5389](./rfc5389)] 第 9 节中所述）。当使用 SRV 记录时，服务名称必须设置为"stuns"，协议名称设置为"udp"。

---

Classic STUN [[RFC3489](./rfc3489)] (which was obsoleted by [[RFC5389](./rfc5389)]) defines only UDP as a transport, and DTLS MUST NOT be used. Any STUN request or indication without the magic cookie (see Section 6 of [[RFC5389](./rfc5389)]) over DTLS MUST always result in an error.

经典 STUN [[RFC3489](./rfc3489)]（被 [[RFC5389](./rfc5389)] 废弃）仅将 UDP 定义为传输，不得使用 DTLS。任何通过 DTLS 发送的没有魔数 cookie（见 [[RFC5389](./rfc5389)] 第 6 节）的 STUN 请求或指示必须始终导致错误。

---

## 4. STUN Usages | 4. STUN 用法

Section 7.2 of [[RFC5389](./rfc5389)] states that STUN usages must specify which transport protocol is used. The following sections discuss if and how the existing STUN usages are used with DTLS as the transport. Future STUN usages MUST take into account DTLS as a transport and discuss its applicability. In all cases, new STUN usages MUST explicitly state if implementing the denial-of-service countermeasure described in Section 4.2.1 of [[RFC6347](./rfc6347)] is mandatory.

[[RFC5389](./rfc5389)] 第 7.2 节规定 STUN 用法必须指定使用哪种传输协议。以下各节讨论现有 STUN 用法是否以及如何与 DTLS 一起作为传输使用。未来的 STUN 用法必须考虑 DTLS 作为传输并讨论其适用性。在所有情况下，新的 STUN 用法必须明确说明实现 [[RFC6347](./rfc6347)] 第 4.2.1 节中描述的拒绝服务对策是否为强制性的。

---

### 4.1. NAT Discovery Usage | 4.1. NAT 发现用法

As stated by Section 13 of [[RFC5389](./rfc5389)], "...TLS provides minimal security benefits..." for this particular STUN usage. DTLS will also similarly offer only limited benefit. This is because the only mandatory attribute that is TLS/DTLS protected is the XOR-MAPPED-ADDRESS, which is already known by an on-path attacker, since it is the same as the source address and port of the STUN request. On the other hand, using TLS/DTLS will prevent an active attacker to inject XOR-MAPPED-ADDRESS in responses. The TLS/DTLS transport will also protect the SOFTWARE attribute, which can be used to find vulnerabilities in STUN implementations.

正如 [[RFC5389](./rfc5389)] 第 13 节所述，"...TLS 提供最小的安全好处..."对于这个特定的 STUN 用法。DTLS 同样只会提供有限的好处。这是因为唯一必须由 TLS/DTLS 保护的是 XOR-MAPPED-ADDRESS 属性，它已经被路径上的攻击者所知，因为它与 STUN 请求的源地址和端口相同。另一方面，使用 TLS/DTLS 将防止主动攻击者在响应中注入 XOR-MAPPED-ADDRESS。TLS/DTLS 传输还将保护 SOFTWARE 属性，该属性可用于发现 STUN 实现中的漏洞。

---

Regardless, this usage is rarely used by itself, since using TURN [[RFC5766](./rfc5766)] with Interactive Connectivity Establishment (ICE) [[RFC5245](./rfc5245)] is generally indispensable, and TURN provides the same NAT Discovery feature as part of an allocation creation. In fact, with ICE, the NAT Discovery usage is only used when there is no longer any resource available for new allocations in the TURN server.

无论如何，此用法很少单独使用，因为使用 TURN [[RFC5766](./rfc5766)] 与交互式连接建立（ICE）[[RFC5245](./rfc5245)] 通常是不可或缺的，而 TURN 作为分配创建的一部分提供相同的 NAT 发现功能。事实上，使用 ICE 时，NAT 发现用法仅在 TURN 服务器中没有可用于新分配的资源时使用。

---

A STUN server implementing the NAT Discovery usage and using DTLS MUST implement the denial-of-service countermeasure described in Section 4.2.1 of [[RFC6347](./rfc6347)].

实现 NAT 发现用法并使用 DTLS 的 STUN 服务器必须实现 [[RFC6347](./rfc6347)] 第 4.2.1 节中描述的拒绝服务对策。

---

#### 4.1.1. DTLS Support in STUN URIs | 4.1.1. STUN URI 中的 DTLS 支持

This document does not make any changes to the syntax of a STUN URI [[RFC7064](./rfc7064)]. As indicated in Section 3.2 of [[RFC7064](./rfc7064)], secure transports like STUN over TLS, and now STUN over DTLS, MUST use the "stuns" URI scheme.

本文档不对 STUN URI [[RFC7064](./rfc7064)] 的语法进行任何更改。如 [[RFC7064](./rfc7064)] 第 3.2 节所示，安全的传输（如 STUN over TLS 和现在的 STUN over DTLS）必须使用"stuns" URI 方案。

---

The <host> value MUST be used when using the rules in Section 7.2.2 of [[RFC5389](./rfc5389)] to verify the server identity. A STUN URI containing an IP address MUST be rejected, unless the domain name is provided by the same mechanism that provided the STUN URI, and that domain name can be passed to the verification code.

使用 [[RFC5389](./rfc5389)] 第 7.2.2 节中的规则验证服务器身份时，必须使用 <host> 值。包含 IP 地址的 STUN URI 必须被拒绝，除非提供 STUN URI 的相同机制提供了域名，并且该域名可以传递给验证代码。

---

### 4.2. Connectivity Check Usage | 4.2. 连接检查用法

Using DTLS would hide the USERNAME, PRIORITY, USE-CANDIDATE, ICE-CONTROLLED, and ICE-CONTROLLING attributes. But, because MESSAGE-INTEGRITY protects the entire STUN response using a password that is known only by looking at the Session Description Protocol (SDP) exchanged, it is not possible for an attacker that does not have access to this SDP to inject an incorrect XOR-MAPPED-ADDRESS, which would subsequently be used as a peer reflexive candidate.

使用 DTLS 会隐藏 USERNAME、PRIORITY、USE-CANDIDATE、ICE-CONTROLLED 和 ICE-CONTROLLING 属性。但是，因为 MESSAGE-INTEGRITY 使用仅通过查看交换的会话描述协议（SDP）才知道的密码来保护整个 STUN 响应，所以无法访问此 SDP 的攻击者不可能注入错误的 XOR-MAPPED-ADDRESS（随后将用作对等方反射候选）。

---

Adding DTLS on top of the connectivity check would delay, and consequently impair, the ICE process. Adding additional round trips to ICE is undesirable, so much that there is a proposal ([[ICE-DTLS](./ref-ICE-DTLS)]) to use the DTLS handshake used by the WebRTC Secure Real-time Transport Protocol (SRTP) streams as a replacement for the connectivity checks.

在连接检查之上添加 DTLS 会延迟，从而损害 ICE 过程。向 ICE 添加额外的往返是不受欢迎的，以至于有一个提案（[[ICE-DTLS](./ref-ICE-DTLS)]）使用 WebRTC 安全实时传输协议（SRTP）流使用的 DTLS 握手作为连接检查的替代。

---

STUN URIs are not used with this usage.

此用法不使用 STUN URI。

---

### 4.3. Media Keep-Alive Usage | 4.3. 媒体保活用法

When STUN Binding Indications are being used for media keep-alive (described in Section 10 of [[RFC5245](./rfc5245)]), it runs alongside an RTP or RTP Control Protocol (RTCP) session. It is possible to send these media keep-alive packets inside a separately negotiated non-SRTP DTLS session if DTLS-SRTP [[RFC5764](./rfc5764)] is used, but that would add overhead, with minimal security benefit.

当 STUN 绑定指示用于媒体保活（如 [[RFC5245](./rfc5245)] 第 10 节中所述）时，它与 RTP 或 RTP 控制协议（RTCP）会话一起运行。如果使用 DTLS-SRTP [[RFC5764](./rfc5764)]，可以在单独协商的非 SRTP DTLS 会话中发送这些媒体保活数据包，但那会增加开销，而安全好处微乎其微。

---

STUN URIs are not used with this usage.

此用法不使用 STUN URI。

---

### 4.4. SIP Keep-Alive Usage | 4.4. SIP 保活用法

The SIP keep-alive (described in [[RFC5626](./rfc5626)]) runs inside a SIP flow. This flow would be protected if a SIP over DTLS transport mechanism is implemented (such as described in [[SIP-DTLS](./ref-SIP-DTLS)]).

SIP 保活（如 [[RFC5626](./rfc5626)] 中所述）在 SIP 流内运行。如果实现了 SIP over DTLS 传输机制（如 [[SIP-DTLS](./ref-SIP-DTLS)] 中所述），则此流将受到保护。

---

STUN URIs are not used with this usage.

此用法不使用 STUN URI。

---

### 4.5. NAT Behavior Discovery Usage | 4.5. NAT 行为发现用法

The NAT Behavior Discovery usage is Experimental and to date has never been effectively deployed. Despite this, using DTLS would add the same security properties as for the NAT Discovery usage (Section 4.1).

NAT 行为发现用法是实验性的，迄今为止从未有效部署过。尽管如此，使用 DTLS 将为 NAT 发现用法添加相同的安全特性（第 4.1 节）。

---

The STUN URI can be used to access the NAT Discovery feature of a NAT Behavior Discovery server, but accessing the full features would require definition of a "stun-behaviors:" URI, which is out of scope for this document.

STUN URI 可用于访问 NAT 行为发现服务器的 NAT 发现功能，但访问完整功能需要定义"stun-behaviors:" URI，这超出了本文档的范围。

---

A STUN server implementing the NAT Behavior Discovery usage and using DTLS MUST implement the denial-of-service countermeasure described in Section 4.2.1 of [[RFC6347](./rfc6347)].

实现 NAT 行为发现用法并使用 DTLS 的 STUN 服务器必须实现 [[RFC6347](./rfc6347)] 第 4.2.1 节中描述的拒绝服务对策。

---

### 4.6. TURN Usage | 4.6. TURN 用法

TURN [[RFC5766](./rfc5766)] defines three combinations of transports/allocations: UDP/UDP, TCP/UDP, and TLS/UDP. This document adds DTLS/UDP as a valid combination. A TURN server using DTLS MUST implement the denial-of-service countermeasure described in Section 4.2.1 of [[RFC6347](./rfc6347)].

TURN [[RFC5766](./rfc5766)] 定义了三种传输/分配组合：UDP/UDP、TCP/UDP 和 TLS/UDP。本文档添加 DTLS/UDP 作为有效组合。使用 DTLS 的 TURN 服务器必须实现 [[RFC6347](./rfc6347)] 第 4.2.1 节中描述的拒绝服务对策。

---

[[RFC6062](./rfc6062)] states that TCP allocations cannot be obtained using a UDP association between client and server. The fact that DTLS uses UDP implies that TCP allocations MUST NOT be obtained using a DTLS association between client and server.

[[RFC6062](./rfc6062)] 规定不能使用客户端和服务器之间的 UDP 关联获取 TCP 分配。DTLS 使用 UDP 这一事实意味着不能使用客户端和服务器之间的 DTLS 关联获取 TCP 分配。

---

By default, TURN over DTLS uses port 5349, the same port number as TURN over TLS. However, the SRV procedures can be implemented to use a different port (as described in Section 6 of [[RFC5766](./rfc5766)]). When using SRV records, the service name MUST be set to "turns" and the protocol name to "udp".

默认情况下，TURN over DTLS 使用端口 5349，与 TURN over TLS 相同。但是，可以实现 SRV 程序来使用不同的端口（如 [[RFC5766](./rfc5766)] 第 6 节中所述）。当使用 SRV 记录时，服务名称必须设置为"turns"，协议名称设置为"udp"。

---

#### 4.6.1. DTLS Support in TURN URIs | 4.6.1. TURN URI 中的 DTLS 支持

This document does not make any changes to the syntax of a TURN URI [[RFC7065](./rfc7065)]. As indicated in Section 3 of [[RFC7065](./rfc7065)], secure transports like TURN over TLS, and now TURN over DTLS, MUST use the "turns" URI scheme. When using the "turns" URI scheme to designate TURN over DTLS, the transport value of the TURN URI, if set, MUST be "udp".

本文档不对 TURN URI [[RFC7065](./rfc7065)] 的语法进行任何更改。如 [[RFC7065](./rfc7065)] 第 3 节所示，安全的传输（如 TURN over TLS 和现在的 TURN over DTLS）必须使用"turns" URI 方案。当使用"turns" URI 方案来指定 TURN over DTLS 时，如果设置了 TURN URI 的传输值，则必须为"udp"。

---

The <host> value MUST be used when using the rules in Section 7.2.2 of [[RFC5389](./rfc5389)] to verify the server identity. A TURN URI containing an IP address MUST be rejected, unless the domain is provided by the same mechanism that provided the TURN URI, and that domain name can be passed to the verification code.

使用 [[RFC5389](./rfc5389)] 第 7.2.2 节中的规则验证服务器身份时，必须使用 <host> 值。包含 IP 地址的 TURN URI 必须被拒绝，除非提供 TURN URI 的相同机制提供了域名，并且该域名可以传递给验证代码。

---

#### 4.6.2. Resolution Mechanism for TURN over DTLS | 4.6.2. TURN over DTLS 的解析机制

This document defines a new Straightforward-Naming Authority Pointer (S-NAPTR) application protocol tag: "turn.dtls".

本文档定义了一个新的直接命名权威指针（S-NAPTR）应用协议标签："turn.dtls"。

---

The <transport> component, as provisioned or resulting from the parsing of a TURN URI, is passed without modification to the TURN resolution mechanism defined in Section 3 of [[RFC5928](./rfc5928)], but with the following alterations to that algorithm:

<transport> 组件（如配置或 TURN URI 解析的结果）不变地传递给 [[RFC5928](./rfc5928)] 第 3 节中定义的 TURN 解析机制，但对算法进行以下更改：

---

- The acceptable values for the transport name are extended with the addition of "dtls".
- 传输名称的可接受值通过添加"dtls"来扩展。

- The acceptable values in the ordered list of supported TURN transports is extended with the addition of "Datagram Transport Layer Security (DTLS)".
- 支持的 TURN 传输的有序列表中的可接受值通过添加"数据报传输层安全（DTLS）"来扩展。

- The resolution algorithm check rules list is extended with the addition of the following step:
- 解析算法检查规则列表通过添加以下步骤来扩展：

  If <secure> is true and <transport> is defined as "udp" but the list of TURN transports supported by the application does not contain DTLS, then the resolution MUST stop with an error.
  如果 <secure> 为 true 且 <transport> 定义为"udp"，但应用程序支持的 TURN 传输列表不包含 DTLS，则解析必须停止并返回错误。

- The 5th rule of the resolution algorithm check rules list is modified to read like this:
- 解析算法检查规则列表的第 5 条规则被修改为：

  If <secure> is true and <transport> is not defined but the list of TURN transports supported by the application does not contain TLS or DTLS, then the resolution MUST stop with an error.
  如果 <secure> 为 true 且 <transport> 未定义，但应用程序支持的 TURN 传输列表不包含 TLS 或 DTLS，则解析必须停止并返回错误。

- Table 1 is modified to add the following line:
- 表 1 被修改以添加以下行：

```

                +----------+-------------+----------------+
                | <secure> | <transport> | TURN Transport |
                +----------+-------------+----------------+
                | true     | "udp"       | DTLS           |
                +----------+-------------+----------------+

```

- In step 1 of the resolution algorithm, the default port for DTLS is 5349.
- 在解析算法的第 1 步中，DTLS 的默认端口为 5349。

- In step 4 of the resolution algorithm, the following is added to the list of conversions between the filtered list of TURN transports supported by the application and application protocol tags:
- 在解析算法的第 4 步中，以下内容被添加到应用程序支持的过滤 TURN 传输列表与应用协议标签之间的转换列表中：

  "turn.dtls" is used if the TURN transport is DTLS.
  如果 TURN 传输是 DTLS，则使用"turn.dtls"。

---

Note that using the resolution mechanism in [[RFC5928](./rfc5928)] does not imply that additional round trips to the DNS server will be needed (e.g., the TURN client will start immediately if the TURN URI contains an IP address).

请注意，使用 [[RFC5928](./rfc5928)] 中的解析机制并不意味着需要额外的 DNS 服务器往返（例如，如果 TURN URI 包含 IP 地址，TURN 客户端将立即启动）。

## 5. Security Considerations | 5. 安全考虑

STUN over DTLS as a STUN transport does not introduce any specific security considerations beyond those for STUN over TLS detailed in [[RFC5389](./rfc5389)].

作为 STUN 传输的 STUN over DTLS 不会引入 [[RFC5389](./rfc5389)] 中详述的 STUN over TLS 以外的任何特定安全考虑。

---

The usage of "udp" as a transport parameter with the "stuns" URI scheme does not introduce any specific security issues beyond those discussed in [[RFC7064](./rfc7064)].

将"udp"用作"stuns" URI 方案的传输参数不会引入 [[RFC7064](./rfc7064)] 中讨论以外的任何特定安全问题。

---

TURN over DTLS as a TURN transport does not introduce any specific security considerations beyond those for TURN over TLS detailed in [[RFC5766](./rfc5766)].

作为 TURN 传输的 TURN over DTLS 不会引入 [[RFC5766](./rfc5766)] 中详述的 TURN over TLS 以外的任何特定安全考虑。

---

The usage of "udp" as a transport parameter with the "turns" URI scheme does not introduce any specific security issues beyond those discussed in [[RFC7065](./rfc7065)].

将"udp"用作"turns" URI 方案的传输参数不会引入 [[RFC7065](./rfc7065)] 中讨论以外的任何特定安全问题。

---

The new S-NAPTR application protocol tag defined in this document as well as the modifications this document makes to the TURN resolution mechanism described in [[RFC5928](./rfc5928)] do not introduce any additional security considerations beyond those outlined in [[RFC5928](./rfc5928)].

本文档定义的新 S-NAPTR 应用协议标签以及本文档对 [[RFC5928](./rfc5928)] 中描述的 TURN 解析机制的修改不会引入 [[RFC5928](./rfc5928)] 中概述以外的任何额外安全考虑。

表 1 显示了如何为使用 DTLS 作为其传输的 TURN URI 填充 <secure>、<port> 和 <transport> 组件。对于所有这些示例，<host> 组件填充为"example.net"。

```

   +---------------------------------+----------+--------+-------------+
   | URI                             | <secure> | <port> | <transport> |
   +---------------------------------+----------+--------+-------------+
   | turns:example.net?transport=udp | true     |        | DTLS        |
   +---------------------------------+----------+--------+-------------+

```

---

With the DNS Resource Records (RRs) in Figure 1 and an ordered TURN transport list of {DTLS, TLS, TCP, UDP}, the resolution algorithm will convert the TURN URI "turns:example.net" to the ordered list of IP address, port, and protocol tuples in Table 2.

通过图 1 中的 DNS 资源记录（RR）以及有序 TURN 传输列表 {DTLS, TLS, TCP, UDP}，解析算法将把 TURN URI "turns:example.net" 转换为表 2 中 IP 地址、端口和协议元组的有序列表。

```

   example.net.
   IN NAPTR 100 10 "" RELAY:turn.udp:turn.dtls "" datagram.example.net.
   IN NAPTR 200 10 "" RELAY:turn.tcp:turn.tls "" stream.example.net.

   datagram.example.net.
   IN NAPTR 100 10 S RELAY:turn.udp "" _turn._udp.example.net.
   IN NAPTR 200 10 S RELAY:turn.dtls "" _turns._udp.example.net.

   stream.example.net.
   IN NAPTR 100 10 S RELAY:turn.tcp "" _turn._tcp.example.net.
   IN NAPTR 200 10 A RELAY:turn.tls "" a.example.net.

   _turn._udp.example.net.
   IN SRV   0 0 3478 a.example.net.

   _turn._tcp.example.net.
   IN SRV   0 0 5000 a.example.net.

   _turns._udp.example.net.
   IN SRV   0 0 5349 a.example.net.

   a.example.net.
   IN A     192.0.2.1

```
