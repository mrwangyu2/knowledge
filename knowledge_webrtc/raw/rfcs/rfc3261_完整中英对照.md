## Abstract | 摘要

#### 原文

This document describes Session Initiation Protocol (SIP), an application-layer control (signaling) protocol for creating, modifying, and terminating sessions with one or more participants. These sessions include Internet telephone calls, multimedia distribution, and multimedia conferences.

SIP invitations used to create sessions carry session descriptions that allow participants to agree on a set of compatible media types. SIP makes use of elements called proxy servers to help route requests to the user's current location, authenticate and authorize users for services, implement provider call-routing policies, and provide features to users. SIP also provides a registration function that allows users to upload their current locations for use by proxy servers. SIP runs on top of several different transport protocols.

#### 中文

本文档描述了会话发起协议 (SIP)，一种用于创建、修改和终止与一个或多个参与者会话的应用层控制（信令）协议。这些会话包括互联网电话呼叫、多媒体分发和多媒体会议。

用于创建会话的 SIP 邀请携带会话描述，允许参与者就一组兼容的媒体类型达成一致。SIP 利用称为代理服务器的元素来帮助将请求路由到用户的当前位置、对用户进行服务的认证和授权、实施提供商的呼叫路由策略，并为用户提供功能。SIP 还提供注册功能，允许用户上传其当前位置供代理服务器使用。SIP 运行在多种不同的传输协议之上。

## 1. Introduction | 1. 引言

#### 原文

There are many applications of the Internet that require the creation and management of a session, where a session is considered an exchange of data between an association of participants. The implementation of these applications is complicated by the practices of participants: users may move between endpoints, they may be addressable by multiple names, and they may communicate in several different media - sometimes simultaneously. Numerous protocols have been authored that carry various forms of real-time multimedia session data such as voice, video, or text messages. The Session Initiation Protocol (SIP) works in concert with these protocols by enabling Internet endpoints (called user agents) to discover one another and to agree on a characterization of a session they would like to share. For locating prospective session participants, and for other functions, SIP enables the creation of an infrastructure of network hosts (called proxy servers) to which user agents can send registrations, invitations to sessions, and other requests. SIP is an agile, general-purpose tool for creating, modifying, and terminating sessions that works independently of underlying transport protocols and without dependency on the type of session that is being established.

#### 中文

互联网上有许多应用需要创建和管理会话，会话被视为参与者之间交换数据的过程。这些应用的实现因参与者的行为而变得复杂：用户可能在端点之间移动，他们可能有多个可寻址名称，他们可能以多种不同的媒体进行通信——有时甚至是同时进行。已经创建了多种协议来传输各种实时多媒体会话数据，如语音、视频或文本消息。会话发起协议 (SIP) 与这些协议协同工作，使互联网端点（称为用户代理）能够相互发现并就他们想要共享的会话特性达成一致。为了定位潜在的会话参与者以及其他功能，SIP 使网络主机（称为代理服务器）的基础设施能够被创建，用户代理可以向其发送注册、会话邀请和其他请求。SIP 是一个灵活的通用工具，用于创建、修改和终止会话，它独立于底层传输协议工作，不依赖于正在建立的会话类型。

## 2. Overview of SIP Functionality | 2. SIP 功能概述

#### 原文

SIP is an application-layer control protocol that can establish, modify, and terminate multimedia sessions (conferences) such as Internet telephony calls. SIP can also invite participants to already existing sessions, such as multicast conferences. Media can be added to (and removed from) an existing session. SIP transparently supports name mapping and redirection services, which supports personal mobility - users can maintain a single externally visible identifier regardless of their network location.

SIP supports five facets of establishing and terminating multimedia communications:

User location: determination of the end system to be used for communication;

User availability: determination of the willingness of the called party to engage in communications;

User capabilities: determination of the media and media parameters to be used;

Session setup: "ringing", establishment of session parameters at both called and calling party;

Session management: including transfer and termination of sessions, modifying session parameters, and invoking services.

#### 中文

SIP 是一个应用层控制协议，可以建立、修改和终止多媒体会话（会议），如互联网电话呼叫。SIP 还可以邀请参与者加入已存在的会话，如多播会议。媒体可以添加到现有会话中（也可以从中移除）。SIP 透明地支持名称映射和重定向服务，这支持个人移动性——用户可以维护一个单一的对外部可见的标识符，而不管其网络位置如何。

SIP 支持建立和终止多媒体通信的五个方面：

用户位置：确定用于通信的终端系统；

用户可用性：确定被叫方愿意参与通信；

用户能力：确定要使用的媒体和媒体参数；

会话建立："振铃"，在主叫方和被叫方两端建立会话参数；

会话管理：包括会话的转移和终止、修改会话参数以及调用服务。

#### 原文

SIP is not a vertically integrated communications system. SIP is rather a component that can be used with other IETF protocols to build a complete multimedia architecture. Typically, these architectures will include protocols such as the Real-time Transport Protocol (RTP) (RFC 1889) for transporting real-time data and providing QoS feedback, the Real-Time Streaming Protocol (RTSP) (RFC 2326) for controlling delivery of streaming media, the Gateway Control Protocol (MEGACO) (RFC 3015) for controlling gateways to the Public Switched Telephone Network (PSTN), and the Session Description Protocol (SDP) (RFC 2327) for describing multimedia sessions. Therefore, SIP should be used in conjunction with other protocols in order to provide complete services to the users. However, the basic functionality and operation of SIP does not depend on any of these protocols.

#### 中文

SIP 不是垂直集成的通信系统。SIP 是一个可与其他 IETF 协议一起使用来构建完整多媒体架构的组件。通常，这些架构将包括诸如实时传输协议 (RTP) (RFC 1889) 用于传输实时数据并提供 QoS 反馈、实时流协议 (RTSP) (RFC 2326) 用于控制流媒体传递、网关控制协议 (MEGACO) (RFC 3015) 用于控制到公共交换电话网络 (PSTN) 的网关，以及会话描述协议 (SDP) (RFC 2327) 用于描述多媒体会话等协议。因此，SIP 应该与其他协议结合使用，以向用户提供完整的服务。然而，SIP 的基本功能和操作不依赖于这些协议中的任何一个。

#### 原文

SIP does not provide services. Rather, SIP provides primitives that can be used to implement different services. For example, SIP can locate a user and deliver an opaque object to his current location. If this primitive is used to deliver a session description written in SDP, for instance, the endpoints can agree on the parameters of a session. If the same primitive is used to deliver a photo of the caller as well as the session description, a "caller ID" service can be easily implemented. As this example shows, a single primitive is typically used to provide several different services.

SIP does not offer conference control services such as floor control or voting and does not prescribe how a conference is to be managed. SIP can be used to initiate a session that uses some other conference control protocol. Since SIP messages and the sessions they establish can pass through entirely different networks, SIP cannot, and does not, provide any kind of network resource reservation capabilities.

The nature of the services provided make security particularly important. To that end, SIP provides a suite of security services, which include denial-of-service prevention, authentication (both user to user and proxy to user), integrity protection, and encryption and privacy services.

SIP works with both IPv4 and IPv6.

#### 中文

SIP 不提供服务。确切地说，SIP 提供可以被用来实现不同服务的基本功能。例如，SIP 可以定位用户并将不透明对象传送到其当前位置。如果使用此基本功能来传送用 SDP 编写的会话描述，端点可以就会话参数达成一致。如果使用相同的基本功能来传送呼叫者的照片以及会话描述，则可以轻松实现"来电显示"服务。正如这个例子所示，单个基本功能通常用于提供几种不同的服务。

SIP 不提供会议室控制服务，如发言权控制或投票，也不规定会议的管理方式。SIP 可用于发起使用其他会议控制协议的会话。由于 SIP 消息及其建立的会话可以通过完全不同的网络传递，SIP 不能也不提供任何类型的网络资源预留功能。

所提供服务的性质使安全性尤为重要。为此，SIP 提供了一套安全服务，包括拒绝服务防护、认证（用户对用户以及代理对用户）、完整性保护以及加密和隐私服务。

SIP 可与 IPv4 和 IPv6 配合工作。

## 4. Overview of Operation | 4. 操作概述

#### 原文

This section introduces the basic operations of SIP using simple examples. This section is tutorial in nature and does not contain any normative statements.

The first example shows the basic functions of SIP: location of an end point, signal of a desire to communicate, negotiation of session parameters to establish the session, and teardown of the session once established.

#### 中文

本节通过简单的示例介绍 SIP 的基本操作。本节本质上是教程性质，不包含任何规范性声明。

第一个示例展示了 SIP 的基本功能：端点定位、通信意愿的信令、会话建立时会话参数的协商，以及一旦建立后的会话拆除。

#### 原文

Figure 1 shows a typical example of a SIP message exchange between two users, Alice and Bob. (Each message is labeled with the letter "F" and a number for reference by the text.) In this example, Alice uses a SIP application on her PC (referred to as a softphone) to call Bob on his SIP phone over the Internet. Also shown are two SIP proxy servers that act on behalf of Alice and Bob to facilitate the session establishment. This typical arrangement is often referred to as the "SIP trapezoid" as shown by the geometric shape of the dotted lines in Figure 1.

#### 中文

图 1 显示了 Alice 和 Bob 两个用户之间典型的 SIP 消息交换示例。（每个消息都用字母"F"和一个数字标记，供文本参考。）在这个示例中，Alice 在她的 PC 上使用 SIP 应用程序（称为软电话）通过互联网呼叫 Bob 的 SIP 电话。还显示了两个 SIP 代理服务器，代表 Alice 和 Bob 行事的，以促进会话建立。这种典型的安排通常被称为"SIP 梯形"，如图 1 中虚线形成的几何形状所示。

#### 原文

Alice "calls" Bob using his SIP identity, a type of Uniform Resource Identifier (URI) called a SIP URI. SIP URIs are defined in Section 19.1. It has a similar form to an email address, typically containing a username and a host name. In this case, it is sip:bob@biloxi.com, where biloxi.com is the domain of Bob's SIP service provider. Alice has a SIP URI of sip:alice@atlanta.com. Alice might have typed in Bob's URI or perhaps clicked on a hyperlink or an entry in an address book. SIP also provides a secure URI, called a SIPS URI. An example would be sips:bob@biloxi.com. A call made to a SIPS URI guarantees that secure, encrypted transport (namely TLS) is used to carry all SIP messages from the caller to the domain of the callee. From there, the request is sent securely to the callee, but with security mechanisms that depend on the policy of the domain of the callee.

#### 中文

Alice 使用 Bob 的 SIP 身份（一种称为 SIP URI 的统一资源标识符）"呼叫"Bob。SIP URI 在第 19.1 节中定义。它与电子邮件地址的形式类似，通常包含用户名和主机名。在这种情况下，它是 sip:bob@biloxi.com，其中 biloxi.com 是 Bob 的 SIP 服务提供商的域。Alice 的 SIP URI 是 sip:alice@atlanta.com。Alice 可能输入了 Bob 的 URI，或者点击了超链接或地址簿中的条目。SIP 还提供一种安全的 URI，称为 SIPS URI。例如 sips:bob@biloxi.com。呼叫 SIPS URI 保证使用安全加密传输（即 TLS）来承载从呼叫者到被呼叫者域的所有 SIP 消息。从那里开始，请求被安全地发送到被呼叫者，但安全机制取决于被呼叫者域的策略。

#### 原文

SIP is based on an HTTP-like request/response transaction model. Each transaction consists of a request that invokes a particular method, or function, on the server and at least one response. In this example, the transaction begins with Alice's softphone sending an INVITE request addressed to Bob's SIP URI. INVITE is an example of a SIP method that specifies the action that the requestor (Alice) wants the server (Bob) to take. The INVITE request contains a number of header fields. Header fields are named attributes that provide additional information about a message. The ones present in an INVITE include a unique identifier for the call, the destination address, Alice's address, and information about the type of session that Alice wishes to establish with Bob. The INVITE (message F1 in Figure 1) might look like this:

#### 中文

SIP 基于类似 HTTP 的请求/响应事务模型。每个事务由一个请求组成，该请求调用服务器上的特定方法或功能，以及至少一个响应。在这个示例中，事务从 Alice 的软电话发送一个寻址到 Bob 的 SIP URI 的 INVITE 请求开始。INVITE 是 SIP 方法的一个示例，它指定请求者（Alice）希望服务器（Bob）执行的动作。INVITE 请求包含多个头字段。头字段是命名的属性，提供关于消息的附加信息。INVITE 中存在的头字段包括：呼叫的唯一标识符、目标地址、Alice 的地址以及关于 Alice 希望与 Bob 建立的会话类型的信息。INVITE（如图 1 中的消息 F1）可能如下所示：

#### 原文

```
INVITE sip:bob@biloxi.com SIP/2.0
Via: SIP/2.0/UDP pc33.atlanta.com;branch=z9hG4bK776asdhds
Max-Forwards: 70
To: Bob <sip:bob@biloxi.com>
From: Alice <sip:alice@atlanta.com>;tag=1928301774
Call-ID: a84b4c76e66710@pc33.atlanta.com
CSeq: 314159 INVITE
Contact: <sip:alice@pc33.atlanta.com>
Content-Type: application/sdp
Content-Length: 142

(Alice's SDP not shown)
```

#### 中文

```
INVITE sip:bob@biloxi.com SIP/2.0
Via: SIP/2.0/UDP pc33.atlanta.com;branch=z9hG4bK776asdhds
Max-Forwards: 70
To: Bob <sip:bob@biloxi.com>
From: Alice <sip:alice@atlanta.com>;tag=1928301774
Call-ID: a84b4c76e66710@pc33.atlanta.com
CSeq: 314159 INVITE
Contact: <sip:alice@pc33.atlanta.com>
Content-Type: application/sdp
Content-Length: 142

(Alice's SDP not shown)
```

#### 原文

The first line of the text-encoded message contains the method name (INVITE). The lines that follow are a list of header fields. This example contains a minimum required set. The header fields are briefly described below:

Via contains the address (pc33.atlanta.com) at which Alice is expecting to receive responses to this request. It also contains a branch parameter that identifies this transaction.

To contains a display name (Bob) and a SIP or SIPS URI (sip:bob@biloxi.com) towards which the request was originally directed. Display names are described in RFC 2822.

From also contains a display name (Alice) and a SIP or SIPS URI (sip:alice@atlanta.com) that indicate the originator of the request. This header field also has a tag parameter containing a random string (1928301774) that was added to the URI by the softphone. It is used for identification purposes.

Call-ID contains a globally unique identifier for this call, generated by the combination of a random string and the softphone's host name or IP address. The combination of the To tag, From tag, and Call-ID completely defines a peer-to-peer SIP relationship between Alice and Bob and is referred to as a dialog.

CSeq or Command Sequence contains an integer and a method name. The CSeq number is incremented for each new request within a dialog and is a traditional sequence number.

Contact contains a SIP or SIPS URI that represents a direct route to contact Alice, usually composed of a username at a fully qualified domain name (FQDN). While an FQDN is preferred, many end systems do not have registered domain names, so IP addresses are permitted. While the Via header field tells other elements where to send the response, the Contact header field tells other elements where to send future requests.

Max-Forwards serves to limit the number of hops a request can make on the way to its destination. It consists of an integer that is decremented by one at each hop.

Content-Type contains a description of the message body (not shown).

Content-Length contains an octet (byte) count of the message body.

The complete set of SIP header fields is defined in Section 20.

#### 中文

文本编码消息的第一行包含方法名（INVITE）。后面的行是头字段列表。此示例包含最小必需集。头字段简要说明如下：

Via 包含 Alice 期望接收对此请求的响应的地址（pc33.atlanta.com）。它还包含一个用于标识此事务的 branch 参数。

To 包含显示名（Bob）和请求最初定向到的 SIP 或 SIPS URI（sip:bob@biloxi.com）。显示名在 RFC 2822 中描述。

From 也包含显示名（Alice）和指示请求发起者的 SIP 或 SIPS URI（sip:alice@atlanta.com）。此头字段还有一个 tag 参数，包含由软电话添加到 URI 的随机字符串（1928301774）。它用于识别目的。

Call-ID 包含此呼叫的全局唯一标识符，由随机字符串和软电话的主机名或 IP 地址组合生成。To tag、From tag 和 Call-ID 的组合完全定义了 Alice 和 Bob 之间的点对点 SIP 关系，并被称为对话。

CSeq 或命令序列包含一个整数和一个方法名。CSeq 编号在每个对话内的新请求时递增，是一个传统的序列号。

Contact 包含一个 SIP 或 SIPS URI，表示直接联系 Alice 的路由，通常由完全限定域名 (FQDN) 上的用户名组成。虽然首选 FQDN，但许多终端系统没有注册域名，因此允许使用 IP 地址。Via 头字段告诉其他元素将响应发送到哪里，而 Contact 头字段告诉其他元素将未来的请求发送到哪里。

Max-Forwards 用于限制请求在到达其目的地的途中可以经过的跳数。它由一个整数组成，每经过一跳递减一。

Content-Type 包含消息体（未显示）的描述。

Content-Length 包含消息体的八位字节（字节）计数。

完整的 SIP 头字段集在第 20 节中定义。

#### 原文

The details of the session, such as the type of media, codec, or sampling rate, are not described using SIP. Rather, the body of a SIP message contains a description of the session, encoded in some other protocol format. One such format is the Session Description Protocol (SDP) (RFC 2327). This SDP message (not shown in the example) is carried by the SIP message in a way that is analogous to a document attachment being carried by an email message, or a web page being carried in an HTTP message.

#### 中文

会话的详细信息，如媒体类型、编解码器或采样率，不使用 SIP 描述。确切地说，SIP 消息的主体包含会话的描述，用某种其他协议格式编码。一种这样的格式是会描述协议 (SDP) (RFC 2327)。此 SDP 消息（示例中未显示）由 SIP 消息承载，方式类似于电子邮件消息承载文档附件，或 HTTP 消息承载网页。

#### 原文

Since the softphone does not know the location of Bob or the SIP server in the biloxi.com domain, the softphone sends the INVITE to the SIP server that serves Alice's domain, atlanta.com. The address of the atlanta.com SIP server could have been configured in Alice's softphone, or it could have been discovered by DHCP, for example.

#### 中文

#### 原文

The atlanta.com SIP server is a type of SIP server known as a proxy server. A proxy server receives SIP requests and forwards them on behalf of the requestor. In this example, the proxy server receives the INVITE request and sends a 100 (Trying) response back to Alice's softphone. The 100 (Trying) response indicates that the INVITE has been received and that the proxy is working on her behalf to route the INVITE to the destination. Responses in SIP use a three-digit code followed by a descriptive phrase. This response contains the same To, From, Call-ID, CSeq and branch parameter in the Via as the INVITE, which allows Alice's softphone to correlate this response to the sent INVITE. The atlanta.com proxy server locates the proxy server at biloxi.com, possibly by performing a particular type of DNS (Domain Name Service) lookup to find the SIP server that serves the biloxi.com domain. As a result, it obtains the IP address of the biloxi.com proxy server and forwards, or proxies, the INVITE request there. Before forwarding the request, the atlanta.com proxy server adds an additional Via header field value that contains its own address (the INVITE already contains Alice's address in the first Via). The biloxi.com proxy server receives the INVITE and responds with a 100 (Trying) response back to the atlanta.com proxy server to indicate that it has received the INVITE and is processing the request. Bob's SIP phone receives the INVITE and alerts Bob to the incoming call from Alice so that Bob can decide whether to answer the call, that is, Bob's phone rings. #### 中文

Bob 的 SIP 电话收到 INVITE，并提醒 Bob 有来自 Alice 的来电，以便 Bob 决定是否接听电话，即 Bob 的电话振铃。Bob 的 SIP 电话在 180 (Ringing) 响应中表示这一点，该响应通过两个代理以相反方向路由回来。每个代理使用 Via 头字段来确定将响应发送到哪里，并从顶部移除其自己的地址。结果，虽然路由初始 INVITE 需要 DNS 和位置服务查找，但 180 (Ringing) 响应可以在不进行查找或不维护代理中状态的情况下返回给呼叫者。这还具有一个理想的特性，即看到 INVITE 的每个代理也将看到 INVITE 的所有响应。

#### 原文

When Alice's softphone receives the 180 (Ringing) response, it passes this information to Alice, perhaps using an audio ringback tone or by displaying a message on Alice's screen.

In this example, Bob decides to answer the call. When he picks up the handset, his SIP phone sends a 200 (OK) response to indicate that the call has been answered. The 200 (OK) contains a message body with the SDP media description of the type of session that Bob is willing to establish with Alice. As a result, there is a two-phase exchange of SDP messages: Alice sent one to Bob, and Bob sent one back to Alice. This two-phase exchange provides basic negotiation capabilities and is based on a simple offer/answer model of SDP exchange. If Bob did not wish to answer the call or was busy on another call, an error response would have been sent instead of the 200 (OK), which would have resulted in no media session being established. In addition to DNS and location service lookups shown in this example, proxy servers can make flexible "routing decisions" to decide where to send a request. For example, if Bob's SIP phone returned a 486 (Busy Here) response, the biloxi.com proxy server could proxy the INVITE to Bob's voicemail server. #### 中文

除了此示例中显示的 DNS 和位置服务查找外，代理服务器可以做出灵活的"路由决策"来决定将请求发送到哪里。例如，如果 Bob 的 SIP 电话返回 486 (Busy Here) 响应，biloxi.com 代理服务器可以将 INVITE 代理到 Bob 的语音邮件服务器。代理服务器也可以同时将 INVITE 发送到多个位置。这种并行搜索类型称为分叉。

In this example, the ACK is sent directly from Alice's softphone to Bob's SIP phone, bypassing the two proxies. This occurs because the endpoints have learned each other's address from the Contact header fields through the INVITE/200 (OK) exchange, which was not known when the initial INVITE was sent. The lookups performed by the two proxies are no longer needed, so the proxies drop out of the call flow. This completes the INVITE/200/ACK three-way handshake used to establish SIP sessions. #### 中文

在这种情况下，200 (OK) 通过两个代理路由回来，被 Alice 的软电话接收，然后软电话停止回铃音并指示电话已接听。最后，Alice 的软电话发送确认消息 ACK 到 Bob 的 SIP 电话，以确认收到最终响应 (200 (OK))。在这个示例中，ACK 直接从 Alice 的软电话发送到 Bob 的 SIP 电话，绕过两个代理。这是因为端点通过 INVITE/200 (OK) 交换从 Contact 头字段中了解了彼此的地址，而这是初始 INVITE 发送时不知道的。两个代理执行的查找不再需要，因此代理退出呼叫流程。这完成了用于建立 SIP 会话的 INVITE/200/ACK 三次握手。会话设置的完整细节在第 13 节中。

#### 原文

Alice and Bob's media session has now begun, and they send media packets using the format to which they agreed in the exchange of SDP. In general, the end-to-end media packets take a different path from the SIP signaling messages.

During the session, either Alice or Bob may decide to change the characteristics of the media session. This is accomplished by sending a re-INVITE containing a new media description. This re-INVITE references the existing dialog so that the other party knows that it is to modify an existing session instead of establishing a new session. The other party sends a 200 (OK) to accept the change. The requestor responds to the 200 (OK) with an ACK. If the other party does not accept the change, he sends an error response such as 488 (Not Acceptable Here), which also receives an ACK. However, the failure of the re-INVITE does not cause the existing call to fail - the session continues using the previously negotiated characteristics. Full details on session modification are in Section 14.

#### 中文

Alice 和 Bob 的媒体会话现在开始，他们使用在 SDP 交换中协商的格式发送媒体数据包。一般来说，端到端的媒体数据包与 SIP 信令消息走不同的路径。

在会话期间，Alice 或 Bob 都可以决定更改媒体会话的特性。这是通过发送包含新媒体描述的 re-INVITE 来完成的。此 re-INVITE 引用现有对话，以便另一方知道要修改现有会话而不是建立新会话。另一方发送 200 (OK) 以接受更改。请求者用 ACK 响应 200 (OK)。如果另一方不接受更改，他发送错误响应，如 488 (Not Acceptable Here)，也会收到 ACK。然而，re-INVITE 的失败不会导致现有呼叫失败——会话继续使用先前协商的特性。会话修改的完整细节在第 14 节中。

#### 原文

At the end of the call, Bob disconnects (hangs up) first and generates a BYE message. This BYE is routed directly to Alice's softphone, again bypassing the proxies. Alice confirms receipt of the BYE with a 200 (OK) response, which terminates the session and the BYE transaction. No ACK is sent - an ACK is only sent in response to a response to an INVITE request. The reasons for this special handling for INVITE will be discussed later, but relate to the reliability mechanisms in SIP, the length of time it can take for a ringing phone to be answered, and forking. For this reason, request handling in SIP is often classified as either INVITE or non-INVITE, referring to all other methods besides INVITE. Full details on session termination are in Section 15.

#### 中文

在通话结束时，Bob 首先挂断（挂机）并生成 BYE 消息。此 BYE 直接路由到 Alice 的软电话，再次绕过代理。Alice 用 200 (OK) 响应确认收到 BYE，这会终止会话和 BYE 事务。不发送 ACK——ACK 只在响应 INVITE 请求的响应时发送。INVITE 这种特殊处理的原因将在后面讨论，但与 SIP 中的可靠性机制、响铃电话被接听所需的时间以及分叉有关。因此，SIP 中的请求处理通常分为 INVITE 或非 INVITE，指的是 INVITE 之外的所有其他方法。会话终止的完整细节在第 15 节中。

#### 原文

Registration is another common operation in SIP. Registration is one way that the biloxi.com server can learn the current location of Bob. Upon initialization, and at periodic intervals, Bob's SIP phone sends REGISTER messages to a server in the biloxi.com domain known as a SIP registrar. Often, a registrar server for a domain is co-located with the proxy for that domain. It is an important concept that the distinction between types of SIP servers is logical, not physical.

#### 中文

Similarly, more than one user can be registered on a single device at the same time.

#### 中文

Bob 不限于从单个设备注册。例如，他家中的 SIP 电话和办公室的那个都可以发送注册。这些信息一起存储在位置服务中，允许代理执行各种类型的搜索来定位 Bob。类似地，同一设备上可以同时注册多个用户。

#### 原文

The location service is just an abstract concept. It generally contains information that allows a proxy to input a URI and receive a set of zero or more URIs that tell the proxy where to send the request. Registrations are one way to create this information, but not the only way. Arbitrary mapping functions can be configured at the discretion of the administrator.

#### 中文

位置服务只是一个抽象概念。它通常包含允许代理输入 URI 并接收零个或多个 URI 集合的信息，这些 URI 告诉代理将请求发送到哪里。注册是创建此信息的一种方式，但不是唯一的方式。任意映射函数可以由管理员自行配置。

#### 原文

Finally, it is important to note that in SIP, registration is used for routing incoming SIP requests and has no role in authorizing outgoing requests. Authorization and authentication are handled in SIP either on a request-by-request basis with a challenge/response mechanism, or by using a lower layer scheme as discussed in Section 26.

The complete set of SIP message details for this registration example is in Section 24.1.

最后，需要注意的是，在 SIP 中，注册用于路由传入的 SIP 请求，对授权传出请求没有作用。认证和授权在 SIP 中是通过每次请求使用挑战/响应机制处理的，或者使用第 26 节中讨论的更低层方案处理。

## 5. Structure of the Protocol | 5. 协议结构

#### 原文

SIP is structured as a layered protocol, which means that its behavior is described in terms of a set of fairly independent processing stages with only a loose coupling between each stage. The protocol behavior is described as layers for the purpose of presentation, allowing the description of functions common across elements in a single section. It does not dictate an implementation in any way. When we say that an element "contains" a layer, we mean it is compliant to the set of rules defined by that layer.

Not every element specified by the protocol contains every layer. Furthermore, the elements specified by SIP are logical elements, not physical ones. A physical realization can choose to act as different logical elements, perhaps even on a transaction-by-transaction basis.

#### 中文

SIP 被构造为一个分层协议，这意味着其行为是用一组相当独立的处理阶段来描述的，各阶段之间只有松散的耦合。协议行为被描述为层次是为了表述的目的，允许在单个章节中描述跨元素的公共功能。它不以任何方式规定实现。当我们说一个元素"包含"一个层时，我们的意思是它符合该层定义的一组规则。

并非协议规定的每个元素都包含每个层。此外，SIP 规定的元素是逻辑元素，而不是物理元素。物理实现可以选择充当不同的逻辑元素，甚至可能按事务逐个事务地决定。

#### 原文

The lowest layer of SIP is its syntax and encoding. Its encoding is specified using an augmented Backus-Naur Form grammar (BNF). The complete BNF is specified in Section 25; an overview of a SIP message's structure can be found in Section 7.

#### 中文

SIP 的最底层是其语法和编码。其编码使用扩展的巴科斯-诺尔形式语法 (BNF) 指定。完整的 BNF 在第 25 节中指定；SIP 消息结构概述可在第 7 节中找到。

#### 原文

The second layer is the transport layer. It defines how a client sends requests and receives responses and how a server receives requests and sends responses over the network. All SIP elements contain a transport layer. The transport layer is described in Section 18.

#### 中文

第二层是传输层。它定义客户端如何发送请求和接收响应，以及服务器如何通过网络接收请求和发送响应。所有 SIP 元素都包含传输层。传输层在第 18 节中描述。

#### 原文

The third layer is the transaction layer. Transactions are a fundamental component of SIP. A transaction is a request sent by a client transaction (using the transport layer) to a server transaction, along with all responses to that request sent from the server transaction back to the client. The transaction layer handles application-layer retransmissions, matching of responses to requests, and application-layer timeouts. Any task that a user agent client (UAC) accomplishes takes place using a series of transactions. Discussion of transactions can be found in Section 17. User agents contain a transaction layer, as do stateful proxies. Stateless proxies do not contain a transaction layer. The transaction layer has a client component (referred to as a client transaction) and a server component (referred to as a server transaction), each of which are represented by a finite state machine that is constructed to process a particular request.

#### 中文

第三层是事务层。事务是 SIP 的基本组成部分。事务是由客户端事务（使用传输层）发送到服务器事务的请求，以及从服务器事务发送回客户端的所有对该请求的响应。事务层处理应用层重传、响应与请求的匹配以及应用层超时。用户代理客户端 (UAC) 完成的任何任务都通过一系列事务来执行。事务的讨论在第 17 节中。用户代理包含事务层，有状态代理也是如此。无状态代理不包含事务层。事务层有一个客户端组件（称为客户端事务）和一个服务器组件（称为服务器事务），每个都由一个有限状态机表示，该状态机被构造为处理特定请求。

#### 原文

The layer above the transaction layer is called the transaction user (TU). Each of the SIP entities, except the stateless proxy, is a transaction user. When a TU wishes to send a request, it creates a client transaction instance and passes it the request along with the destination IP address, port, and transport to which to send the request. A TU that creates a client transaction can also cancel it. When a client cancels a transaction, it requests that the server stop further processing, revert to the state that existed before the transaction was initiated, and generate a specific error response to that transaction. This is done with a CANCEL request, which constitutes its own transaction, but references the transaction to be cancelled (Section 9).

#### 中文

事务层之上的层称为事务用户 (TU)。除了无状态代理之外，每个 SIP 实体都是一个事务用户。当 TU 希望发送请求时，它创建一个客户端事务实例，并将请求以及目标 IP 地址、端口和传输一起传递给它。创建客户端事务的 TU 也可以取消它。当客户端取消事务时，它请求服务器停止进一步处理，恢复到事务启动之前存在的状态，并生成对该事务的特定错误响应。这是用 CANCEL 请求完成的，它构成自己的事务，但引用要取消的事务（第 9 节）。

#### 原文

The SIP elements, that is, user agent clients and servers, stateless and stateful proxies and registrars, contain a core that distinguishes them from each other. Cores, except for the stateless proxy, are transaction users. While the behavior of the UAC and UAS cores depends on the method, there are some common rules for all methods (Section 8). For a UAC, these rules govern the construction of a request; for a UAS, they govern the processing of a request and generating a response. Since registrations play an important role in SIP, a UAS that handles a REGISTER is given the special name registrar. Section 10 describes UAC and UAS core behavior for the REGISTER method. Section 11 describes UAC and UAS core behavior for the OPTIONS method, used for determining the capabilities of a UA.

#### 中文

SIP 元素，即用户代理客户端和服务器、无状态和有状态代理以及注册服务器，包含一个核心来区分它们。除了无状态代理之外，核心都是事务用户。虽然 UAC 和 UAS 核心的行为取决于方法，但对于所有方法都有一些通用规则（第 8 节）。对于 UAC，这些规则控制请求的构建；对于 UAS，它们控制请求的处理和响应的生成。由于注册在 SIP 中起着重要作用，处理 REGISTER 的 UAS 被给予特殊名称注册服务器。第 10 节描述了 REGISTER 方法的 UAC 和 UAS 核心行为。第 11 节描述了用于确定 UA 能力的 OPTIONS 方法的 UAC 和 UAS 核心行为。

#### 原文

Certain other requests are sent within a dialog. A dialog is a peer-to-peer SIP relationship between two user agents that persists for some time. The dialog facilitates sequencing of messages and proper routing of requests between the user agents. The INVITE method is the only way defined in this specification to establish a dialog. When a UAC sends a request that is within the context of a dialog, it follows the common UAC rules as discussed in Section 8 but also the rules for mid-dialog requests. Section 12 discusses dialogs and presents the procedures for their construction and maintenance, in addition to construction of requests within a dialog.

#### 中文

某些其他请求在对话中发送。对话是两个用户代理之间持续一段时间的点对点 SIP 关系。对话促进消息的排序和用户代理之间请求的正确路由。INVITE 方法是本规范中定义的建立对话的唯一方式。当 UAC 发送在对话上下文中的请求时，它遵循第 8 节中讨论的通用 UAC 规则，但也遵循对话中请求的规则。第 12 节讨论对话并介绍其构建和维护的程序，以及对话中请求的构建。

#### 原文

The most important method in SIP is the INVITE method, which is used to establish a session between participants. A session is a collection of participants, and streams of media between them, for the purposes of communication. Section 13 discusses how sessions are initiated, resulting in one or more SIP dialogs. Section 14 discusses how characteristics of that session are modified through the use of an INVITE request within a dialog. Finally, section 15 discusses how a session is terminated.

The procedures of Sections 8, 10, 11, 12, 13, 14, and 15 deal entirely with the UA core (Section 9 describes cancellation, which applies to both UA core and proxy core). Section 16 discusses the proxy element, which facilitates routing of messages between user agents.

#### 中文

SIP 中最重要的方法是 INVITE 方法，用于在参与者之间建立会话。会话是参与者的集合，以及他们之间的媒体流，用于通信目的。第 13 节讨论如何发起会话，从而产生一个或多个 SIP 对话。第 14 节讨论如何通过对会话中的 INVITE 请求来修改该会话的特性。最后，第 15 节讨论如何终止会话。

第 8、10、11、12、13、14 和 15 节的程序完全涉及 UA 核心（第 9 节描述取消，适用于 UA 核心和代理核心）。第 16 节讨论代理元素，它促进用户代理之间消息的路由。

## 6. Definitions | 6. 定义

#### 原文

The following terms have special significance for SIP.

Address-of-Record: An address-of-record (AOR) is a SIP or SIPS URI that points to a domain with a location service that can map the URI to another URI where the user might be available. Typically, the location service is populated through registrations. An AOR is frequently thought of as the "public address" of the user.

#### 中文

以下术语对 SIP 具有特殊意义。

地址记录：地址记录 (AOR) 是 SIP 或 SIPS URI，指向具有位置服务的域，该服务可以将 URI 映射到用户可能可用的另一个 URI。通常，位置服务通过注册填充。AOR 通常被认为是用户的"公共地址"。

#### 原文

Back-to-Back User Agent: A back-to-back user agent (B2BUA) is a logical entity that receives a request and processes it as a user agent server (UAS). In order to determine how the request should be answered, it acts as a user agent client (UAC) and generates requests. Unlike a proxy server, it maintains dialog state and must participate in all requests sent on the dialogs it has established. Since it is a concatenation of a UAC and UAS, no explicit definitions are needed for its behavior.

#### 中文

背靠背用户代理：背靠背用户代理 (B2BUA) 是一个逻辑实体，接收请求并作为用户代理服务器 (UAS) 处理它。为了确定应该如何回答请求，它充当用户代理客户端 (UAC) 并生成请求。与代理服务器不同，它维护对话状态，并且必须参与其建立的对话上发送的所有请求。由于它是 UAC 和 UAS 的串联，其行为不需要明确的定义。

#### 原文

Call: A call is an informal term that refers to some communication between peers, generally set up for the purposes of a multimedia conversation.

Call Leg: Another name for a dialog; no longer used in this specification.

Call Stateful: A proxy is call stateful if it retains state for a dialog from the initiating INVITE to the terminating BYE request. A call stateful proxy is always transaction stateful, but the converse is not necessarily true.

#### 中文

呼叫：呼叫是一个非正式术语，指同行之间的一些通信，通常是为多媒体对话的目的而设置的。

呼叫支路：对话的另一个名称；本规范中不再使用。

呼叫有状态：如果代理从初始 INVITE 到终止 BYE 请求保留对话状态，则代理是呼叫有状态的。呼叫有状态代理总是事务有状态的，但反之不一定成立。

#### 原文

Client: A client is any network element that sends SIP requests and receives SIP responses. Clients may or may not interact directly with a human user. User agent clients and proxies are clients.

Conference: A multimedia session (see below) that contains multiple participants.

Core: Core designates the functions specific to a particular type of SIP entity, i.e., specific to either a stateful or stateless proxy, a user agent or registrar. All cores, except those for the stateless proxy, are transaction users.

#### 中文

客户端：客户端是发送 SIP 请求并接收 SIP 响应的任何网络元素。客户端可能直接与人类用户交互，也可能不直接交互。用户代理客户端和代理是客户端。

会议：包含多个参与者的多媒体会话（见下文）。

核心：核心指定特定类型 SIP 实体特有的功能，即特定于有状态或无状态代理、用户代理或注册服务器的核心。除无状态代理的核心外，所有核心都是事务用户。

#### 原文

Dialog: A dialog is a peer-to-peer SIP relationship between two UAs that persists for some time. A dialog is established by SIP messages, such as a 2xx response to an INVITE request. A dialog is identified by a call identifier, local tag, and a remote tag. A dialog was formerly known as a call leg in RFC 2543.

Downstream: A direction of message forwarding within a transaction that refers to the direction that requests flow from the user agent client to user agent server.

#### 中文

对话：对话是两个 UA 之间持续一段时间的点对点 SIP 关系。对话由 SIP 消息建立，如对 INVITE 请求的 2xx 响应。对话由呼叫标识符、本地 tag 和远程 tag 标识。对话在 RFC 2543 中曾称为呼叫支路。

下游：事务内消息转发的方向，指请求从用户代理客户端流向用户代理服务器的方向。

#### 原文

Final Response: A response that terminates a SIP transaction, as opposed to a provisional response that does not. All 2xx, 3xx, 4xx, 5xx and 6xx responses are final.

Header: A header is a component of a SIP message that conveys information about the message. It is structured as a sequence of header fields.

Header Field: A header field is a component of the SIP message header. A header field can appear as one or more header field rows. Header field rows consist of a header field name and zero or more header field values. Multiple header field values on a given header field row are separated by commas. Some header fields can only have a single header field value, and as a result, always appear as a single header field row.

Header Field Value: A header field value is a single value; a header field consists of zero or more header field values.

#### 中文

最终响应：终止 SIP 事务的响应，与不会终止的临时响应相对。所有 2xx、3xx、4xx、5xx 和 6xx 响应都是最终的。

头：头是 SIP 消息的一个组成部分，传递关于消息的信息。它被构造为头字段的序列。

头字段：头字段是 SIP 消息头的一个组成部分。头字段可以出现为一个或多个头字段行。头字段行由头字段名称和零个或多个头字段值组成。给定头字段行上的多个头字段值用逗号分隔。有些头字段只能有一个头字段值，因此总是作为单个头字段行出现。

头字段值：头字段值是单个值；头字段由零个或多个头字段值组成。

#### 原文

Home Domain: The domain providing service to a SIP user. Typically, this is the domain present in the URI in the address-of-record of a registration.

Informational Response: Same as a provisional response.

Initiator, Calling Party, Caller: The party initiating a session (and dialog) with an INVITE request. A caller retains this role from the time it sends the initial INVITE that established a dialog until the termination of that dialog.

Invitation: An INVITE request.

Invitee, Invited User, Called Party, Callee: The party that receives an INVITE request for the purpose of establishing a new session. A callee retains this role from the time it receives the INVITE until the termination of the dialog established by that INVITE.

#### 中文

本地域：为 SIP 用户提供服务的域。通常，这是注册地址记录中 URI 中存在的域。

信息响应：与临时响应相同。

发起者、主叫方、呼叫者：使用 INVITE 请求发起会话（和对话）的一方。呼叫者从发送建立对话的初始 INVITE 起到该对话终止期间保持此角色。

邀请：INVITE 请求。

被邀请者、被邀请用户、被叫方、被呼叫者：为建立新会话而接收 INVITE 请求的一方。被呼叫者从收到 INVITE 起直到该 INVITE 建立的对话终止期间保持此角色。

#### 原文

Location Service: A location service is used by a SIP redirect or proxy server to obtain information about a callee's possible location(s). It contains a list of bindings of address-of-record keys to zero or more contact addresses. The bindings can be created and removed in many ways; this specification defines a REGISTER method that updates the bindings.

Loop: A request that arrives at a proxy, is forwarded, and later arrives back at the same proxy. When it arrives the second time, its Request-URI is identical to the first time, and other header fields that affect proxy operation are unchanged, so that the proxy would make the same processing decision on the request it made the first time. Looped requests are errors, and the procedures for detecting them and handling them are described by the protocol.

#### 中文

位置服务：位置服务被 SIP 重定向或代理服务器用来获取关于被呼叫者可能位置的信息。它包含地址记录键到零个或多个联系地址的绑定列表。绑定可以通过多种方式创建和删除；本规范定义了一种更新绑定的 REGISTER 方法。

循环：到达代理、被转发、然后稍后再次到达同一代理的请求。当它第二次到达时，其 Request-URI 与第一次相同，其他影响代理操作的头字段没有变化，因此代理会对请求做出与第一次相同的处理决定。循环请求是错误，协议描述了检测和处理它们的程序。

#### 原文

Loose Routing: A proxy is said to be loose routing if it follows the procedures defined in this specification for processing of the Route header field. These procedures separate the destination of the request (present in the Request-URI) from the set of proxies that need to be visited along the way (present in the Route header field). A proxy compliant to these mechanisms is also known as a loose router.

Message: Data sent between SIP elements as part of the protocol. SIP messages are either requests or responses.

Method: The method is the primary function that a request is meant to invoke on a server. The method is carried in the request message itself. Example methods are INVITE and BYE.

#### 中文

松散路由：如果代理遵循本规范中定义的 Route 头字段处理程序，则称其为松散路由。这些程序将请求的目的地（存在于 Request-URI 中）与沿途需要访问的代理集合（存在于 Route 头字段中）分开。符合这些机制的代理也称为松散路由器。

消息：作为协议的一部分在 SIP 元素之间发送的数据。SIP 消息要么是请求，要么是响应。

方法：方法是请求旨在在服务器上调用的主要功能。方法在请求消息本身中携带。示例方法是 INVITE 和 BYE。

#### 原文

Outbound Proxy: A proxy that receives requests from a client, even though it may not be the server resolved by the Request-URI. Typically, a UA is manually configured with an outbound proxy, or can learn about one through auto-configuration protocols.

Parallel Search: In a parallel search, a proxy issues several requests to possible user locations upon receiving an incoming request. Rather than issuing one request and then waiting for the final response before issuing the next request as in a sequential search, a parallel search issues requests without waiting for the result of previous requests.

Provisional Response: A response used by the server to indicate progress, but that does not terminate a SIP transaction. 1xx responses are provisional, other responses are considered final.

#### 中文

出站代理：从客户端接收请求的代理，即使它可能不是由 Request-URI 解析的服务器。通常，UA 手动配置出站代理，或者可以通过自动配置协议了解一个。

并行搜索：在并行搜索中，代理在收到传入请求时向可能的用户位置发出多个请求。与顺序搜索中发出一个请求然后等待最终响应再发出下一个请求不同，并行搜索在不等待先前请求结果的情况下发出请求。

临时响应：服务器用来表示进展的响应，但不终止 SIP 事务。1xx 响应是临时的，其他响应被认为是最终的。

#### 原文

Proxy, Proxy Server: An intermediary entity that acts as both a server and a client for the purpose of making requests on behalf of other clients. A proxy server primarily plays the role of routing, which means its job is to ensure that a request is sent to another entity "closer" to the targeted user. Proxies are also useful for enforcing policy (for example, making sure a user is allowed to make a call). A proxy interprets, and, if necessary, rewrites specific parts of a request message before forwarding it.

Recursion: A client recurses on a 3xx response when it generates a new request to one or more of the URIs in the Contact header field in the response.

Redirect Server: A redirect server is a user agent server that generates 3xx responses to requests it receives, directing the client to contact an alternate set of URIs.

#### 中文

代理、代理服务器：充当中介实体，代表其他客户端发出请求，充当服务器和客户端。代理服务器主要扮演路由的角色，这意味着其工作是确保请求被发送到"更接近"目标用户的另一个实体。代理也有助于执行策略（例如，确保用户被允许打电话）。代理在转发之前解释并在必要时重写请求消息的特定部分。

递归：当客户端对响应中 Contact 头字段中的一个或多个 URI 生成新请求时，它会在 3xx 响应上递归。

重定向服务器：重定向服务器是生成 3xx 响应以响应其收到的请求的用户代理服务器，将客户端定向到联系备用 URI 集。

#### 原文

Registrar: A registrar is a server that accepts REGISTER requests and places the information it receives in those requests into the location service for the domain it handles.

Regular Transaction: A regular transaction is any transaction with a method other than INVITE, ACK, or CANCEL.

Request: A SIP message sent from a client to a server, for the purpose of invoking a particular operation.

Response: A SIP message sent from a server to a client, for indicating the status of a request sent from the client to the server.

Ringback: Ringback is the signaling tone produced by the calling party's application indicating that a called party is being alerted (ringing).

#### 中文

注册服务器：注册服务器是接受 REGISTER 请求并将其在这些请求中收到的信息放入其处理的域的位置服务的服务器。

常规事务：常规事务是除 INVITE、ACK 或 CANCEL 之外的方法的任何事务。

请求：为调用特定操作而从客户端发送到服务器的 SIP 消息。

响应：为指示从客户端发送到服务器的请求状态而从服务器发送到客户端的 SIP 消息。

回铃音：回铃音是主叫方应用程序产生的信令音，表示被叫方正在被提醒（振铃）。

#### 原文

Route Set: A route set is a collection of ordered SIP or SIPS URI which represent a list of proxies that must be traversed when sending a particular request. A route set can be learned, through headers like Record-Route, or it can be configured.

Server: A server is a network element that receives requests in order to service them and sends back responses to those requests. Examples of servers are proxies, user agent servers, redirect servers, and registrars.

Sequential Search: In a sequential search, a proxy server attempts each contact address in sequence, proceeding to the next one only after the previous has generated a final response. A 2xx or 6xx class final response always terminates a sequential search.

#### 中文

路由集：路由集是排序的 SIP 或 SIPS URI 的集合，表示发送特定请求时必须遍历的代理列表。路由集可以通过 Record-Route 等头字段学习，也可以配置。

服务器：服务器是接收请求以服务它们并将这些请求的响应发送回去的网络元素。服务器的例子包括代理、用户代理服务器、重定向服务器和注册服务器。

顺序搜索：在顺序搜索中，代理服务器按顺序尝试每个联系地址，只有在前一个生成最终响应后才继续下一个。2xx 或 6xx 类最终响应总是终止顺序搜索。

#### 原文

Session: From the SDP specification: "A multimedia session is a set of multimedia senders and receivers and the data streams flowing from senders to receivers. A multimedia conference is an example of a multimedia session." (RFC 2327) (A session as defined for SDP can comprise one or more RTP sessions.) As defined, a callee can be invited several times, by different calls, to the same session. If SDP is used, a session is defined by the concatenation of the SDP user name, session id, network type, address type, and address elements in the origin field.

SIP Transaction: A SIP transaction occurs between a client and a server and comprises all messages from the first request sent from the client to the server up to a final (non-1xx) response sent from the server to the client. If the request is INVITE and the final response is a non-2xx, the transaction also includes an ACK to the response. The ACK for a 2xx response to an INVITE request is a separate transaction.

#### 中文

会话：来自 SDP 规范："多媒体会话是一组多媒体发送者和接收者以及从发送者流向接收者的数据流。多媒体会议是多媒体会话的一个例子。"（RFC 2327）（为 SDP 定义的会话可以包含一个或多个 RTP 会话。）按照定义，被呼叫者可以通过不同的呼叫被多次邀请到同一会话。如果使用 SDP，会话由源字段中 SDP 用户名、会话 ID、网络类型、地址类型和地址元素的串联定义。

SIP 事务：SIP 事务发生在客户端和服务器之间，包括从客户端发送到服务器的第一个请求到从服务器发送到客户端的最终（非 1xx）响应的所有消息。如果请求是 INVITE 且最终响应是非 2xx，则事务还包括对该响应的 ACK。对 INVITE 请求的 2xx 响应的 ACK 是一个单独的事务。

#### 原文

Spiral: A spiral is a SIP request that is routed to a proxy, forwarded onwards, and arrives once again at that proxy, but this time differs in a way that will result in a different processing decision than the original request. Typically, this means that the request's Request-URI differs from its previous arrival. A spiral is not an error condition, unlike a loop. A typical cause for this is call forwarding. A user calls joe@example.com. The example.com proxy forwards it to Joe's PC, which in turn, forwards it to bob@example.com. This request is proxied back to the example.com proxy. However, this is not a loop. Since the request is targeted at a different user, it is considered a spiral, and is a valid condition.

#### 中文

螺旋：螺旋是路由到代理、继续转发并再次到达该代理的 SIP 请求，但这次的方式不同，将导致与原始请求不同的处理决定。通常，这意味着请求的 Request-URI 与其先前的到达不同。与循环不同，螺旋不是错误情况。典型的原因是呼叫转移。用户呼叫 joe@example.com。example.com 代理将其转发到 Joe 的 PC，PC 又将其转发到 bob@example.com。此请求被代理回 example.com 代理。然而，这不是循环。由于请求针对不同的用户，它被认为是螺旋，是一种有效的情况。

#### 原文

Stateful Proxy: A logical entity that maintains the client and server transaction state machines defined by this specification during the processing of a request, also known as a transaction stateful proxy. The behavior of a stateful proxy is further defined in Section 16. A (transaction) stateful proxy is not the same as a call stateful proxy.

Stateless Proxy: A logical entity that does not maintain the client or server transaction state machines defined in this specification when it processes requests. A stateless proxy forwards every request it receives downstream and every response it receives upstream.

Strict Routing: A proxy is said to be strict routing if it follows the Route processing rules of RFC 2543 and many prior work in progress versions of this RFC. That rule caused proxies to destroy the contents of the Request-URI when a Route header field was present. Strict routing behavior is not used in this specification, in favor of a loose routing behavior. Proxies that perform strict routing are also known as strict routers.

#### 中文

有状态代理：在处理请求期间维护本规范定义的客户端和服务器事务状态机的逻辑实体，也称为事务有状态代理。有状态代理的行为在第 16 节中进一步定义。（事务）有状态代理与呼叫有状态代理不同。

无状态代理：在处理请求时不维护本规范定义的客户端或服务器事务状态机的逻辑实体。无状态代理将其收到的每个请求向下游转发，并将其收到的每个响应向上游转发。

严格路由：如果代理遵循 RFC 2543 的 Route 处理规则以及本 RFC 的许多先前工作进度版本，则称其为严格路由。该规则导致代理在存在 Route 头字段时销毁 Request-URI 的内容。本规范不使用严格路由行为，而是采用松散路由行为。执行严格路由的代理也称为严格路由器。

#### 原文

Target Refresh Request: A target refresh request sent within a dialog is defined as a request that can modify the remote target of the dialog.

Transaction User (TU): The layer of protocol processing that resides above the transaction layer. Transaction users include the UAC core, UAS core, and proxy core.

Upstream: A direction of message forwarding within a transaction that refers to the direction that responses flow from the user agent server back to the user agent client.

URL-encoded: A character string encoded according to RFC 2396, Section 2.4.

#### 中文

目标刷新请求：在对话中发送的目标刷新请求被定义为可以修改对话远程目标的请求。

事务用户 (TU)：位于事务层之上的协议处理层。事务用户包括 UAC 核心、UAS 核心和代理核心。

上游：事务内消息转发的方向，指响应从用户代理服务器流回用户代理客户端的方向。

URL 编码：按照 RFC 2396 第 2.4 节编码的字符串。

#### 原文

User Agent Client (UAC): A user agent client is a logical entity that creates a new request, and then uses the client transaction state machinery to send it. The role of UAC lasts only for the duration of that transaction. In other words, if a piece of software initiates a request, it acts as a UAC for the duration of that transaction. If it receives a request later, it assumes the role of a user agent server for the processing of that transaction.

UAC Core: The set of processing functions required of a UAC that reside above the transaction and transport layers.

User Agent Server (UAS): A user agent server is a logical entity that generates a response to a SIP request. The response accepts, rejects, or redirects the request. This role lasts only for the duration of that transaction. In other words, if a piece of software responds to a request, it acts as a UAS for the duration of that transaction. If it generates a request later, it assumes the role of a user agent client for the processing of that transaction.

UAS Core: The set of processing functions required at a UAS that resides above the transaction and transport layers.

User Agent (UA): A logical entity that can act as both a user agent client and user agent server.

#### 中文

用户代理客户端 (UAC)：用户代理客户端是创建新请求然后使用客户端事务状态机制发送它的逻辑实体。UAC 的角色仅在该事务持续期间有效。换句话说，如果一段软件发起一个请求，它在该事务持续期间充当 UAC。如果它稍后收到一个请求，它承担用户代理服务器的角色来处理该事务。

UAC 核心：UAC 需要的位于事务和传输层之上的处理功能集。

用户代理服务器 (UAS)：用户代理服务器是生成对 SIP 请求响应的逻辑实体。响应接受、拒绝或重定向请求。此角色仅在该事务持续期间有效。换句话说，如果一段软件响应一个请求，它在该事务持续期间充当 UAS。如果它稍后生成一个请求，它承担用户代理客户端的角色来处理该事务。

UAS 核心：UAS 需要的位于事务和传输层之上的处理功能集。

用户代理 (UA)：可以充当用户代理客户端和用户代理服务器的逻辑实体。

#### 原文

The role of UAC and UAS, as well as proxy and redirect servers, are defined on a transaction-by-transaction basis. For example, the user agent initiating a call acts as a UAC when sending the initial INVITE request and as a UAS when receiving a BYE request from the callee. Similarly, the same software can act as a proxy server for one request and as a redirect server for the next request.

Proxy, location, and registrar servers defined above are logical entities; implementations MAY combine them into a single application.

#### 中文

UAC 和 UAS 的角色，以及代理和重定向服务器，是按事务定义的。例如发起呼叫的用户代理在发送初始 INVITE 请求时充当 UAC，在收到被呼叫者的 BYE 请求时充当 UAS。类似地，相同的软件可以为一个请求充当代理服务器，为下一个请求充当重定向服务器。

上述定义的代理、位置和注册服务器是逻辑实体；实现可以将它们组合成单个应用程序。

## 7. SIP Messages | 7. SIP 消息

#### 原文

SIP is a text-based protocol and uses the UTF-8 charset.

A SIP message is either a request from a client to a server, or a response from a server to a client.

Both Request and Response messages use the basic format of RFC 2822, even though the syntax differs in character set and syntax specifics. Both types of messages consist of a start-line, one or more header fields, an empty line indicating the end of the header fields, and an optional message-body.

```
generic-message  =  start-line
                    *message-header
                    CRLF
                    [ message-body ]
start-line       =  Request-Line / Status-Line
```

The start-line, each message-header line, and the empty line MUST be terminated by a carriage-return line-feed sequence (CRLF). Note that the empty line MUST be present even if the message-body is not.

Except for the above difference in character sets, much of SIP's message and header field syntax is identical to HTTP/1.1. Rather than repeating the syntax and semantics here, we use [HX.Y] to refer to Section X.Y of the current HTTP/1.1 specification (RFC 2616).

However, SIP is not an extension of HTTP.

#### 中文

SIP 是一个基于文本的协议，使用 UTF-8 字符集。

SIP 消息要么是从客户端到服务器的请求，要么是从服务器到客户端的响应。

请求和响应消息都使用 RFC 2822 的基本格式，即使语法在字符集和语法细节上有所不同。两种类型的消息都由起始行、一个或多个头字段、指示头字段结束的空行和可选的消息体组成。

```
generic-message  =  start-line
                    *message-header
                    CRLF
                    [ message-body ]
start-line       =  Request-Line / Status-Line
```

起始行、每个消息头行和空行必须以回车换行序列 (CRLF) 终止。注意，即使消息体不存在，空行也必须存在。

除了上述字符集的差异外，SIP 的消息和头字段语法大多与 HTTP/1.1 相同。我们在这里不再重复语法和语义，而是使用 [HX.Y] 来引用当前 HTTP/1.1 规范 (RFC 2616) 的第 X.Y 节。

但是，SIP 不是 HTTP 的扩展。

---

### 7.1 Requests | 7.1 请求

#### 原文

SIP requests are distinguished by having a Request-Line for a start-line. A Request-Line contains a method name, a Request-URI, and the protocol version separated by a single space (SP) character.

The Request-Line ends with CRLF. No CR or LF are allowed except in the end-of-line CRLF sequence. No linear whitespace (LWS) is allowed in any of the elements.

```
Request-Line  =  Method SP Request-URI SP SIP-Version CRLF
```

Method: This specification defines six methods: REGISTER for adding bindings, INVITE and ACK for establishing sessions, BYE for terminating sessions, OPTIONS for querying capabilities, and CANCEL for canceling pending requests. Extensions to SIP define additional methods (Section 13 describes the INVITE method, Section 10 describes REGISTER, etc.).

#### 中文

SIP 请求通过使用 Request-Line 作为起始行来区分。Request-Line 包含方法名、Request-URI 和协议版本，用单个空格 (SP) 字符分隔。

Request-Line 以 CRLF 结束。除行尾 CRLF 序列外，不允许 CR 或 LF。任何元素中都不允许使用线性空白 (LWS)。

```
Request-Line  =  Method SP Request-URI SP SIP-Version CRLF
```

方法：本规范定义了六种方法：REGISTER 用于添加绑定，INVITE 和 ACK 用于建立会话，BYE 用于终止会话，OPTIONS 用于查询能力，CANCEL 用于取消待处理的请求。对 SIP 的扩展定义了额外的方法（第 13 节描述 INVITE 方法，第 10 节描述 REGISTER 等）。

**Request-URI**：Request-URI 是第 19.1 节描述的 SIP 或 SIPS URI，或是通用 URI (RFC 2396)。它指示该请求所针对的用户或服务。Request-URI 不得包含未转义的空格或控制字符，且不得用 "<>" 括起。

SIP 元素可以支持非 "sip" 和 "sips" 的 Request-URI，例如 RFC 2806 的 "tel" URI 方案。SIP 元素可以使用任何可用的机制转换非 SIP URI，结果可以是 SIP URI、SIPS URI 或其他方案。

**SIP-Version**：请求和响应消息都包含所使用 SIP 版本的版本号，并遵循 [H3.1]（将 HTTP 替换为 SIP，HTTP/1.1 替换为 SIP/2.0）关于版本排序、合规要求和版本号升级的规定。为符合本规范，发送 SIP 消息的应用程序必须包含 "SIP/2.0" 的 SIP-Version。SIP-Version 字符串不区分大小写，但实现必须发送大写。

与 HTTP/1.1 不同，SIP 将版本号视为字面字符串。实际上，这应该没有区别。

---

### 7.2 Responses | 7.2 响应

#### 原文

SIP responses are distinguished from requests by having a Status-Line as their start-line. A Status-Line consists of the protocol version followed by a numeric Status-Code and its associated textual phrase, with each element separated by a single SP character.

No CR or LF is allowed except in the final CRLF sequence.

```
Status-Line  =  SIP-Version SP Status-Code SP Reason-Phrase CRLF
```

The Status-Code is a 3-digit integer result code that indicates the outcome of an attempt to understand and satisfy a request. The Reason-Phrase is intended to give a short textual description of the Status-Code. The Status-Code is intended for use by automata, whereas the Reason-Phrase is intended for the human user. A client is not required to examine or display the Reason-Phrase.

While this specification suggests specific wording for the reason phrase, implementations MAY choose other text, for example, in the language indicated in the Accept-Language header field of the request.

The first digit of the Status-Code defines the class of response. The last two digits do not have any categorization role. For this reason, any response with a status code between 100 and 199 is referred to as a "1xx response", any response with a status code between 200 and 299 as a "2xx response", and so on. SIP/2.0 allows six values for the first digit:

- **1xx**: Provisional — request received, continuing to process the request;
- **2xx**: Success — the action was successfully received, understood, and accepted;
- **3xx**: Redirection — further action needs to be taken in order to complete the request;
- **4xx**: Client Error — the request contains bad syntax or cannot be fulfilled at this server;
- **5xx**: Server Error — the server failed to fulfill an apparently valid request;
- **6xx**: Global Failure — the request cannot be fulfilled at any server.

Section 21 defines these classes and describes the individual codes.

#### 中文

SIP 响应通过使用 Status-Line 作为起始行来与请求区分。Status-Line 由协议版本、后跟数字 Status-Code 及其相关的文本原因短语组成，每个元素用单个 SP 字符分隔。

除最终 CRLF 序列外，不允许 CR 或 LF。

```
Status-Line  =  SIP-Version SP Status-Code SP Reason-Phrase CRLF
```

Status-Code 是一个三位整数结果码，指示理解和满足请求尝试的结果。Reason-Phrase 旨在提供 Status-Code 的简短文本描述。Status-Code 旨在供自动机使用，而 Reason-Phrase 旨在供人类用户使用。客户端不需要检查或显示 Reason-Phrase。

虽然本规范建议使用特定的措辞作为原因短语，但实现可以选择其他文本，例如使用请求的 Accept-Language 头字段指示的语言。

Status-Code 的第一位数字定义响应的类别。最后两位数字没有任何分类作用。因此，任何状态码在 100 到 199 之间的响应称为 "1xx 响应"，任何状态码在 200 到 299 之间的响应称为 "2xx 响应"，以此类推。SIP/2.0 允许第一位数字有六个值：

- **1xx**：临时性 — 请求已收到，正在继续处理；
- **2xx**：成功 — 操作已成功接收、理解和接受；
- **3xx**：重定向 — 需要进一步操作才能完成请求；
- **4xx**：客户端错误 — 请求包含语法错误或无法在此服务器上完成；
- **5xx**：服务器错误 — 服务器未能满足一个明显有效的请求；
- **6xx**：全局失败 — 请求无法在任何服务器上完成。

第 21 节定义了这些类别并描述了各个码。

### 7.3 Header Fields | 7.3 头字段

#### 原文

SIP header fields are similar to HTTP header fields in both syntax and semantics. In particular, SIP header fields follow the [H4.2] definitions of syntax for the message-header and the rules for extending header fields over multiple lines. However, the latter is specified in HTTP with implicit whitespace and folding. This specification conforms to RFC 2234 [10] and uses only explicit whitespace and folding as an integral part of the grammar.

[H4.2] also specifies that multiple header fields of the same field name whose value is a comma-separated list can be combined into one header field. That applies to SIP as well, but the specific rule is different because of the different grammars. Specifically, any SIP header whose grammar is of the form

```
header  =  "header-name" HCOLON header-value *(COMMA header-value)
```

allows for combining header fields of the same name into a comma-separated list. The Contact header field allows a comma-separated list unless the header field value is "*".

#### 中文

SIP 头字段在语法和语义上都类似于 HTTP 头字段。特别是，SIP 头字段遵循 [H4.2] 关于 message-header 语法的定义以及多行扩展头字段的规则。但是，后者是在 HTTP 中通过隐式空白和折叠指定的。本规范符合 RFC 2234 [10]，仅使用显式空白和折叠作为语法的组成部分。

[H4.2] 还规定，多个相同字段名的头字段，如果其值是逗号分隔的列表，可以合并为一个头字段。这也适用于 SIP，但由于语法不同，具体规则有所不同。具体而言，任何符合以下形式的 SIP 头

```
header  =  "header-name" HCOLON header-value *(COMMA header-value)
```

都允许将相同名称的头字段合并为逗号分隔的列表。除非头字段值为 "*"，否则 Contact 头字段允许使用逗号分隔的列表。

---

### 7.3.1 Header Field Format | 7.3.1 头字段格式

#### 原文

Header fields follow the same generic header format as that given in Section 2.2 of RFC 2822 [3]. Each header field consists of a field name followed by a colon (":") and the field value.

```
field-name: field-value
```

The formal grammar for a message-header specified in Section 25 allows for an arbitrary amount of whitespace on either side of the colon; however, implementations should avoid spaces between the field name and the colon and use a single space (SP) between the colon and the field-value.

```
Subject:            lunch
Subject      :      lunch
Subject            :lunch
Subject: lunch
```

Thus, the above are all valid and equivalent, but the last is the preferred form.

Header fields can be extended over multiple lines by preceding each extra line with at least one SP or horizontal tab (HT). The line break and the whitespace at the beginning of the next line are treated as a single SP character. Thus, the following are equivalent:

```
Subject: I know you're there, pick up the phone and talk to me!
Subject: I know you're there,
         pick up the phone
         and talk to me!
```

The relative order of header fields with different field names is not significant. However, it is RECOMMENDED that header fields which are needed for proxy processing (Via, Route, Record-Route, Proxy-Require, Max-Forwards, and Proxy-Authorization, for example) appear towards the top of the message to facilitate rapid parsing. The relative order of header field rows with the same field name is important. Multiple header field rows with the same field-name MAY be present in a message if and only if the entire field-value for that header field is defined as a comma-separated list (that is, if follows the grammar defined in Section 7.3). It MUST be possible to combine the multiple header field rows into one "field-name: field-value" pair, without changing the semantics of the message, by appending each subsequent field-value to the first, each separated by a comma. The exceptions to this rule are the WWW-Authenticate, Authorization, Proxy-Authenticate, and Proxy-Authorization header fields. Multiple header field rows with these names MAY be present in a message, but since their grammar does not follow the general form listed in Section 7.3, they MUST NOT be combined into a single header field row.

Implementations MUST be able to process multiple header field rows with the same name in any combination of the single-value-per-line or comma-separated value forms.

The format of a header field-value is defined per header-name. It will always be either an opaque sequence of TEXT-UTF8 octets, or a combination of whitespace, tokens, separators, and quoted strings. Many existing header fields will adhere to the general form of a value followed by a semi-colon separated sequence of parameter-name, parameter-value pairs:

```
field-name: field-value *(;parameter-name=parameter-value)
```

Even though an arbitrary number of parameter pairs may be attached to a header field value, any given parameter-name MUST NOT appear more than once.

When comparing header fields, field names are always case-insensitive. Unless otherwise stated in the definition of a particular header field, field values, parameter names, and parameter values are case-insensitive. Tokens are always case-insensitive. Unless specified otherwise, values expressed as quoted strings are case-sensitive. For example,

```
Contact: <sip:alice@atlanta.com>;expires=3600
```

is equivalent to

```
CONTACT: <sip:alice@atlanta.com>;ExPiReS=3600
```

and

```
Content-Disposition: session;handling=optional
```

is equivalent to

```
content-disposition: Session;HANDLING=OPTIONAL
```

The following two header fields are not equivalent:

```
Warning: 370 devnull "Choose a bigger pipe"
Warning: 370 devnull "CHOOSE A BIGGER PIPE"
```

#### 中文

头字段遵循 RFC 2822 [3] 第 2.2 节给出的相同通用头格式。每个头字段由字段名、后跟冒号 (":") 和字段值组成。

```
field-name: field-value
```

第 25 节中指定的消息头形式语法允许在冒号两侧有任意数量的空白；但是，实现应避免在字段名和冒号之间使用空格，并在冒号和字段值之间使用单个空格 (SP)。

```
Subject:            lunch
Subject      :      lunch
Subject            :lunch
Subject: lunch
```

因此，以上所有都是有效且等效的，但最后一种是可取的格式。

头字段可以通过在每一额外行前至少加一个 SP 或水平制表符 (HT) 来扩展到多行。断行和下一行开头的空白被视为单个 SP 字符。因此，以下是等效的：

```
Subject: I know you're there, pick up the phone and talk to me!
Subject: I know you're there,
         pick up the phone
         and talk to me!
```

具有不同字段名的头字段的相对顺序并不重要。但是，建议将对代理处理有用的头字段（如 Via、Route、Record-Route、Proxy-Require、Max-Forwards 和 Proxy-Authorization）出现在消息顶部，以方便快速解析。具有相同字段名的头字段行的相对顺序很重要。只有当该头字段的整个字段值被定义为逗号分隔的列表时（即遵循第 7.3 节定义的语法），才可以在消息中出现具有相同字段名的多个头字段行。必须能够将多个头字段行合并为一个 "field-name: field-value" 对，而不改变消息的语义，方法是将每个后续字段值附加到第一个字段值，每个字段值之间用逗号分隔。此规则的例外是 WWW-Authenticate、Authorization、Proxy-Authenticate 和 Proxy-Authorization 头字段。这些名称的多个头字段行可以出现在消息中，但由于它们的语法不符合第 7.3 节列出的通用形式，因此不得合并为单个头字段行。

实现必须能够以单值每行或逗号分隔值的任意组合形式处理具有相同名称的多个头字段行。

头字段值的格式是按每个 header-name 定义的。它要么是 TEXT-UTF8 八位字节的不透明序列，要么是空白、标记、分隔符和带引号字符串的组合。许多现有头字段将遵循由值和分号分隔的参数名/参数值对序列组成的通用形式：

```
field-name: field-value *(;parameter-name=parameter-value)
```

尽管可以将任意数量的参数对附加到头字段值，但任何给定的参数名不得出现多次。

比较头字段时，字段名始终不区分大小写。除非特定头字段的定义中另有说明，否则字段值、参数名和参数值都不区分大小写。标记始终不区分大小写。除非另有说明，否则表示为带引号字符串的值是区分大小写的。例如：

```
Contact: <sip:alice@atlanta.com>;expires=3600
```

等效于

```
CONTACT: <sip:alice@atlanta.com>;ExPiReS=3600
```

而

```
Content-Disposition: session;handling=optional
```

等效于

```
content-disposition: Session;HANDLING=OPTIONAL
```

以下两个头字段不等效：

```
Warning: 370 devnull "Choose a bigger pipe"
Warning: 370 devnull "CHOOSE A BIGGER PIPE"
```

### 7.3.2 Header Field Classification | 7.3.2 头字段分类

#### 原文

Some header fields only make sense in requests or responses. These are called request header fields and response header fields, respectively. If a header field appears in a message not matching its category (such as a request header field in a response), it MUST be ignored. Section 20 defines the classification of each header field.

#### 中文

某些头字段仅在请求或响应中有意义。这些分别称为请求头字段和响应头字段。如果头字段出现在与其类别不匹配的消息中（如响应中的请求头字段），则必须忽略该字段。第 20 节定义了每个头字段的分类。

### 7.3.3 Compact Form | 7.3.3 压缩形式

#### 原文

SIP provides a mechanism to represent common header field names in an abbreviated form. This may be useful when messages would otherwise become too large to be carried on the transport available to it (exceeding the maximum transmission unit (MTU) when using UDP, for example). These compact forms are defined in Section 20. A compact form MAY be substituted for the longer form of a header field name at any time without changing the semantics of the message. A header field name MAY appear in both long and short forms within the same message. Implementations MUST accept both the long and short forms of each header name.

#### 中文

SIP 提供了一种以缩写形式表示常见头字段名的机制。当消息变得太大而无法在可用的传输上传输时（例如使用 UDP 时超过最大传输单元 MTU），这可能很有用。这些压缩形式在第 20 节中定义。压缩形式可以在任何时候替换头字段名的较长形式，而不改变消息的语义。头字段名可以在同一消息中同时出现长形式和短形式。实现必须接受每个头字段名的长形式和短形式。

---

### 7.4 Bodies | 7.4 消息体

#### 原文

Requests, including new requests defined in extensions to this specification, MAY contain message bodies unless otherwise noted. The interpretation of the body depends on the request method.

For response messages, the request method and the response status code determine the type and interpretation of any message body. All responses MAY include a body.

#### 中文

除非另有说明，否则请求（包括本规范扩展中定义的新请求）可以包含消息体。消息体的解释取决于请求方法。

对于响应消息，请求方法和响应状态码决定任何消息体的类型和解释。所有响应都可以包含消息体。

---

### 7.4.1 Message Body Type | 7.4.1 消息体类型

#### 原文

The Internet media type of the message body MUST be given by the Content-Type header field. If the body has undergone any encoding such as compression, then this MUST be indicated by the Content-Encoding header field; otherwise, Content-Encoding MUST be omitted. If applicable, the character set of the message body is indicated as part of the Content-Type header-field value.

The "multipart" MIME type defined in RFC 2046 [11] MAY be used within the body of the message. Implementations that send requests containing multipart message bodies MUST send a session description as a non-multipart message body if the remote implementation requests this through an Accept header field that does not contain multipart.

SIP messages MAY contain binary bodies or body parts. When no explicit charset parameter is provided by the sender, media subtypes of the "text" type are defined to have a default charset value of "UTF-8".

#### 中文

消息体的 Internet 媒体类型必须由 Content-Type 头字段给出。如果消息体经过了任何编码（如压缩），则必须由 Content-Encoding 头字段指示；否则必须省略 Content-Encoding。如果适用，消息体的字符集作为 Content-Type 头字段值的一部分指示。

RFC 2046 [11] 定义的 "multipart" MIME 类型可以在消息体中使用。如果远程实现通过不包含 multipart 的 Accept 头字段请求此功能，则发送包含多部分消息体的请求的实现必须将会话描述作为非多部分消息体发送。

SIP 消息可以包含二进制消息体或消息体部分。当发送方未提供显式 charset 参数时，"text" 类型的媒体子类型被定义为具有默认 charset 值 "UTF-8"。

---

### 7.4.2 Message Body Length | 7.4.2 消息体长度

#### 原文

The body length in bytes is provided by the Content-Length header field. Section 20.14 describes the necessary contents of this header field in detail.

The "chunked" transfer encoding of HTTP/1.1 MUST NOT be used for SIP. (Note: The chunked encoding modifies the body of a message in order to transfer it as a series of chunks, each with its own size indicator.)

#### 中文

消息体的长度（以字节为单位）由 Content-Length 头字段提供。第 20.14 节详细描述了该头字段的必要内容。

HTTP/1.1 的 "chunked" 传输编码不得用于 SIP。（注：分块编码修改消息体以便作为一系列块传输，每个块都有自己的大小指示符。）

---

### 7.5 Framing SIP Messages | 7.5 SIP 消息分帧

#### 原文

Unlike HTTP, SIP implementations can use UDP or other unreliable datagram protocols. Each such datagram carries one request or response. See Section 18 on constraints on usage of unreliable transports.

Implementations processing SIP messages over stream-oriented transports MUST ignore any CRLF appearing before the start-line [H4.1].

The Content-Length header field value is used to locate the end of each SIP message in a stream. It will always be present when SIP messages are sent over stream-oriented transports.

#### 中文

与 HTTP 不同，SIP 实现可以使用 UDP 或其他不可靠的数据报协议。每个这样的数据报携带一个请求或响应。参见第 18 节关于不可靠传输使用约束的内容。

在面向流的传输上处理 SIP 消息的实现必须忽略起始行之前的任何 CRLF [H4.1]。

Content-Length 头字段值用于在流中定位每个 SIP 消息的结尾。当 SIP 消息通过面向流的传输发送时，它始终存在。

## 8. General User Agent Behavior | 8. 一般用户代理行为

#### 原文

A user agent represents an end system. It contains a user agent client (UAC), which generates requests, and a user agent server (UAS), which responds to them. A UAC is capable of generating a request based on some external stimulus (the user clicking a button, or a signal on a PSTN line) and processing a response. A UAS is capable of receiving a request and generating a response based on user input, external stimulus, the result of a program execution, or some other mechanism.

When a UAC sends a request, the request passes through some number of proxy servers, which forward the request towards the UAS. When the UAS generates a response, the response is forwarded towards the UAC.

UAC and UAS procedures depend strongly on two factors. First, based on whether the request or response is inside or outside of a dialog, and second, based on the method of a request. Dialogs are discussed thoroughly in Section 12; they represent a peer-to-peer relationship between user agents and are established by specific SIP methods, such as INVITE.

In this section, we discuss the method-independent rules for UAC and UAS behavior when processing requests that are outside of a dialog. This includes, of course, the requests which themselves establish a dialog.

Security procedures for requests and responses outside of a dialog are described in Section 26. Specifically, mechanisms exist for the UAS and UAC to mutually authenticate. A limited set of privacy features are also supported through encryption of bodies using S/MIME.

#### 中文

用户代理代表一个端系统。它包含生成请求的用户代理客户端 (UAC) 和响应请求的用户代理服务器 (UAS)。UAC 能够基于某些外部刺激（用户点击按钮，或 PSTN 线路上的信号）生成请求并处理响应。UAS 能够接收请求并基于用户输入、外部刺激、程序执行结果或其他一些机制生成响应。

当 UAC 发送请求时，请求会经过一些代理服务器，代理服务器将请求转发给 UAS。当 UAS 生成响应时，响应会转发给 UAC。

UAC 和 UAS 的过程在很大程度上取决于两个因素。第一，基于请求或响应是否在对话内或对话外；第二，基于请求的方法。对话在第 12 节中有详细讨论；它们代表用户代理之间的点对点关系，并由特定的 SIP 方法（如 INVITE）建立。

在本节中，我们讨论在处理对话外的请求时 UAC 和 UAS 行为的与方法无关的规则。当然，这包括本身建立对话的请求。

第 26 节描述了对话外的请求和响应的安全过程。具体来说，存在 UAS 和 UAC 相互认证的机制。还通过使用 S/MIME 加密消息体来支持有限的隐私功能集。

---

### 8.1 UAC Behavior | 8.1 UAC 行为

This section covers UAC behavior outside of a dialog.

本节涵盖对话外 UAC 的行为。

#### 原文

A valid SIP request formulated by a UAC MUST, at a minimum, contain the following header fields: To, From, CSeq, Call-ID, Max-Forwards, and Via; all of these header fields are mandatory in all SIP requests. These six header fields are the fundamental building blocks of a SIP message, as they jointly provide for most of the critical message routing services including the addressing of messages, the routing of responses, limiting message propagation, ordering of messages, and the unique identification of transactions. These header fields are in addition to the mandatory request line, which contains the method, Request-URI, and SIP version.

Examples of requests sent outside of a dialog include an INVITE to establish a session (Section 13) and an OPTIONS to query for capabilities (Section 11).

#### 中文

UAC 生成的合法 SIP 请求至少必须包含以下头字段：To、From、CSeq、Call-ID、Max-Forwards 和 Via；所有这些头字段在所有 SIP 请求中都是必需的。这六个头字段是 SIP 消息的基本构建块，因为它们共同提供了大多数关键的消息路由服务，包括消息寻址、响应路由、限制消息传播、消息排序和事务的唯一标识。这些头字段是必需的请求行（包含方法、Request-URI 和 SIP 版本）的补充。

在对话外发送的请求示例包括建立会话的 INVITE（第 13 节）和查询能力的 OPTIONS（第 11 节）。

---

### 8.1.1 Generating the Request | 8.1.1 生成请求

#### 原文

The initial Request-URI of the message SHOULD be set to the value of the URI in the To field. One notable exception is the REGISTER method; behavior for setting the Request-URI of REGISTER is given in Section 10. It may also be undesirable for privacy reasons or convenience to set these fields to the same value (especially if the originating UA expects that the Request-URI will be changed during transit).

In some special circumstances, the presence of a pre-existing route set can affect the Request-URI of the message. A pre-existing route set is an ordered set of URIs that identify a chain of servers, to which a UAC will send outgoing requests that are outside of a dialog. Commonly, they are configured on the UA by a user or service provider manually, or through some other non-SIP mechanism. When a provider wishes to configure a UA with an outbound proxy, it is RECOMMENDED that this be done by providing it with a pre-existing route set with a single URI, that of the outbound proxy.

When a pre-existing route set is present, the procedures for populating the Request-URI and Route header field detailed in Section 12.2.1.1 MUST be followed (even though there is no dialog), using the desired Request-URI as the remote target URI.

#### 中文

消息的初始 Request-URI 应设置为 To 字段中 URI 的值。一个值得注意的例外是 REGISTER 方法；设置 REGISTER 的 Request-URI 的行为在第 10 节中给出。出于隐私原因或方便考虑，将这些字段设置为相同的值可能也不可取（特别是如果发起 UA 期望 Request-URI 在传输过程中被更改）。

在某些特殊情况下，预先存在的路由集的存在可能会影响消息的 Request-URI。预先存在的路由集是一个有序的 URI 集合，标识服务器链，UAC 将向其发送对话外的传出请求。通常，它们由用户或服务提供商手动配置在 UA 上，或通过其他非 SIP 机制配置。当提供商希望使用出站代理配置 UA 时，建议通过提供包含单个 URI（出站代理的 URI）的预存在路由集来完成。

当存在预存在的路由集时，必须遵循第 12.2.1.1 节详述的填充 Request-URI 和 Route 头字段的过程（即使没有对话），使用所需的 Request-URI 作为远程目标 URI。

---

### 8.1.1.2 To | 8.1.1.2 To

#### 原文

The To header field first and foremost specifies the desired "logical" recipient of the request, or the address-of-record of the user or resource that is the target of this request. This may or may not be the ultimate recipient of the request. The To header field MAY contain a SIP or SIPS URI, but it may also make use of other URI schemes (the tel URL (RFC 2806 [9]), for example) when appropriate. All SIP implementations MUST support the SIP URI scheme. Any implementation that supports TLS MUST support the SIPS URI scheme. The To header field allows for a display name.

A UAC may learn how to populate the To header field for a particular request in a number of ways. Usually the user will suggest the To header field through a human interface, perhaps inputting the URI manually or selecting it from some sort of address book. Frequently, the user will not enter a complete URI, but rather a string of digits or letters (for example, "bob"). It is at the discretion of the UA to choose how to interpret this input. Using the string to form the user part of a SIP URI implies that the UA wishes the name to be resolved in the domain to the right-hand side (RHS) of the at-sign in the SIP URI (for instance, sip:bob@example.com). Using the string to form the user part of a SIPS URI implies that the UA wishes to communicate securely, and that the name is to be resolved in the domain to the RHS of the at-sign. The RHS will frequently be the home domain of the requestor, which allows for the home domain to process the outgoing request. This is useful for features like "speed dial" that require interpretation of the user part in the home domain. The tel URL may be used when the UA does not wish to specify the domain that should interpret a telephone number that has been input by the user. Rather, each domain through which the request passes would be given that opportunity. As an example, a user in an airport might log in and send requests through an outbound proxy in the airport. If they enter "411" (this is the phone number for local directory assistance in the United States), that needs to be interpreted and processed by the outbound proxy in the airport, not the user's home domain. In this case, tel:411 would be the right choice.

A request outside of a dialog MUST NOT contain a To tag; the tag in the To field of a request identifies the peer of the dialog. Since no dialog is established, no tag is present.

For further information on the To header field, see Section 20.39. The following is an example of a valid To header field:

```
To: Carol <sip:carol@chicago.com>
```

#### 中文

To 头字段首先指定请求所需的"逻辑"接收者，或者是该请求目标的用户或资源的地址记录。这可能是也可能不是请求的最终接收者。To 头字段可以包含 SIP 或 SIPS URI，但在适当的时候也可以使用其他 URI 方案（例如 tel URL (RFC 2806 [9])）。所有 SIP 实现必须支持 SIP URI 方案。任何支持 TLS 的实现必须支持 SIPS URI 方案。To 头字段允许显示名称。

UAC 可以通过多种方式了解如何为特定请求填充 To 头字段。通常，用户将通过人机界面建议 To 头字段，可能手动输入 URI 或从某种地址簿中选择。用户经常不会输入完整的 URI，而是一串数字或字母（例如 "bob"）。由 UA 自行决定如何解释此输入。使用该字符串形成 SIP URI 的用户部分意味着 UA 希望在 SIP URI 中 at 符号右侧 (RHS) 的域中解析该名称（例如 sip:bob@example.com）。使用该字符串形成 SIPS URI 的用户部分意味着 UA 希望安全通信，并且该名称将在 at 符号右侧的域中解析。RHS 通常是请求者的主域，这允许主域处理传出请求。这对于需要在主域中解释用户部分的"快速拨号"等功能很有用。当 UA 不希望指定应该解释用户输入的电话号码的域时，可以使用 tel URL。相反，请求经过的每个域都将有机会进行解释。例如，用户在机场登录并通过机场的出站代理发送请求。如果他们输入 "411"（这是美国本地查号台的电话号码），则需要由机场的出站代理（而不是用户的主域）进行解释和处理。在这种情况下，tel:411 是正确的选择。

对话外的请求不得包含 To tag；请求中 To 字段的 tag 用于标识对话的对等方。由于没有建立对话，因此不存在 tag。

有关 To 头字段的更多信息，请参见第 20.39 节。以下是有效 To 头字段的示例：

```
To: Carol <sip:carol@chicago.com>
```

---

### 8.1.1.3 From | 8.1.1.3 From

#### 原文

The From header field indicates the logical identity of the initiator of the request, possibly the user's address-of-record. Like the To header field, it contains a URI and optionally a display name. It is used by SIP elements to determine which processing rules to apply to a request (for example, automatic call rejection). As such, it is very important that the From URI not contain IP addresses or the FQDN of the host on which the UA is running, since these are not logical names.

The From header field allows for a display name. A UAC SHOULD use the display name "Anonymous", along with a syntactically correct, but otherwise meaningless URI (like sip:thisis@anonymous.invalid), if the identity of the client is to remain hidden.

Usually, the value that populates the From header field in requests generated by a particular UA is pre-provisioned by the user or by the administrators of the user's local domain. If a particular UA is used by multiple users, it might have switchable profiles that include a URI corresponding to the identity of the profiled user. Recipients of requests can authenticate the originator of a request in order to ascertain that they are who their From header field claims they are (see Section 22 for more on authentication).

The From field MUST contain a new "tag" parameter, chosen by the UAC. See Section 19.3 for details on choosing a tag.

For further information on the From header field, see Section 20.20. Examples:

```
From: "Bob" <sips:bob@biloxi.com> ;tag=a48s
From: sip:+12125551212@phone2net.com;tag=887s
From: Anonymous <sip:c8oqz84zk7z@privacy.org>;tag=hyh8
```

#### 中文

From 头字段指示请求发起者的逻辑身份，可能是用户的地址记录。与 To 头字段类似，它包含一个 URI 和可选的显示名称。SIP 元素使用它来确定要将哪些处理规则应用于请求（例如自动呼叫拒绝）。因此，非常重要的是 From URI 不包含 IP 地址或 UA 运行所在主机的 FQDN，因为这些不是逻辑名称。

From 头字段允许显示名称。如果要隐藏客户端的身份，UAC 应该使用显示名称 "Anonymous" 以及一个语法正确但其他方面无意义的 URI（如 sip:thisis@anonymous.invalid）。

通常，填充由特定 UA 生成的请求中的 From 头字段的值由用户或用户本地域的管理员预先配置。如果特定 UA 由多个用户使用，它可能具有可切换的配置文件，其中包含与配置文件用户身份对应的 URI。请求的接收者可以对请求发起者进行认证，以确认他们是 From 头字段所声称的人（有关认证的更多信息，请参见第 22 节）。

From 字段必须包含一个新的 "tag" 参数，由 UAC 选择。选择 tag 的详细信息请参见第 19.3 节。

有关 From 头字段的更多信息，请参见第 20.20 节。示例：

```
From: "Bob" <sips:bob@biloxi.com> ;tag=a48s
From: sip:+12125551212@phone2net.com;tag=887s
From: Anonymous <sip:c8oqz84zk7z@privacy.org>;tag=hyh8
```

### 8.1.1.4 Call-ID | 8.1.1.4 Call-ID

#### 原文

The Call-ID header field acts as a unique identifier to group together a series of messages. It MUST be the same for all requests and responses sent by either UA in a dialog. It SHOULD be the same in each registration from a UA.

In a new request created by a UAC outside of any dialog, the Call-ID header field MUST be selected by the UAC as a globally unique identifier over space and time unless overridden by method-specific behavior. All SIP UAs must have a means to guarantee that the Call-ID header fields they produce will not be inadvertently generated by any other UA. Note that when requests are retried after certain failure responses (Section 14.1), the same Call-ID MUST be used.

#### 中文

Call-ID 头字段用作唯一标识符，将一系列消息分组在一起。它在对话中由任一 UA 发送的所有请求和响应中必须相同。它在 UA 的每次注册中也应该相同。

在 UAC 在任何对话外创建的新请求中，Call-ID 头字段必须由 UAC 选择为在空间和时间上全局唯一的标识符，除非被特定于方法的行为覆盖。所有 SIP UA 必须有办法保证它们生成的 Call-ID 头字段不会被任何其他 UA 无意中生成。请注意，当在某些失败响应（第 14.1 节）后重试请求时，必须使用相同的 Call-ID。

---

### 8.1.1.5 CSeq | 8.1.1.5 CSeq

#### 原文

The CSeq header field serves as a unique transaction identifier within a dialog and as a means to order transactions within a dialog, to provide a means to unambiguously distinguish the behavior of a UAS when receiving a request outside of a dialog (Section 12.2.2), and to simplify fork matching (Section 16.6).

A CSeq header field contains a sequence number and a method name. The sequence number is a decimal string consisting of one or more digits, at least one in most cases, which serves to identify the transaction. The method name MUST match the method of the request. For ACK requests, the sequence number MUST match the sequence number of the INVITE request that triggered the ACK. For CANCEL requests, the sequence number MUST match the sequence number of the request being cancelled.

#### 中文

CSeq 头字段在对话内充当唯一的事务标识符，并作为在对话内对事务进行排序的手段，作为在对话外收到请求时 UAS 行为（第 12.2.2 节）进行明确区分的手段，并简化分叉匹配（第 16.6 节）。

CSeq 头字段包含序列号和方法名。序列号是一个十进制字符串，由一个或多个数字组成，在大多数情况下至少有一个，用于标识事务。方法名必须与请求的方法匹配。对于 ACK 请求，序列号必须与触发 ACK 的 INVITE 请求的序列号匹配。对于 CANCEL 请求，序列号必须与被取消请求的序列号匹配。

---

### 8.1.1.6 Max-Forwards | 8.1.1.6 Max-Forwards

#### 原文

The Max-Forwards header field may be used by any client that is directly connected to a proxy server, and it serves to limit the number of proxies or gateways that can forward the request to the next proxy server or gateway. This header field MUST be included with every request that is forwarded by a proxy.

The Max-Forwards header field has an integer value that indicates the remaining number of times this request is allowed to be forwarded. Each proxy or gateway that receives a request MUST check to verify that Max-Forwards is greater than 0, decrement it by one, and then forward the request.

If Max-Forwards is received with a value of 0, the receiving element MUST NOT forward the request. Instead, it MUST act as the final destination and respond with 483 (Too Many Hops).

If Max-Forwards is received with a value less than 0 (a negative number), it is an error. The element MUST reject the request with a 500 (Internal Server Error) response.

#### 中文

Max-Forwards 头字段可由直接连接到代理服务器的任何客户端使用，它用于限制可以转发请求的代理或网关的数量，以转发到下一个代理服务器或网关。此头字段必须包含在代理转发的每个请求中。

Max-Forwards 头字段有一个整数值，指示该请求允许继续转发的剩余次数。接收请求的每个代理或网关必须检查以验证 Max-Forwards 大于 0，然后将其减一，再转发请求。

如果 Max-Forwards 的值为 0，接收元素不得转发请求。相反，它必须充当最终目的地并回复 483（太多跳）响应。

如果 Max-Forwards 的值小于 0（负数），则是错误的。元素必须用 500（内部服务器错误）响应拒绝请求。

---

### 8.1.1.7 Via | 8.1.1.7 Via

#### 原文

The Via header field indicates the path taken by a request so far and indicates the path that should be taken in responding to the request. It is used to prevent request looping, to ensure that responses take the same path back to the originator via the same set of proxies, and to facilitate forking matching (Section 16.6).

Each client MUST add a Via header field to any request it sends. The added Via header field MUST contain its own address (the "sent-by" value), and MAY contain parameters such as "rport" or "maddr" as appropriate. If the client cannot determine its own address (for example, due to being behind a NAT), it MAY use the address resolved via DNS, or it MAY be configured with a specific address.

For requests being sent to a multicast group, it is RECOMMENDED that a "maddr" parameter be present, containing the destination multicast address, rather than the unicast address of a specific element.

When a UAC creates a request, it MUST add a Via header field. The Via header field MUST contain a "branch" parameter. This parameter is used to identify the transaction created by that request. The branch parameter value MUST be unique across all transactions that use the same combination of Call-ID, CSeq, and To tag.

The initial Request-URI of the message SHOULD be set to the value of the URI in the To field. One notable exception is the REGISTER method; behavior for setting the Request-URI of REGISTER is given in Section 10. It may also be undesirable for privacy reasons or convenience to set these fields to the same value (especially if the originating UA expects that the Request-URI will be changed during transit).

#### 中文

Via 头字段指示请求到目前为止所采用的路径，并指示响应应该采用的路径。它用于防止请求循环，确保响应通过同一组代理沿着相同的路径返回到发起者，并促进分叉匹配（第 16.6 节）。

每个客户端必须向其发送的任何请求添加 Via 头字段。添加的 Via 头字段必须包含自己的地址（"sent-by" 值），并且可以酌情包含 "rport" 或 "maddr" 等参数。如果客户端无法确定自己的地址（例如，由于位于 NAT 后面），它可以使用通过 DNS 解析的地址，或者可以使用特定地址进行配置。

对于发送到多播组的请求，建议存在一个包含目标多播地址的 "maddr" 参数，而不是特定元素的多播地址。

当 UAC 创建请求时，它必须添加 Via 头字段。Via 头字段必须包含一个 "branch" 参数。此参数用于标识由该请求创建的事务。branch 参数值在使用相同 Call-ID、CSeq 和 To tag 组合的所有事务中必须唯一。

建议使用加密随机标识符（RFC 1750 [12]）生成 Call-ID。这可以防止会话劫持并减少 Call-ID 意外碰撞的可能性。

选择请求的 Call-ID 头字段值不需要配置或人机界面。

有关 Call-ID 头字段的更多信息，请参见第 20.8 节。

示例：

```
Call-ID: f81d4fae-7dec-11d0-a765-00a0c91e6bf6@foo.bar.com
```

### 8.1.1.5 CSeq | 8.1.1.5 CSeq

#### 原文

The CSeq header field serves as a way to identify and order transactions. It consists of a sequence number and a method. The method MUST match that of the request. For non-REGISTER requests outside of a dialog, the sequence number value is arbitrary. The sequence number value MUST be expressible as a 32-bit unsigned integer and MUST be less than 2**31. As long as it follows the above guidelines, a client may use any mechanism it would like to select CSeq header field values.

Section 12.2.1.1 discusses construction of the CSeq for requests within a dialog.

示例：

```
CSeq: 4711 INVITE
```

#### 中文

CSeq 头字段用作识别和排序事务的方法。它由序列号和方法组成。方法必须与请求的方法匹配。对于对话外的非 REGISTER 请求，序列号值是任意的。序列号值必须可以表示为 32 位无符号整数，且必须小于 2**31。只要遵循上述准则，客户端可以使用任何机制来选择 CSeq 头字段值。

第 12.2.1.1 节讨论了对话内请求的 CSeq 构造。

示例：

```
CSeq: 4711 INVITE
```

### 8.1.1.6 Max-Forwards | 8.1.1.6 Max-Forwards

#### 原文

The Max-Forwards header field serves to limit the number of hops a request can transit on the way to its destination. It consists of an integer that is decremented by one at each hop. If the Max-Forwards value reaches 0 before the request reaches its destination, it will be rejected with a 483(Too Many Hops) error response.

A UAC MUST insert a Max-Forwards header field into each request it originates with a value that SHOULD be 70. This number was chosen to be sufficiently large to guarantee that a request would not be dropped in any SIP network when there were no loops, but not so large as to consume proxy resources when a loop does occur. Lower values should be used with caution and only in networks where topologies are known by the UA.

#### 中文

Max-Forwards 头字段用于限制请求在到达其目的地之前可以传输的跳数。它由一个整数组成，每跳递减一。如果 Max-Forwards 值在请求到达目的地之前达到 0，它将被拒绝并返回 483（太多跳）错误响应。

UAC 必须在其发起的每个请求中插入一个 Max-Forwards 头字段，其值应为 70。选择这个数字是为了足够大以保证在没有任何循环的任何 SIP 网络中请求不会被丢弃，但又不会大到在发生循环时消耗代理资源。较低的值应谨慎使用，仅在 UA 知道网络拓扑的情况下使用。

### 8.1.1.7 Via | 8.1.1.7 Via

#### 原文

The Via header field indicates the transport used for the transaction and identifies the location where the response is to be sent. A Via header field value is added only after the transport that will be used to reach the next hop has been selected (which may involve the usage of the procedures in [4]).

When the UAC creates a request, it MUST insert a Via into that request. The protocol name and protocol version in the header field MUST be SIP and 2.0, respectively. The Via header field value MUST contain a branch parameter. This parameter is used to identify the transaction created by that request. This parameter is used by both the client and the server.

The branch parameter value MUST be unique across space and time for all requests sent by the UA. The exceptions to this rule are CANCEL and ACK for non-2xx responses. As discussed below, a CANCEL request will have the same value of the branch parameter as the request it cancels. As discussed in Section 17.1.1.3, an ACK for a non-2xx response will also have the same branch ID as the INVITE whose response it acknowledges.

The uniqueness property of the branch ID parameter, to facilitate its use as a transaction ID, was not part of RFC 2543.

The branch ID inserted by an element compliant with this specification MUST always begin with the characters "z9hG4bK". These 7 characters are used as a magic cookie (7 is deemed sufficient to ensure that an older RFC 2543 implementation would not pick such a value), so that servers receiving the request can determine that the branch ID was constructed in the fashion described by this specification (that is, globally unique). Beyond this requirement, the precise format of the branch token is implementation-defined.

The Via header maddr, ttl, and sent-by components will be set when the request is processed by the transport layer (Section 18).

Via processing for proxies is described in Section 16.6 Item 8 and Section 16.7 Item 3.

#### 中文

Via 头字段指示用于事务的传输，并标识要发送响应的位置。只有在选择了用于到达下一跳的传输后（可能涉及使用 [4] 中的过程），才会添加 Via 头字段值。

当 UAC 创建请求时，它必须向该请求插入 Via。头字段中的协议名称和协议版本必须分别是 SIP 和 2.0。Via 头字段值必须包含一个 branch 参数。此参数用于标识由该请求创建的事务。此参数由客户端和服务器使用。

branch 参数值必须在空间和时间上对 UA 发送的所有请求唯一。此规则的例外是 CANCEL 和非 2xx 响应的 ACK。如下所述，CANCEL 请求将具有与其取消的请求相同的 branch 参数值。如第 17.1.1.3 节所述，非 2xx 响应的 ACK 也将具有与其确认响应的 INVITE 相同的 branch ID。

branch ID 参数的唯一性属性（便于其用作事务 ID）不是 RFC 2543 的一部分。

符合本规范的元素插入的 branch ID 必须始终以字符 "z9hG4bK" 开头。这 7 个字符用作 magic cookie（7 被认为足以确保较旧的 RFC 2543 实现不会选择这样的值），以便接收请求的服务器可以确定 branch ID 是按照本规范描述的方式构建的（即全局唯一的）。除此要求外，branch token 的确切格式由实现定义。

Via 头字段的 maddr、ttl 和 sent-by 组件将在请求由传输层处理时设置（第 18 节）。

代理的 Via 处理在第 16.6 节第 8 项和第 16.7 节第 3 项中描述。

### 8.1.1.8 Contact | 8.1.1.8 Contact

#### 原文

The Contact header field provides a SIP or SIPS URI that can be used to contact that specific instance of the UA for subsequent requests. The Contact header field MUST be present and contain exactly one SIP or SIPS URI in any request that can result in the establishment of a dialog. For the methods defined in this specification, that includes only the INVITE request. For these requests, the scope of the Contact is global. That is, the Contact header field value contains the URI at which the UA would like to receive requests, and this URI MUST be valid even if used in subsequent requests outside of any dialogs.

If the Request-URI or top Route header field value contains a SIPS URI, the Contact header field MUST contain a SIPS URI as well.

For further information on the Contact header field, see Section 20.10.

#### 中文

Contact 头字段提供一个 SIP 或 SIPS URI，可用于联系该 UA 的特定实例以进行后续请求。Contact 头字段必须存在于任何可能导致建立对话的请求中，并且必须恰好包含一个 SIP 或 SIPS URI。对于本规范中定义的方法，这仅包括 INVITE 请求。对于这些请求，Contact 的范围是全局的。也就是说，Contact 头字段值包含 UA 希望接收请求的 URI，并且此 URI 即使用于任何对话外的后续请求也必须是有效的。

如果 Request-URI 或顶部 Route 头字段值包含 SIPS URI，则 Contact 头字段也必须包含 SIPS URI。

有关 Contact 头字段的更多信息，请参见第 20.10 节。

---

### 8.1.1.9 Supported and Require | 8.1.1.9 Supported 和 Require

#### 原文

If the UAC supports extensions to SIP that can be applied by the server to the response, the UAC SHOULD include a Supported header field in the request listing the option tags (Section 19.2) for those extensions.

The option tags listed MUST only refer to extensions defined in standards-track RFCs. This is to prevent servers from insisting that clients implement non-standard, vendor-defined features in order to receive service. Extensions defined by experimental and informational RFCs are explicitly excluded from usage with the Supported header field in a request, since they too are often used to document vendor-defined extensions.

If the UAC wishes to insist that a UAS understand an extension that the UAC will apply to the request in order to process the request, it MUST insert a Require header field into the request listing the option tag for that extension. If the UAC wishes to apply an extension to the request and insist that any proxies that are traversed understand that extension, it MUST insert a Proxy-Require header field into the request listing the option tag for that extension.

As with the Supported header field, the option tags in the Require and Proxy-Require header fields MUST only refer to extensions defined in standards-track RFCs.

#### 中文

如果 UAC 支持可由服务器应用于响应的 SIP 扩展，UAC 应在请求中包含一个 Supported 头字段，列出这些扩展的选项标签（第 19.2 节）。

列出的选项标签只能引用标准跟踪 RFC 中定义的扩展。这是为了防止服务器坚持要求客户端实现非标准的供应商定义功能才能接收服务。实验性和信息性 RFC 定义的扩展明确排除在请求中与 Supported 头字段一起使用，因为它们也经常用于记录供应商定义的扩展。

如果 UAC 希望坚持要求 UAS 理解 UAC 将应用于请求以处理请求的扩展，它必须在请求中插入一个 Require 头字段，列出该扩展的选项标签。如果 UAC 希望将扩展应用于请求并坚持要求遍历的任何代理理解该扩展，它必须在请求中插入一个 Proxy-Require 头字段，列出该扩展的选项标签。

与 Supported 头字段一样，Require 和 Proxy-Require 头字段中的选项标签只能引用标准跟踪 RFC 中定义的扩展。

### 8.1.1.10 Additional Message Components | 8.1.1.10 附加消息组件

#### 原文

After a new request has been created, and the header fields described above have been properly constructed, any additional optional header fields are added, as are any header fields specific to the method.

SIP requests MAY contain a MIME-encoded message-body. Regardless of the type of body that a request contains, certain header fields must be formulated to characterize the contents of the body. For further information on these header fields, see Sections 20.11 through 20.15.

#### 中文

创建新请求并正确构造上述头字段后，将添加任何其他可选头字段以及特定于方法的头字段。

SIP 请求可以包含 MIME 编码的消息体。无论请求包含什么类型的消息体，某些头字段必须被制定以表征消息体的内容。有关这些头字段的更多信息，请参见第 20.11 至 20.15 节。

### 8.1.2 Sending the Request | 8.1.2 发送请求

#### 原文

The destination for the request is then computed. Unless there is local policy specifying otherwise, the destination MUST be determined by applying the DNS procedures described in [4] as follows. If the first element in the route set indicated a strict router (resulting in forming the request as described in Section 12.2.1.1), the procedures MUST be applied to the Request-URI of the request. Otherwise, the procedures are applied to the first Route header field value in the request (if one exists), or to the request's Request-URI if there is no Route header field present. These procedures yield an ordered set of address, port, and transports to attempt. Independent of which URI is used as the target of the DNS resolution procedures, the Request-URI MUST be used in the request.

Local policy MAY specify an alternate set of destinations to attempt. If the Request-URI contains a SIPS URI, any alternate destinations MUST be contacted with TLS. Beyond that, there are no restrictions on the alternate destinations if the request contains no Route header field. This provides a simple alternative to a pre-existing route set as a way to specify an outbound proxy. However, that approach for configuring an outbound proxy is NOT RECOMMENDED; a pre-existing route set with a single URI SHOULD be used instead. If the request contains a Route header field, the request SHOULD be sent to the locations derived from its topmost value, but MAY be sent to any server that the UA is certain will honor the Route and Request-URI policies specified in this document. In particular, a UAC configured with an outbound proxy SHOULD attempt to send the request to the location indicated in the first Route header field value instead of adopting the policy of sending all messages to the outbound proxy.

The UAC SHOULD follow the procedures defined in [4] for stateful elements, trying each address until a server is contacted. Each try constitutes a new transaction, and therefore each carries a different topmost Via header field value with a new branch parameter. Furthermore, the transport value in the Via header field is set to whatever transport was determined for the target server.

#### 中文

然后计算请求的目的地。除非有本地策略另有指定，否则必须按如下方式应用 [4] 中描述的 DNS 过程来确定目的地。如果路由集中的第一个元素指示严格路由器（导致按照第 12.2.1.1 节中所述形成请求），则必须将过程应用于请求的 Request-URI。否则，过程将应用于请求中的第一个 Route 头字段值（如果存在），如果没有 Route 头字段，则应用于请求的 Request-URI。这些过程产生要尝试的有序地址、端口和传输集合。无论使用哪个 URI 作为 DNS 解析过程的输入，如果 Request-URI 指定了 SIPS 资源，UAC 必须像输入是 SIPS URI 一样遵循 [4] 的过程。

本地策略可以指定要尝试的备用目的地集。如果 Request-URI 包含 SIPS URI，则必须使用 TLS 联系任何备用目的地。除此之外，如果请求不包含 Route 头字段，则对备用目的地没有限制。这提供了一种简单的替代预存在路由集的方法来指定出站代理。但是，不推荐使用该方法来配置出站代理；应该改用具有单个 URI 的预存在路由集。如果请求包含 Route 头字段，则应将请求发送到从其最顶层值派生出的位置，但可以发送到 UA 确定会遵守本规范中指定的 Route 和 Request-URI 策略的任何服务器。特别地，配置有出站代理的 UAC 应该尝试将请求发送到第一个 Route 头字段值指示的位置，而不是采用将所有消息发送到出站代理的策略。

UAC 应该遵循 [4] 中为有状态元素定义的过程，尝试每个地址直到联系到服务器。每次尝试构成一个新的事务，因此每个都带有不同的顶部 Via 头字段值和新的 branch 参数。此外，Via 头字段中的传输值被设置为为目标服务器确定的传输。

### 8.1.3 Processing Responses | 8.1.3 处理响应

#### 原文

Responses are first processed by the transport layer and then passed up to the transaction layer. The transaction layer performs its processing and then passes the response up to the TU. The majority of response processing in the TU is method specific. However, there are some general behaviors independent of the method.

#### 中文

响应首先由传输层处理，然后传递到事务层。事务层执行其处理，然后将响应传递给 TU。TU 中的大多数响应处理是特定于方法的。但是，有一些与方法是无关的一般行为。

---

### 8.1.3.1 Transaction Layer Errors | 8.1.3.1 事务层错误

#### 原文

In some cases, the response returned by the transaction layer will not be a SIP message, but rather a transaction layer error. When a timeout error is received from the transaction layer, it MUST be treated as if a 408 (Request Timeout) status code has been received. If a fatal transport error is reported by the transport layer (generally, due to fatal ICMP errors in UDP or connection failures in TCP), the condition MUST be treated as a 503 (Service Unavailable) status code.

#### 中文

在某些情况下，事务层返回的响应不是 SIP 消息，而是事务层错误。当从事务层收到超时错误时，必须将其视为收到了 408（请求超时）状态码。如果传输层报告了致命的传输错误（通常由于 UDP 中的致命 ICMP 错误或 TCP 中的连接失败），则必须将此情况视为 503（服务不可用）状态码。

---

### 8.1.3.2 Unrecognized Responses | 8.1.3.2 未识别的响应

#### 原文

A UAC MUST treat any final response it does not recognize as being equivalent to the x00 response code of that class, and MUST be able to process the x00 response code for all classes. For example, if a UAC receives an unrecognized response code of 431, it can safely assume that there was something wrong with its request and treat the response as if it had received a 400 (Bad Request) response code. A UAC MUST treat any provisional response different than 100 that it does not recognize as 183 (Session Progress). A UAC MUST be able to process 100 and 183 responses.

#### 中文

UAC 必须将其不识别的任何最终响应视为等同于该类的 x00 响应码，并且必须能够处理所有类的 x00 响应码。例如，如果 UAC 收到未识别的响应码 431，它可以安全地假设其请求有问题，并将响应视为收到了 400（错误请求）响应码。UAC 必须将其不识别的除 100 之外的任何临时响应视为 183（会话进度）。UAC 必须能够处理 100 和 183 响应。

---

### 8.1.3.3 Vias | 8.1.3.3 Vias

#### 原文

If more than one Via header field value is present in a response, the UAC SHOULD discard the message.

The presence of additional Via header field values that precede the originator of the request suggests that the message was misrouted or possibly corrupted.

#### 中文

如果响应中存在多个 Via 头字段值，UAC 应该丢弃该消息。

在请求发起者之前存在额外的 Via 头字段值表明消息可能被错误路由或可能已损坏。

---

### 8.1.3.4 Processing 3xx Responses | 8.1.3.4 处理 3xx 响应

#### 原文

Upon receipt of a redirection response (for example, a 301 response status code), clients SHOULD use the URI(s) in the Contact header field to formulate one or more new requests based on the redirected request. This process is similar to that of a proxy recursing on a 3xx class response as detailed in Sections 16.5 and 16.6. A client starts with an initial target set containing exactly one URI, the Request-URI of the original request. If a client wishes to formulate new requests based on a 3xx class response to that request, it places the URIs to try into the target set. Subject to the restrictions in this specification, a client can choose which Contact URIs it places into the target set. As with proxy recursion, a client processing 3xx class responses MUST NOT add any given URI to the target set more than once. If the original request had a SIPS URI in the Request-URI, the client MAY choose to recurse to a non-SIPS URI, but SHOULD inform the user of the redirection to an insecure URI.

As the target set grows, the client MAY generate new requests to the URIs in any order. A common mechanism is to order the set by the "q" parameter value from the Contact header field value. Requests to the URIs MAY be generated serially or in parallel. One approach is to process groups of decreasing q-values serially and process the URIs in each q-value group in parallel. Another is to perform only serial processing in decreasing q-value order, arbitrarily choosing between contacts of equal q-value.

If contacting an address in the list results in a failure, as defined in the next paragraph, the element moves to the next address in the list, until the list is exhausted. If the list is exhausted, then the request has failed.

Failures SHOULD be detected through failure response codes (codes greater than 399); for network errors the client transaction will report any transport layer failures to the transaction user. Note that some response codes (detailed in 8.1.3.5) indicate that the request can be retried; requests that are reattempted should not be considered failures.

When a failure for a particular contact address is received, the client SHOULD try the next contact address. This will involve creating a new client transaction to deliver a new request.

In order to create a request based on a contact address in a 3xx response, a UAC MUST copy the entire URI from the target set into the Request-URI, except for the "method-param" and "header" URI parameters (see Section 19.1.1 for a definition of these parameters). It uses the "header" parameters to create header field values for the new request, overwriting header field values associated with the redirected request in accordance with the guidelines in Section 19.1.5.

Note that in some instances, header fields that have been communicated in the contact address may instead append to existing request header fields in the original redirected request. As a general rule, if the header field can accept a comma-separated list of values, then the new header field value MAY be appended to any existing values in the original redirected request. If the header field does not accept multiple values, the value in the original redirected request MAY be overwritten by the header field value communicated in the contact address.

It is RECOMMENDED that the UAC reuse the same To, From, and Call-ID used in the original redirected request, but the UAC MAY also choose to update the Call-ID header field value for new requests.

Finally, once the new request has been constructed, it is sent using a new client transaction, and therefore MUST have a new branch ID in the top Via field as discussed in Section 8.1.1.7.

In all other respects, requests sent upon receipt of a redirect response SHOULD re-use the header fields and bodies of the original request.

#### 中文

收到重定向响应（例如，301 响应状态码）后，客户端应使用 Contact 头字段中的 URI 来基于重定向的请求制定一个或多个新请求。此过程类似于代理对 3xx 类响应进行递归，如第 16.5 和 16.6 节中详述的那样。客户端从一个仅包含原始请求 Request-URI 的初始目标集开始。如果客户端希望基于对该请求的 3xx 类响应来制定新请求，它会将要尝试的 URI 放入目标集。根据本规范的限制，客户端可以选择将哪些 Contact URI 放入目标集。与代理递归一样，处理 3xx 类响应的客户端不得将任何给定的 URI 添加到目标集超过一次。如果原始请求的 Request-URI 中有 SIPS URI，客户端可以选择递归到非 SIPS URI，但应该通知用户重定向到不安全的 URI。

随着目标集的增长，客户端可以按任何顺序向 URI 生成新请求。一个常见的机制是按 Contact 头字段值中的 "q" 参数值对集合进行排序。可以串行或并行生成对 URI 的请求。一种方法是按递减的 q 值顺序串行处理组，并在每个 q 值组内并行处理 URI。另一种是仅按递减 q 值顺序执行串行处理，在具有相等 q 值的联系人之间任意选择。

如果联系列表中的某个地址导致失败（下段定义），则元素移动到列表中的下一个地址，直到列表耗尽。如果列表耗尽，则请求失败。

失败应该通过失败响应码（大于 399 的码）检测；对于网络错误，客户端事务将向事务用户报告任何传输层故障。请注意，某些响应码（第 8.1.3.5 节详述）表示可以重试请求；不应将重新尝试的请求视为失败。

当收到针对特定联系人地址的失败时，客户端应该尝试下一个联系人地址。这将涉及创建新的客户端事务来传递新请求。

为了基于 3xx 响应中的联系人地址创建请求，UAC 必须将目标集中的整个 URI 复制到 Request-URI，但 "method-param" 和 "header" URI 参数除外（这些参数的定义见第 19.1.1 节）。它使用 "header" 参数为新请求创建头字段值，根据第 19.1.5 节中的指南覆盖与重定向请求关联的头字段值。

请注意，在某些情况下，在联系人地址中传达的头字段可能会附加到原始重定向请求中的现有请求头字段。作为一般规则，如果头字段可以接受逗号分隔的值列表，则新头字段值可以附加到原始重定向请求中的任何现有值。如果头字段不接受多个值，则原始重定向请求中的值可以被联系人地址中传达的头字段值覆盖。

建议 UAC 重用原始重定向请求中使用的相同 To、From 和 Call-ID，但 UAC 也可以选择为新请求更新 Call-ID 头字段值。

最后，一旦新请求构建完成，它会使用新的客户端事务发送，因此必须在顶部 Via 字段中有一个新的 branch ID（如第 8.1.1.7 节所述）。

在所有其他方面，收到重定向响应后发送的请求应该重用原始请求的头字段和消息体。

---

### 8.1.3.5 Processing 4xx Responses | 8.1.3.5 处理 4xx 响应

#### 原文

A 401 (Unauthorized) response MUST be challenged by the UAC, if it does not have credentials, and the request resent with credentials. A 407 (Proxy Authentication Required) response MUST be challenged by the UAC, if it does not have credentials, and the request resent with credentials. The processing for these is described in Section 22.

If a request is challenged with a 401 or 407, the client MUST follow the challenge and not reprocess the request unchanged.

For other 4xx responses, including 403 and 404, the response is passed to the TU, which has the responsibility to decide what to do. The UAC SHOULD NOT retry the request automatically.

#### 中文

如果 UAC 没有凭证，401（未授权）响应必须由 UAC 质疑，并使用凭证重新发送请求。如果 UAC 没有凭证，407（需要代理认证）响应必须由 UAC 质疑，并使用凭证重新发送请求。这些的处理在第 22 节中描述。

如果请求被 401 或 407 质疑，客户端必须遵循质询而不重新处理未更改的请求。

对于其他 4xx 响应，包括 403 和 404，响应被传递给 TU，TU 负责决定该怎么做。UAC 不应该自动重试请求。

---

### 8.2 UAS Behavior | 8.2 UAS 行为

#### 原文

When a request is received by a UAS, it examines the request's Request-URI, Call-ID, To, CSeq, and Via header fields. The Request-URI indicates to whom the request should be routed within this server. The To header field indicates the desired recipient of this request. The Call-ID is used to identify a dialog, and together with the From tag and Call-ID, it identifies a particular session. The CSeq determines the sequence number of a transaction. The Via header field is used to route responses.

UASs should be careful to not generate responses to requests with unknown methods. For example, a UAS that did not understand the "MESSAGE" method would still need to generate a 405 (Method Not Allowed) response if it received an OPTIONS request that listed "MESSAGE" as an option. The UAS should check the Require header field (Section 8.2.1) for options that it does not understand, and if present, generate a 420 (Bad Extension) response.

A UAS MUST also include a Allow header field in a response to an OPTIONS request. A UAS MUST also include a Allow header field in a 100 (Trying) response if it does not allow other methods to be used in place of the method in the request.

#### 中文

当请求被 UAS 接收时，它会检查请求的 Request-URI、Call-ID、To、CSeq 和 Via 头字段。Request-URI 指示请求应该在此服务器内路由到谁。To 头字段指示该请求的期望接收者。Call-ID 用于识别对话，并与 From tag 和 Call-ID 一起识别特定会话。CSeq 决定事务的序列号。Via 头字段用于路由响应。

UAS 应注意不要对未知方法的请求生成响应。例如，不理解 "MESSAGE" 方法的 UAS 如果收到列出 "MESSAGE" 作为选项的 OPTIONS 请求，仍然需要生成 405（方法不允许）响应。UAS 应检查 Require 头字段（第 8.2.1 节）中它不理解的选项，如果存在，则生成 420（错误扩展）响应。

UAS 在对 OPTIONS 请求的响应中也必须包含一个 Allow 头字段。如果 UAS 不允许使用其他方法代替请求中的方法，它也必须在 100（正在尝试）响应中包含 Allow 头字段。

---

### 8.2.1 Processing the Request | 8.2.1 处理请求

#### 原文

When receiving a request, a UAS MUST apply the following general rules, independent of the specific method being handled.

The UAS MUST validate the request. This includes the items listed in Section 18.2 (for requests received over stream transports) and the header field validity requirements listed for each method.

If a UAS does not understand the request method, it MUST generate a 405 (Method Not Allowed) response. The UAS MUST also include an Allow header field with the list of methods it understands and is willing to accept.

The UAS MUST check the request for any Require header field values (Section 8.2.1.2) that it does not understand. If there are no unknown Require header field values, the UAS MUST check the Proxy-Require header field values (Section 8.2.1.2) it does not understand. If there are no unknown Require or Proxy-Require header field values, the UAS MUST process the request.

If the UAS receives a request with a Supported header field listing an option tag that is not understood, the request is processed normally. However, if the UAS receives a request with a Require header field listing an option tag that is not understood, the UAS MUST reject the request with a 420 (Bad Extension) response. The UAS MUST add an Unsupported header field with the option tag for which there is no support.

#### 中文

当收到请求时，UAS 必须应用以下一般规则，与正在处理的特定方法无关。

UAS 必须验证请求。这包括第 18.2 节中列出的项目（对于通过流传输接收的请求）以及为每个方法列出的头字段有效性要求。

如果 UAS 不理解请求方法，它必须生成 405（方法不允许）响应。UAS 还必须包含一个 Allow 头字段，列出它理解和愿意接受的 methods 列表。

UAS 必须检查请求中是否存在它不理解的任何 Require 头字段值（第 8.2.1.2 节）。如果没有未知的 Require 头字段值，UAS 必须检查它不理解的 Proxy-Require 头字段值（第 8.2.1.2 节）。如果没有未知的 Require 或 Proxy-Require 头字段值，UAS 必须处理请求。

如果 UAS 收到包含不理解的选项标签的 Supported 头字段的请求，请求会正常处理。但是，如果 UAS 收到包含不理解选项标签的 Require 头字段的请求，UAS 必须用 420（错误扩展）响应拒绝该请求。UAS 必须添加一个 Unsupported 头字段，其中包含不支持的选项标签。

---

### 8.2.2 Generating the Response | 8.2.2 生成响应

#### 原文

Since the request is addressed to this UAS, it will be processed here. A request is "addressed to this UAS" if the Request-URI matches a SIP or SIPS URI that resolves to this UAS (Section 10.3 describes how URIs are matched). A UAS MUST NOT accept traffic directed to it using an IP address or host name placed in the Request-URI that does not identify this specific UA. For example, if the Request-URI contains an IP address of the host on which the UAS is running, but the UA does not want to receive requests for this address, it MUST reject the request.

The UAS MUST always add a tag to the To header field in any response (including 100 Trying) it sends to this request (Section 8.2.1.2 describes when tags can be omitted). The tag MUST be unique across all 2xx responses sent by this UAS within this dialog. The Caller and callee will use the tags to identify the dialog.

The UAS MUST add a Via header field to the response. The Via header field values MUST be the same as the topmost Via value in the request.

The response MUST contain a CSeq header field that exactly matches the sequence number in the request.

The UAS MUST check the request's CSeq header field value. If it does not match the sequence number of any requests sent by the UAS within this dialog, the UAS MUST respond with a 500 (Internal Server Error) response. Note that for ACK requests within a dialog, the CSeq sequence number matches that of the INVITE whose acknowledgment it is.

#### 中文

由于请求被寻址到此 UAS，它将在这里处理。如果 Request-URI 解析为此 UAS（第 10.3 节描述了 URI 如何匹配），则请求是"寻址到此 UAS"的。UAS 不得接受使用 Request-URI 中放置的不标识此特定 UA 的 IP 地址或主机名定向到它的流量。例如，如果 Request-URI 包含 UAS 运行所在主机的 IP 地址，但 UA 不想接收此地址的请求，则必须拒绝该请求。

UAS 必须始终在它发送的对此请求的任何响应（包括 100 Trying）中向 To 头字段添加一个 tag（第 8.2.1.2 节描述了何时可以省略 tag）。在此对话中，此 UAS 发送的所有 2xx 响应中，tag 必须唯一。呼叫者和被呼叫者将使用 tag 来识别对话。

UAS 必须向响应添加一个 Via 头字段。Via 头字段值必须与请求中最顶层 Via 值相同。

响应必须包含一个 CSeq 头字段，该字段与请求中的序列号完全匹配。

UAS 必须检查请求的 CSeq 头字段值。如果它与此对话中 UAS 发送的任何请求的序列号不匹配，UAS 必须用 500（内部服务器错误）响应回复。请注意，对于对话中的 ACK 请求，CSeq 序列号与其确认的 INVITE 的序列号匹配。

### 8.3 Redirect Servers | 8.3 重定向服务器

#### 原文

A redirect server is a UAS that generates 3xx responses to redirect the client to alternate URIs. The processing of these alternate URIs by the client follows the rules in Section 8.1.3.4.

Redirect servers do not forward requests.

#### 中文

重定向服务器是生成 3xx 响应以将客户端重定向到备用 URI 的 UAS。客户端对这些备用 URI 的处理遵循第 8.1.3.4 节中的规则。

重定向服务器不转发请求。

## 9. Canceling a Request | 9. 取消请求

#### 原文

A CANCEL request is used by a UAC to cancel a previously sent request that is not final. The CANCEL method does not affect a request that has already received a final response. Because of this, the CANCEL is best-effort.

A cancel request SHOULD be issued by a UAC if the prior request receives a provisional response, and the UAC no longer wishes to pursue the transaction.

A UAC SHOULD NOT issue a CANCEL request if the prior request has already received a final response. If the UAC has received a 2xx class response to the request, the request has succeeded, and the only way to terminate the session is to send a BYE request within the resulting dialog.

A CANCEL request does not "undo" a previous request. It merely prevents the final response from being sent back. If the UAS had already generated a final response before the CANCEL request was received, the final response would still be sent to the UAC, and the CANCEL would have no effect.

#### 中文

CANCEL 请求由 UAC 用于取消先前发送的非最终请求。CANCEL 方法不影响已收到最终响应的请求。正因为此，CANCEL 是尽力而为的。

如果先前请求收到临时响应且 UAC 不再希望继续该事务，则 UAC 应发出 CANCEL 请求。

如果先前请求已收到最终响应，UAC 不应发出 CANCEL 请求。如果 UAC 已收到对该请求的 2xx 类响应，则请求已成功，终止会话的唯一方式是在 resulting dialog 中发送 BYE 请求。

CANCEL 请求不会"撤销"先前的请求。它只是阻止最终响应被发送回。如果 UAS 在收到 CANCEL 请求之前已经生成了最终响应，则最终响应仍会被发送到 UAC，而 CANCEL 将没有效果。

## 10. Registrations | 10. 注册

#### 原文

SIP offers a REGISTER method that allows a UA to create, modify, and remove bindings in a location service. A binding is a association between a SIP URI (for example, sip:alice@atlanta.com) and one or more contact addresses (for example, sip:alice@pc.atlant.com). The URI in the binding is called the address-of-record (AOR). Bindings are typically maintained by a registrar, which is a UAS that processes REGISTER requests and updates the location service accordingly.

REGISTER requests do not establish dialogs.

A UA sends a REGISTER request to a registrar. The Request-URI names the domain of the registrar. The Via header field contains a branch parameter that identifies the transaction.

The To header field of a REGISTER request contains the AOR being registered. The Contact header fields contain the contact addresses being bound to the AOR.

#### 中文

SIP 提供了一种 REGISTER 方法，允许 UA 在位置服务中创建、修改和删除绑定。绑定是 SIP URI（例如 sip:alice@atlanta.com）与一个或多个联系人地址（例如 sip:alice@pc.atlant.com）之间的关联。绑定中的 URI 称为地址记录 (AOR)。绑定通常由 registrar 维护，registrar 是处理 REGISTER 请求并相应更新位置服务的 UAS。

REGISTER 请求不建立对话。

UA 向 registrar 发送 REGISTER 请求。Request-URI 指定 registrar 的域名。Via 头字段包含一个标识事务的 branch 参数。

REGISTER 请求的 To 头字段包含正在注册的 AOR。Contact 头字段包含绑定到 AOR 的联系人地址。

## 11. Querying for Capabilities | 11. 查询能力

#### 原文

A UA may query another UA via the OPTIONS method for its capabilities. This allows a client to query another UA to determine the SIP methods and extensions it supports.

The response to an OPTIONS request is the same as an INVITE request, except it does not establish a dialog. A UAS that receives an OPTIONS request SHOULD respond the same as it would to an INVITE request, except it MUST NOT generate a 2xx response unless it is willing to accept the session establishment.

#### 中文

UA 可以通过 OPTIONS 方法查询另一个 UA 的能力。这允许客户端查询另一个 UA 以确定其支持的 SIP 方法和扩展。

对 OPTIONS 请求的响应与对 INVITE 请求的响应相同，只是它不建立对话。收到 OPTIONS 请求的 UAS 应该像对 INVITE 请求一样响应，只是除非它愿意接受会话建立，否则不得生成 2xx 响应。

## 12. Dialogs | 12. 对话

#### 原文

A dialog is a peer-to-peer SIP relationship between two user agents that persists for some time. A dialog is identified at each UA with a dialog ID, which consists of a Call-ID, a local tag, and a remote tag. The dialog ID is local to each UA.

A dialog is established through the creation of a session, which is initiated with an INVITE request that receives a 2xx response. The remote tag in the dialog ID is set to the tag in the To header field of the response, and the local tag is set to the tag in the From header field of the request.

A dialog is also established by a UAS sending a 2xx response to an INVITE request, or by the UAC receiving a 2xx response to an INVITE request.

Within a dialog, requests can be sent by either UA. These in-dialog requests are sent within the context of the dialog, and they MUST contain an appropriate To tag (the remote tag) and From tag (the local tag).

The methods for initiating, modifying, and terminating sessions are discussed in Sections 13, 14, and 15 respectively.

#### 中文

对话是两个用户代理之间持续一段时间的点对点 SIP 关系。每个 UA 中的对话由对话 ID 标识，对话 ID 由 Call-ID、本地 tag 和远程 tag 组成。对话 ID 在每个 UA 本地。

对话通过会话的创建来建立，会话由 INVITE 请求发起并收到 2xx 响应。对话 ID 中的远程 tag 设置为响应中 To 头字段的 tag，本地 tag 设置为请求中 From 头字段的 tag。

对话也由 UAS 发送对 INVITE 请求的 2xx 响应来建立，或由 UAC 接收对 INVITE 请求的 2xx 响应来建立。

在对话中，任一 UA 都可以发送请求。这些对话内请求在对话的上下文中发送，并且必须包含适当的 To tag（远程 tag）和 From tag（本地 tag）。

发起、修改和终止会话的方法分别在第 13、14 和 15 节中讨论。

---

## 13. Initiating a Session | 13. 发起会话

### 13.1 Overview | 13.1 概述

#### 原文

When a user agent client desires to initiate a session (for example, audio, video, or a game), it formulates an INVITE request. The INVITE request asks a server to establish a session. This request may be forwarded by proxies, eventually arriving at one or more UAS that can potentially accept the invitation. These UASs will frequently need to query the user about whether to accept the invitation. After some time, those UASs can accept the invitation (meaning the session is to be established) by sending a 2xx response. If the invitation is not accepted, a 3xx, 4xx, 5xx or 6xx response is sent, depending on the reason for the rejection. Before sending a final response, the UAS can also send provisional responses (1xx) to advise the UAC of progress in contacting the called user.

After possibly receiving one or more provisional responses, the UAC will get one or more 2xx responses or one non-2xx final response. Because of the protracted amount of time it can take to receive final responses to INVITE, the reliability mechanisms for INVITE transactions differ from those of other requests (like OPTIONS). Once it receives a final response, the UAC needs to send an ACK for every final response it receives. The procedure for sending this ACK depends on the type of response. For final responses between 300 and 699, the ACK processing is done in the transaction layer and follows one set of rules (See Section 17). For 2xx responses, the ACK is generated by the UAC core.

A 2xx response to an INVITE establishes a session, and it also creates a dialog between the UA that issued the INVITE and the UA that generated the 2xx response. Therefore, when multiple 2xx responses are received from different remote UAs (because the INVITE forked), each 2xx establishes a different dialog. All these dialogs are part of the same call.

This section provides details on the establishment of a session using INVITE. A UA that supports INVITE MUST also support ACK, CANCEL and BYE.

#### 中文

当用户代理客户端希望发起会话时（例如音频、视频或游戏），它会构建一个 INVITE 请求。INVITE 请求要求服务器建立会话。此请求可能由代理转发，最终到达一个或多个可能接受邀请的 UAS。这些 UAS 通常需要询问用户是否接受邀请。一段时间后，这些 UAS 可以通过发送 2xx 响应来接受邀请（意味着将要建立会话）。如果不接受邀请，则根据拒绝原因发送 3xx、4xx、5xx 或 6xx 响应。在发送最终响应之前，UAS 还可以发送临时响应（1xx）以告知 UAC 联系被叫用户的进度。

在可能收到一个或多个临时响应后，UAC 将获得一个或多个 2xx 响应或一个非 2xx 最终响应。由于收到 INVITE 的最终响应可能需要很长时间，INVITE 事务的可靠性机制不同于其他请求（如 OPTIONS）的可靠性机制。一旦收到最终响应，UAC 需要为它收到的每个最终响应发送 ACK。发送此 ACK 的过程取决于响应的类型。对于 300 到 699 之间的最终响应，ACK 处理在事务层中完成，并遵循一组规则（参见第 17 节）。对于 2xx 响应，ACK 由 UAC 核心生成。

对 INVITE 的 2xx 响应建立了一个会话，同时也在发出 INVITE 的 UA 和生成 2xx 响应的 UA 之间创建了一个对话。因此，当从不同的远程 UA（因为 INVITE 分叉）收到多个 2xx 响应时，每个 2xx 建立一个不同的对话。所有这些对话都是同一呼叫的一部分。

本节提供了使用 INVITE 建立会话的详细信息。支持 INVITE 的 UA 还必须支持 ACK、CANCEL 和 BYE。

---

### 13.2 UAC Processing | 13.2 UAC 处理

### 13.2.1 Creating the Initial INVITE | 13.2.1 创建初始 INVITE

#### 原文

Since the initial INVITE represents a request outside of a dialog, its construction follows the procedures of Section 8.1.1. Additional processing is required for the specific case of INVITE.

An Allow header field (Section 20.5) SHOULD be present in the INVITE. It indicates what methods can be invoked within a dialog, on the UA sending the INVITE, for the duration of the dialog. For example, a UA capable of receiving INFO requests within a dialog [34] SHOULD include an Allow header field listing the INFO method.

A Supported header field (Section 20.37) SHOULD be present in the INVITE. It enumerates all the extensions understood by the UAC.

An Accept (Section 20.1) header field MAY be present in the INVITE. It indicates which Content-Types are acceptable to the UA, in both the response received by it, and in any subsequent requests sent to it within dialogs established by the INVITE. The Accept header field is especially useful for indicating support of various session description formats.

The UAC MAY add an Expires header field (Section 20.19) to limit the validity of the invitation. If the time indicated in the Expires header field is reached and no final answer for the INVITE has been received, the UAC core SHOULD generate a CANCEL request for the INVITE, as per Section 9.

A UAC MAY also find it useful to add, among others, Subject (Section 20.36), Organization (Section 20.25) and User-Agent (Section 20.41) header fields. They all contain information related to the INVITE.

The UAC MAY choose to add a message body to the INVITE. Section 8.1.1.10 deals with how to construct the header fields -- Content-Type among others -- needed to describe the message body.

There are special rules for message bodies that contain a session description - their corresponding Content-Disposition is "session". SIP uses an offer/answer model where one UA sends a session description, called the offer, which contains a proposed description of the session. The offer indicates the desired communications means (audio, video, games), parameters of those means (such as codec types) and addresses for receiving media from the answerer. The other UA responds with another session description, called the answer, which indicates which communications means are accepted, the parameters that apply to those means, and addresses for receiving media from the offerer. An offer/answer exchange is within the context of a dialog, so that if a SIP INVITE results in multiple dialogs, each is a separate offer/answer exchange. The offer/answer model defines restrictions on when offers and answers can be made (for example, you cannot make a new offer while one is in progress). This results in restrictions on where the offers and answers can appear in SIP messages. In this specification, offers and answers can only appear in INVITE requests and responses, and ACK. The usage of offers and answers is further restricted. For the initial INVITE transaction, the rules are:

- The initial offer MUST be in either an INVITE or, if not there, in the first reliable non-failure message from the UAS back to the UAC. In this specification, that is the final 2xx response.
- If the initial offer is in an INVITE, the answer MUST be in a reliable non-failure message from UAS back to UAC which is correlated to that INVITE. For this specification, that is only the final 2xx response to that INVITE. That same exact answer MAY also be placed in any provisional responses sent prior to the answer. The UAC MUST treat the first session description it receives as the answer, and MUST ignore any session descriptions in subsequent responses to the initial INVITE.
- If the initial offer is in the first reliable non-failure message from the UAS back to UAC, the answer MUST be in the acknowledgement for that message (in this specification, ACK for a 2xx response).
- After having sent or received an answer to the first offer, the UAC MAY generate subsequent offers in requests based on rules specified for that method, but only if it has received answers to any previous offers, and has not sent any offers to which it hasn't gotten an answer.
- Once the UAS has sent or received an answer to the initial offer, it MUST NOT generate subsequent offers in any responses to the initial INVITE. This means that a UAS based on this specification alone can never generate subsequent offers until completion of the initial transaction.

Concretely, the above rules specify two exchanges for UAs compliant to this specification alone - the offer is in the INVITE, and the answer in the 2xx (and possibly in a 1xx as well, with the same value), or the offer is in the 2xx, and the answer is in the ACK. All user agents that support INVITE MUST support these two exchanges.

The Session Description Protocol (SDP) (RFC 2327 [1]) MUST be supported by all user agents as a means to describe sessions, and its usage for constructing offers and answers MUST follow the procedures defined in [13].

The restrictions of the offer-answer model just described only apply to bodies whose Content-Disposition header field value is "session". Therefore, it is possible that both the INVITE and the ACK contain a body message (for example, the INVITE carries a photo (Content-Disposition: render) and the ACK a session description (Content-Disposition: session)).

If the Content-Disposition header field is missing, bodies of Content-Type application/sdp imply the disposition "session", while other content types imply "render".

Once the INVITE has been created, the UAC follows the procedures defined for sending requests outside of a dialog (Section 8). This results in the construction of a client transaction that will ultimately send the request and deliver responses to the UAC.

#### 中文

由于初始 INVITE 代表对话外的请求，其构建遵循第 8.1.1 节的过程。对于 INVITE 的特殊情况需要额外的处理。

INVITE 中应该存在 Allow 头字段（第 20.5 节）。它指示在发送 INVITE 的 UA 上，在对话持续时间内可以在对话中调用哪些方法。例如，能够在对话中接收 INFO 请求的 UA [34] 应该包含一个列出 INFO 方法的 Allow 头字段。

INVITE 中应该存在 Supported 头字段（第 20.37 节）。它枚举了 UAC 理解的所有扩展。

INVITE 中可能存在 Accept（第 20.1 节）头字段。它指示 UA 可接受的 Content-Type，包括它接收的响应以及在 INVITE 建立的对话中发送给它的任何后续请求。Accept 头字段对于指示对各种会话描述格式的支持特别有用。

UAC 可以添加 Expires 头字段（第 20.19 节）来限制邀请的有效期。如果达到 Expires 头字段中指示的时间而未收到 INVITE 的最终答案，UAC 核心应该根据第 9 节为 INVITE 生成一个 CANCEL 请求。

UAC 还可以添加 Subject（第 20.36 节）、Organization（第 20.25 节）和 User-Agent（第 20.41 节）头字段，它们都包含与 INVITE 相关的信息。

UAC 可以选择向 INVITE 添加消息体。第 8.1.1.10 节处理如何构造描述消息体所需的头字段——包括 Content-Type 等。

对于包含会话描述的消息体有特殊规则——它们相应的 Content-Disposition 为 "session"。SIP 使用 offer/answer 模型，其中一个 UA 发送一个会话描述，称为 offer，其中包含提议的会话描述。offer 指示期望的通信方式（音频、视频、游戏）、这些方式的参数（如编解码器类型）以及用于从应答者接收媒体的地址。另一个 UA 用另一个会话描述（称为 answer）响应，指示接受哪些通信方式、适用于这些方式的参数以及用于从发起者接收媒体的地址。offer/answer 交换在对话的上下文中进行，因此如果 SIP INVITE 导致多个对话，每个都是一个单独的 offer/answer 交换。offer/answer 模型定义了关于何时可以发出 offer 和 answer 的限制（例如，当一个 offer 正在进行时，不能发出新的 offer）。这导致了对 offer 和 answer 可以出现在 SIP 消息中何处的限制。在本规范中，offer 和 answer 只能出现在 INVITE 请求和响应以及 ACK 中。offer 和 answer 的使用有进一步限制。对于初始 INVITE 事务，规则是：

- 初始 offer 必须在一个 INVITE 中，或者如果不在那里，则在 UAS 返回 UAC 的第一个可靠的非失败消息中。在本规范中，那是最终的 2xx 响应。
- 如果初始 offer 在 INVITE 中，则 answer 必须在 UAS 返回 UAC 的可靠非失败消息中，该消息与该 INVITE 相关联。对于本规范，那只是对该 INVITE 的最终 2xx 响应。同样的 answer 也可以放在 answer 之前发送的任何临时响应中。UAC 必须将其收到的第一个会话描述视为 answer，并且必须忽略对初始 INVITE 的后续响应中的任何会话描述。
- 如果初始 offer 在 UAS 返回 UAC 的第一个可靠非失败消息中，则 answer 必须在该消息的确认中（在本规范中，是对 2xx 响应的 ACK）。
- 在发送或收到第一个 offer 的 answer 后，UAC 可以根据为该方法指定的规则在请求中生成后续 offer，但前提是它已收到对任何先前 offer 的 answer，并且没有发送任何尚未获得 answer 的 offer。
- 一旦 UAS 发送或收到初始 offer 的 answer，它不得在初始 INVITE 的任何响应中生成后续 offer。这意味着仅基于本规范的 UAS 在初始事务完成之前永远不能生成后续 offer。

具体来说，上述规则为符合本规范的 UA 指定了两种交换——offer 在 INVITE 中，answer 在 2xx 中（也可能在 1xx 中，值相同），或者 offer 在 2xx 中，answer 在 ACK 中。所有支持 INVITE 的用户代理必须支持这两种交换。

会话描述协议 (SDP) (RFC 2327 [1]) 必须被所有用户代理支持作为描述会话的手段，其用于构造 offer 和 answer 的使用必须遵循 [13] 中定义的过程。

刚才描述的 offer-answer 模型的限制仅适用于 Content-Disposition 头字段值为 "session" 的消息体。因此，INVITE 和 ACK 都可能包含消息体（例如，INVITE 携带照片（Content-Disposition: render），ACK 携带会话描述（Content-Disposition: session））。

如果缺少 Content-Disposition 头字段，则 Content-Type 为 application/sdp 的消息体暗示配置为 "session"，而其他内容类型暗示 "render"。

一旦 INVITE 创建完成，UAC 遵循为在对话外发送请求定义的过程（第 8 节）。这导致构建一个客户端事务，该事务最终将发送请求并将响应传递给 UAC。

### 13.2.2 Processing INVITE Responses | 13.2.2 处理 INVITE 响应

#### 原文

Once the INVITE has been passed to the INVITE client transaction, the UAC waits for responses for the INVITE. If the INVITE client transaction returns a timeout rather than a response the TU acts as if a 408 (Request Timeout) response had been received, as described in Section 8.1.3.

#### 中文

一旦 INVITE 被传递给 INVITE 客户端事务，UAC 就等待 INVITE 的响应。如果 INVITE 客户端事务返回超时而不是响应，TU 会表现得好像收到了 408（请求超时）响应一样，如第 8.1.3 节中所述。

---

### 13.2.2.1 1xx Responses | 13.2.2.1 1xx 响应

#### 原文

If a provisional response was received before the transaction is in the "Completed" state, the TU moves to the "Proceeding" state. It is possible that it receives multiple 1xx responses. The TU should update the From tag if an SDP answer is present in the response.

#### 中文

如果在与事务进入"已完成"状态之前收到了临时响应，TU 移动到"进行中"状态。它可能收到多个 1xx 响应。如果响应中存在 SDP answer，TU 应该更新 From tag。

---

### 13.2.2.2 2xx Responses | 13.2.2.2 2xx 响应

#### 原文

If a 2xx response is received, the UAC core moves to the "Accepted" state. The 2xx response creates a dialog.

The UAC core MUST generate an ACK request for each 2xx response it receives. The ACK MUST be sent to the same address as the original request, not to the address in the Contact header field of the 2xx response (which is only valid for subsequent requests within the dialog).

The UAC core MUST peform the processing described in Section 12.2.1, using the values from the Contact header field of the response to set the dialog's remote target and route set.

#### 中文

如果收到 2xx 响应，UAC 核心移动到"已接受"状态。2xx 响应创建一个对话。

UAC 核心必须为它收到的每个 2xx 响应生成一个 ACK 请求。ACK 必须发送到与原始请求相同的地址，而不是 2xx 响应的 Contact 头字段中的地址（该地址仅对对话内的后续请求有效）。

UAC 核心必须执行第 12.2.1 节中描述的处理，使用响应中 Contact 头字段的值来设置对话的远程目标和路由集。

---

### 13.2.2.3 3xx-6xx Responses | 13.2.2.3 3xx-6xx 响应

#### 原文

If a 3xx-6xx response is received, the UAC core moves to the "Terminated" state. The response creates no dialog.

For 300-329 responses, the UAC core follows the processing described in Section 8.1.3.4, placing the URIs from the Contact header field into the target set. These URIs can then be tried in parallel or serially.

For 430, 480, 486, 487, 488, 491, 493, and 494 responses, the UAC core should not retry the request. For 408 and 503, the UAC core should retry at a later time.

For other 4xx, 5xx, and 6xx responses, the UAC core SHOULD NOT retry the request automatically. However, since 2xx responses are allowed to be received after a non-2xx final response, if the UAC core receives a 2xx response after having received a non-2xx final response, it moves to the "Accepted" state, generates an ACK, and establishes a dialog.

For ACK processing of non-2xx responses, see Section 17.1.1.3.

#### 中文

如果收到 3xx-6xx 响应，UAC 核心移动到"已终止"状态。该响应不创建对话。

对于 300-329 响应，UAC 核心遵循第 8.1.3.4 节中描述的处理，将 Contact 头字段中的 URI 放入目标集。然后可以并行或串行尝试这些 URI。

对于 430、480、486、487、488、491、493 和 494 响应，UAC 核心不应重试请求。对于 408 和 503，UAC 核心应该稍后重试。

对于其他 4xx、5xx 和 6xx 响应，UAC 核心不应该自动重试请求。但是，由于在非 2xx 最终响应之后允许接收 2xx 响应，如果 UAC 核心在收到非 2xx 最终响应后收到 2xx 响应，它会移动到"已接受"状态，生成 ACK，并建立对话。

有关非 2xx 响应的 ACK 处理，请参见第 17.1.1.3 节。

---

### 13.3 UAS Processing | 13.3 UAS 处理

### 13.3.1 Overview of INVITE Handling | 13.3.1 INVITE 处理概述

#### 原文

When a UAS receives an INVITE request, it checks if it has been invited to the session before (dialog-match). If so, it processes the request as a mid-dialog request, as described in Section 12.2.2. If not, it processes the request as a new session invitation.

#### 中文

当 UAS 收到 INVITE 请求时，它检查是否已被邀请加入该会话（对话匹配）。如果是，它会将对请求作为对话中请求处理，如第 12.2.2 节中所述。如果不是，它会将请求作为新会话邀请处理。

---

### 13.3.2 Resource Priority | 13.3.2 资源优先级

#### 原文

If the Request-URI or the Contact header field contains a resource priority flag [35], the UAS SHOULD determine the priority of the session based on this value. If no priority is indicated, the session has a priority of "normal".

A UAS that does not understand the resource priority flag class of the header field value MUST ignore it and process the session as having normal priority.

#### 中文

如果 Request-URI 或 Contact 头字段包含资源优先级标志 [35]，UAS 应该根据此值确定会话的优先级。如果没有指示优先级，则会话的优先级为"正常"。

不理解头字段值资源优先级标志类的 UAS 必须忽略它，并将会话作为正常优先级处理。

---

### 13.3.3 Processing the INVITE | 13.3.3 处理 INVITE

#### 原文

The UAS MUST process the INVITE request as follows:

1. The UAS MUST validate the request (Section 8.2.1).
2. The UAS SHOULD check if the session description is acceptable. If not, it MUST generate an appropriate 4xx response.
3. The UAS SHOULD check if the user is busy. If so, it MUST generate a 486 (Busy Here) response.
4. The UAS can accept the invitation by sending a 2xx response. The UAS SHOULD delay the 2xx response until the user has been alerted, unless the INVITE request contains an indication that an early session description is desired.
5. The UAS can reject the invitation by sending a 4xx response (or a 3xx, 5xx, or 6xx response). If the INVITE request contains an offer, and the UAS rejects the invitation with a response that is not a 2xx, the UAS MUST NOT generate an answer.
6. The UAS can redirect the invitation by sending a 3xx response.

#### 中文

UAS 必须按如下方式处理 INVITE 请求：

1. UAS 必须验证请求（第 8.2.1 节）。
2. UAS 应该检查会话描述是否可接受。如果不可接受，它必须生成适当的 4xx 响应。
3. UAS 应该检查用户是否忙。如果忙，它必须生成 486（这里忙）响应。
4. UAS 可以通过发送 2xx 响应来接受邀请。除非 INVITE 请求包含需要早期会话描述的指示，否则 UAS 应该延迟 2xx 响应直到用户已收到警报。
5. UAS 可以通过发送 4xx 响应（或 3xx、5xx 或 6xx 响应）来拒绝邀请。如果 INVITE 请求包含 offer，且 UAS 用非 2xx 的响应拒绝邀请，则 UAS 不得生成 answer。
6. UAS 可以通过发送 3xx 响应来重定向邀请。

---

### 13.3.4 Generating the Response | 13.3.4 生成响应

#### 原文

The UAS MUST add a tag to the To header field (if not present in the request) in any response to the INVITE (including 100 Trying). The tag MUST be unique across all 2xx responses sent by this UAS within this dialog.

If the INVITE contains an offer, and the UAS generates a 2xx response, the answer MUST be in the 2xx response.

If the INVITE does not contain an offer, the UAS MUST generate an offer in the 2xx response, and the answer MUST be in the ACK.

#### 中文

UAS 必须在任何对 INVITE 的响应（包括 100 Trying）中向 To 头字段添加一个 tag（如果请求中不存在）。在此对话中，此 UAS 发送的所有 2xx 响应中，tag 必须唯一。

如果 INVITE 包含 offer，且 UAS 生成 2xx 响应，则 answer 必须在 2xx 响应中。

如果 INVITE 不包含 offer，UAS 必须在 2xx 响应中生成 offer，且 answer 必须在 ACK 中。

---

## 14. Modifying an Existing Session | 14. 修改现有会话

#### 原文

A successful INVITE request (that results in a 2xx response) establishes both a dialog and a session. The session can be modified by sending a new INVITE request within the dialog (called a re-INVITE). A re-INVITE is like an INVITE, except:

- It is sent within an existing dialog.
- Its Request-URI is taken from the remote target of the dialog.
- It does not establish a dialog, only modifies the session.
- Its CSeq sequence number is higher than any previous CSeq within the dialog.
- It does not change the route set.

The UAC SHOULD add a Supported header field listing the option tags for extensions the UAC supports.

The UAC MAY add a Contact header field. If added, it contains the URI at which the UA would like to receive requests.

If the UAC wishes to modify the session parameters, it can send a re-INVITE containing a new offer.

If the UAS receives a re-INVITE, it can accept it by sending a 2xx response with an answer, or reject it by sending an error response.

If the re-INVITE is accepted, the UAS MUST update the dialog's remote target to the Contact header field in the response.

#### 中文

成功的 INVITE 请求（导致 2xx 响应）同时建立了一个对话和一个会话。可以通过在对话中发送新的 INVITE 请求（称为 re-INVITE）来修改会话。re-INVITE 类似于 INVITE，不同之处在于：

- 它在现有对话内发送。
- 它的 Request-URI 取自对话的远程目标。
- 它不建立对话，只修改会话。
- 它的 CSeq 序列号高于对话中任何先前的 CSeq。
- 它不改变路由集。

UAC 应该添加一个 Supported 头字段，列出 UAC 支持的扩展的选项标签。

UAC 可以添加 Contact 头字段。如果添加，它包含 UA 希望接收请求的 URI。

如果 UAC 希望修改会话参数，它可以发送包含新 offer 的 re-INVITE。

如果 UAS 收到 re-INVITE，它可以通过发送带有 answer 的 2xx 响应来接受它，或通过发送错误响应来拒绝它。

如果 re-INVITE 被接受，UAS 必须将对话的远程目标更新为响应中的 Contact 头字段。

---

## 15. Terminating a Session | 15. 终止会话

#### 原文

Sessions can be terminated at any time by sending a BYE request. A BYE request MUST only be sent by a UAC on a dialog that was established by an INVITE request. The callee MUST NOT send a BYE to the caller before having sent a 2xx response for the INVITE.

A 2xx response to a BYE request terminates the session and the dialog. If the BYE request is never answered (because it reached a UAS that didn't send a response), the client transaction will timeout, which is also considered a 2xx response for the purposes of terminating the session.

A UAS that receives a BYE request MUST confirm that it is part of an existing dialog. If no dialog matches, the UAS MUST respond with 481 (Call/Transaction Does Not Exist).

A UAS MUST NOT send a BYE to the caller before having received the initial INVITE. This allows a caller to send a BYE to a callee that has not yet responded.

#### 中文

会话可以随时通过发送 BYE 请求来终止。BYE 请求只能由在由 INVITE 请求建立的对话上的 UAC 发送。被叫人在发送 INVITE 的 2xx 响应之前不得向主叫人发送 BYE。

对 BYE 请求的 2xx 响应终止会话和对话。如果 BYE 请求永远得不到回答（因为它到达了没有发送响应的 UAS），客户端事务将超时，这也被视为终止会话的 2xx 响应。

收到 BYE 请求的 UAS 必须确认它是现有对话的一部分。如果没有对话匹配，UAS 必须响应 481（呼叫/事务不存在）。

UAS 在收到初始 INVITE 之前不得向主叫人发送 BYE。这允许主叫人向尚未响应的被叫人发送 BYE。

---

## 16. Proxy Behavior | 16. 代理行为

### 16.1 Overview | 16.1 概述

#### 原文

SIP proxies are elements that route SIP requests to user agent servers and SIP responses to user agent clients. A request may traverse several proxies on its way to a UAS. Each will make routing decisions, modifying the request before forwarding it to the next element. Responses will route through the same set of proxies traversed by the request in the reverse order.

Being a proxy is a logical role for a SIP element. When a request arrives, an element that can play the role of a proxy first decides if it needs to respond to the request on its own. For instance, the request may be malformed or the element may need credentials from the client before acting as a proxy. The element MAY respond with any appropriate error code. When responding directly to a request, the element is playing the role of a UAS and MUST behave as described in Section 8.2.

A proxy can operate in either a stateful or stateless mode for each new request. When stateless, a proxy acts as a simple forwarding element. It forwards each request downstream to a single element determined by making a targeting and routing decision based on the request. It simply forwards every response it receives upstream. A stateless proxy discards information about a message once the message has been forwarded. A stateful proxy remembers information (specifically, transaction state) about each incoming request and any requests it sends as a result of processing the incoming request. It uses this information to affect the processing of future messages associated with that request. A stateful proxy MAY choose to "fork" a request, routing it to multiple destinations. Any request that is forwarded to more than one location MUST be handled statefully.

In some circumstances, a proxy MAY forward requests using stateful transports (such as TCP) without being transaction-stateful. For instance, a proxy MAY forward a request from one TCP connection to another transaction statelessly as long as it places enough information in the message to be able to forward the response down the same connection the request arrived on. Requests forwarded between different types of transports where the proxy's TU must take an active role in ensuring reliable delivery on one of the transports MUST be forwarded transaction statefully.

A stateful proxy MAY transition to stateless operation at any time during the processing of a request, so long as it did not do anything that would otherwise prevent it from being stateless initially (forking, for example, or generation of a 100 response). When performing such a transition, all state is simply discarded. The proxy SHOULD NOT initiate a CANCEL request.

Much of the processing involved when acting statelessly or statefully for a request is identical. The next several subsections are written from the point of view of a stateful proxy. The last section calls out those places where a stateless proxy behaves differently.

#### 中文

SIP 代理是向用户代理服务器路由 SIP 请求并向用户代理客户端路由 SIP 响应的元素。请求在到达 UAS 的过程中可能经过多个代理。每个代理都会做出路由决策，在转发给下一个元素之前修改请求。响应将按与请求相反的顺序经过同一组代理。

作为代理是 SIP 元素的逻辑角色。当请求到达时，能够扮演代理角色的元素首先决定是否需要自行响应请求。例如，请求可能格式不正确，或者元素可能需要从客户端获取凭证才能作为代理。元素可以用任何适当的错误码响应。当直接响应请求时，该元素扮演的是 UAS 角色，必须按照第 8.2 节中的描述行事。

代理可以为每个新请求以有状态或无状态模式运行。当无状态时，代理充当简单的转发元素。它根据请求做出定位和路由决策，将每个请求向下游转发到单个元素。它只是将收到的每个响应向上游转发。无状态代理在消息被转发后立即丢弃关于该消息的信息。有状态代理记住有关每个传入请求的信息（具体来说是事务状态）以及由于处理传入请求而发送的任何请求的信息。它使用这些信息来影响与该请求相关联的将来消息的处理。有状态代理可以选择"分叉"请求，将其路由到多个目的地。转发到多个位置的任何请求必须以有状态方式处理。

在某些情况下，代理可以使用有状态传输（如 TCP）转发请求而不必是事务有状态的。例如，代理可以事务无状态地将请求从一个 TCP 连接转发到另一个 TCP 连接，只要它在消息中放置足够的信息以便能够将响应沿着请求到达的同一连接向下转发。在不同类型的传输之间转发的请求（其中代理的 TU 必须主动确保其中一个传输的可靠传递）必须以事务有状态的方式转发。

有状态代理可以在处理请求期间的任何时候转换到无状态操作，只要它没有做任何会阻止其最初成为无状态的事情（例如分叉，或生成 100 响应）。执行此类转换时，所有状态都会被简单地丢弃。代理不应该发起 CANCEL 请求。

在有状态或无状态处理请求时，涉及的大部分处理是相同的。以下几个小节是从有状态代理的角度编写的。最后一节指出了无状态代理行为不同的地方。

### 16.2 Stateful Proxy | 16.2 有状态代理

#### 原文

When stateful, a proxy is purely a SIP transaction processing engine. Its behavior is modeled here in terms of the server and client transactions defined in Section 17. A stateful proxy has a server transaction associated with one or more client transactions by a higher layer proxy processing component (known as a proxy core). An incoming request is processed by a server transaction. Requests from the server transaction are passed to a proxy core. The proxy core determines where to route the request, choosing one or more next-hop locations. An outgoing request for each next-hop location is processed by its own associated client transaction. The proxy core collects the responses from the client transactions and uses them to send responses to the server transaction.

A stateful proxy creates a new server transaction for each new request received. Any retransmissions of the request will then be handled by that server transaction per Section 17. The proxy core MUST behave as a UAS with respect to sending an immediate provisional on that server transaction (such as 100 Trying) as described in Section 8.2.6. Thus, a stateful proxy SHOULD NOT generate 100 (Trying) responses to non-INVITE requests.

This is a model of proxy behavior, not of software. An implementation is free to take any approach that replicates the external behavior this model defines.

For all new requests, including any with unknown methods, an element intending to proxy the request MUST:

1. Validate the request (Section 16.3)
2. Preprocess routing information (Section 16.4)
3. Determine target(s) for the request (Section 16.5)
4. Forward the request to each target (Section 16.6)
5. Process all responses (Section 16.7)

#### 中文

当有状态时，代理纯粹是一个 SIP 事务处理引擎。其行为在此根据第 17 节中定义的服务器和客户端事务来建模。有状态代理有一个服务器事务，通过更高级别的代理处理组件（称为代理核心）与一个或多个客户端事务相关联。传入请求由服务器事务处理。来自服务器事务的请求被传递给代理核心。代理核心决定将请求路由到哪里，选择一个或多个下一跳位置。为每个下一跳位置发出的传出请求由其自己关联的客户端事务处理。代理核心收集来自客户端事务的响应，并使用它们向服务器事务发送响应。

有状态代理为每个收到的请求创建一个新的服务器事务。然后，根据第 17 节，该服务器事务处理该请求的任何重传。代理核心在向该服务器事务发送即时临时响应（如 100 Trying）方面必须表现得像 UAS，如第 8.2.6 节所述。因此，有状态代理不应该为非 INVITE 请求生成 100（正在尝试）响应。

这是代理行为模型，而非软件模型。实现可以自由采用任何能复制此模型定义的外部行为的方法。

对于所有新请求，包括任何具有未知方法的请求，打算代理该请求的元素必须：

1. 验证请求（第 16.3 节）
2. 预处理路由信息（第 16.4 节）
3. 确定请求的目标（第 16.5 节）
4. 将请求转发到每个目标（第 16.6 节）
5. 处理所有响应（第 16.7 节）

### 16.3 Request Validation | 16.3 请求验证

#### 原文

Before an element can proxy a request, it MUST verify the message's validity. A valid message must pass the following checks:

1. Reasonable Syntax
2. URI scheme
3. Max-Forwards
4. (Optional) Loop Detection
5. Proxy-Require
6. Proxy-Authorization

If any of these checks fail, the element MUST behave as a user agent server (see Section 8.2) and respond with an error code.

Notice that a proxy is not required to detect merged requests and MUST NOT treat merged requests as an error condition. The endpoints receiving the requests will resolve the merge as described in Section 8.2.2.2.

**1. Reasonable syntax check**

The request MUST be well-formed enough to be handled with a server transaction. Any components involved in the remainder of these Request Validation steps or the Request Forwarding section MUST be well-formed. Any other components, well-formed or not, SHOULD be ignored and remain unchanged when the message is forwarded. For instance, an element would not reject a request because of a malformed Date header field. Likewise, a proxy would not remove a malformed Date header field before forwarding a request.

This protocol is designed to be extended. Future extensions may define new methods and header fields at any time. An element MUST NOT refuse to proxy a request because it contains a method or header field it does not know about.

**2. URI scheme check**

If the Request-URI has a URI whose scheme is not understood by the proxy, the proxy SHOULD reject the request with a 416 (Unsupported URI Scheme) response.

**3. Max-Forwards check**

If the Max-Forwards header field is present in the request and contains an integer value of zero, the proxy MUST NOT forward the request. Instead, it MUST respond with 483 (Too Many Hops). If the Max-Forwards header field is present with a value of zero, it MUST be removed before forwarding.

If the Max-Forwards header field is not present, the proxy MUST add it with a value that SHOULD be 70.

**4. (Optional) Loop Detection**

The proxy MAY check for loops. If a loop is detected, the proxy MUST respond with 482 (Loop Detected).

**5. Proxy-Require**

The proxy MUST check the Proxy-Require header field for any option tags it does not understand. If there are any, the proxy MUST respond with 420 (Bad Extension) and include an Unsupported header field listing the unsupported options.

**6. Proxy-Authorization**

If the request does not contain a Proxy-Authorization header field, the proxy MAY challenge the request by responding with 407 (Proxy Authentication Required). The proxy MUST follow the processing described in Section 22 for authentication.

#### 中文

在元素可以代理请求之前，它必须验证消息的有效性。有效消息必须通过以下检查：

1. 合理语法
2. URI 方案
3. Max-Forwards
4. （可选）循环检测
5. Proxy-Require
6. Proxy-Authorization

如果任何检查失败，元素必须表现得像用户代理服务器（参见第 8.2 节）并用错误码响应。

请注意，代理不需要检测合并请求，也不得将合并请求视为错误条件。接收请求的端点将按照第 8.2.2.2 节中所述解决合并。

**1. 合理语法检查**

请求必须格式正确，足以由服务器事务处理。这些请求验证步骤的其余部分或请求转发部分所涉及的任何组件必须是格式正确的。任何其他组件，无论格式正确与否，都应该在消息被转发时被忽略并保持不变。例如，元素不会因为格式不正确的 Date 头字段而拒绝请求。同样，代理在转发请求之前不会删除格式不正确的 Date 头字段。

本协议设计为可扩展的。未来的扩展可以随时定义新的方法和头字段。元素不得因为请求包含它不知道的方法或头字段而拒绝代理该请求。

**2. URI 方案检查**

如果 Request-URI 包含代理不理解的 URI 方案，代理应该用 416（不支持的 URI 方案）响应拒绝请求。

**3. Max-Forwards 检查**

如果请求中存在 Max-Forwards 头字段且其整数值为零，代理不得转发请求。相反，它必须用 483（太多跳）响应。如果 Max-Forwards 头字段存在且值为零，则在转发之前必须将其删除。

如果不存在 Max-Forwards 头字段，代理必须添加它，其值应为 70。

**4.（可选）循环检测**

代理可以检查循环。如果检测到循环，代理必须用 482（检测到循环）响应。

**5. Proxy-Require**

代理必须检查 Proxy-Require 头字段中是否有任何他不理解的选项标签。如果有，代理必须用 420（错误扩展）响应，并包含一个 Unsupported 头字段，列出不支持的选项。

**6. Proxy-Authorization**

如果请求不包含 Proxy-Authorization 头字段，代理可以质询请求，方法是响应 407（需要代理认证）。代理必须遵循第 22 节中描述的认证处理。

## 17. Transactions | 17. 事务

#### 原文

SIP is a transactional protocol. Interactions between components take place in a series of independent message exchanges. The most important exchange is the transaction.

A transaction is a request sent from a client to a server, along with all responses to that request sent from the server back to the client. A transaction is identified by the branch parameter in the Via header field and the method. The branch parameter identifies the transaction, and the method is used to differentiate transactions between the same client and server.

For INVITE transactions, there is an ACK for non-2xx responses. However, the ACK is considered a separate transaction from the INVITE transaction it acknowledges.

All SIP elements, except the stateless proxy, are transaction users. The transaction user creates client transactions to send requests and absorbs responses. The transaction user is also the generator of the request.

#### 中文

SIP 是一种事务性协议。组件之间的交互以一系列独立的消息交换进行。最重要的是事务。

事务是从客户端发送到服务器的请求，以及从服务器发送回客户端的该请求的所有响应。事务由 Via 头字段中的 branch 参数和 method 标识。branch 参数标识事务，method 用于区分同一客户端和服务器之间的事务。

对于 INVITE 事务，对于非 2xx 响应有一个 ACK。但是，ACK 被视为与其确认的 INVITE 事务分开的事务。

除无状态代理外，所有 SIP 元素都是事务用户。事务用户创建客户端事务来发送请求并吸收响应。事务用户也是请求的生成者。

## 18. Transport | 18. 传输

#### 原文

The transport layer is responsible for transmitting messages between client and server. SIP can be run over any transport protocol that can guarantee that its messages are delivered in the order in which they were sent.

All SIP implementations MUST support UDP (Section 18.1), but MAY also support other transport protocols.

When choosing a transport protocol, implementations MUST prefer TCP over UDP when SIP is used for messages larger than the MTU. For reliability, all implementations MUST support TCP.

If a SIP server is contacted using a transport protocol other than TLS, it MUST reject the request if it contains a SIPS URI in the Request-URI.

All SIP elements MUST support sending and receiving UDP messages. UDP is unreliable, so implementations MUST implement the following features:

- Retransmission behavior (Section 18.1.1)
- Parsing rules (Section 18.1.2)
- Framed messages (Section 18.1.3)

#### 中文

传输层负责在客户端和服务器之间传输消息。SIP 可以在任何能够保证消息按发送顺序传递的传输协议上运行。

所有 SIP 实现必须支持 UDP（第 18.1 节），但也可以支持其他传输协议。

选择传输协议时，当 SIP 用于大于 MTU 的消息时，实现必须优先选择 TCP 而不是 UDP。为了可靠性，所有实现必须支持 TCP。

如果使用 TLS 以外的传输协议联系 SIP 服务器，如果请求的 Request-URI 中包含 SIPS URI，则必须拒绝该请求。

所有 SIP 元素必须支持发送和接收 UDP 消息。UDP 是不可靠的，因此实现必须实现以下功能：

- 重传行为（第 18.1.1 节）
- 解析规则（第 18.1.2 节）
- 分帧消息（第 18.1.3 节）

## 19. Common Message Components | 19. 通用消息组件

### 19.1 SIP and SIPS URI Components | 19.1 SIP 和 SIPS URI 组件

#### 原文

A SIP URI follows the general URI syntax defined in RFC 2396. It identifies a communications resource, such as a user, and is used in requests and To/From header fields.

The SIP URI scheme is "sip:" and the SIPS URI scheme is "sips:". These schemes are used for routing SIP messages and are similar to HTTP URLs.

A SIP URI contains:
- User part (optional)
- Host part (required)
- Port number (optional)
- Header field parameters
- Transport parameters

Examples:
```
sip:alice@atlanta.com
sip:alice:secretword@atlanta.com;transport=tcp
sips:alice@atlanta.com?subject=project%20meeting
```

#### 中文

SIP URI 遵循 RFC 2396 中定义的通用 URI 语法。它标识通信资源（如用户），并用于请求和 To/From 头字段。

SIP URI 方案是 "sip:"，SIPS URI 方案是 "sips:"。这些方案用于路由 SIP 消息，类似于 HTTP URL。

SIP URI 包含：
- 用户部分（可选）
- 主机部分（必需）
- 端口号（可选）
- 头字段参数
- 传输参数

示例：
```
sip:alice@atlanta.com
sip:alice:secretword@atlanta.com;transport=tcp
sips:alice@atlanta.com?subject=project%20meeting
```

### 19.2 Option Tags | 19.2 选项标签

#### 原文

Option tags are used in Require and Supported header fields to indicate required or supported SIP extensions. An option tag is a string identifying a SIP extension.

Option tags are case-insensitive.

When a UAC includes a Require header field, it is indicating that the UAS must understand the extension for it to process the request successfully.

When a UAC includes a Supported header field, it is indicating that the UAS may understand the extension but it is not required.

#### 中文

选项标签在 Require 和 Supported 头字段中使用，用于指示必需或支持的 SIP 扩展。选项标签是标识 SIP 扩展的字符串。

选项标签不区分大小写。

当 UAC 包含 Require 头字段时，表示 UAS 必须理解该扩展才能成功处理请求。

当 UAC 包含 Supported 头字段时，表示 UAS 可能理解该扩展，但不是必需的。

### 19.3 Tags | 19.3 标签

#### 原文

Tags are a key part of SIP request and response header fields. They are used to identify participants in a dialog and to help with call routing.

A tag is a string that is inserted into the To and From header fields of SIP requests and responses. The tag in the From header field is chosen by the UAC, and the tag in the To header field is chosen by the UAS.

Tags are used to:
- Identify the two participants in a dialog
- Help with loop detection
- Assist in forking scenarios

The tag parameter is case-insensitive and MUST be globally unique.

#### 中文

标签是 SIP 请求和响应头字段的关键部分。它们用于识别对话中的参与者并帮助呼叫路由。

标签是插入到 SIP 请求和响应的 To 和 From 头字段中的字符串。From 头字段中的 tag 由 UAC 选择，To 头字段中的 tag 由 UAS 选择。

标签用于：
- 识别对话中的两个参与者
- 帮助循环检测
- 协助分叉场景

tag 参数不区分大小写，必须全局唯一。

## 20. Header Fields | 20. 头字段

### 20.1 Overview | 20.1 概述

#### 原文

The general syntax for header fields is covered in Section 7.3. This section lists the full set of header fields along with notes on syntax, meaning, and usage.

The "where" column describes the request and response types in which the header field can be used:

- **R**: header field may only appear in requests
- **r**: header field may only appear in responses
- **2xx, 4xx, etc.**: A numerical value or range indicates response codes with which the header field can be used
- **c**: header field is copied from the request to the response
- An empty entry indicates that the header field may be present in all requests and responses

The "proxy" column describes the operations a proxy may perform on a header field:

- **a**: A proxy can add or concatenate the header field if not present
- **m**: A proxy can modify an existing header field value
- **d**: A proxy can delete a header field value
- **r**: A proxy must be able to read the header field, and thus this header field cannot be encrypted

#### 中文

第 7.3 节介绍了头字段的一般语法。本节列出完整的头字段集以及关于语法、含义和用法的说明。

"where" 列描述了头字段可以使用的请求和响应类型：

- **R**：头字段只能出现在请求中
- **r**：头字段只能出现在响应中
- **2xx, 4xx 等**：数值或范围表示头字段可以使用的响应码
- **c**：头字段从请求复制到响应
- 空条目表示头字段可以出现在所有请求和响应中

"proxy" 列描述了代理可以对头字段执行的操作：

- **a**：如果不存在，代理可以添加或连接头字段
- **m**：代理可以修改现有头字段值
- **d**：代理可以删除头字段值
- **r**：代理必须能够读取头字段，因此此头字段不能被加密

### 20.2 Common Header Fields | 20.2 常见头字段

#### 原文

Contact, From, and To header fields contain a URI. If the URI contains a comma, question mark or semicolon, the URI MUST be enclosed in angle brackets (< and >). Any URI parameters are contained within these brackets. If the URI is not enclosed in angle brackets, any semicolon-delimited parameters are header-parameters, not URI parameters.

#### 中文

Contact、From 和 To 头字段包含一个 URI。如果 URI 包含逗号、问号或分号，URI 必须用尖括号（< 和 >）括起。任何 URI 参数都包含在这些括号内。如果 URI 没有用尖括号括起，任何以分号分隔的参数都是 header-parameters，而不是 URI 参数。

## 22. Usage of HTTP Authentication | 22. HTTP 认证的使用

#### 原文

SIP provides a challenge-response authentication mechanism similar to HTTP. When a UAS or proxy receives a request that requires authentication, it challenges the request with a 401 or 407 response containing authentication credentials.

The authentication mechanism uses the WWW-Authenticate and Authorization header fields for UAS authentication, and Proxy-Authenticate and Proxy-Authorization for proxy authentication.

SIP supports both digest and basic authentication schemes, but digest authentication is RECOMMENDED for security reasons.

#### 中文

SIP 提供了类似于 HTTP 的质询-响应认证机制。当 UAS 或代理收到需要认证的请求时，它会用包含认证凭证的 401 或 407 响应来质询请求。

认证机制对 UAS 认证使用 WWW-Authenticate 和 Authorization 头字段，对代理认证使用 Proxy-Authenticate 和 Proxy-Authorization 头字段。

SIP 支持摘要和基本认证方案，但出于安全原因，建议使用摘要认证。

## 23. S/MIME | 23. S/MIME

#### 原文

SIP messages can carry MIME bodies. SIP uses S/MIME to provide integrity and confidentiality for message bodies and to enable end-to-end encryption.

S/MIME provides:
- Message integrity through digital signatures
- Confidentiality through encryption
- Sender authentication

#### 中文

SIP 消息可以携带 MIME 消息体。SIP 使用 S/MIME 为消息体提供完整性和机密性，并实现端到端加密。

S/MIME 提供：
- 通过数字签名的消息完整性
- 通过加密实现机密性
- 发送者认证

## 25. Augmented BNF for the SIP Protocol | 25. SIP 协议的扩展 BNF

#### 原文

SIP uses an augmented Backus-Naur Form (BNF) grammar for its message syntax. The base grammar is defined in RFC 2234.

Key elements of the SIP grammar:
- Request-Line: Method SP Request-URI SP SIP-Version CRLF
- Status-Line: SIP-Version SP Status-Code SP Reason-Phrase CRLF
- SIP-URI: "sip:" [userinfo "@"] hostport uri-parameters ["?" headers]
- SIPS-URI: "sips:" [userinfo "@"] hostport uri-parameters ["?" headers]
- Via: "Via:" SP sent-protocol SP sent-by *( ";" via-params )

#### 中文

SIP 使用扩展的巴科斯-诺尔范式 (BNF) 语法来定义其消息语法。基础语法在 RFC 2234 中定义。

SIP 语法的关键元素：
- Request-Line: Method SP Request-URI SP SIP-Version CRLF
- Status-Line: SIP-Version SP Status-Code SP Reason-Phrase CRLF
- SIP-URI: "sip:" [userinfo "@"] hostport uri-parameters ["?" headers]
- SIPS-URI: "sips:" [userinfo "@"] hostport uri-parameters ["?" headers]
- Via: "Via:" SP sent-protocol SP sent-by *( ";" via-params )

## 26. Security Considerations | 26. 安全考虑

#### 原文

SIP presents several security challenges. These include:

1. **Authentication**: SIP provides digest authentication similar to HTTP, but this only provides replay protection, not integrity.

2. **Confidentiality**: S/MIME provides end-to-end encryption of message bodies, but headers remain visible.

3. **Integrity**: Digital signatures can provide message integrity, but require PKI infrastructure.

4. **Denial of Service**: SIP proxies can be vulnerable to flooding attacks, malformed requests, and loop attacks.

5. **Privacy**: Headers like From and Contact can reveal user identity. Anonymous calls can hide this information.

#### 中文

SIP 带来了一些安全挑战。这些包括：

1. **认证**：SIP 提供类似于 HTTP 的摘要认证，但这只提供重放保护，而不是完整性。

2. **机密性**：S/MIME 提供消息体的端到端加密，但头字段仍然可见。

3. **完整性**：数字签名可以提供消息完整性，但需要 PKI 基础设施。

4. **拒绝服务**：SIP 代理可能容易受到泛洪攻击、格式错误的请求和循环攻击。

5. **隐私**：From 和 Contact 等头字段可能泄露用户身份。匿名呼叫可以隐藏此信息。

## 28. Changes From RFC 2543 | 28. RFC 2543 的变更

#### 原文

RFC 3261 obsoletes RFC 2543. Major changes include:

1. **Transaction Layer**: Separated from the transaction user, enabling proper timeout handling.

2. **Huge Header Changes**: Via branch parameter must begin with "z9hG4bK" magic cookie.

3. **Authentication**: Proxy-Authenticate and Proxy-Authorization added.

4. **OPTIONS**: Allow header field required in response.

5. **INVITE**: ACK for non-2xx is handled by transaction layer, 2xx ACK by UAC core.

6. **URI Requirements**: SIP URI scheme now required, SIPS URI scheme added.

7. **Record-Route**: Always copied to all downstream 2xx responses.

8. **Proxies**: Stateful proxy behavior more clearly specified.

9. **Dialog**: Tag in response required, establishing dialog properly.

#### 中文

RFC 3261 废弃了 RFC 2543。主要变更包括：

1. **事务层**：从事务用户中分离出来，实现适当的超时处理。

2. **大量头字段变更**：Via branch 参数必须以 "z9hG4bK" magic cookie 开头。

3. **认证**：添加了 Proxy-Authenticate 和 Proxy-Authorization。

4. **OPTIONS**：响应中需要 Allow 头字段。

5. **INVITE**：非 2xx 的 ACK 由事务层处理，2xx 的 ACK 由 UAC 核心处理。

6. **URI 要求**：现在需要 SIP URI 方案，添加了 SIPS URI 方案。

7. **Record-Route**：始终复制到所有下游 2xx 响应。

8. **代理**：有状态代理行为更加明确。

9. **对话**：响应中需要 tag，正确建立对话。
