## Abstract | 摘要

This document describes a protocol for Network Address Translator (NAT) traversal for UDP-based communication. This protocol is called Interactive Connectivity Establishment (ICE). ICE makes use of the Session Traversal Utilities for NAT (STUN) protocol and its extension, Traversal Using Relay NAT (TURN).

本文档描述了一种用于基于UDP通信的网络地址转换器 (NAT) 穿越协议。该协议称为交互式连接建立 (ICE)。ICE 利用 NAT 会话遍历实用工具 (STUN) 协议及其扩展——NAT 中继遍历 (TURN)。

This document obsoletes [RFC 5245](./rfc5245).
本文档废弃了 [RFC 5245](./rfc5245)。

# 1. Introduction | 1. 引言

Protocols establishing communication sessions between peers typically involve exchanging IP addresses and ports for the data sources and sinks. However, this poses challenges when operated through Network Address Translators (NATs) [[RFC3235](./rfc3235 "\"Network Address Translator (NAT)-Friendly Application Design Guidelines\"")]. These protocols also seek to create a data flow directly between participants, so that there is no application-layer intermediary between them. This is done to reduce data latency, decrease packet loss, and reduce the operational costs of deploying the application. However, this is difficult to accomplish through NATs. A full treatment of the reasons for this is beyond the scope of this specification.

在对等端之间建立通信会话的协议通常涉及交换数据源和接收器的 IP 地址和端口。然而，当通过网络安全地址转换器 (NAT) [[RFC3235](./rfc3235 "\"Network Address Translator (NAT)-Friendly Application Design Guidelines\"")] 进行操作时，这会带来挑战。这些协议还试图在对等方之间直接创建数据流，从而在对等方之间不存在应用层中介。这样做是为了减少数据延迟、降低数据包丢失并降低部署应用程序的运营成本。然而，这很难通过 NAT 实现。完整论述其原因超出了本规范的范围。

Numerous solutions have been defined for allowing these protocols to operate through NATs. These include Application Layer Gateways (ALGs), the Middlebox Control Protocol [[RFC3303](./rfc3303 "\"Middlebox communication architecture and framework\"")], the original Simple Traversal of UDP Through NAT (STUN) specification [[RFC3489](./rfc3489 "\"STUN - Simple Traversal of User Datagram Protocol (UDP) Through Network Address Translators (NATs)\"")] (note that [RFC 3489](./rfc3489) has been obsoleted by [RFC 5389](./rfc5389)), and Realm Specific IP [[RFC3102](./rfc3102 "\"Realm Specific IP: Framework\"")] [[RFC3103](./rfc3103 "\"Realm Specific IP: Protocol Specification\"")] along with session description extensions needed to make them work, such as the Session Description Protocol (SDP) attribute [[RFC4566](./rfc4566 "\"SDP: Session Description Protocol\"")] for the Real-Time Control Protocol (RTCP) [[RFC3605](./rfc3605 "\"Real Time Control Protocol (RTCP) attribute in Session Description Protocol (SDP)\"")]. Unfortunately, these techniques all have pros and cons that make each one optimal in some network topologies, but a poor choice in others. The result is that administrators and implementers are making assumptions about the topologies of the networks in which their solutions will be deployed. This introduces complexity and brittleness into the system.

已经为允许这些协议通过 NAT 运行定义了多种解决方案。这些包括应用层网关 (ALG)、中继盒控制协议 [[RFC3303](./rfc3303 "\"Middlebox communication architecture and framework\"")]、原始的 UDP 穿越 NAT 简单遍历 (STUN) 规范 [[RFC3489](./rfc3489 "\"STUN - Simple Traversal of User Datagram Protocol (UDP) Through Network Address Translators (NATs)\"")]（请注意，[RFC 3489](./rfc3489) 已被 [RFC 5389](./rfc5389) 废弃）、以及领域特定 IP [[RFC3102](./rfc3102 "\"Realm Specific IP: Framework\"")] [[RFC3103](./rfc3103 "\"Realm Specific IP: Protocol Specification\"")] 以及使它们正常工作所需的会话描述扩展，例如实时控制协议 (RTCP) [[RFC3605](./rfc3605 "\"Real Time Control Protocol (RTCP) attribute in Session Description Protocol (SDP)\"")] 的会话描述协议 (SDP) 属性 [[RFC4566](./rfc4566 "\"SDP: Session Description Protocol\"")]。遗憾的是，这些技术都有各自的优缺点，使得每种技术在某些网络拓扑中是最佳的，但在其他拓扑中却是糟糕的选择。其结果是管理员和实现者对他们将部署解决方案的网络拓扑做出假设。这给系统引入了复杂性和脆弱性。

This specification defines Interactive Connectivity Establishment (ICE) as a technique for NAT traversal for UDP-based data streams (though ICE has been extended to handle other transport protocols, such as TCP [[RFC6544](./rfc6544 "\"TCP Candidates with Interactive Connectivity Establishment (ICE)\"")]). ICE works by exchanging a multiplicity of IP addresses and ports, which are then tested for connectivity by peer-to-peer connectivity checks. The IP addresses and ports are exchanged using ICE-usage-specific mechanisms (e.g., in an Offer/Answer exchange), and the connectivity checks are performed using STUN [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]. ICE also makes use of Traversal Using Relay around NAT (TURN) [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")], an extension to STUN. Because ICE exchanges a multiplicity of IP addresses and ports for each media stream, it also allows for address selection for multihomed and dual-stack hosts. For this reason, [RFC 5245](./rfc5245) [[RFC5245](./rfc5245 "\"Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal for Offer/Answer Protocols\"")] deprecated the solutions previously defined in [RFC 4091](./rfc4091) [[RFC4091](./rfc4091 "\"The Alternative Network Address Types (ANAT) Semantics for the Session Description Protocol (SDP) Grouping Framework\"")] and [RFC 4092](./rfc4092) [[RFC4092](./rfc4092 "\"Usage of the Session Description Protocol (SDP) Alternative Network Address Types (ANAT) Semantics in the Session Initiation Protocol (SIP)\"")]].

本规范将交互式连接建立 (ICE) 定义为一种用于基于 UDP 数据流的 NAT 穿越技术（尽管 ICE 已扩展为处理其他传输协议，如 TCP [[RFC6544](./rfc6544 "\"TCP Candidates with Interactive Connectivity Establishment (ICE)\"")]]）。ICE 的工作原理是交换多个 IP 地址和端口，然后通过对等点间的连通性检查来测试这些地址和端口的连通性。IP 地址和端口使用特定于 ICE 使用的机制（例如，在 Offer/Answer 交换中）进行交换，连通性检查使用 STUN [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] 执行。ICE 还使用 NAT 中继遍历 (TURN) [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")]，这是 STUN 的扩展。由于 ICE 为每个媒体流交换多个 IP 地址和端口，它还允许为多宿主机和双栈主机进行地址选择。因此，[RFC 5245](./rfc5245) [[RFC5245](./rfc5245 "\"Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal for Offer/Answer Protocols\"")] 废弃了之前在 [RFC 4091](./rfc4091) [[RFC4091](./rfc4091 "\"The Alternative Network Address Types (ANAT) Semantics for the Session Description Protocol (SDP) Grouping Framework\"")] 和 [RFC 4092](./rfc4092) [[RFC4092](./rfc4092 "\"Usage of the Session Description Protocol (SDP) Alternative Network Address Types (ANAT) Semantics in the Session Initiation Protocol (SIP)\"")]] 中定义的解决方案。

[Appendix B](#appendix-B) provides background information and motivations regarding the design decisions that were made when designing ICE.

[附录 B](#appendix-B) 提供了有关设计 ICE 时所做设计决策的背景信息和动机。

# 2. Overview of ICE | 2. ICE 概述

In a typical ICE deployment, there are two endpoints (ICE agents) that want to communicate. Note that ICE is not intended for NAT traversal for the signaling protocol, which is assumed to be provided via another mechanism. ICE assumes that the agents are able to establish a signaling connection between each other.

在典型的 ICE 部署中，有两个想要通信的端点（ICE 代理）。请注意，ICE 不是用于信令协议的 NAT 穿越，信令协议假定通过另一种机制提供。ICE 假定代理之间能够建立信令连接。

Initially, the agents are ignorant of their own topologies. In particular, the agents may or may not be behind NATs (or multiple tiers of NATs). ICE allows the agents to discover enough information about their topologies to potentially find one or more paths by which they can establish a data session.

最初，代理对自己的拓扑一无所知。特别地，代理可能位于 NAT 之后（或多级 NAT 之后），也可能不在 NAT 之后。ICE 允许代理发现关于其拓扑的足够信息，以可能找到一个或多个可建立数据会话的路径。

Figure 1 shows a typical ICE deployment. The agents are labeled L and R. Both L and R are behind their own respective NATs, though they may not be aware of it. The type of NAT and its properties are also unknown. L and R are capable of engaging in a candidate exchange process, whose purpose is to set up a data session between L and R. Typically, this exchange will occur through a signaling server (e.g., a SIP proxy).

图 1 显示了一个典型的 ICE 部署。代理标记为 L 和 R。L 和 R 都在各自的 NAT 之后，尽管他们可能没有意识到这一点。NAT 的类型及其属性也是未知的。L 和 R 能够参与候选者交换过程，其目的是在 L 和 R 之间建立数据会话。通常，这种交换将通过信令服务器（例如 SIP 代理）进行。

In addition to the agents, a signaling server, and NATs, ICE is typically used in concert with STUN or TURN servers in the network. Each agent can have its own STUN or TURN server, or they can be the same.

除了代理、信令服务器和 NAT 之外，ICE 通常与网络中的 STUN 或 TURN 服务器配合使用。每个代理可以有自己的 STUN 或 TURN 服务器，或者可以是同一个服务器。

```
                               +---------+
             +--------+        |Signaling|         +--------+
             | STUN   |        |Server   |         | STUN   |
             | Server |        +---------+         | Server |
             +--------+       /           \        +--------+
                             /             \
                            /               \
                           / <- Signaling -> \
                          /                   \
                   +--------+               +--------+
                   |  NAT   |               |  NAT   |
                   +--------+               +--------+
                      /                             \
                     /                               \
                 +-------+                       +-------+
                 | Agent |                       | Agent |
                 |   L   |                       |   R   |
                 +-------+                       +-------+

                     Figure 1: ICE Deployment Scenario
                     图 1: ICE 部署场景
```

The basic idea behind ICE is as follows: each agent has a variety of candidate transport addresses (combination of IP address and port for a particular transport protocol, which is always UDP in this specification) it could use to communicate with the other agent. These might include:

ICE 的基本思想如下：每个代理都有多种候选传输地址（特定传输协议的 IP 地址和端口组合，在本规范中始终是 UDP），可用于与其他代理通信。这些可能包括：

* A transport address on a directly attached network interface
* 直接附加网络接口上的传输地址

* A translated transport address on the public side of a NAT (a "server-reflexive" address)
* NAT 公用侧上的转换传输地址（"服务器自反"地址）

* A transport address allocated from a TURN server (a "relayed address")
* 从 TURN 服务器分配的传输地址（"中继地址"）

Potentially, any of L's candidate transport addresses can be used to communicate with any of R's candidate transport addresses. In practice, however, many combinations will not work. For instance, if L and R are both behind NATs, their directly attached interface addresses are unlikely to be able to communicate directly (this is why ICE is needed, after all!). The purpose of ICE is to discover which pairs of addresses will work. The way that ICE does this is to systematically try all possible pairs (in a carefully sorted order) until it finds one or more that work.

原则上，L 的任何候选传输地址都可用于与 R 的任何候选传输地址通信。然而在实践中，许多组合将无法工作。例如，如果 L 和 R 都在 NAT 之后，它们直接附加的接口地址不太可能直接通信（毕竟这就是需要 ICE 的原因！）。ICE 的目的是发现哪些地址对可以工作。ICE 实现这一目的的方式是系统地尝试所有可能的候选对（按精心排序的顺序），直到找到一个或多个可用的。

## 2.1. Gathering Candidates | 2.1. 收集候选者

In order to execute ICE, an ICE agent identifies and gathers one or more address candidates. A candidate has a transport address -- a combination of IP address and port for a particular transport protocol (with only UDP specified here). There are different types of candidates; some are derived from physical or logical network interfaces, and others are discoverable via STUN and TURN.

为了执行 ICE，ICE 代理识别并收集一个或多个地址候选者。候选者具有传输地址——特定传输协议的 IP 地址和端口组合（这里仅指定 UDP）。候选者有不同类型；有些来自物理或逻辑网络接口，有些可通过 STUN 和 TURN 发现。

The first category of candidates are those with a transport address obtained directly from a local interface. Such a candidate is called a "host candidate". The local interface could be Ethernet or Wi-Fi, or it could be one that is obtained through a tunnel mechanism, such as a Virtual Private Network (VPN) or Mobile IP (MIP). In all cases, such a network interface appears to the agent as a local interface from which ports (and thus candidates) can be allocated.

第一类候选者是从本地接口直接获取传输地址的候选者。这样的候选者称为"主机候选者"。本地接口可以是以太网或 Wi-Fi，也可以是通过隧道机制（如虚拟专用网络 (VPN) 或移动 IP (MIP)）获得的接口。在所有情况下，这样的网络接口对代理来说都表现为本地接口，可以从中分配端口（从而分配候选者）。

Next, the agent uses STUN or TURN to obtain additional candidates. These come in two flavors: translated addresses on the public side of a NAT (server-reflexive candidates) and addresses on TURN servers (relayed candidates). When TURN servers are utilized, both types of candidates are obtained from the TURN server. If only STUN servers are utilized, only server-reflexive candidates are obtained from them. The relationship of these candidates to the host candidate is shown in Figure 2. In this figure, both types of candidates are discovered using TURN. In the figure, the notation X:x means IP address X and UDP port x.

接下来，代理使用 STUN 或 TURN 获取其他候选者。这些有两种类型：NAT 公用侧上的转换地址（服务器自反候选者）和 TURN 服务器上的地址（中继候选者）。当使用 TURN 服务器时，两种类型的候选者都从 TURN 服务器获取。如果仅使用 STUN 服务器，则仅从 STUN 服务器获取服务器自反候选者。这些候选者与主机候选者的关系如图 2 所示。在该图中，两种类型的候选者都使用 TURN 发现。在图中，符号 X:x 表示 IP 地址 X 和 UDP 端口 x。

```

                          |

                      Y:y | /               Address
                      中继地址
                      +--------+

                      | Server |
                      |        |

                   X1':x1'|/               Reflexive
                    服务器自反            Address
                    +------------+         地址
                    |    NAT     |
                    +------------+
                          |
                          | /------------  Local
                      X:x |/               Address
                      本地地址
                      +--------+

                     Figure 2: Candidate Relationships
                     图 2: 候选者关系
```

When the agent sends a TURN Allocate request from IP address and port X:x, the NAT (assuming there is one) will create a binding X1':x1', mapping this server-reflexive candidate to the host candidate X:x. Outgoing packets sent from the host candidate will be translated by the NAT to the server-reflexive candidate. Incoming packets sent to the server-reflexive candidate will be translated by the NAT to the host candidate and forwarded to the agent. The host candidate associated with a given server-reflexive candidate is the "base".

当代理从 IP 地址和端口 X:x 发送 TURN Allocate 请求时，NAT（假设存在一个）将创建一个绑定 X1':x1'，将此服务器自反候选者映射到主机候选者 X:x。从主机候选者发送的传出数据包将被 NAT 转换到服务器自反候选者。发送到服务器自反候选者的传入数据包将被 NAT 转换到主机候选者并转发给代理。与给定服务器自反候选者关联的主机候选者是"基础"。

> Note: "Base" refers to the address an agent sends from for a particular candidate. Thus, as a degenerate case, host candidates also have a base, but it's the same as the host candidate.
> 注意："基础"指代理从特定候选者发送的地址。因此，作为一个退化情况，主机候选者也有基础，但它与主机候选者相同。

When there are multiple NATs between the agent and the TURN server, the TURN request will create a binding on each NAT, but only the outermost server-reflexive candidate (the one nearest the TURN server) will be discovered by the agent. If the agent is not behind a NAT, then the base candidate will be the same as the server-reflexive candidate, and the server-reflexive candidate is redundant and will be eliminated.

当代理和 TURN 服务器之间有多个 NAT 时，TURN 请求将在每个 NAT 上创建一个绑定，但只有最外层的服务器自反候选者（最靠近 TURN 服务器的那个）会被代理发现。如果代理不在 NAT 之后，则基础候选者将与服务器自反候选者相同，服务器自反候选者是冗余的，将被消除。

The Allocate request then arrives at the TURN server. The TURN server allocates a port y from its local IP address Y, and generates an Allocate response, informing the agent of this relayed candidate. The TURN server also informs the agent of the server-reflexive candidate, X1':x1', by copying the source transport address of the Allocate request into the Allocate response. The TURN server acts as a packet relay, forwarding traffic between L and R. In order to send traffic to L, R sends traffic to the TURN server at Y:y, and the TURN server forwards that to X1':x1', which passes through the NAT where it is mapped to X:x and delivered to L.

然后 Allocate 请求到达 TURN 服务器。TURN 服务器从其本地 IP 地址 Y 分配一个端口 y，并生成一个 Allocate 响应，通知代理此中继候选者。TURN 服务器还通过将 Allocate 请求的源传输地址复制到 Allocate 响应中来通知代理服务器自反候选者 X1':x1'。TURN 服务器充当数据包中继，在 L 和 R 之间转发流量。为了向 L 发送流量，R 将流量发送到 TURN 服务器的 Y:y，TURN 服务器将其转发到 X1':x1'，这会通过 NAT，在那里被映射到 X:x 并传送到 L。

When only STUN servers are utilized, the agent sends a STUN Binding request [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] to its STUN server. The STUN server will inform the agent of the server-reflexive candidate X1':x1' by copying the source transport address of the Binding request into the Binding response.

当仅使用 STUN 服务器时，代理向其 STUN 服务器发送 STUN Binding 请求 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]。STUN 服务器将通过把 Binding 请求的源传输地址复制到 Binding 响应中来通知代理服务器自反候选者 X1':x1'。

## 2.2. Connectivity Checks | 2.2. 连通性检查

Once L has gathered all of its candidates, it orders them by highest-to-lowest priority and sends them to R over the signaling channel. When R receives the candidates from L, it performs the same gathering process and responds with its own list of candidates. At the end of this process, each ICE agent has a complete list of both its candidates and its peer's candidates. It pairs them up, resulting in candidate pairs. To see which pairs work, each agent schedules a series of connectivity checks. Each check is a STUN request/response transaction that the client will perform on a particular candidate pair by sending a STUN request from the local candidate to the remote candidate.

一旦 L 收集完所有候选者，它按从高到低的优先级对它们进行排序，然后通过信令通道将它们发送给 R。当 R 从 L 收到候选者时，它执行相同的收集过程并用自己的候选者列表进行响应。在这个过程结束时，每个 ICE 代理都有了自己和对端候选者的完整列表。它将它们配对，形成候选者对。为了查看哪些候选对可以工作，每个代理安排一系列连通性检查。每个检查是一个 STUN 请求/响应事务，客户端通过从本地候选者向远程候选者发送 STUN 请求来对特定候选者对执行该事务。

The basic principle of the connectivity checks is simple:

连通性检查的基本原理很简单：

1. Sort the candidate pairs in priority order.
2. 按优先级顺序对候选者对进行排序。

3. Send checks on each candidate pair in priority order.
4. 按优先级顺序对每个候选者对发送检查。

5. Acknowledge checks received from the other agent.
6. 确认从对方代理收到的检查。

With both agents performing a check on a candidate pair, the result is a 4-way handshake:

由于两个代理都对候选者对执行检查，结果是一个 4 次握手：

```
                  L                        R
                  -                        -
                  STUN request ->             \  L's
                            <- STUN response  /  check
                                          \
                   检查
                             <- STUN request  \  R's
                  STUN response ->            /  check
                                          \
                   检查

                    Figure 3: Basic Connectivity Check
                    图 3: 基本连通性检查
```

It is important to note that STUN requests are sent to and from the exact same IP addresses and ports that will be used for data (e.g., RTP, RTCP, or other protocols). Consequently, agents demultiplex STUN and data using the contents of the packets rather than the port on which they are received.

重要的是要注意，STUN 请求是从将用于数据（例如 RTP、RTCP 或其他协议）的完全相同的 IP 地址和端口发送和接收的。因此，代理使用数据包的内容而不是接收它们的端口来分解 STUN 和数据。

Because a STUN Binding request is used for the connectivity check, the STUN Binding response will contain the agent's translated transport address on the public side of any NATs between the agent and its peer. If this transport address is different from that of other candidates the agent already learned, it represents a new candidate (peer-reflexive candidate), which then gets tested by ICE just the same as any other candidate.

因为 STUN Binding 请求用于连通性检查，STUN Binding 响应将包含代理在其和对端之间的任何 NAT 公用侧上的转换传输地址。如果此传输地址与代理已获知的其他候选者不同，则它代表一个新的候选者（对端自反候选者），然后与任何其他候选者一样接受 ICE 测试。

Because the algorithm above searches all candidate pairs, if a working pair exists, the algorithm will eventually find it no matter what order the candidates are tried in. In order to produce faster (and better) results, the candidates are sorted in a specified order. The resulting list of sorted candidate pairs is called the "checklist".

因为上述算法搜索所有候选者对，如果存在可用的候选对，算法最终会找到它，无论按什么顺序尝试候选者。为了产生更快（更好）的结果，候选者按指定顺序排序。排序后的候选者对列表称为"检查列表"。

The agent works through the checklist by sending a STUN request for the next candidate pair on the list periodically. These are called "ordinary checks". When a STUN transaction succeeds, one or more candidate pairs will become so-called "valid pairs" and will be added to a candidate-pair list called the "valid list".

代理通过定期发送下一个候选者对的 STUN 请求来处理检查列表。这些称为"普通检查"。当 STUN 事务成功时，一个或多个候选者对将变成所谓的"有效对"，并被添加到称为"有效列表"的候选者对列表中。

As an optimization, as soon as R gets L's check message, R schedules a connectivity-check message to be sent to L on the same candidate pair. This is called a "triggered check", and it accelerates the process of finding valid pairs.

作为一种优化，一旦 R 收到 L 的检查消息，R 就安排在同一候选者对上向 L 发送连通性检查消息。这称为"触发检查"，它加速了发现有效候选对的过程。

At the end of this handshake, both L and R know that they can send (and receive) messages end to end in both directions.

在这个握手结束时，L 和 R 都知道它们可以双向端到端发送（和接收）消息。

In general, the priority algorithm is designed so that candidates of a similar type get similar priorities so that more direct routes (that is, routes without data relays or NATs) are preferred over indirect routes (routes with data relays or NATs). Within those guidelines, however, agents have a fair amount of discretion about how to tune their algorithms.

一般来说，优先级算法的设计使得相似类型的候选者获得相似的优先级，从而更倾向于直接路由（即没有数据中继或 NAT 的路由）而不是间接路由（带有数据中继或 NAT 的路由）。然而，在这些指导方针范围内，代理在如何调整其算法方面有相当大的自主权。

A data stream might consist of multiple components (pieces of a data stream that require their own set of candidates, e.g., RTP and RTCP).

数据流可能由多个组件组成（数据流的各个部分需要自己的候选者集，例如 RTP 和 RTCP）。

## 2.3. Nominating Candidate Pairs and Concluding ICE | 2.3. 提名候选对并结束 ICE

ICE assigns one of the ICE agents in the role of the controlling agent, and the other in the role of the controlled agent. For each component of a data stream, the controlling agent nominates a valid pair (from the valid list) to be used for data. The exact timing of the nomination is based on local policy.

ICE 将其中一个 ICE 代理指定为控制代理的角色，另一个指定为受控代理的角色。对于数据流的每个组件，控制代理提名一个有效对（从有效列表中）用于数据。提名的确切时间基于本地策略。

When nominating, the controlling agent lets the checks continue until at least one valid pair for each component of a data stream is found, and then it picks a valid pair and sends a STUN request on that pair, using an attribute to indicate to the controlled peer that it has been nominated. This is shown in Figure 4.

在提名时，控制代理让检查继续进行，直到找到数据流每个组件的至少一个有效对，然后它选择一个有效对并在该对上发送 STUN 请求，使用一个属性向受控对端指示它已被提名。如图 4 所示。

```
             L                        R
             -                        -
             STUN request ->             \  L's
                       <- STUN response  /  check
                                     \
              检查
                        <- STUN request  \  R's
             STUN response ->            /  check
                                     \
              检查
             STUN request + attribute -> \  L's
                       <- STUN response  /  check
                                     \
              检查

                           Figure 4: Nomination
                           图 4: 提名
```

Once the controlled agent receives the STUN request with the attribute, it will check (unless the check has already been done) the same pair. If the transactions above succeed, the agents will set the nominated flag for the pairs and will cancel any future checks for that component of the data stream. Once an agent has set the nominated flag for each component of a data stream, the pairs become the selected pairs. After that, only the selected pairs will be used for sending and receiving data associated with that data stream.

一旦受控代理收到带有该属性的 STUN 请求，它将检查（除非检查已经完成）相同的对。如果上述事务成功，代理将为这些对设置提名标志，并将取消该数据流组件的任何未来检查。一旦代理为数据流的每个组件设置了提名标志，这些对就成为选定对。之后，只有选定对将用于发送和接收与该数据流相关的数据。

## 2.4. ICE Restart | 2.4. ICE 重启

Once ICE is concluded, it can be restarted at any time for one or all of the data streams by either ICE agent. This is done by sending updated candidate information indicating a restart.

一旦 ICE 结束，任何 ICE 代理都可以随时为一个或所有数据流重启它。这是通过发送表示重启的更新候选者信息来完成的。

## 2.5. Lite Implementations | 2.5. 轻量级实现

Certain ICE agents will always be connected to the public Internet and have a public IP address at which it can receive packets from any correspondent. To make it easier for these devices to support ICE, ICE defines a special type of implementation called "lite" (in contrast to the normal full implementation). Lite agents only use host candidates and do not generate connectivity checks or run state machines, though they need to be able to respond to connectivity checks.

某些 ICE 代理将始终连接到公共互联网，并拥有一个公共 IP 地址，可以从任何通信方接收数据包。为了使这些设备更容易支持 ICE，ICE 定义了一种称为"lite"的特殊实现类型（与正常的完整实现相对）。Lite 代理仅使用主机候选者，不生成连通性检查或运行状态机，尽管它们需要能够响应连通性检查。

# 3. ICE Usage | 3. ICE 使用

This document specifies generic use of ICE with protocols that provide means to exchange candidate information between ICE agents. The specific details (i.e., how to encode candidate information and the actual candidate exchange process) for different protocols using ICE (referred to as "using protocol") are described in separate usage documents.

本文档规定了与提供 ICE 代理之间交换候选者信息手段的协议一起使用的通用 ICE。具体细节（即如何对候选者信息进行编码以及实际候选者交换过程）对于使用 ICE 的不同协议（称为"使用协议"）在单独的用法文档中描述。

One mechanism that allows agents to exchange candidate information is the utilization of Offer/Answer semantics (which are based on [[RFC3264](./rfc3264 "\"An Offer/Answer Model with Session Description Protocol (SDP)\"")]) as part of the SIP protocol [[RFC3261](./rfc3261 "\"SIP: Session Initiation Protocol\"")] [[ICE-SIP-SDP](#ref-ICE-SIP-SDP)].

允许代理交换候选者信息的一种机制是利用 Offer/Answer 语义（基于 [[RFC3264](./rfc3264 "\"An Offer/Answer Model with Session Description Protocol (SDP)\"")]]）作为 SIP 协议 [[RFC3261](./rfc3261 "\"SIP: Session Initiation Protocol\"")] [[ICE-SIP-SDP](#ref-ICE-SIP-SDP)] 的一部分。

[RFC7825] defines an ICE usage for the Real-Time Streaming Protocol (RTSP). Note, however, that the ICE usage is based on [RFC 5245](./rfc5245).

[RFC7825] 为实时流协议 (RTSP) 定义了一种 ICE 用法。然而请注意，该 ICE 用法基于 [RFC 5245](./rfc5245)。

# 4. Terminology | 4. 术语

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP 14](https://www.rfc-editor.org/bcp/bcp14) [[RFC2119](./rfc2119 "\"Key words for use in RFCs to Indicate Requirement Levels\"")] [[RFC8174](./rfc8174 "\"Ambiguity of Uppercase vs Lowercase in RFC 2119 Key Words\"")] when, and only when, they appear in all capitals, as shown here.

本文档中的关键词"MUST"、"MUST NOT"、"REQUIRED"、"SHALL"、"SHALL NOT"、"SHOULD"、"SHOULD NOT"、"RECOMMENDED"、"NOT RECOMMENDED"、"MAY"和"OPTIONAL"应按 [BCP 14](https://www.rfc-editor.org/bcp/bcp14) [[RFC2119](./rfc2119 "\"Key words for use in RFCs to Indicate Requirement Levels\"")] [[RFC8174](./rfc8174 "\"Ambiguity of Uppercase vs Lowercase in RFC 2119 Key Words\"")] 中所述进行解释，但仅在它们如所示那样以全部大写出现时才适用。

Readers need to be familiar with the terminology defined in [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] and NAT Behavioral requirements for UDP [[RFC4787](./rfc4787 "\"Network Address Translation (NAT) Behavioral Requirements for Unicast UDP\"")].

读者需要熟悉 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] 和 UDP 的 NAT 行为要求 [[RFC4787](./rfc4787 "\"Network Address Translation (NAT) Behavioral Requirements for Unicast UDP\"")] 中定义的术语。

This specification makes use of the following additional terminology:

本规范使用以下附加术语：

**ICE Session | ICE 会话**

An ICE session consists of all ICE-related actions starting with the candidate gathering, followed by the interactions (candidate exchange, connectivity checks, nominations, and keepalives) between the ICE agents until all the candidates are released or an ICE restart is triggered.

ICE 会话包括所有 ICE 相关操作，从候选者收集开始，然后是 ICE 代理之间的交互（候选者交换、连通性检查、提名和保活），直到所有候选者被释放或触发 ICE 重启。

**ICE Agent, Agent | ICE 代理，代理**

An ICE agent (sometimes simply referred to as an "agent") is the protocol implementation involved in the ICE candidate exchange. There are two agents involved in a typical candidate exchange.

ICE 代理（有时简称为"代理"）是参与 ICE 候选者交换的协议实现。在典型的候选者交换中有两个代理参与。

**Initiating Peer, Initiating Agent, Initiator | 发起对端，发起代理，发起方**

An initiating agent is an ICE agent that initiates the ICE candidate exchange process.

发起代理是发起 ICE 候选者交换过程的 ICE 代理。

**Responding Peer, Responding Agent, Responder | 响应对端，响应代理，响应方**

A responding agent is an ICE agent that receives and responds to the candidate exchange process initiated by the initiating agent.

响应代理是接收并响应发起代理发起的候选者交换过程的 ICE 代理。

**ICE Candidate Exchange, Candidate Exchange | ICE 候选者交换，候选者交换**

The process where ICE agents exchange information (e.g., candidates and passwords) that is needed to perform ICE. Offer/Answer with SDP encoding [[RFC3264](./rfc3264 "\"An Offer/Answer Model with Session Description Protocol (SDP)\"")] is one example of a protocol that can be used for exchanging the candidate information.

ICE 代理交换执行 ICE 所需信息（例如候选者和密码）的过程。带有 SDP 编码的 Offer/Answer [[RFC3264](./rfc3264 "\"An Offer/Answer Model with Session Description Protocol (SDP)\"")] 是可用于交换候选者信息的协议的一个例子。

**Peer | 对端**

From the perspective of one of the ICE agents in a session, its peer is the other agent. Specifically, from the perspective of the initiating agent, the peer is the responding agent. From the perspective of the responding agent, the peer is the initiating agent.

从一个 ICE 会话中的 ICE 代理的角度来看，其对端是另一个代理。具体来说，从发起代理的角度来看，对端是响应代理。从响应代理的角度来看，对端是发起代理。

**Transport Address | 传输地址**

The combination of an IP address and the transport protocol (such as UDP or TCP) port.

IP 地址和传输协议（如 UDP 或 TCP）端口的组合。

**Data, Data Stream, Data Session | 数据，数据流，数据会话**

When ICE is used to set up data sessions, the data is transported using some protocol. Media is usually transported over RTP, composed of a stream of RTP packets. Data session refers to data packets that are exchanged between the peer on the path created and tested with ICE.

当使用 ICE 建立数据会话时，数据使用某种协议传输。媒体通常通过 RTP 传输，由一系列 RTP 数据包组成。数据会话指的是在对端之间交换的数据包，这些数据包是在使用 ICE 创建和测试的路径上交换的。

**Candidate, Candidate Information | 候选者，候选者信息**

A transport address that is a potential point of contact for receipt of data. Candidates also have properties -- their type (server reflexive, relayed, or host), priority, foundation, and base.

作为接收数据潜在联系点的传输地址。候选者也有属性——它们的类型（服务器自反、中继或主机）、优先级、基础和 foundation。

**Component | 组件**

A component is a piece of a data stream. A data stream may require multiple components, each of which has to work in order for the data stream as a whole to work. For RTP/RTCP data streams, unless RTP and RTCP are multiplexed in the same port, there are two components per data stream -- one for RTP, and one for RTCP. A component has a candidate pair, which cannot be used by other components.

组件是数据流的一部分。数据流可能需要多个组件，每个组件都必须工作，数据流才能整体工作。对于 RTP/RTCP 数据流，除非 RTP 和 RTCP 在同一端口上复用，否则每个数据流有两个组件——一个用于 RTP，一个用于 RTCP。组件有一个候选者对，其他组件不能使用该候选者对。

**Host Candidate | 主机候选者**

A candidate obtained by binding to a specific port from an IP address on the host. This includes IP addresses on physical interfaces and logical ones, such as ones obtained through VPNs.

通过从主机上的 IP 地址绑定到特定端口而获得的候选者。这包括物理接口和逻辑接口上的 IP 地址，如通过 VPN 获取的地址。

**Server-Reflexive Candidate | 服务器自反候选者**

A candidate whose IP address and port are a binding allocated by a NAT for an ICE agent after it sends a packet through the NAT to a server, such as a STUN server.

其 IP 地址和端口是由 NAT 为 ICE 代理分配的绑定，在代理通过 NAT 向服务器（如 STUN 服务器）发送数据包之后分配。

**Peer-Reflexive Candidate | 对端自反候选者**

A candidate whose IP address and port are a binding allocated by a NAT for an ICE agent after it sends a packet through the NAT to its peer.

其 IP 地址和端口是由 NAT 为 ICE 代理分配的绑定，在代理通过 NAT 向其对端发送数据包之后分配。

**Relayed Candidate | 中继候选者**

A candidate obtained from a relay server, such as a TURN server.

从转发服务器（如 TURN 服务器）获取的候选者。

**Base | 基础**

The transport address that an ICE agent sends from for a particular candidate. For host, server-reflexive, and peer-reflexive candidates, the base is the same as the host candidate. For relayed candidates, the base is the same as the relayed candidate (i.e., the transport address used by the TURN server to send from).

ICE 代理从特定候选者发送所使用的传输地址。对于主机、服务器自反和对端自反候选者，基础与主机候选者相同。对于中继候选者，基础与中继候选者相同（即 TURN 服务器发送所使用的传输地址）。

**Related Address and Port | 相关地址和端口**

A transport address related to a candidate, which is useful for diagnostics and other purposes. If a candidate is server or peer reflexive, the related address and port is equal to the base for that server or peer-reflexive candidate. If the candidate is relayed, the related address and port are equal to the mapped address in the Allocate response that provided the client with that relayed candidate. If the candidate is a host candidate, the related address and port is identical to the host candidate.

与候选者相关的传输地址，这对诊断和其他目的很有用。如果候选者是服务器或对端自反的，相关地址和端口等于该服务器或对端自反候选者的基础。如果候选者是中继的，相关地址和端口等于 Allocate 响应中的映射地址，该响应为客户端提供了该中继候选者。如果候选者是主机候选者，相关地址和端口与主机候选者相同。

**Foundation | Foundation（基础标识符）**

An arbitrary string used in the freezing algorithm to group similar candidates. It is the same for two candidates that have the same type, base IP address, protocol (UDP, TCP, etc.), and STUN or TURN server. If any of these are different, then the foundation will be different.

在冻结算法中用于将相似候选者分组的任意字符串。对于具有相同类型、基础 IP 地址、协议（UDP、TCP 等）和 STUN 或 TURN 服务器的两个候选者，foundation 是相同的。如果其中任何一个不同，则 foundation 将不同。

**Local Candidate | 本地候选者**

A candidate that an ICE agent has obtained and may send to its peer.

ICE 代理已获得并可发送给其对端的候选者。

**Remote Candidate | 远程候选者**

A candidate that an ICE agent received from its peer.

ICE 代理从其对端接收到的候选者。

**Default Destination/Candidate | 默认目的地/候选者**

The default destination for a component of a data stream is the transport address that would be used by an ICE agent that is not ICE aware. A default candidate for a component is one whose transport address matches the default destination for that component.

数据流组件的默认目的地是 ICE 代理（如果该代理不支持 ICE）将使用的传输地址。组件的默认候选者是其传输地址与该组件的默认目的地匹配的候选者。

**Candidate Pair | 候选者对**

A pair containing a local candidate and a remote candidate.

包含本地候选者和远程候选者的一对。

**Check, Connectivity Check, STUN Check | 检查，连通性检查，STUN 检查**

A STUN Binding request for the purpose of verifying connectivity. A check is sent from the base of the local candidate to the remote candidate of a candidate pair.

用于验证连通性的 STUN Binding 请求。检查从本地候选者的基础发送到候选者对的远程候选者。

**Checklist | 检查列表**

An ordered set of candidate pairs that an ICE agent will use to generate checks.

ICE 代理将用于生成检查的有序候选者对集合。

**Ordinary Check | 普通检查**

A connectivity check generated by an ICE agent as a consequence of a timer that fires periodically, instructing it to send a check.

作为定期触发计时器的结果而由 ICE 代理生成的连通性检查，指示其发送检查。

**Triggered Check | 触发检查**

A connectivity check generated as a consequence of the receipt of a connectivity check from the peer.

作为接收对端连通性检查的结果而生成的连通性检查。

**Valid Pair | 有效对**

A candidate pair whose local candidate equals the mapped address of a successful connectivity-check response and whose remote candidate equals the destination address to which the connectivity-check request was sent.

本地候选者等于成功连通性检查响应的映射地址，且远程候选者等于连通性检查请求发送到的目的地地址的候选者对。

**Valid List | 有效列表**

An ordered set of candidate pairs for a data stream that have been validated by a successful STUN transaction.

已通过成功 STUN 事务验证的数据流候选者对的有序集合。

**Checklist Set | 检查列表集**

The ordered list of all checklists. The order is determined by each ICE usage.

所有检查列表的有序列表。顺序由每个 ICE 用法决定。

**Full Implementation | 完整实现**

An ICE implementation that performs the complete set of functionality defined by this specification.

执行本规范定义的完整功能集的 ICE 实现。

**Lite Implementation | 轻量级实现**

An ICE implementation that omits certain functions, implementing only as much as is necessary for a peer that is not a lite implementation to gain the benefits of ICE. Lite implementations do not maintain any of the state machines and do not generate connectivity checks.

省略某些功能的 ICE 实现，仅实现非轻量级实现的对端获得 ICE 好处所需的最低限度功能。轻量级实现不维护任何状态机，也不生成连通性检查。

**Controlling Agent | 控制代理**

The ICE agent that nominates a candidate pair. In any session, there is always one controlling agent and one controlled agent.

提名候选者对的 ICE 代理。在任何会话中，始终有一个控制代理和一个受控代理。

**Controlled Agent | 受控代理**

The ICE agent that waits for the controlling agent to nominate a candidate pair.

等待控制代理提名候选者对的 ICE 代理。

**Nomination | 提名**

The process of the controlling agent indicating to the controlled agent which candidate pair the ICE agents will use for sending and receiving data. The nomination process defined in this specification was referred to as "regular nomination" in [RFC 5245](./rfc5245). The nomination process that was referred to as "aggressive nomination" in [RFC 5245](./rfc5245) has been deprecated in this specification.

控制代理向受控代理指示 ICE 代理将使用哪个候选者对发送和接收数据的过程。本规范中定义的提名过程在 [RFC 5245](./rfc5245) 中称为"常规提名"。在 [RFC 5245](./rfc5245) 中称为"激进提名"的提名过程已在本规范中废弃。

**Nominated, Nominated Flag | 已提名，提名标志**

Once the nomination of a candidate pair has succeeded, the candidate pair has become nominated, and the value of its nominated flag is set to true.

一旦候选者对的提名成功，该候选者对就已变成已提名状态，其提名标志的值被设置为真。

**Selected Pair, Selected Candidate Pair | 选定对，选定候选者对**

The candidate pair used for sending and receiving data for a component of a data stream is referred to as the "selected pair". Before selected pairs have been produced for a data stream, any valid pair associated with a component of a data stream can be used for sending and receiving data for the component. Once there are nominated pairs for each component of a data stream, the nominated pairs become the selected pairs for the data stream. The candidates associated with the selected pairs are referred to as "selected candidates".

用于发送和接收数据流组件数据的一对候选者称为"选定对"。在为数据流生成选定对之前，与数据流组件关联的任何有效对都可用于该组件的发送和接收数据。一旦数据流的每个组件都有提名对，这些提名对就成为该数据流的选定对。与选定对关联的候选者称为"选定候选者"。

**Using Protocol, ICE Usage | 使用协议，ICE 用法**

The protocol that uses ICE for NAT traversal. A usage specification defines the protocol-specific details on how the procedures defined here are applied to that protocol.

使用 ICE 进行 NAT 穿越的协议。用法规范定义了如何将此处定义的过程应用于该协议的协议特定细节。

**Timer Ta | 定时器 Ta**

The timer for generating new STUN or TURN transactions.

用于生成新 STUN 或 TURN 事务的定时器。

**Timer RTO (Retransmission Timeout) | 定时器 RTO（重传超时）**

The retransmission timer for a given STUN or TURN transaction.

给定 STUN 或 TURN 事务的重传定时器。

# 5. ICE Candidate Gathering and Exchange | 5. ICE 候选者收集与交换

As part of ICE processing, both the initiating and responding agents gather candidates, prioritize and eliminate redundant candidates, and exchange candidate information with the peer as defined by the using protocol (ICE usage). Specifics of the candidate-encoding mechanism and the semantics of candidate information exchange is out of scope of this specification.

作为 ICE 处理的一部分，发起代理和响应代理都收集候选者、确定优先级并消除冗余候选者，并按照使用协议（ICE 用法）的定义与对端交换候选者信息。候选者编码机制的细节和候选者信息交换的语义不在本规范的范围内。

---

## 5.1. Full Implementation | 5.1. 完整实现

### 5.1.1. Gathering Candidates | 5.1.1. 收集候选者

An ICE agent gathers candidates when it believes that communication is imminent. An initiating agent can do this based on a user interface cue or on an explicit request to initiate a session. Every candidate has a transport address. It also has a type and a base. Four types are defined and gathered by this specification -- host candidates, server-reflexive candidates, peer-reflexive candidates, and relayed candidates. The server-reflexive candidates are gathered using STUN or TURN, and relayed candidates are obtained through TURN. Peer-reflexive candidates are obtained in later phases of ICE, as a consequence of connectivity checks.

ICE 代理在认为通信即将发生时收集候选者。发起代理可以基于用户界面提示或明确请求发起会话来执行此操作。每个候选者都有一个传输地址。它也有一个类型和一个基础。本规范定义了四种类型并收集——主机候选者、服务器自反候选者、对端自反候选者和中继候选者。服务器自反候选者使用 STUN 或 TURN 收集，中继候选者通过 TURN 获取。对端自反候选者在 ICE 的后续阶段作为连通性检查的结果获取。

The process for gathering candidates at the responding agent is identical to the process for the initiating agent. It is RECOMMENDED that the responding agent begin this process immediately on receipt of the candidate information, prior to alerting the user of the application associated with the ICE session.

响应代理收集候选者的过程与发起代理的过程相同。建议响应代理在收到候选者信息后立即开始此过程，而不是等到提醒与 ICE 会话关联的应用程序用户之后。

---

### 5.1.1.1. Host Candidates | 5.1.1.1. 主机候选者

Host candidates are obtained by binding to ports on an IP address attached to an interface (physical or virtual, including VPN interfaces) on the host.

主机候选者通过绑定到附加在主机接口（物理或虚拟，包括 VPN 接口）上的 IP 地址的端口来获取。

For each component of each data stream the ICE agent wishes to use, the agent SHOULD obtain a candidate on each IP address that the host has, with the exceptions listed below. The agent obtains each candidate by binding to a UDP port on the specific IP address. A host candidate (and indeed every candidate) is always associated with a specific component for which it is a candidate.

对于 ICE 代理希望使用的每个数据流的每个组件，代理应该在主机拥有的每个 IP 地址上获取候选者，但以下例外情况除外。代理通过绑定到特定 IP 地址上的 UDP 端口来获取每个候选者。主机候选者（实际上是每个候选者）总是与它作为候选者的特定组件相关联。

Each component has an ID assigned to it, called the "component ID". For RTP/RTCP data streams, unless both RTP and RTCP are multiplexed in the same UDP port (RTP/RTCP multiplexing), the RTP itself has a component ID of 1, and RTCP has a component ID of 2. In case of RTP/RTCP multiplexing, a component ID of 1 is used for both RTP and RTCP.

每个组件都有一个分配给它的 ID，称为"组件 ID"。对于 RTP/RTCP 数据流，除非 RTP 和 RTCP 在同一 UDP 端口上复用（RTP/RTCP 复用），否则 RTP 本身的组件 ID 为 1，RTCP 的组件 ID 为 2。在 RTP/RTCP 复用的情况下，RTP 和 RTCP 都使用组件 ID 1。

When candidates are obtained, unless the agent knows for sure that RTP/RTCP multiplexing will be used (i.e., the agent knows that the other agent also supports, and is willing to use, RTP/RTCP multiplexing), or unless the agent only supports RTP/RTCP multiplexing, the agent MUST obtain a separate candidate for RTCP. If an agent has obtained a candidate for RTCP, and ends up using RTP/RTCP multiplexing, the agent does not need to perform connectivity checks on the RTCP candidate. Absence of a component ID 2 as such does not imply use of RTCP/RTP multiplexing, as it could also mean that RTCP is not used.

获取候选者时，除非代理确定知道将使用 RTP/RTCP 复用（即代理知道另一代理也支持并愿意使用 RTP/RTCP 复用），或者除非代理仅支持 RTP/RTCP 复用，否则代理必须为 RTCP 获取单独的候选者。如果代理已获取了 RTCP 的候选者，但最终使用了 RTP/RTCP 复用，则代理不需要对 RTCP 候选者执行连通性检查。缺少组件 ID 2 并不意味着使用了 RTCP/RTP 复用，因为它也可能意味着 RTCP 未被使用。

If an agent is using separate candidates for RTP and RTCP, it will end up with 2*K host candidates if an agent has K IP addresses.

如果代理为 RTP 和 RTCP 使用单独的候选者，如果代理有 K 个 IP 地址，它最终将有 2*K 个主机候选者。

Note that the responding agent, when obtaining its candidates, will typically know if the other agent supports RTP/RTCP multiplexing, in which case it will not need to obtain a separate candidate for RTCP. However, absence of a component ID 2 as such does not imply use of RTCP/RTP multiplexing, as it could also mean that RTCP is not used.

请注意，响应代理在获取其候选者时通常会知道另一代理是否支持 RTP/RTCP 复用，如果是，它将不需要为 RTCP 获取单独的候选者。然而，缺少组件 ID 2 并不意味着使用了 RTCP/RTP 复用，因为它也可能意味着 RTCP 未被使用。

The use of multiple components, other than for RTP/RTCP streams, is discouraged as it increases the complexity of ICE processing. If multiple components are needed, the component IDs SHOULD start with 1 and increase by 1 for each component.

除了 RTP/RTCP 流之外，不鼓励使用多个组件，因为这会增加 ICE 处理的复杂性。如果需要多个组件，组件 ID 应从 1 开始，每个组件增加 1。

The base for each host candidate is set to the candidate itself.

每个主机候选者的基础设置为候选者本身。

The host candidates are gathered from all IP addresses with the following exceptions:

主机候选者从所有 IP 地址收集，但以下例外情况除外：

* Addresses from a loopback interface MUST NOT be included in the candidate addresses.
* 来自环回接口的地址不得包含在候选者地址中。

* Deprecated IPv4-compatible IPv6 addresses [[RFC4291](./rfc4291 "\"IP Version 6 Addressing Architecture\"")] and IPv6 site-local unicast addresses [[RFC3879](./rfc3879 "\"Deprecating Site Local Addresses\"")] MUST NOT be included in the address candidates.
* 废弃的 IPv4 兼容 IPv6 地址 [[RFC4291](./rfc4291 "\"IP Version 6 Addressing Architecture\"")] 和 IPv6 站点本地单播地址 [[RFC3879](./rfc3879 "\"Deprecating Site Local Addresses\"")] 不得包含在地址候选者中。

* IPv4-mapped IPv6 addresses SHOULD NOT be included in the address candidates unless the application using ICE does not support IPv4 (i.e., it is an IPv6-only application [[RFC4038](./rfc4038 "\"Application Aspects of IPv6 Transition\"")]).
* IPv4 映射的 IPv6 地址不应包含在地址候选者中，除非使用 ICE 的应用程序不支持 IPv4（即它是一个仅支持 IPv6 的应用程序 [[RFC4038](./rfc4038 "\"Application Aspects of IPv6 Transition\"")]]）。

* If gathering one or more host candidates that correspond to an IPv6 address that was generated using a mechanism that prevents location tracking [[RFC7721](./rfc7721 "\"Security and Privacy Considerations for IPv6 Address Generation Mechanisms\"")], host candidates that correspond to IPv6 addresses that do allow location tracking, are configured on the same interface, and are part of the same network prefix MUST NOT be gathered. Similarly, when host candidates corresponding to an IPv6 address generated using a mechanism that prevents location tracking are gathered, then host candidates corresponding to IPv6 link-local addresses [[RFC4291](./rfc4291 "\"IP Version 6 Addressing Architecture\"")] MUST NOT be gathered.
* 如果收集一个或多个对应于使用防止位置跟踪的机制生成的 IPv6 地址的主机候选者 [[RFC7721](./rfc7721 "\"Security and Privacy Considerations for IPv6 Address Generation Mechanisms\"")]，则不得收集对应于允许位置跟踪的 IPv6 地址、配置在同一接口上且属于同一网络前缀的主机候选者。类似地，当收集对应于使用防止位置跟踪的机制生成的 IPv6 地址的主机候选者时，不得收集对应于 IPv6 链路本地地址 [[RFC4291](./rfc4291 "\"IP Version 6 Addressing Architecture\"")] 的主机候选者。

The IPv6 default address selection specification [[RFC6724](./rfc6724 "\"Default Address Selection for Internet Protocol Version 6 (IPv6)\"")] specifies that temporary addresses [[RFC4941](./rfc4941 "\"Privacy Extensions for Stateless Address Autoconfiguration in IPv6\"")] are to be preferred over permanent addresses.

IPv6 默认地址选择规范 [[RFC6724](./rfc6724 "\"Default Address Selection for Internet Protocol Version 6 (IPv6)\"")] 指定临时地址 [[RFC4941](./rfc4941 "\"Privacy Extensions for Stateless Address Autoconfiguration in IPv6\"")] 应优先于永久地址。

---

### 5.1.1.2. Server-Reflexive and Relayed Candidates | 5.1.1.2. 服务器自反候选者和中继候选者

An ICE agent SHOULD gather server-reflexive and relayed candidates. However, use of STUN and TURN servers may be unnecessary in certain networks and use of TURN servers may be expensive, so some deployments may elect not to use them. If an agent does not gather server-reflexive or relayed candidates, it is RECOMMENDED that the functionality be implemented and just disabled through configuration, so that it can be re-enabled through configuration if conditions change in the future.

ICE 代理应该收集服务器自反候选者和中继候选者。然而，在某些网络中 STUN 和 TURN 服务器的使用可能是不必要的，而 TURN 服务器的使用可能很昂贵，因此某些部署可能选择不使用它们。如果代理不收集服务器自反候选者或中继候选者，建议实现该功能但通过配置禁用它，以便将来条件变化时可以通过配置重新启用。

The agent pairs each host candidate with the STUN or TURN servers with which it is configured or has discovered by some means. It is RECOMMENDED that a domain name be configured, the DNS procedures in [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] (using SRV records with the "stun" service) be used to discover the STUN server, and the DNS procedures in [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")] (using SRV records with the "turn" service) be used to discover the TURN server.

代理将每个主机候选者与其配置或通过某种方式发现的 STUN 或 TURN 服务器配对。建议配置域名，使用 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] 中的 DNS 过程（使用带有"stun"服务的 SRV 记录）来发现 STUN 服务器，使用 [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")] 中的 DNS 过程（使用带有"turn"服务的 SRV 记录）来发现 TURN 服务器。

When multiple STUN or TURN servers are available (or when they are learned through DNS records and multiple results are returned), the agent MAY gather candidates for all of them and SHOULD gather candidates for at least one of them (one STUN server and one TURN server). It does so by pairing host candidates with STUN or TURN servers, and for each pair, the agent sends a Binding or Allocate request to the server from the host candidate. Binding requests to a STUN server are not authenticated, and any ALTERNATE-SERVER attribute in a response is ignored. Agents MUST support the backwards-compatibility mode for the Binding request defined in [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]. Allocate requests SHOULD be authenticated using a long-term credential obtained by the client through some other means.

当有多个 STUN 或 TURN 服务器可用时（或当通过 DNS 记录学习到多个结果时），代理可以为所有这些服务器收集候选者，并应该至少为其中一个（一个 STUN 服务器和一个 TURN 服务器）收集候选者。它通过将主机候选者与 STUN 或 TURN 服务器配对来做到这一点，对于每对，代理从主机候选者向服务器发送 Binding 或 Allocate 请求。发送到 STUN 服务器的 Binding 请求不经过身份验证，响应中的任何 ALTERNATE-SERVER 属性都会被忽略。代理必须支持 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] 中定义的 Binding 请求的向后兼容模式。Allocate 请求应该使用客户端通过其他方式获取的长期凭证进行身份验证。

The gathering process is controlled using a timer, Ta. Every time Ta expires, the agent can generate another new STUN or TURN transaction. This transaction can be either a retry of a previous transaction that failed with a recoverable error (such as authentication failure) or a transaction for a new host candidate and STUN or TURN server pair. The agent SHOULD NOT generate transactions more frequently than once per each ta expiration. See [Section 14](#section-14) for guidance on how to set Ta and the STUN retransmit timer, RTO.

收集过程使用定时器 Ta 控制。每次 Ta 到期时，代理可以生成另一个新的 STUN 或 TURN 事务。此事务可以是重试之前因可恢复错误（如身份验证失败）而失败的事务，也可以是用于新主机候选者和 STUN 或 TURN 服务器对的事务。代理不应比每次 Ta 到期更频繁地生成事务。关于如何设置 Ta 和 STUN 重传定时器 RTO 的指导，请参见 [第 14 节](#section-14)。

The agent will receive a Binding or Allocate response. A successful Allocate response will provide the agent with a server-reflexive candidate (obtained from the mapped address) and a relayed candidate in the XOR-RELAYED-ADDRESS attribute. If the Allocate request is rejected because the server lacks resources to fulfill it, the agent SHOULD instead send a Binding request to obtain a server-reflexive candidate. A Binding response will provide the agent with only a server-reflexive candidate (also obtained from the mapped address). The base of the server-reflexive candidate is the host candidate from which the Allocate or Binding request was sent. The base of a relayed candidate is that candidate itself. If a relayed candidate is identical to a host candidate (which can happen in rare cases), the relayed candidate MUST be discarded.

代理将收到 Binding 或 Allocate 响应。成功的 Allocate 响应将为代理提供服务器自反候选者（从映射地址获取）和 XOR-RELAYED-ADDRESS 属性中的中继候选者。如果 Allocate 请求因服务器缺乏资源而被拒绝，代理应该改为发送 Binding 请求以获取服务器自反候选者。Binding 响应将为代理仅提供服务器自反候选者（也是从映射地址获取的）。服务器自反候选者的基础是发送 Allocate 或 Binding 请求的主机候选者。中继候选者的基础是该候选者本身。如果中继候选者与主机候选者相同（在极少数情况下可能发生），则必须丢弃中继候选者。

If an IPv6-only agent is in a network that utilizes NAT64 [[RFC6146](./rfc6146 "\"Stateful NAT64: Network Address and Protocol Translation from IPv6 Clients to IPv4 Servers\"")] and DNS64 [[RFC6147](./rfc6147 "\"DNS64: DNS Extensions for Network Address Translation from IPv6 Clients to IPv4 Servers\"")] technologies, it may also gather IPv4 server-reflexive and/or relayed candidates from IPv4-only STUN or TURN servers. IPv6-only agents SHOULD also utilize IPv6 prefix discovery [[RFC7050](./rfc7050 "\"Discovery of the IPv6 Prefix Used for IPv6 Address Synthesis\"")] to discover the IPv6 prefix used by NAT64 (if any) and generate server-reflexive candidates for each IPv6-only interface, accordingly. The NAT64 server-reflexive candidates are prioritized like IPv4 server-reflexive candidates.

如果仅支持 IPv6 的代理处于使用 NAT64 [[RFC6146](./rfc6146 "\"Stateful NAT64: Network Address and Protocol Translation from IPv6 Clients to IPv4 Servers\"")] 和 DNS64 [[RFC6147](./rfc6147 "\"DNS64: DNS Extensions for Network Address Translation from IPv6 Clients to IPv4 Servers\"")] 技术的网络中，它也可以从仅支持 IPv4 的 STUN 或 TURN 服务器收集 IPv4 服务器自反候选者和/或中继候选者。仅支持 IPv6 的代理也应该利用 IPv6 前缀发现 [[RFC7050](./rfc7050 "\"Discovery of the IPv6 Prefix Used for IPv6 Address Synthesis\"")] 来发现 NAT64 使用的 IPv6 前缀（如果有的话），并相应地为每个仅支持 IPv6 的接口生成服务器自反候选者。NAT64 服务器自反候选者的优先级与 IPv4 服务器自反候选者相同。

---

### 5.1.1.3. Computing Foundations | 5.1.1.3. 计算 Foundation

The ICE agent assigns each candidate a foundation. Two candidates have the same foundation when all of the following are true:

ICE 代理为每个候选者分配一个 foundation。当满足以下所有条件时，两个候选者具有相同的 foundation：

* They have the same type (host, relayed, server reflexive, or peer reflexive).
* 它们具有相同的类型（主机、中继、服务器自反或对端自反）。

* Their bases have the same IP address (the ports can be different).
* 它们的基础具有相同的 IP 地址（端口可以不同）。

* For reflexive and relayed candidates, the STUN or TURN servers used to obtain them have the same IP address (the IP address used by the agent to contact the STUN or TURN server).
* 对于自反和中继候选者，用于获取它们的 STUN 或 TURN 服务器具有相同的 IP 地址（代理用于联系 STUN 或 TURN 服务器的 IP 地址）。

* They were obtained using the same transport protocol (TCP, UDP).
* 它们使用相同的传输协议（TCP、UDP）获取。

Similarly, two candidates have different foundations if their types are different, their bases have different IP addresses, the STUN or TURN servers used to obtain them have different IP addresses (the IP addresses used by the agent to contact the STUN or TURN server), or their transport protocols are different.

类似地，如果两个候选者的类型不同、它们的基础具有不同的 IP 地址、用于获取它们的 STUN 或 TURN 服务器具有不同的 IP 地址（代理用于联系 STUN 或 TURN 服务器的 IP 地址），或者它们的传输协议不同，则它们具有不同的 foundation。

---

### 5.1.1.4. Keeping Candidates Alive | 5.1.1.4. 保持候选者活跃

Once server-reflexive and relayed candidates are allocated, they MUST be kept alive until ICE processing has completed, as described in [Section 8.3](#section-8.3). For server-reflexive candidates learned through a Binding request, the bindings MUST be kept alive by additional Binding requests to the server. Refreshes for allocations are done using the Refresh transaction, as described in [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")]. The Refresh requests will also refresh the server-reflexive candidate.

一旦分配了服务器自反候选者和中继候选者，必须保持它们活跃，直到 ICE 处理完成，如 [第 8.3 节](#section-8.3) 中所述。对于通过 Binding 请求学习的服务器自反候选者，必须通过向服务器发送额外的 Binding 请求来保持绑定的活跃。分配的刷新使用 Refresh 事务完成，如 [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")] 中所述。Refresh 请求也将刷新服务器自反候选者。

Host candidates do not time out, but the candidate addresses may change or disappear for a number of reasons. An ICE agent SHOULD monitor the interfaces it uses, invalidate candidates whose base has gone away, and acquire new candidates as appropriate when new IP addresses (on new or currently used interfaces) appear.

主机候选者不会超时，但候选者地址可能因多种原因而改变或消失。ICE 代理应该监控其使用的接口，使基础已消失的候选者失效，并在新的 IP 地址出现在新接口或当前使用的接口上时适当地获取新候选者。

### 5.1.2. Prioritizing Candidates | 5.1.2. 候选者优先级

The prioritization process results in the assignment of a priority to each candidate. Each candidate for a data stream MUST have a unique priority that MUST be a positive integer between 1 and (2\*\*31 - 1). This priority will be used by ICE to determine the order of the connectivity checks and the relative preference for candidates. Higher-priority values give more priority over lower values.

优先级过程导致为每个候选者分配优先级。数据流的每个候选者必须具有唯一的优先级，优先级必须是介于 1 和 (2\*\*31 - 1) 之间的正整数。此优先级将被 ICE 用来确定连通性检查的顺序和候选者的相对偏好。较高的优先级值比较低的值具有更多优先级。

An ICE agent SHOULD compute this priority using the formula in [Section 5.1.2.1](#section-5.1.2.1) and choose its parameters using the guidelines in [Section 5.1.2.2](#section-5.1.2.2). If an agent elects to use a different formula, ICE may take longer to converge since the agents will not be coordinated in their checks.

ICE 代理应该使用 [第 5.1.2.1 节](#section-5.1.2.1) 中的公式计算此优先级，并使用 [第 5.1.2.2 节](#section-5.1.2.2) 中的指南选择其参数。如果代理选择使用不同的公式，ICE 可能需要更长时间才能收敛，因为代理在检查中不会协调。

The process for prioritizing candidates is common across the initiating and the responding agent.

候选者优先级排序过程在发起代理和响应代理中是相同的。

---

### 5.1.2.1. Recommended Formula | 5.1.2.1. 推荐公式

The recommended formula combines a preference for the candidate type (server reflexive, peer reflexive, relayed, and host), a preference for the IP address for which the candidate was obtained, and a component ID using the following formula:

推荐的公式结合了候选者类型的偏好（服务器自反、对端自反、中继和主机）、获取候选者的 IP 地址的偏好以及组件 ID，使用以下公式：

```
priority = (2^24)*(type preference) +
           (2^8)*(local preference) +
           (2^0)*(256 - component ID)
```

The type preference MUST be an integer from 0 (lowest preference) to 126 (highest preference) inclusive, MUST be identical for all candidates of the same type, and MUST be different for candidates of different types. The type preference for peer-reflexive candidates MUST be higher than that of server-reflexive candidates. Setting the value to 0 means that candidates of this type will only be used as a last resort. Note that candidates gathered based on the procedures of [Section 5.1.1](#section-5.1.1) will never be peer-reflexive candidates; candidates of this type are learned from the connectivity checks performed by ICE.

类型优先级必须是一个介于 0（最低偏好）到 126（最高偏好，含）之间的整数，对于相同类型的所有候选者必须相同，对于不同类型的候选者必须不同。对端自反候选者的类型优先级必须高于服务器自反候选者。将值设置为 0 意味着此类型的候选者将仅作为最后手段使用。请注意，基于 [第 5.1.1 节](#section-5.1.1) 中的过程收集的候选者永远不会是对端自反候选者；此类型的候选者是从 ICE 执行的连通性检查中学习的。

The local preference MUST be an integer from 0 (lowest preference) to 65535 (highest preference) inclusive. When there is only a single IP address, this value SHOULD be set to 65535. If there are multiple candidates for a particular component for a particular data stream that have the same type, the local preference MUST be unique for each one. If an ICE agent is dual stack, the local preference SHOULD be set according to the current best practice described in [[RFC8421](./rfc8421 "\"Interactive Connectivity Establishment (ICE) Multihomed and IPv4/IPv6 Dual-Stack Guidelines\"")].

本地优先级必须是一个介于 0（最低偏好）到 65535（最高偏好，含）之间的整数。当只有一个 IP 地址时，此值应设置为 65535。如果特定数据流的特定组件有多个具有相同类型的候选者，本地优先级对于每个候选者必须唯一。如果 ICE 代理是双栈，本地优先级应根据 [[RFC8421](./rfc8421 "\"Interactive Connectivity Establishment (ICE) Multihomed and IPv4/IPv6 Dual-Stack Guidelines\"")] 中描述的当前最佳实践设置。

The component ID MUST be an integer between 1 and 256 inclusive.

组件 ID 必须是一个介于 1 和 256（含）之间的整数。

---

### 5.1.2.2. Guidelines for Choosing Type and Local Preferences | 5.1.2.2. 类型和本地优先级选择指南

The RECOMMENDED values for type preferences are 126 for host candidates, 110 for peer-reflexive candidates, 100 for server-reflexive candidates, and 0 for relayed candidates.

类型优先级的推荐值为：主机候选者 126，对端自反候选者 110，服务器自反候选者 100，中继候选者 0。

If an ICE agent is multihomed and has multiple IP addresses, the recommendations in [[RFC8421](./rfc8421 "\"Interactive Connectivity Establishment (ICE) Multihomed and IPv4/IPv6 Dual-Stack Guidelines\"")] SHOULD be followed. If multiple TURN servers are used, local priorities for the candidates obtained from the TURN servers are chosen in a similar fashion as for multihomed local candidates: the local preference value is used to indicate a preference among different servers, but the preference MUST be unique for each one.

如果 ICE 代理是多宿主的并有多个 IP 地址，应遵循 [[RFC8421](./rfc8421 "\"Interactive Connectivity Establishment (ICE) Multihomed and IPv4/IPv6 Dual-Stack Guidelines\"")] 中的建议。如果使用多个 TURN 服务器，从 TURN 服务器获取的候选者的本地优先级以类似于多宿主本地候选者的方式选择：本地优先级值用于指示不同服务器之间的偏好，但偏好对于每个服务器必须唯一。

When choosing type preferences, agents may take into account factors such as latency, packet loss, cost, network topology, security, privacy, and others.

在选择类型优先级时，代理可以考虑延迟、数据包丢失、成本、网络拓扑、安全性、隐私性等因素。

---

### 5.1.3. Eliminating Redundant Candidates | 5.1.3. 消除冗余候选者

Next, the ICE agents (initiating and responding) eliminate redundant candidates. Two candidates can have the same transport address yet different bases, and these would not be considered redundant. Frequently, a server-reflexive candidate and a host candidate will be redundant when the agent is not behind a NAT. A candidate is redundant if and only if its transport address and base equal those of another candidate. The agent SHOULD eliminate the redundant candidate with the lower priority.

接下来，ICE 代理（发起和响应）消除冗余候选者。两个候选者可能具有相同的传输地址但不同的基础，这些不会被视为冗余。通常，当代理不在 NAT 之后时，服务器自反候选者和主机候选者将是冗余的。当且仅当候选者的传输地址和基础等于另一个候选者的传输地址和基础时，该候选者是冗余的。代理应该消除优先级较低的冗余候选者。

## 5.2. Lite Implementation Procedures | 5.2. 轻量级实现程序

Lite implementations only utilize host candidates. For each IP address, independent of an IP address family, there MUST be zero or one candidate. With the lite implementation, ICE cannot be used to dynamically choose amongst candidates. Therefore, including more than one candidate from a particular IP address family is NOT RECOMMENDED, since only a connectivity check can truly determine whether to use one address or the other. Instead, it is RECOMMENDED that agents that have multiple public IP addresses run full ICE implementations to ensure the best usage of its addresses.

轻量级实现仅使用主机候选者。对于每个 IP 地址（独立于 IP 地址族），必须为零个或一个候选者。使用轻量级实现，ICE 不能用于动态选择候选者。因此，不建议从特定 IP 地址族包含多个候选者，因为只有连通性检查才能真正确定是使用一个地址还是另一个地址。相反，建议拥有多个公共 IP 地址的代理运行完整 ICE 实现，以确保最佳利用其地址。

Each component has an ID assigned to it, called the "component ID". For RTP/RTCP data streams, unless RTCP is multiplexed in the same port with RTP, the RTP itself has a component ID of 1 and RTCP a component ID of 2. If an agent is using RTCP without multiplexing, it MUST obtain candidates for it. However, absence of a component ID 2 as such does not imply use of RTCP/RTP multiplexing, as it could also mean that RTCP is not used.

每个组件都有一个分配给它的 ID，称为"组件 ID"。对于 RTP/RTCP 数据流，除非 RTCP 与 RTP 在同一端口上复用，否则 RTP 本身的组件 ID 为 1，RTCP 的组件 ID 为 2。如果代理使用 RTCP 而不复用，它必须为其获取候选者。然而，缺少组件 ID 2 并不意味着使用了 RTCP/RTP 复用，因为它也可能意味着 RTCP 未被使用。

Each candidate is assigned a foundation. The foundation MUST be different for two candidates allocated from different IP addresses; otherwise, it MUST be the same. A simple integer that increments for each IP address will suffice. In addition, each candidate MUST be assigned a unique priority amongst all candidates for the same data stream. If the formula in [Section 5.1.2.1](#section-5.1.2.1) is used to calculate the priority, the type preference value SHOULD be set to 126. If a host is IPv4 only, the local preference value SHOULD be set to 65535. If a host is IPv6 only, the local preference value SHOULD be set to the precedence value for IP addresses described in [RFC 6724](./rfc6724) [[RFC6724](./rfc6724 "\"Default Address Selection for Internet Protocol Version 6 (IPv6)\"")].

每个候选者被分配一个 foundation。从不同 IP 地址分配的两个候选者的 foundation 必须不同；否则，它们必须相同。一个简单的随每个 IP 地址递增的整数就足够了。此外，每个候选者必须在同一数据流的所有候选者中分配唯一的优先级。如果使用 [第 5.1.2.1 节](#section-5.1.2.1) 中的公式计算优先级，类型优先级值应设置为 126。如果主机仅支持 IPv4，本地优先级值应设置为 65535。如果主机仅支持 IPv6，本地优先级值应设置为 [RFC 6724](./rfc6724) [[RFC6724](./rfc6724 "\"Default Address Selection for Internet Protocol Version 6 (IPv6)\"")] 中描述的 IP 地址优先级值。

Next, an agent chooses a default candidate for each component of each data stream. If a host is IPv4 only, there would only be one candidate for each component of each data stream; therefore, that candidate is the default. If a host is IPv6 only, the default candidate would typically be a globally scoped IPv6 address. Dual-stack hosts SHOULD allow configuration whether IPv4 or IPv6 is used for the default candidate, and the configuration needs to be based on which one its administrator believes has a higher chance of success in the current network environment.

接下来，代理为每个数据流的每个组件选择默认候选者。如果主机仅支持 IPv4，每个数据流的每个组件只有一个候选者；因此，该候选者就是默认值。如果主机仅支持 IPv6，默认候选者通常是全局范围的 IPv6 地址。双栈主机应该允许配置是使用 IPv4 还是 IPv6 作为默认候选者，配置需要基于其管理员认为在当前网络环境中具有更高成功机会的那个。

The procedures in this section are common across the initiating and responding agents.

本节中的过程在发起代理和响应代理中是相同的。

---

## 5.3. Exchanging Candidate Information | 5.3. 交换候选者信息

ICE agents (initiating and responding) need the following information about candidates to be exchanged. Each ICE usage MUST define how the information is exchanged with the using protocol. This section describes the information that needs to be exchanged.

ICE 代理（发起和响应）需要交换以下关于候选者的信息。每个 ICE 用法必须定义如何使用使用协议交换信息。本节描述需要交换的信息。

**Candidates | 候选者**

One or more candidates. For each candidate:
一个或多个候选者。对于每个候选者：

* Address: The IP address and transport protocol port of the candidate.
* 地址：候选者的 IP 地址和传输协议端口。

* Transport: The transport protocol of the candidate. This MAY be omitted if the using protocol only runs over a single transport protocol.
* 传输：候选者的传输协议。如果使用协议仅在单一传输协议上运行，则可以省略。

* Foundation: A sequence of up to 32 characters.
* Foundation：最多 32 个字符的序列。

* Component ID: The component ID of the candidate. This MAY be omitted if the using protocol does not use the concept of components.
* 组件 ID：候选者的组件 ID。如果使用协议不使用组件概念，则可以省略。

* Priority: The 32-bit priority of the candidate.
* 优先级：候选者的 32 位优先级。

* Type: The type of the candidate.
* 类型：候选者的类型。

* Related Address and Port: The related IP address and port of the candidate. These MAY be omitted or set to invalid values if the agent does not want to reveal them, e.g., for privacy reasons.
* 相关地址和端口：候选者的相关 IP 地址和端口。如果代理不想透露这些信息（例如，出于隐私原因），可以省略或设置为无效值。

* Extensibility Parameters: The using protocol might define means for adding new per-candidate ICE parameters in the future.
* 可扩展性参数：使用协议可能会定义未来添加每个候选者新 ICE 参数的手段。

**Lite or Full | 轻量级或完整**

Whether the agent is a lite agent or full agent.
代理是轻量级代理还是完整代理。

**Connectivity-Check Pacing Value | 连通性检查节拍值**

The pacing value for connectivity checks that the agent wishes to use. This MAY be omitted if the agent wishes to use a defined default value.
代理希望使用的连通性检查的节拍值。如果代理希望使用定义的默认值，则可以省略。

**Username Fragment and Password | 用户名片段和密码**

Values used to perform connectivity checks. The values MUST be unguessable, with at least 128 bits of random number generator output used to generate the password, and at least 24 bits of output to generate the username fragment.
用于执行连通性检查的值。这些值必须不可猜测，使用至少 128 位的随机数生成器输出生成密码，使用至少 24 位的输出生成用户名片段。

**Extensions | 扩展**

New media-stream or session-level attributes (ICE options).
新的媒体流或会话级属性（ICE 选项）。

If the using protocol is vulnerable to, and able to detect, ICE mismatch ([Section 5.4](#section-5.4)), a way is needed for the detecting agent to convey this information to its peer. It is a boolean flag.

如果使用协议容易受到并能够检测 ICE 不匹配（[第 5.4 节](#section-5.4)），检测代理需要一种方式将此信息传达给其对端。它是一个布尔标志。

The using protocol may (or may not) need to deal with backwards compatibility with older implementations that do not support ICE. If a fallback mechanism to non-ICE is supported and is being used, then presumably the using protocol provides a way of conveying the default candidate (its IP address and port) in addition to the ICE parameters.

使用协议可能需要（也可能不需要）处理与不支持 ICE 的旧实现的向后兼容性。如果支持并正在使用非 ICE 回退机制，则使用协议应该提供一种除了 ICE 参数之外传达默认候选者（其 IP 地址和端口）的方式。

Once an agent has sent its candidate information, it MUST be prepared to receive both STUN and data packets on each candidate. As discussed in [Section 12.1](#section-12.1), data packets can be sent to a candidate prior to its appearance as the default destination for data.

一旦代理发送了其候选者信息，它必须准备好在每个候选者上接收 STUN 和数据包。如 [第 12.1 节](#section-12.1) 中所讨论的，数据包可以在候选者作为数据默认目的地出现之前发送到该候选者。

## 5.4. ICE Mismatch | 5.4. ICE 不匹配

Certain middleboxes, such as ALGs, can alter signaling information in ways that break ICE (e.g., by rewriting IP addresses in SDP). This is referred to as "ICE mismatch". If the using protocol is vulnerable to ICE mismatch, the responding agent needs to be able to detect it and inform the peer ICE agent about the ICE mismatch.

某些中间盒（如 ALG）可以以破坏 ICE 的方式改变信令信息（例如，通过重写 SDP 中的 IP 地址）。这被称为"ICE 不匹配"。如果使用协议容易受到 ICE 不匹配的影响，响应代理需要能够检测到它并通知对端 ICE 代理有关 ICE 不匹配的信息。

Each using protocol needs to define whether the using protocol is vulnerable to ICE mismatch, how ICE mismatch is detected, and whether specific actions need to be taken when ICE mismatch is detected.

每个使用协议需要定义使用协议是否容易受到 ICE 不匹配的影响，如何检测 ICE 不匹配，以及在检测到 ICE 不匹配时是否需要采取特定操作。

# 6. ICE Candidate Processing | 6. ICE 候选者处理

Once an ICE agent has gathered its candidates and exchanged candidates with its peer ([Section 5](#section-5)), it will determine its own role. In addition, full implementations will form checklists and begin performing connectivity checks with the peer.

一旦 ICE 代理收集了其候选者并与对端交换了候选者（[第 5 节](#section-5)），它将确定自己的角色。此外，完整实现将形成检查列表并开始与对端执行连通性检查。

---

## 6.1. Procedures for Full Implementation | 6.1. 完整实现程序

### 6.1.1. Determining Role | 6.1.1. 确定角色

For each session, each ICE agent (initiating and responding) takes on a role. There are two roles -- controlling and controlled. The controlling agent is responsible for the choice of the final candidate pairs used for communications. The sections below describe in detail the actual procedures followed by controlling and controlled agents.

对于每个会话，每个 ICE 代理（发起和响应）都承担一个角色。有两个角色——控制方和被控方。控制代理负责选择用于通信的最终候选者对。以下各节详细描述控制代理和被控代理遵循的实际程序。

The rules for determining the role and the impact on behavior are as follows:

确定角色及行为影响的规则如下：

**Both agents are full | 两个代理都是完整实现**

The initiating agent that started the ICE processing MUST take the controlling role, and the other MUST take the controlled role. Both agents will form checklists, run the ICE state machines, and generate connectivity checks. The controlling agent will execute the logic in [Section 8.1](#section-8.1) to nominate pairs that will become (if the connectivity checks associated with the nominations succeed) the selected pairs, and then both agents end ICE as described in [Section 8.1.2](#section-8.1.2).

发起 ICE 处理的发起代理必须承担控制角色，另一个必须承担被控角色。两个代理都将形成检查列表、运行 ICE 状态机并生成连通性检查。控制代理将执行 [第 8.1 节](#section-8.1) 中的逻辑来提名候选对，这些候选对将成为（如果与提名关联的连通性检查成功）选定对，然后两个代理如 [第 8.1.2 节](#section-8.1.2) 中所述结束 ICE。

**One agent full, one lite | 一个代理完整，一个轻量级**

The full agent MUST take the controlling role, and the lite agent MUST take the controlled role. The full agent will form checklists, run the ICE state machines, and generate connectivity checks. That agent will execute the logic in [Section 8.1](#section-8.1) to nominate pairs that will become (if the connectivity checks associated with the nominations succeed) the selected pairs and use the logic in [Section 8.1.2](#section-8.1.2) to end ICE. The lite implementation will just listen for connectivity checks, receive them and respond to them, and then conclude ICE as described in [Section 8.2](#section-8.2). For the lite implementation, the state of ICE processing for each data stream is considered to be Running, and the state of ICE overall is Running.

完整代理必须承担控制角色，轻量级代理必须承担被控角色。完整代理将形成检查列表、运行 ICE 状态机并生成连通性检查。该代理将执行 [第 8.1 节](#section-8.1) 中的逻辑来提名候选对，这些候选对将成为（如果与提名关联的连通性检查成功）选定对，并使用 [第 8.1.2 节](#section-8.1.2) 中的逻辑结束 ICE。轻量级实现将仅监听连通性检查，接收并响应它们，然后如 [第 8.2 节](#section-8.2) 中所述结束 ICE。对于轻量级实现，每个数据流的 ICE 处理状态被视为 Running，ICE 整体状态为 Running。

**Both lite | 两个都是轻量级**

The initiating agent that started the ICE processing MUST take the controlling role, and the other MUST take the controlled role. In this case, no connectivity checks are ever sent. Rather, once the candidates are exchanged, each agent performs the processing described in [Section 8](#section-8) without connectivity checks. It is possible that both agents will believe they are controlled or controlling. In the latter case, the conflict is resolved through glare detection capabilities in the signaling protocol enabling the candidate exchange. The state of ICE processing for each data stream is considered to be Running, and the state of ICE overall is Running.

发起 ICE 处理的发起代理必须承担控制角色，另一个必须承担被控角色。在这种情况下，永远不会发送连通性检查。相反，一旦交换了候选者，每个代理执行 [第 8 节](#section-8) 中描述的处理，但不带连通性检查。两个代理都可能认为自己是被控方或控制方。在后一种情况下，冲突通过信令协议中实现候选者交换的眩光检测能力来解决。每个数据流的 ICE 处理状态被视为 Running，ICE 整体状态为 Running。

Once the roles are determined for a session, they persist throughout the lifetime of the session. The roles can be redetermined as part of an ICE restart ([Section 9](#section-9)), but an ICE agent MUST NOT redetermine the role as part of an ICE restart unless one or more of the following criteria is fulfilled:

一旦为会话确定了角色，它们将在会话的整个生命周期内保持。角色可以作为 ICE 重启的一部分重新确定（[第 9 节](#section-9)），但 ICE 代理不得作为 ICE 重启的一部分重新确定角色，除非满足以下一个或多个条件：

**Full becomes lite | 完整变为轻量级**

If the controlling agent is full, and switches to lite, the roles MUST be redetermined if the peer agent is also full.

如果控制代理是完整的并切换到轻量级，如果对端代理也是完整的，则必须重新确定角色。

**Role conflict | 角色冲突**

If the ICE restart causes a role conflict, the roles might be redetermined due to the role conflict procedures in [Section 7.3.1.1](#section-7.3.1.1).

如果 ICE 重启导致角色冲突，由于 [第 7.3.1.1 节](#section-7.3.1.1) 中的角色冲突过程，角色可能会被重新确定。

> NOTE: There are certain Third Party Call Control (3PCC) [[RFC3725](./rfc3725 "\"Best Current Practices for Third Party Call Control (3pcc) in the Session Initiation Protocol (SIP)\"")] scenarios where an ICE restart might cause a role conflict.
> 注意：某些第三方呼叫控制 (3PCC) [[RFC3725](./rfc3725 "\"Best Current Practices for Third Party Call Control (3pcc) in the Session Initiation Protocol (SIP)\"")] 场景中，ICE 重启可能会导致角色冲突。

> NOTE: The agents need to inform each other whether they are full or lite before the roles are determined. The mechanism for that is specific to the signaling protocol and outside the scope of the document.
> 注意：代理需要在确定角色之前相互告知它们是完整还是轻量级。该机制是特定于信令协议的，超出本文档的范围。

An agent MUST accept if the peer initiates a redetermination of the roles even if the criteria for doing so are not fulfilled. This can happen if the peer is compliant with [RFC 5245](./rfc5245).

如果对端发起角色重新确定，即使不满足这样做标准，代理也必须接受。如果对端符合 [RFC 5245](./rfc5245)，则可能发生这种情况。

---

### 6.1.2. Forming the Checklists | 6.1.2. 形成检查列表

There is one checklist for each data stream. To form a checklist, initiating and responding ICE agents form candidate pairs, compute pair priorities, order pairs by priority, prune pairs, remove lower-priority pairs, and set checklist states. If candidates are added to a checklist (e.g., due to detection of peer-reflexive candidates), the agent will re-perform these steps for the updated checklist.

每个数据流有一个检查列表。要形成检查列表，发起和响应 ICE 代理形成候选者对、计算候选对优先级、按优先级排序候选对、剪枝候选对、移除较低优先级候选对，并设置检查列表状态。如果候选者被添加到检查列表（例如，由于检测到对端自反候选者），代理将为更新的检查列表重新执行这些步骤。

---

#### 6.1.2.1. Checklist State | 6.1.2.1. 检查列表状态

Each checklist has a state, which captures the state of ICE checks for the data stream associated with the checklist. The states are:

每个检查列表都有一个状态，它捕获与检查列表关联的数据流的 ICE 检查状态。状态如下：

**Running | 运行中**

The checklist is neither Completed nor Failed yet. Checklists are initially set to the Running state.

检查列表既未 Completed 也未 Failed。检查列表最初设置为 Running 状态。

**Completed | 已完成**

The checklist contains a nominated pair for each component of the data stream.

检查列表包含数据流每个组件的提名对。

**Failed | 失败**

The checklist does not have a valid pair for each component of the data stream, and all of the candidate pairs in the checklist are in either the Failed or the Succeeded state. In other words, at least one component of the checklist has candidate pairs that are all in the Failed state, which means the component has failed, which means the checklist has failed.

检查列表没有数据流每个组件的有效对，并且检查列表中的所有候选者对都处于 Failed 或 Succeeded 状态。换句话说，检查列表的至少一个组件的候选者对都处于 Failed 状态，这意味着该组件失败了，这意味着检查列表失败了。

---

#### 6.1.2.2. Forming Candidate Pairs | 6.1.2.2. 形成候选者对

The ICE agent pairs each local candidate with each remote candidate for the same component of the same data stream with the same IP address family. It is possible that some of the local candidates won't get paired with remote candidates, and some of the remote candidates won't get paired with local candidates. This can happen if one agent doesn't include candidates for all of the components for a data stream. If this happens, the number of components for that data stream is effectively reduced and is considered to be equal to the minimum across both agents of the maximum component ID provided by each agent across all components for the data stream.

ICE 代理将每个本地候选者与同一数据流同一组件的同一 IP 地址族的每个远程候选者配对。某些本地候选者可能不会与远程候选者配对，某些远程候选者可能不会与本地候选者配对。如果一个代理没有为数据流的所有组件包含候选者，就会发生这种情况。如果发生这种情况，该数据流的组件数量会有效减少，被视为等于两个代理在数据流所有组件上提供的最大组件 ID 中的最小值。

In the case of RTP, this would happen when one agent provides candidates for RTCP, and the other does not. As another example, the initiating agent can multiplex RTP and RTCP on the same port [[RFC5761](./rfc5761 "\"Multiplexing RTP Data and Control Packets on a Single Port\"")]. However, since the initiating agent doesn't know if the peer agent can perform such multiplexing, it includes candidates for RTP and RTCP on separate ports. If the peer agent can perform such multiplexing, it would include just a single component for each candidate -- for the combined RTP/RTCP mux. ICE would end up acting as if there was just a single component for this candidate.

在 RTP 的情况下，当一个代理为 RTCP 提供候选者而另一个不提供时，就会发生这种情况。另一个例子是，发起代理可以在同一端口上复用 RTP 和 RTCP [[RFC5761](./rfc5761 "\"Multiplexing RTP Data and Control Packets on a Single Port\"")]]。然而，由于发起代理不知道对端代理是否能执行这种复用，它在单独的端口上包含 RTP 和 RTCP 的候选者。如果对端代理能执行这种复用，它将为每个候选者只包含一个组件——用于组合的 RTP/RTCP 复用。ICE 最终将表现得好像这个候选者只有一个组件一样。

With IPv6, it is common for a host to have multiple host candidates for each interface. To keep the amount of resulting candidate pairs reasonable and to avoid candidate pairs that are highly unlikely to work, IPv6 link-local addresses MUST NOT be paired with other than link-local addresses.

使用 IPv6，主机通常为每个接口有多个主机候选者。为了使生成的候选者对数量合理并避免极不可能工作的候选者对，IPv6 链路本地地址不得与链路本地地址以外的地址配对。

The candidate pairs whose local and remote candidates are both the default candidates for a particular component is called the "default candidate pair" for that component. This is the pair that would be used to transmit data if both agents had not been ICE aware.

本地和远程候选者都是特定组件默认候选者的候选者对称为该组件的"默认候选者对"。如果两个代理都不支持 ICE，这将是要用于传输数据的候选对。

#### 6.1.2.3. Computing Pair Priority and Ordering Pairs | 6.1.2.3. 计算候选对优先级和对排序

The ICE agent computes a priority for each candidate pair. Let G be the priority for the candidate provided by the controlling agent. Let D be the priority for the candidate provided by the controlled agent. The priority for a pair is computed as follows:

ICE 代理为每个候选者对计算优先级。设 G 为控制代理提供的候选者的优先级。设 D 为被控代理提供的候选者的优先级。候选对的优先级计算如下：

```
pair priority = 2^32*MIN(G,D) + 2*MAX(G,D) + (G>D?1:0)
```

The agent sorts each checklist in decreasing order of candidate pair priority. If two pairs have identical priority, the ordering amongst them is arbitrary.

代理按候选对优先级降序对每个检查列表排序。如果两个候选对的优先级相同，它们之间的排序是任意的。

---

#### 6.1.2.4. Pruning the Pairs | 6.1.2.4. 剪枝候选对

This sorted list of candidate pairs is used to determine a sequence of connectivity checks that will be performed. Each check involves sending a request from a local candidate to a remote candidate. Since an ICE agent cannot send requests directly from a reflexive candidate (server reflexive or peer reflexive), but only from its base, the agent next goes through the sorted list of candidate pairs. For each pair where the local candidate is reflexive, the candidate MUST be replaced by its base.

此排序后的候选者对列表用于确定将执行的连通性检查序列。每个检查涉及从本地候选者向远程候选者发送请求。由于 ICE 代理不能直接从自反候选者（服务器自反或对端自反）发送请求，只能从其基础发送，代理接下来遍历排序后的候选者对列表。对于本地候选者是自反的每个候选对，必须用其基础替换候选者。

The agent prunes each checklist. This is done by removing a candidate pair if it is redundant with a higher-priority candidate pair in the same checklist. Two candidate pairs are redundant if their local candidates have the same base and their remote candidates are identical. The result is a sequence of ordered candidate pairs, called the "checklist" for that data stream.

代理对每个检查列表进行剪枝。这是通过移除与同一检查列表中更高优先级候选对冗余的候选对来完成的。如果两个候选对的本地候选者具有相同基础且远程候选者相同，则它们是冗余的。结果是称为该数据流"检查列表"的有序候选者对序列。

---

#### 6.1.2.5. Removing Lower-Priority Pairs | 6.1.2.5. 移除低优先级候选对

In order to limit the attacks described in [Section 19.5.1](#section-19.5.1), an ICE agent MUST limit the total number of connectivity checks the agent performs across all checklists in the checklist set. This is done by limiting the total number of candidate pairs in the checklist set. The default limit of candidate pairs for the checklist set is 100, but the value MUST be configurable. The limit is enforced by, within in each checklist, discarding lower-priority candidate pairs until the total number of candidate pairs in the checklist set is smaller than the limit value. The discarding SHOULD be done evenly so that the number of candidate pairs in each checklist is reduced the same amount.

为了限制 [第 19.5.1 节](#section-19.5.1) 中描述的攻击，ICE 代理必须限制代理在检查列表集中所有检查列表上执行的连通性检查总数。这是通过限制检查列表集中候选者对的总数来完成的。检查列表集候选者对的默认限制是 100，但该值必须可配置。限制是通过在每个检查列表中丢弃较低优先级的候选者对，直到检查列表集中候选者对的总数小于限制值来执行的。丢弃应该均匀进行，使每个检查列表中的候选者对数量减少相同的量。

It is RECOMMENDED that a lower-limit value than the default is picked when possible, and that the value is set to the maximum number of plausible candidate pairs that might be created in an actual deployment configuration. The requirement for configuration is meant to provide a tool for fixing this value in the field if, once deployed, it is found to be problematic.

建议尽可能选择低于默认值的限制值，并将该值设置为在实际部署配置中可能创建的最大合理候选者对数量。要求可配置是为了提供一个工具，以便在部署后发现问题时在现场修复此值。

---

#### 6.1.2.6. Computing Candidate Pair States | 6.1.2.6. 计算候选者对状态

Each candidate pair in the checklist has a foundation (the combination of the foundations of the local and remote candidates in the pair) and one of the following states:

检查列表中的每个候选者对都有一个 foundation（候选对中本地和远程候选者 foundation 的组合）和以下状态之一：

**Waiting | 等待中**

A check has not been sent for this pair, but the pair is not Frozen.
尚未为此候选对发送检查，但候选对不是 Frozen 状态。

**In-Progress | 进行中**

A check has been sent for this pair, but the transaction is in progress.
已为此候选对发送检查，但事务正在进行中。

**Succeeded | 成功**

A check has been sent for this pair, and it produced a successful result.
已为此候选对发送检查，并产生了成功结果。

**Failed | 失败**

A check has been sent for this pair, and it failed (a response to the check was never received, or a failure response was received).
已为此候选对发送检查，但失败了（从未收到检查的响应，或收到了失败响应）。

**Frozen | 冻结**

A check for this pair has not been sent, and it cannot be sent until the pair is unfrozen and moved into the Waiting state.
尚未为此候选对发送检查，在候选对解冻并移动到 Waiting 状态之前不能发送检查。

Pairs move between states as shown in Figure 6.

候选对按照图 6 所示在状态之间移动。

```

      |           |
      |           |
      |  Frozen   |
      |           |
      |           |
      +-----------+
            |
            |unfreeze
            |
            V
      +-----------+         +-----------+
      |           |         |           |
      |           | perform |           |
      |  Waiting  |-------->|In-Progress|
      |           |         |           |
      |           |         |           |

                                //  |

                     //             |

      +-----------+         +-----------+

              Figure 6: Pair State Finite State Machine (FSM)
              图 6: 候选对状态有限状态机 (FSM)
```

The initial states for each pair in a checklist are computed by performing the following sequence of steps:

检查列表中每个候选对的初始状态通过执行以下步骤序列来计算：

1. The checklists are placed in an ordered list (the order is determined by each ICE usage), called the "checklist set".
   检查列表被放入有序列表（顺序由每个 ICE 用法确定），称为"检查列表集"。

2. The ICE agent initially places all candidate pairs in the Frozen state.
   ICE 代理最初将所有候选者对置于 Frozen 状态。

3. The agent sets all of the checklists in the checklist set to the Running state.
   代理将检查列表集中所有检查列表设置为 Running 状态。

4. For each foundation, the agent sets the state of exactly one candidate pair to the Waiting state (unfreezing it). The candidate pair to unfreeze is chosen by finding the first candidate pair (ordered by the lowest component ID and then the highest priority if component IDs are equal) in the first checklist (according to the usage-defined checklist set order) that has that foundation.
   对于每个 foundation，代理将恰好一个候选者对的状态设置为 Waiting 状态（解冻它）。要解冻的候选者对是通过在第一个检查列表（根据用法定义的检查列表集顺序）中找到具有该 foundation 的第一个候选者对（按最低组件 ID 排序，如果组件 ID 相同则按最高优先级排序）来选择的。

> NOTE: The procedures above are different from [RFC 5245](./rfc5245), where only candidate pairs in the first checklist were initially placed in the Waiting state. Now it applies to candidate pairs in the first checklist that have that foundation, even if the checklist is not the first one in the checklist set.
> 注意：上述过程与 [RFC 5245](./rfc5245) 不同，后者最初只有第一个检查列表中的候选者对被置于 Waiting 状态。现在它适用于第一个检查列表中具有该 foundation 的候选者对，即使该检查列表不是检查列表集中的第一个。

下表说明了一个示例。

Each column (f1, f2,...) represents a foundation. Every candidate pair within a given column share the same foundation.

   对于每个 foundation，具有最低组件 ID 的候选者对被置于 Waiting 状态，除非与同一 foundation 关联的候选者对已在检查列表集中其他检查列表中置于 Waiting 状态。

In the first checklist (m1), the candidate pair for each foundation is placed in the Waiting state, as no pairs for the same foundations have yet been placed in the Waiting state.
在第一个检查列表 (m1) 中，每个 foundation 的候选者对被置于 Waiting 状态，因为尚未将与相同 foundation 关联的候选对置于 Waiting 状态。

In the second checklist (m2), the candidate pair for foundation f4 is placed in the Waiting state. The candidate pair for foundations f1, f2, and f3 are kept in the Frozen state, as candidate pairs for those foundations have already been placed in the Waiting state (within checklist m1).
在第二个检查列表 (m2) 中，foundation f4 的候选者对被置于 Waiting 状态。Foundation f1、f2 和 f3 的候选者对保持 Frozen 状态，因为这些 foundation 的候选者对已在（检查列表 m1 中）置于 Waiting 状态。

In the third checklist (m3), the candidate pair for foundation f5 is placed in the Waiting state. The candidate pair for foundation f1 is kept in the Frozen state, as a candidate pair for that foundation has already been placed in the Waiting state (within checklist m1).
在第三个检查列表 (m3) 中，foundation f5 的候选者对被置于 Waiting 状态。Foundation f1 的候选者对保持 Frozen 状态，因为该 foundation 的候选者对已在（检查列表 m1 中）置于 Waiting 状态。

Once each checklist have been processed, one candidate pair for each foundation in the checklist set has been placed in the Waiting state.
一旦处理完每个检查列表，检查列表集中每个 foundation 的一个候选者对已被置于 Waiting 状态。

### 6.1.3. ICE State | 6.1.3. ICE 状态

The ICE agent has a state determined by the state of the checklists. The state is Completed if all checklists are Completed, Failed if all checklists are Failed, or Running otherwise.

ICE 代理有一个由检查列表状态决定的状态。如果所有检查列表都是 Completed，则状态为 Completed；如果所有检查列表都是 Failed，则状态为 Failed；否则为 Running。

---

### 6.1.4. Scheduling Checks | 6.1.4. 调度检查

#### 6.1.4.1. Triggered-Check Queue | 6.1.4.1. 触发检查队列

Once the ICE agent has computed the checklists and created the checklist set, as described in [Section 6.1.2](#section-6.1.2), the agent will begin performing connectivity checks (ordinary and triggered). For triggered connectivity checks, the agent maintains a FIFO queue for each checklist, referred to as the "triggered-check queue", which contains candidate pairs for which checks are to be sent at the next available opportunity. The triggered-check queue is initially empty.

一旦 ICE 代理计算了检查列表并创建了检查列表集（如 [第 6.1.2 节](#section-6.1.2) 中所述），代理将开始执行连通性检查（普通和触发）。对于触发的连通性检查，代理为每个检查列表维护一个 FIFO 队列，称为"触发检查队列"，其中包含下次可用机会时发送检查的候选者对。触发检查队列最初为空。

#### 6.1.4.2. Performing Connectivity Checks | 6.1.4.2. 执行连通性检查

The generation of ordinary and triggered connectivity checks is governed by timer Ta. As soon as the initial states for the candidate pairs in the checklist set have been set, a check is performed for a candidate pair within the first checklist in the Running state, following the procedures in [Section 7](#section-7). After that, whenever Ta fires the next checklist in the Running state in the checklist set is picked, and a check is performed for a candidate within that checklist. After the last checklist in the Running state in the checklist set has been processed, the first checklist is picked again, etc.

普通和触发连通性检查的生成由定时器 Ta 控制。一旦为检查列表集中的候选者对设置了初始状态，就按照 [第 7 节](#section-7) 中的程序对 Running 状态第一个检查列表中的候选者对执行检查。之后，每当 Ta 触发时，选择检查列表集中 Running 状态的下个检查列表，并对该检查列表中的候选者执行检查。在处理完检查列表集中 Running 状态的最后一个检查列表后，再次选择第一个检查列表，等等。

Whenever Ta fires, the ICE agent will perform a check for a candidate pair within the checklist that was picked by performing the following steps:

每当 Ta 触发时，ICE 代理将通过对以下步骤选择检查列表中的候选者对执行检查：

1. If the triggered-check queue associated with the checklist contains one or more candidate pairs, the agent removes the top pair from the queue, performs a connectivity check on that pair, puts the candidate pair state to In-Progress, and aborts the subsequent steps.
   如果与检查列表关联的触发检查队列包含一个或多个候选者对，代理从队列中移除顶部的候选对，对该候选对执行连通性检查，将候选对状态设置为 In-Progress，并中止后续步骤。

2. If there is no candidate pair in the Waiting state, and if there are one or more pairs in the Frozen state, the agent checks the foundation associated with each pair in the Frozen state. For a given foundation, if there is no pair (in any checklist in the checklist set) in the Waiting or In-Progress state, the agent puts the candidate pair state to Waiting and continues with the next step.
   如果没有处于 Waiting 状态的候选者对，且有一个或多个处于 Frozen 状态的候选对，代理检查 Frozen 状态中每个候选对关联的 foundation。对于给定的 foundation，如果在检查列表集中任何检查列表中都没有处于 Waiting 或 In-Progress 状态的候选对，代理将候选对状态设置为 Waiting 并继续下一步。

3. If there are one or more candidate pairs in the Waiting state, the agent picks the highest-priority candidate pair (if there are multiple pairs with the same priority, the pair with the lowest component ID is picked) in the Waiting state, performs a connectivity check on that pair, puts the candidate pair state to In-Progress, and aborts the subsequent steps.
   如果有一个或多个处于 Waiting 状态的候选者对，代理选择 Waiting 状态中优先级最高的候选者对（如果有多个具有相同优先级的候选对，选择组件 ID 最低的候选对），对该候选对执行连通性检查，将候选对状态设置为 In-Progress，并中止后续步骤。

4. If this step is reached, no check could be performed for the checklist that was picked. So, without waiting for timer Ta to expire again, select the next checklist in the Running state and return to step #1. If this happens for every single checklist in the Running state, meaning there are no remaining candidate pairs to perform connectivity checks for, abort these steps.
   如果到达此步骤，则无法对所选检查列表执行检查。因此，不等待定时器 Ta 再次到期，选择 Running 状态下下一个检查列表并返回步骤 #1。如果对 Running 状态中的每个检查列表都发生这种情况，意味着没有剩余的候选者对执行连通性检查，则中止这些步骤。

Once the agent has picked a candidate pair for which a connectivity check is to be performed, the agent starts a check and sends the Binding request from the base associated with the local candidate of the pair to the remote candidate of the pair, as described in [Section 7.2.4](#section-7.2.4).

一旦代理选择了要执行连通性检查的候选者对，代理启动检查并从与该候选对的本地候选者关联的基础向该候选对的远程候选者发送 Binding 请求，如 [第 7.2.4 节](#section-7.2.4) 中所述。

Based on local policy, an agent MAY choose to terminate performing the connectivity checks for one or more checklists in the checklist set at any time. However, only the controlling agent is allowed to conclude ICE ([Section 8](#section-8)).

基于本地策略，代理可以选择随时终止对检查列表集中一个或多个检查列表执行连通性检查。但是，只有控制代理被允许结束 ICE（[第 8 节](#section-8)）。

To compute the message integrity for the check, the agent uses the remote username fragment and password learned from the candidate information obtained from its peer. The local username fragment is known directly by the agent for its own candidate.

为了计算检查的消息完整性，代理使用从其对端获取的候选者信息中了解到的远程用户名片段和密码。本地用户名片段由代理直接知道用于自己的候选者。

## 6.2. Lite Implementation Procedures | 6.2. 轻量级实现程序

Lite implementations skip most of the steps in [Section 6](#section-6) except for verifying the peer's ICE support and determining its role in the ICE session, as described in [Section 6.1.1](#section-6.1.1). As described in [Section 8.2](#section-8.2), a lite implementation will only listen for and respond to connectivity checks.

轻量级实现跳过 [第 6 节](#section-6) 中的大多数步骤，除了验证对端的 ICE 支持和确定其在 ICE 会话中的角色（如 [第 6.1.1 节](#section-6.1.1) 中所述）。如 [第 8.2 节](#section-8.2) 中所述，轻量级实现将仅监听和响应连通性检查。

If the lite implementation is the controlling agent (which will only happen if the peer ICE agent is also a lite implementation), it selects a candidate pair based on the ones in the candidate exchange (for IPv4, there is only ever one pair) and then updates the peer with the new candidate information reflecting that selection, if needed (it is never needed for an IPv4-only host).

如果轻量级实现是控制代理（这只会在对端 ICE 代理也是轻量级实现时发生），它根据候选者交换中的候选者选择一个候选者对（对于 IPv4，永远只有一个候选对），然后在需要时（对于仅 IPv4 主机永远不需要）用反映该选择的新候选者信息更新对端。

# 7. Performing Connectivity Checks | 7. 执行连通性检查

This section describes how connectivity checks are performed.

本节描述如何执行连通性检查。

An ICE agent MUST be compliant to [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]. A full implementation acts both as a STUN client and a STUN server, while a lite implementation only acts as a STUN server (as it does not generate connectivity checks).

ICE 代理必须符合 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]。完整实现同时充当 STUN 客户端和 STUN 服务器，而轻量级实现仅充当 STUN 服务器（因为它不生成连通性检查）。

---

## 7.1. STUN Extensions | 7.1. STUN 扩展

ICE extends STUN with the attributes: PRIORITY, USE-CANDIDATE, ICE-CONTROLLED, and ICE-CONTROLLING. These attributes are formally defined in [Section 16.1](#section-16.1). This section describes the usage of the attributes.

ICE 使用以下属性扩展 STUN：PRIORITY、USE-CANDIDATE、ICE-CONTROLLED 和 ICE-CONTROLLING。这些属性在 [第 16.1 节](#section-16.1) 中正式定义。本节描述这些属性的用法。

The attributes are only applicable to ICE connectivity checks.

这些属性仅适用于 ICE 连通性检查。

---

### 7.1.1. PRIORITY

The PRIORITY attribute MUST be included in a Binding request and be set to the value computed by the algorithm in [Section 5.1.2](#section-5.1.2) for the local candidate, but with the candidate type preference of peer-reflexive candidates.

PRIORITY 属性必须包含在 Binding 请求中，并设置为 [第 5.1.2 节](#section-5.1.2) 中为本地候选者计算的算法的值，但对等端自反候选者的候选者类型优先级。

---

### 7.1.2. USE-CANDIDATE

The controlling agent MUST include the USE-CANDIDATE attribute in order to nominate a candidate pair ([Section 8.1.1](#section-8.1.1)). The controlled agent MUST NOT include the USE-CANDIDATE attribute in a Binding request.

控制代理必须包含 USE-CANDIDATE 属性以提名候选者对（[第 8.1.1 节](#section-8.1.1)）。被控代理不得在 Binding 请求中包含 USE-CANDIDATE 属性。

---

### 7.1.3. ICE-CONTROLLED and ICE-CONTROLLING

The controlling agent MUST include the ICE-CONTROLLING attribute in a Binding request. The controlled agent MUST include the ICE-CONTROLLED attribute in a Binding request.

控制代理必须在 Binding 请求中包含 ICE-CONTROLLING 属性。被控代理必须在 Binding 请求中包含 ICE-CONTROLLED 属性。

The content of either attribute is used as tiebreaker values when an ICE role conflict occurs ([Section 7.3.1.1](#section-7.3.1.1)).

当发生 ICE 角色冲突时，任一属性的内容用作决胜值（[第 7.3.1.1 节](#section-7.3.1.1)）。

---

## 7.2. STUN Client Procedures | 7.2. STUN 客户端程序

### 7.2.1. Creating Permissions for Relayed Candidates | 7.2.1. 为中继候选者创建权限

If the connectivity check is being sent using a relayed local candidate, the client MUST create a permission first if it has not already created one previously. It would have created one previously if it had told the TURN server to create a permission for the given relayed candidate towards the IP address of the remote candidate. To create the permission, the ICE agent follows the procedures defined in [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")]. The permission MUST be created towards the IP address of the remote candidate. It is RECOMMENDED that the agent defer creation of a TURN channel until ICE completes, in which case permissions for connectivity checks are normally created using a CreatePermission request. Once established, the agent MUST keep the permission active until ICE concludes.

如果连通性检查是使用中继本地候选者发送的，客户端必须首先创建权限（如果之前尚未创建）。如果之前已告知 TURN 服务器为给定中继候选者创建指向远程候选者 IP 地址的权限，则之前已创建了一个权限。要创建权限，ICE 代理遵循 [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")] 中定义的过程。权限必须针对远程候选者的 IP 地址创建。建议代理推迟创建 TURN 通道直到 ICE 完成，在这种情况下，连通性检查的权限通常使用 CreatePermission 请求创建。一旦建立，代理必须保持权限活跃直到 ICE 结束。

---

### 7.2.2. Forming Credentials | 7.2.2. 形成凭证

A connectivity-check Binding request MUST utilize the STUN short-term credential mechanism.

连通性检查 Binding 请求必须使用 STUN 短期凭证机制。

The username for the credential is formed by concatenating the username fragment provided by the peer with the username fragment of the ICE agent sending the request, separated by a colon (":").

凭证的用户名是通过连接对端提供的用户名片段和发送请求的 ICE 代理的用户名片段形成的，用冒号 (":") 分隔。

The password is equal to the password provided by the peer.

密码等于对端提供的密码。

For example, consider the case where ICE agent L is the initiating agent and ICE agent R is the responding agent. Agent L included a username fragment of LFRAG for its candidates and a password of LPASS. Agent R provided a username fragment of RFRAG and a password of RPASS. A connectivity check from L to R utilizes the username RFRAG:LFRAG and a password of RPASS. A connectivity check from R to L utilizes the username LFRAG:RFRAG and a password of LPASS. The responses utilize the same usernames and passwords as the requests (note that the USERNAME attribute is not present in the response).

例如，考虑 ICE 代理 L 是发起代理而 ICE 代理 R 是响应代理的情况。代理 L 为其候选者包含用户名片段 LFRAG 和密码 LPASS。代理 R 提供用户名片段 RFRAG 和密码 RPASS。从 L 到 R 的连通性检查使用用户名 RFRAG:LFRAG 和密码 RPASS。从 R 到 L 的连通性检查使用用户名 LFRAG:RFRAG 和密码 LPASS。响应使用与请求相同的用户名和密码（请注意，USERNAME 属性不在响应中）。

---

### 7.2.3. Diffserv Treatment | 7.2.3. 差分服务处理

If the agent is using Differentiated Services Code Point (DSCP) markings [[RFC2475](./rfc2475 "\"An Architecture for Differentiated Services\"")] in data packets that it will send, the agent SHOULD apply the same markings to Binding requests and responses that it will send.

如果代理在其将发送的数据包中使用差分服务代码点 (DSCP) 标记 [[RFC2475](./rfc2475 "\"An Architecture for Differentiated Services\"")]，代理应该将相同的标记应用于其将发送的 Binding 请求和响应。

If multiple DSCP markings are used on the data packets, the agent SHOULD choose one of them for use with the connectivity check.

如果数据包上使用多个 DSCP 标记，代理应该选择其中一个用于连通性检查。

---

### 7.2.4. Sending the Request | 7.2.4. 发送请求

A connectivity check is generated by sending a Binding request from the base associated with a local candidate to a remote candidate. [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] describes how Binding requests are constructed and generated.

连通性检查通过从与本地候选者关联的基础向远程候选者发送 Binding 请求来生成。[[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] 描述了如何构造和生成 Binding 请求。

Support for backwards compatibility with [RFC 3489](./rfc3489) MUST NOT be assumed when performing connectivity checks. The FINGERPRINT mechanism MUST be used for connectivity checks.

在执行连通性检查时不得假定支持与 [RFC 3489](./rfc3489) 的向后兼容性。必须使用 FINGERPRINT 机制进行连通性检查。

### 7.2.5. Processing the Response | 7.2.5. 处理响应

This section defines additional procedures for processing Binding responses specific to ICE connectivity checks.

本节定义用于处理特定于 ICE 连通性检查的 Binding 响应的附加程序。

When a Binding response is received, it is correlated to the corresponding Binding request using the transaction ID [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]], which then associates the response with the candidate pair for which the Binding request was sent. After that, the response is processed according to the procedures for a role conflict, a failure, or a success, according to the procedures below.

当收到 Binding 响应时，使用事务 ID [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]] 将其与相应的 Binding 请求相关联，然后将响应与发送 Binding 请求的候选者对相关联。之后，按照以下过程根据角色冲突、失败或成功的过程处理响应。

#### 7.2.5.1. Role Conflict | 7.2.5.1. 角色冲突

If the Binding request generates a 487 (Role Conflict) error response ([Section 7.3.1.1](#section-7.3.1.1)), and if the ICE agent included an ICE-CONTROLLED attribute in the request, the agent MUST switch to the controlling role. If the agent included an ICE-CONTROLLING attribute in the request, the agent MUST switch to the controlled role.

如果 Binding 请求生成 487（角色冲突）错误响应（[第 7.3.1.1 节](#section-7.3.1.1)），并且如果 ICE 代理在请求中包含了 ICE-CONTROLLED 属性，代理必须切换到控制角色。如果代理在请求中包含了 ICE-CONTROLLING 属性，代理必须切换到被控角色。

Once the agent has switched its role, the agent MUST add the candidate pair whose check generated the 487 error response to the triggered-check queue associated with the checklist to which the pair belongs, and set the candidate pair state to Waiting. When the triggered connectivity check is later performed, the ICE-CONTROLLING/ ICE-CONTROLLED attribute of the Binding request will indicate the agent's new role. The agent MUST change the tiebreaker value.

一旦代理切换了其角色，代理必须将生成 487 错误响应的检查的候选者对添加到与该候选对所属的检查列表关联的触发检查队列中，并将候选者对状态设置为 Waiting。当稍后执行触发的连通性检查时，Binding 请求的 ICE-CONTROLLING/ICE-CONTROLLED 属性将指示代理的新角色。代理必须更改决胜值。

> NOTE: A role switch requires an agent to recompute pair priorities ([Section 6.1.2.3](#section-6.1.2.3)), since the priority values depend on the role.
> 注意：角色切换要求代理重新计算候选对优先级（[第 6.1.2.3 节](#section-6.1.2.3)），因为优先级值取决于角色。

> NOTE: A role switch will also impact whether the agent is responsible for nominating candidate pairs, and whether the agent is responsible for initiating the exchange of the updated candidate information with the peer once ICE is concluded.
> 注意：角色切换还将影响代理是否负责提名候选者对，以及代理是否负责在 ICE 结束后启动与对端交换更新的候选者信息。

#### 7.2.5.2. Failure | 7.2.5.2. 失败

This section describes cases when the candidate pair state is set to Failed.

本节描述候选者对状态设置为 Failed 的情况。

> NOTE: When the ICE agent sets the candidate pair state to Failed as a result of a connectivity-check error, the agent does not change the states of other candidate pairs with the same foundation.
> 注意：当 ICE 代理因连通性检查错误将候选者对状态设置为 Failed 时，代理不会更改具有相同 foundation 的其他候选者对的状态。

##### 7.2.5.2.1. Non-Symmetric Transport Addresses | 7.2.5.2.1. 非对称传输地址

The ICE agent MUST check that the source and destination transport addresses in the Binding request and response are symmetric. That is, the source IP address and port of the response MUST be equal to the destination IP address and port to which the Binding request was sent, and the destination IP address and port of the response MUST be equal to the source IP address and port from which the Binding request was sent. If the addresses are not symmetric, the agent MUST set the candidate pair state to Failed.

ICE 代理必须检查 Binding 请求和响应中的源和目的地传输地址是对称的。也就是说，响应的源 IP 地址和端口必须等于发送 Binding 请求的目的地 IP 地址和端口，响应的目的地 IP 地址和端口必须等于发送 Binding 请求的源 IP 地址和端口。如果地址不对称，代理必须将候选者对状态设置为 Failed。

##### 7.2.5.2.2. ICMP Error | 7.2.5.2.2. ICMP 错误

An ICE agent MAY support processing of ICMP errors for connectivity checks. If the agent supports processing of ICMP errors, and if a Binding request generates a hard ICMP error, the agent SHOULD set the state of the candidate pair to Failed. Implementers need to be aware that ICMP errors can be used as a method for Denial-of-Service (DoS) attacks when making a decision on how and if to process ICMP errors.

ICE 代理可以支持处理连通性检查的 ICMP 错误。如果代理支持处理 ICMP 错误，并且如果 Binding 请求生成硬 ICMP 错误，代理应该将候选者对的状态设置为 Failed。实现者需要注意，在决定如何以及是否处理 ICMP 错误时，ICMP 错误可被用作拒绝服务 (DoS) 攻击的方法。

##### 7.2.5.2.3. Timeout | 7.2.5.2.3. 超时

If the Binding request transaction times out, the ICE agent MUST set the candidate pair state to Failed.

如果 Binding 请求事务超时，ICE 代理必须将候选者对状态设置为 Failed。

##### 7.2.5.2.4. Unrecoverable STUN Response | 7.2.5.2.4. 不可恢复的 STUN 响应

If the Binding request generates a STUN error response that is unrecoverable [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]], the ICE agent SHOULD set the candidate pair state to Failed.

如果 Binding 请求生成不可恢复的 STUN 错误响应 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]，ICE 代理应该将候选者对状态设置为 Failed。

#### 7.2.5.3. Success | 7.2.5.3. 成功

A connectivity check is considered a success if each of the following criteria is true:

如果满足以下每个条件，连通性检查被视为成功：

* The Binding request generated a success response; and
* Binding 请求产生了成功响应；并且

* The source and destination transport addresses in the Binding request and response are symmetric.
* Binding 请求和响应中的源和目的地传输地址是对称的。

If a check is considered a success, the ICE agent performs (in order) the actions described in the following sections.

如果检查被视为成功，ICE 代理按顺序执行以下各节中描述的操作。

##### 7.2.5.3.1. Discovering Peer-Reflexive Candidates | 7.2.5.3.1. 发现对端自反候选者

The ICE agent MUST check the mapped address from the STUN response. If the transport address does not match any of the local candidates that the agent knows about, the mapped address represents a new candidate: a peer-reflexive candidate. Like other candidates, a peer-reflexive candidate has a type, base, priority, and foundation. They are computed as follows:

ICE 代理必须检查 STUN 响应中的映射地址。如果传输地址与代理已知的任何本地候选者不匹配，映射地址代表一个新的候选者：对端自反候选者。与其他候选者一样，对端自反候选者具有类型、基础、优先级和 foundation。它们计算如下：

* The type is peer reflexive.
* 类型是对端自反的。

* The base is the local candidate of the candidate pair from which the Binding request was sent.
* 基础是发送 Binding 请求的候选者对的本地候选者。

* The priority is the value of the PRIORITY attribute in the Binding request.
* 优先级是 Binding 请求中 PRIORITY 属性的值。

* The foundation is described in [Section 5.1.1.3](#section-5.1.1.3).
* Foundation 在 [第 5.1.1.3 节](#section-5.1.1.3) 中描述。

The peer-reflexive candidate is then added to the list of local candidates for the data stream. The username fragment and password are the same as for all other local candidates for that data stream.

对端自反候选者随后被添加到数据流的本地候选者列表中。用户名片段和密码与该数据流的所有其他本地候选者相同。

The ICE agent does not need to pair the peer-reflexive candidate with remote candidates, as a valid pair will be created due to the procedures in [Section 7.2.5.3.2](#section-7.2.5.3.2). If an agent wishes to pair the peer-reflexive candidate with remote candidates other than the one in the valid pair that will be generated, the agent MAY provide updated candidate information to the peer that includes the peer-reflexive candidate. This will cause the peer-reflexive candidate to be paired with all other remote candidates.

ICE 代理不需要将対端自反候选者与其他远程候选者配对，因为由于 [第 7.2.5.3.2 节](#section-7.2.5.3.2) 中的过程将创建一个有效对。如果代理希望将対端自反候选者与将生成的有效对中的远程候选者以外的远程候选者配对，代理可以向对端提供包含対端自反候选者的更新候选者信息。这将导致对端自反候选者与所有其他远程候选者配对。

##### 7.2.5.3.2. Constructing a Valid Pair | 7.2.5.3.2. 构建有效对

The ICE agent constructs a candidate pair whose local candidate equals the mapped address of the response and whose remote candidate equals the destination address to which the request was sent. This is called a "valid pair".

ICE 代理构建一个候选者对，其本地候选者等于响应的映射地址，远程候选者等于发送请求的目的地地址。这称为"有效对"。

The valid pair might equal the pair that generated the connectivity check, a different pair in the checklist, or a pair currently not in the checklist.

有效对可能等于生成连通性检查的候选对、检查列表中的不同候选对，或当前不在检查列表中的候选对。

The agent maintains a separate list, referred to as the "valid list". There is a valid list for each checklist in the checklist set. The valid list will contain valid pairs. Initially, each valid list is empty.

代理维护一个称为"有效列表"的单独列表。检查列表集中的每个检查列表都有一个有效列表。有效列表将包含有效对。最初，每个有效列表为空。

Each valid pair within the valid list has a flag, called the "nominated flag". When a valid pair is added to a valid list, the flag value is set to 'false'.

有效列表中的每个有效对都有一个标志，称为"提名标志"。当有效对被添加到有效列表时，标志值设置为'false'。

The valid pair will be added to a valid list as follows:

有效对将按如下方式添加到有效列表：

1. If the valid pair equals the pair that generated the check, the pair is added to the valid list associated with the checklist to which the pair belongs; or
   如果有效对等于生成检查的候选对，则该候选对被添加到与该候选对所属的检查列表关联的有效列表中；或

2. If the valid pair equals another pair in a checklist, that pair is added to the valid list associated with the checklist of that pair. The pair that generated the check is not added to a valid list; or
   如果有效对等于检查列表中的另一个候选对，则该候选对被添加到与该候选对的检查列表关联的有效列表中。生成检查的候选对不会被添加到有效列表中；或

3. If the valid pair is not in any checklist, the agent computes the priority for the pair based on the priority of each candidate, using the algorithm in [Section 6.1.2](#section-6.1.2). The priority of the local candidate depends on its type. Unless the type is peer reflexive, the priority is equal to the priority signaled for that candidate in the candidate exchange. If the type is peer reflexive, it is equal to the PRIORITY attribute the agent placed in the Binding request that just completed. The priority of the remote candidate is taken from the candidate information of the peer. If the candidate does not appear there, then the check has been a triggered check to a new remote candidate. In that case, the priority is taken as the value of the PRIORITY attribute in the Binding request that triggered the check that just completed. The pair is then added to the valid list.
   如果有效对不在任何检查列表中，代理使用 [第 6.1.2 节](#section-6.1.2) 中的算法根据每个候选者的优先级计算该对的优先级。本地候选者的优先级取决于其类型。除非类型是对端自反的，否则优先级等于在候选者交换中为该候选者发送的优先级。如果类型是对端自反的，它等于代理在刚完成的 Binding 请求中放置的 PRIORITY 属性。远程候选者的优先级从对端的候选者信息中获取。如果候选者不在那里，则检查是对新远程候选者的触发检查。在这种情况下，优先级取自触发刚完成的检查的 Binding 请求中的 PRIORITY 属性值。然后将该候选对添加到有效列表中。

> NOTE: It will be very common that the valid pair will not be in any checklist. Recall that the checklist has pairs whose local candidates are never reflexive; those pairs had their local candidates converted to the base of the reflexive candidates and were then pruned if they were redundant. When the response to the Binding request arrives, the mapped address will be reflexive if there is a NAT between the two. In that case, the valid pair will have a local candidate that doesn't match any of the pairs in the checklist.
> 注意：有效对通常不会在任何检查列表中是很常见的。回想一下，检查列表中的候选对的本地候选者从来不是自反的；那些候选对的本地候选者被转换为自反候选者的基础，如果冗余则被剪枝。当对 Binding 请求的响应到达时，如果两者之间存在 NAT，映射地址将是自反的。在这种情况下，有效对将具有与检查列表中任何候选对都不匹配的本地候选者。

##### 7.2.5.3.3. Updating Candidate Pair States | 7.2.5.3.3. 更新候选者对状态

The ICE agent sets the states of both the candidate pair that generated the check and the constructed valid pair (which may be different) to Succeeded.

ICE 代理将生成检查的候选者对和构建的有效对（可能不同）的状态设置为 Succeeded。

The agent MUST set the states for all other Frozen candidate pairs in all checklists with the same foundation to Waiting.

代理必须将所有其他具有相同 foundation 的 Frozen 候选者对的状态设置为 Waiting。

> NOTE: Within a given checklist, candidate pairs with the same foundations will typically have different component ID values.
> 注意：在给定的检查列表中，具有相同 foundation 的候选者对通常具有不同的组件 ID 值。

##### 7.2.5.3.4. Updating the Nominated Flag | 7.2.5.3.4. 更新提名标志

If the controlling agent sends a Binding request with the USE-CANDIDATE attribute set, and if the ICE agent receives a successful response to the request, the agent sets the nominated flag of the pair to true. If the request fails ([Section 7.2.5.2](#section-7.2.5.2)), the agent MUST remove the candidate pair from the valid list, set the candidate pair state to Failed, and set the checklist state to Failed.

如果控制代理发送带有 USE-CANDIDATE 属性集的 Binding 请求，并且如果 ICE 代理收到对请求的成功响应，代理将候选对的提名标志设置为 true。如果请求失败（[第 7.2.5.2 节](#section-7.2.5.2)），代理必须从有效列表中移除候选者对，将候选者对状态设置为 Failed，并将检查列表状态设置为 Failed。

If the controlled agent receives a successful response to a Binding request sent by the agent, and that Binding request was triggered by a received Binding request with the USE-CANDIDATE attribute set ([Section 7.3.1.4](#section-7.3.1.4)), the agent sets the nominated flag of the pair to true. If the triggered request fails, the agent MUST remove the candidate pair from the valid list, set the candidate pair state to Failed, and set the checklist state to Failed.

如果被控代理收到由代理发送的 Binding 请求的成功响应，并且该 Binding 请求是由收到的带有 USE-CANDIDATE 属性集的 Binding 请求触发的（[第 7.3.1.4 节](#section-7.3.1.4)），代理将候选对的提名标志设置为 true。如果触发的请求失败，代理必须从有效列表中移除候选者对，将候选者对状态设置为 Failed，并将检查列表状态设置为 Failed。

Once the nominated flag is set for a component of a data stream, it concludes the ICE processing for that component ([Section 8](#section-8)).

一旦为数据流的组件设置了提名标志，它将结束该组件的 ICE 处理（[第 8 节](#section-8)）。

#### 7.2.5.4. Checklist State Updates | 7.2.5.4. 检查列表状态更新

Regardless of whether a connectivity check was successful or failed, the completion of the check may require updating of checklist states. For each checklist in the checklist set, if all of the candidate pairs are in either Failed or Succeeded state, and if there is not a valid pair in the valid list for each component of the data stream associated with the checklist, the state of the checklist is set to Failed. If there is a valid pair for each component in the valid list, the state of the checklist is set to Succeeded.

无论连通性检查是成功还是失败，检查的完成可能需要更新检查列表状态。对于检查列表集中的每个检查列表，如果所有候选者对都处于 Failed 或 Succeeded 状态，并且如果与检查列表关联的数据流的每个组件的有效列表中没有有效对，则将检查列表的状态设置为 Failed。如果有效列表中每个组件都有一个有效对，则将检查列表的状态设置为 Succeeded。

## 7.3. STUN Server Procedures | 7.3. STUN 服务器程序

An ICE agent (lite or full) MUST be prepared to receive Binding requests on the base of each candidate it included in its most recent candidate exchange.

ICE 代理（轻量级或完整）必须准备好在其最近一次候选者交换中包含的每个候选者的基础上接收 Binding 请求。

The agent MUST use the short-term credential mechanism (i.e., the MESSAGE-INTEGRITY attribute) to authenticate the request and perform a message integrity check. Likewise, the short-term credential mechanism MUST be used for the response. The agent MUST consider the username to be valid if it consists of two values separated by a colon, where the first value is equal to the username fragment generated by the agent in a candidate exchange for a session in progress. It is possible (and in fact very likely) that the initiating agent will receive a Binding request prior to receiving the candidates from its peer. If this happens, the agent MUST immediately generate a response (including computation of the mapped address as described in [Section 7.3.1.2](#section-7.3.1.2)). The agent has sufficient information at this point to generate the response; the password from

代理必须使用短期凭证机制（即 MESSAGE-INTEGRITY 属性）来验证请求并执行消息完整性检查。同样，必须使用短期凭证机制进行响应。如果用户名由两个用冒号分隔的值组成，则代理必须认为用户名有效，其中第一个值等于代理在为进行中的会话进行候选者交换时生成的用户名片段。发起代理可能在收到对端候选者之前收到 Binding 请求是可能的（事实上非常可能）。如果发生这种情况，代理必须立即生成响应（包括 [第 7.3.1.2 节](#section-7.3.1.2) 中描述的映射地址计算）。此时代理有足够的信息来生成响应；对端的密码可以通过对端早先发送的候选者交换来获取。

### 7.3.1. Additional Procedures for Full Implementations | 7.3.1. 完整实现的附加程序

#### 7.3.1.1. Detecting and Repairing Role Conflicts | 7.3.1.1. 检测和修复角色冲突

If the agent is in the controlled role and receives a Binding request with an ICE-CONTROLLING attribute, the agent MUST generate a 487 (Role Conflict) error response and MUST include an ICE-CONTROLLED attribute in the response. Similarly, if the agent is in the controlling role and receives a Binding request with an ICE-CONTROLLED attribute, the agent MUST generate a 487 error response and MUST include an ICE-CONTROLLING attribute in the response.

如果代理处于被控角色并收到带有 ICE-CONTROLLING 属性的 Binding 请求，代理必须生成 487（角色冲突）错误响应，并必须在响应中包含 ICE-CONTROLLED 属性。类似地，如果代理处于控制角色并收到带有 ICE-CONTROLLED 属性的 Binding 请求，代理必须生成 487 错误响应，并必须在响应中包含 ICE-CONTROLLING 属性。

If the agent is in the controlled role and receives a Binding request without either ICE-CONTROLLING or ICE-CONTROLLED attribute, the agent MUST generate a 487 error response and MUST include an ICE-CONTROLLED attribute in the response. Similarly, if the agent is in the controlling role and receives a Binding request without either ICE-CONTROLLING or ICE-CONTROLLED attribute, the agent MUST generate a 487 error response and MUST include an ICE-CONTROLLING attribute in the response.

如果代理处于被控角色并收到既没有 ICE-CONTROLLING 也没有 ICE-CONTROLLED 属性的 Binding 请求，代理必须生成 487 错误响应，并必须在响应中包含 ICE-CONTROLLED 属性。类似地，如果代理处于控制角色并收到既没有 ICE-CONTROLLING 也没有 ICE-CONTROLLED 属性的 Binding 请求，代理必须生成 487 错误响应，并必须在响应中包含 ICE-CONTROLLING 属性。

The content of the ICE-CONTROLLING or ICE-CONTROLLED attribute in the error response MUST be the tiebreaker value of the agent.

错误响应中 ICE-CONTROLLING 或 ICE-CONTROLLED 属性的内容必须是代理的决胜值。

If the agent receives a STUN error response with a 487 error code, and the agent has included the ICE-CONTROLLED attribute in the request, the agent MUST switch to the controlling role. If the agent has included the ICE-CONTROLLING attribute in the request, the agent MUST switch to the controlled role.

如果代理收到带有 487 错误代码的 STUN 错误响应，并且代理在请求中包含了 ICE-CONTROLLED 属性，代理必须切换到控制角色。如果代理在请求中包含了 ICE-CONTROLLING 属性，代理必须切换到被控角色。

#### 7.3.1.2. Computing Mapped Addresses | 7.3.1.2. 计算映射地址

As described in [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")], the agent computes the mapped address from the source transport address of the Binding request. In addition, for IPv4-only agents, if there is a NAT that has both an external IPv4 address and an internal IPv6 prefix [[RFC5844](./rfc5844 "\"IPv4-in-IPv6 Softwire Mesh: Framework and Deployment Scenarios\"")], the agent MUST use the internal address of the NAT as the mapped address.

如 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")] 中所述，代理从 Binding 请求的源传输地址计算映射地址。此外，对于仅 IPv4 代理，如果存在同时具有外部 IPv4 地址和内部 IPv6 前缀 [[RFC5844](./rfc5844 "\"IPv4-in-IPv6 Softwire Mesh: Framework and Deployment Scenarios\"")]] 的 NAT，代理必须使用 NAT 的内部地址作为映射地址。

#### 7.3.1.3. Learning Peer-Reflexive Candidates | 7.3.1.3. 学习对端自反候选者

If the agent discovery of peer-reflexive candidates is performed as described in [Section 7.2.5.3.1](#section-7.2.5.3.1), the mapped address represents a peer-reflexive candidate for the peer. The priority of the candidate is taken from the PRIORITY attribute in the Binding request.

如果按 [第 7.2.5.3.1 节](#section-7.2.5.3.1) 中所述执行对端自反候选者发现，映射地址代表对端的对端自反候选者。候选者的优先级取自 Binding 请求中的 PRIORITY 属性。

#### 7.3.1.4. Triggered Checks | 7.3.1.4. 触发检查

If the agent receives a Binding request on a candidate pair that is not currently in the Waiting, In-Progress, Succeeded, or Failed state, the agent MUST put the candidate pair into the Waiting state and MUST add the candidate pair to the triggered-check queue associated with the checklist to which the pair belongs. If the received Binding request contains the USE-CANDIDATE attribute, the agent MUST add a triggered check to the triggered-check queue.

如果代理在当前不处于 Waiting、In-Progress、Succeeded 或 Failed 状态的候选者对上收到 Binding 请求，代理必须将候选者对置于 Waiting 状态，并必须将候选者对添加到与该候选对所属的检查列表关联的触发检查队列中。如果收到的 Binding 请求包含 USE-CANDIDATE 属性，代理必须将触发的检查添加到触发检查队列中。

The triggered check is generated by sending a Binding request from the base associated with the local candidate to the remote candidate of the candidate pair. The agent MUST include an ICE-CONTROLLING or ICE-CONTROLLED attribute matching the role of the agent. In addition, if the received Binding request contains the USE-CANDIDATE attribute, the agent MUST include a USE-CANDIDATE attribute in the triggered request.

触发的检查通过从与本地候选者关联的基础向候选者对的远程候选者发送 Binding 请求来生成。代理必须包含与代理角色匹配的 ICE-CONTROLLING 或 ICE-CONTROLLED 属性。此外，如果收到的 Binding 请求包含 USE-CANDIDATE 属性，代理必须在触发的请求中包含 USE-CANDIDATE 属性。

If the agent receives a successful response to the triggered request, and if the response is to a request that included the USE-CANDIDATE attribute, the agent sets the nominated flag of the candidate pair to true.

如果代理收到对触发的请求的成功响应，并且如果该响应是对包含 USE-CANDIDATE 属性的请求的响应，代理将候选者对的提名标志设置为 true。

If the agent receives a successful response to the triggered request, and if the response is to a request that did not include the USE-CANDIDATE attribute, the agent does not set the nominated flag.

如果代理收到对触发的请求的成功响应，并且如果该响应是对不包含 USE-CANDIDATE 属性的请求的响应，代理不设置提名标志。

#### 7.3.1.5. Updating the Nominated Flag | 7.3.1.5. 更新提名标志

If the received Binding request includes the USE-CANDIDATE attribute, the agent checks the candidate pair returned from the peer (using the mapped address) against the candidate pairs in the valid list. If the candidate pair is in the valid list and the nominated flag is not set, the agent sets the nominated flag of the candidate pair to true.

如果收到的 Binding 请求包含 USE-CANDIDATE 属性，代理使用映射地址将对端返回的候选者对与有效列表中的候选者对进行比较。如果候选者对在有效列表中且提名标志未设置，代理将候选者对的提名标志设置为 true。

### 7.3.2. Additional Procedures for Lite Implementations | 7.3.2. 轻量级实现的附加程序

A lite implementation MUST be ready to receive and respond to Binding requests at any time after it has provided its candidate information to the peer. A lite implementation does not generate connectivity checks; however, a lite implementation MUST respond to incoming connectivity checks.

轻量级实现必须在向对端提供候选者信息后随时准备接收并响应 Binding 请求。轻量级实现不生成连通性检查；但是，轻量级实现必须响应传入的连通性检查。

When the lite implementation receives a Binding request, the lite implementation MUST generate a success response as described in [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]. In addition, the lite implementation follows the procedures described in [Section 7.3.1.5](#section-7.3.1.5) for updating the nominated flag.

当轻量级实现收到 Binding 请求时，轻量级实现必须如 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]] 中所述生成成功响应。此外，轻量级实现遵循 [第 7.3.1.5 节](#section-7.3.1.5) 中描述的更新提名标志的程序。

If a lite implementation receives a Binding request with the USE-CANDIDATE attribute, and the candidate pair returned from the peer (using the mapped address) is not in the valid list, the candidate pair is added to the valid list as described in [Section 7.2.5.3.2](#section-7.2.5.3.2). If the candidate pair is in the valid list, the nominated flag is set as described in [Section 7.3.1.5](#section-7.3.1.5).

如果轻量级实现收到带有 USE-CANDIDATE 属性的 Binding 请求，并且对端返回的候选者对（使用映射地址）不在有效列表中，则按照 [第 7.2.5.3.2 节](#section-7.2.5.3.2) 中所述将候选者对添加到有效列表中。如果候选者对在有效列表中，则按照 [第 7.3.1.5 节](#section-7.3.1.5) 中所述设置提名标志。

---

# 8. Concluding ICE Processing | 8. 结束 ICE 处理

Once ICE has produced a candidate pair for each component of a data stream that has an ICE candidate, ICE processing is considered complete for that data stream. Once ICE has completed for all data streams, the ICE session as a whole is complete. The following sections describe how ICE is concluded.

一旦 ICE 为具有 ICE 候选者的数据流的每个组件产生了候选者对，该数据流的 ICE 处理就被视为完成。一旦所有数据流的 ICE 都完成，整个 ICE 会话就完成了。以下各节描述如何结束 ICE。

---

## 8.1. Procedures for Full Implementations | 8.1. 完整实现程序

### 8.1.1. Nominating Pairs | 8.1.1. 提名候选对

The controlling agent nominates a candidate pair to be used for data. The nomination is a two-step process. First, the controlling agent lets connectivity checks continue until one or more candidate pairs for a component of the data stream are in the Succeeded state. Then, the agent selects a candidate pair from amongst the Succeeded candidate pairs for a component. The selected candidate pair is the nominated pair for that component. The controlling agent sends a Binding request on that pair with the USE-CANDIDATE attribute set. This causes the controlled agent to nominate the same pair (see [Section 7.2.5.3.4](#section-7.2.5.3.4)), and both agents set the nominated flag for the pair to true.

控制代理提名候选者对用于数据。提名是一个两步过程。首先，控制代理让连通性检查继续，直到数据流组件的一个或多个候选者对处于 Succeeded 状态。然后，代理从组件的 Succeeded 候选者对中选择一个候选者对。所选候选者对是该组件的提名候选对。控制代理在该候选对上发送带有 USE-CANDIDATE 属性集的 Binding 请求。这导致被控代理提名相同的候选对（参见 [第 7.2.5.3.4 节](#section-7.2.5.3.4)），并且两个代理都将该候选对的提名标志设置为 true。

The controlling agent SHOULD nominate the candidate pair with the highest priority. However, as noted in [[RFC5245](./rfc5245 "\"Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal for Offer/Answer Protocols\"")]], the controlling agent MAY also take into account other criteria (such as latency or bandwidth) when selecting which candidate pair to nominate.

控制代理应该提名优先级最高的候选者对。然而，如 [[RFC5245](./rfc5245 "\"Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal for Offer/Answer Protocols\"")]] 中所述，控制代理在选择要提名的候选者对时也可以考虑其他标准（如延迟或带宽）。

### 8.1.2. Updating Checklist and ICE States | 8.1.2. 更新检查列表和 ICE 状态

When a candidate pair is nominated, the agent sets the nominated flag for the nominated pair to true. When a candidate pair is nominated for each component of a data stream, the agent sets the state of the checklist for that data stream to Completed.

当候选者对被提名时，代理将提名候选对的提名标志设置为 true。当数据流的每个组件都提名了候选者对时，代理将该数据流的检查列表状态设置为 Completed。

When the state of each checklist in the checklist set is set to Completed, the state of the ICE session is set to Completed. If the agent concludes that it is not possible to complete connectivity checks for a data stream (see [Section 7.2.5.4](#section-7.2.5.4)), the state of the checklist for that data stream is set to Failed. If all checklists in the checklist set are set to Failed, the state of the ICE session is set to Failed.

当检查列表集中每个检查列表的状态都设置为 Completed 时，ICE 会话的状态设置为 Completed。如果代理得出结论认为不可能完成数据流的连通性检查（参见 [第 7.2.5.4 节](#section-7.2.5.4)），该数据流的检查列表状态设置为 Failed。如果检查列表集中的所有检查列表都设置为 Failed，ICE 会话的状态设置为 Failed。

---

## 8.2. Procedures for Lite Implementations | 8.2. 轻量级实现程序

A lite implementation waits for the controlling agent to nominate candidate pairs. As the lite implementation receives connectivity checks from the peer (controlling agent), it will mark candidate pairs as Succeeded and set the nominated flag (as described in [Section 7.3.2](#section-7.3.2)).

轻量级实现等待控制代理提名候选者对。当轻量级实现从对端（控制代理）收到连通性检查时，它将把候选者对标记为 Succeeded 并设置提名标志（如 [第 7.3.2 节](#section-7.3.2) 中所述）。

When the nominated flag of a candidate pair is set to true, the agent sets the nominated flag for all other candidate pairs for the same component to false. In addition, the agent adds the nominated pair to the valid list (if not already present). Once the nominated pair for each component of a data stream is in the valid list, the state of the checklist for that data stream is set to Completed.

当候选者对的提名标志设置为 true 时，代理将同一组件所有其他候选者对的提名标志设置为 false。此外，代理将提名候选对添加到有效列表中（如果尚未存在）。一旦数据流每个组件的提名候选对都在有效列表中，该数据流的检查列表状态设置为 Completed。

---

## 8.3. Freeing Candidates | 8.3. 释放候选者

Once ICE has concluded for a data stream, the agent MAY free candidates for that data stream (if they are server-reflexive or relayed candidates). However, candidates that are currently in use (i.e., for which there is a selected candidate pair) SHOULD NOT be freed.

一旦数据流的 ICE 结束，代理可以释放该数据流的候选者（如果是服务器自反或中继候选者）。但是，不应该释放正在使用的候选者（即存在选定候选者对的候选者）。

### 8.3.1. Full Implementation Procedures | 8.3.1. 完整实现程序

When ICE has completed for a data stream, the agent SHOULD free all non-relayed candidates for that data stream that are not currently in use.

当数据流的 ICE 完成后，代理应该释放该数据流中所有当前未使用的非中继候选者。

### 8.3.2. Lite Implementation Procedures | 8.3.2. 轻量级实现程序

When ICE has completed for a data stream, the lite implementation frees all candidates for that data stream.

当数据流的 ICE 完成后，轻量级实现释放该数据流的所有候选者。

---

# 9. ICE Restarts | 9. ICE 重启

At any time, the controlling agent can restart ICE for a data stream by sending a new candidate information for the data stream, as described in [Section 5.1](#section-5.1). The data stream is identified by the data stream identifier (which depends on the using protocol).

在任何时候，控制代理可以通过如 [第 5.1 节](#section-5.1) 中所述发送数据流的新候选者信息来重启数据流的 ICE。数据流由数据流标识符（取决于使用协议）标识。

When an agent sends an updated candidate information for a data stream, it MUST indicate to the peer that a restart is occurring. In addition, both agents reset the ICE state for the data stream to Running, rebuild checklists as described in [Section 6.1.2](#section-6.1.2), and run the ICE connectivity checks again.

当代理发送数据流的更新候选者信息时，它必须向对端指示发生了重启。此外，两个代理都将数据流的 ICE 状态重置为 Running，按照 [第 6.1.2 节](#section-6.1.2) 中所述重建检查列表，并再次运行 ICE 连通性检查。

An agent MUST NOT restart ICE for a data stream if there are no nominated pairs for that data stream. This can happen, for example, when the ICE session is in the Running state for a data stream and the agents decide to abort ICE for that data stream.

如果数据流没有提名候选对，代理不得重启该数据流的 ICE。例如，当 ICE 会话处于数据流的 Running 状态且代理决定中止该数据流的 ICE 时，可能发生这种情况。

---

# 10. ICE Option | 10. ICE 选项

The ICE specification defines an ICE option [[RFC6336](./rfc6336 "\"ICE Option Definition for the Session Initiation Protocol\"")] to indicate that an agent supports ICE. This option is included in the ALTERNATE-SERVER attribute in responses to a STUN server request.

ICE 规范定义了一个 ICE 选项 [[RFC6336](./rfc6336 "\"ICE Option Definition for the Session Initiation Protocol\"")] 来指示代理支持 ICE。此选项包含在响应 STUN 服务器请求的 ALTERNATE-SERVER 属性中。

---

# 11. Keepalives | 11. 保活

All ICE agents MUST send keepalives for the selected candidate pairs (i.e., the candidate pairs for which the nominated flag is set to true) in order to keep NAT and firewall mappings alive.

所有 ICE 代理必须为选定的候选者对（即提名标志设置为 true 的候选者对）发送保活，以保持 NAT 和防火墙映射活跃。

The keepalive is a STUN Binding Indication [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]. The agent MUST include the FINGERPRINT attribute in the keepalive. The keepalive can be sent as described in [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]. Typically, the keepalive is sent from the local candidate of the selected candidate pair to the remote candidate of the selected candidate pair. However, if both agents are sending media through symmetric NATs, the directionality of the selected pairs might be opposite (one agent sends from its local candidate to the remote candidate, while the other receives on its local candidate). In that case, each agent sends keepalives to its peer.

保活是 STUN Binding Indication [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]。代理必须在保活中包含 FINGERPRINT 属性。保活可以如 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]] 中所述发送。通常，保活从选定候选者对的本地候选者发送到选定候选者对的远程候选者。但是，如果两个代理都通过对称 NAT 发送媒体，选定对的方向性可能相反（一个代理从其本地候选者向远程候选者发送，而另一个在其本地候选者上接收）。在这种情况下，每个代理都向其对端发送保活。

The keepalive is sent periodically. The default is 15 seconds. The RTO timer can also be used for keepalive transmissions [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]. An agent MAY reduce the frequency of keepalives to a value lower than the default value based on local policy.

保活定期发送。默认值为 15 秒。RTO 定时器也可用于保活传输 [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]]。代理可以根据本地策略将保活频率降低到低于默认值的值。

---

# 12. Data Handling | 12. 数据处理

## 12.1. Sending Data | 12.1. 发送数据

An ICE agent MAY send data on any valid pair before selected pairs have been produced for the data stream.

在数据流产生选定候选对之前，ICE 代理可以在任何有效对上发送数据。

Once selected pairs have been produced for a data stream, an agent MUST send data on those pairs only.

一旦为数据流产生了选定候选对，代理必须仅在这些候选对上发送数据。

An agent sends data from the base of the local candidate to the remote candidate. In the case of a local relayed candidate, data is forwarded through the base (located in the TURN server), using the procedures defined in [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")]].

代理从本地候选者的基础向远程候选者发送数据。在本地中继候选者的情况下，数据通过基础（在 TURN 服务器中）转发，使用 [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")] 中定义的过程。

If the local candidate is a relayed candidate, it is RECOMMENDED that an agent creates a channel on the TURN server towards the remote candidate. This is done using the procedures for channel creation as defined in [Section 11 of RFC5766](./rfc5766#section-11).

如果本地候选者是中继候选者，建议代理在 TURN 服务器上创建到远程候选者的通道。这是使用 [RFC5766 第 11 节](./rfc5766#section-11) 中定义的通道创建过程完成的。

The selected pair for a component of a data stream is:

数据流组件的选定候选对是：

* empty if the state of the checklist for that data stream is Running, and there is no previous selected pair for that component due to an ICE restart
* 如果该数据流的检查列表状态是 Running，并且由于 ICE 重启该组件没有先前的选定候选对，则为空

* equal to the previous selected pair for a component of a data stream if the state of the checklist for that data stream is Running, and there was a previous selected pair for that component due to an ICE restart
* 如果该数据流的检查列表状态是 Running，并且由于 ICE 重启该组件有先前的选定候选对，则等于该组件先前选定的候选对

Unless an agent is able to produce a selected pair for each component associated with a data stream, the agent MUST NOT continue sending data for any component associated with that data stream.

除非代理能够为与数据流关联的每个组件产生选定候选对，否则代理不得继续发送与该数据流关联的任何组件的数据。

### 12.1.1. Procedures for Lite Implementations | 12.1.1. 轻量级实现程序

A lite implementation MUST NOT send data until it has a valid list that contains a candidate pair for each component of that data stream. Once that happens, the ICE agent MAY begin sending data packets. To do that, it sends data to the remote candidate in the pair (setting the destination address and port of the packet equal to that remote candidate) and will send it from the base associated with the candidate pair used for sending data. In case of a relayed candidate, data is sent from the agent and forwarded through the base (located in the TURN server), using the procedures defined in [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")]].

轻量级实现必须在拥有包含该数据流每个组件的候选者对的有效列表之前不得发送数据。一旦发生这种情况，ICE 代理可以开始发送数据包。为此，它向该候选对中的远程候选者发送数据（将数据包的目的地地址和端口设置为该远程候选者），并将从用于发送数据的候选者对关联的基础发送。在中继候选者的情况下，数据从代理发送并通过基础（在 TURN 服务器中）转发，使用 [[RFC5766](./rfc5766 "\"Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)\"")] 中定义的过程。

## 12.2. Receiving Data | 12.2. 接收数据

Even though ICE agents are only allowed to send data using valid candidate pairs (and, once selected pairs have been produced, only on the selected pairs), ICE implementations SHOULD by default be prepared to receive data on any of the candidates provided in the most recent candidate exchange with the peer. ICE usages MAY define rules that differ from this, e.g., by defining that data will not be sent until selected pairs have been produced for a data stream.

尽管 ICE 代理只允许使用有效候选者对发送数据（并且一旦产生了选定候选对，仅在选定候选对上发送），ICE 实现默认应该准备在与对端最近一次候选者交换中提供的任何候选者上接收数据。ICE 用法可以定义与此不同的规则，例如，通过定义在数据流产生选定候选对之前不会发送数据。

When an agent receives an RTP packet with a new source or destination IP address for a particular RTP/RTCP data stream, it is RECOMMENDED that the agent readjust its jitter buffers.

当代理为特定 RTP/RTCP 数据流收到具有新源或目的地 IP 地址的 RTP 数据包时，建议代理重新调整其抖动缓冲区。

[RFC 3550 第 8.2 节](./rfc3550#section-8.2) [[RFC3550](./rfc3550 "\"RTP: A Transport Protocol for Real-Time Applications\"")] 描述了用于检测同步源 (SSRC) 冲突和环路的算法。这些算法部分基于看到具有相同 SSRC 的不同源传输地址。然而，当使用 ICE 时，由于数据流在候选者之间切换，这种变化有时会发生。代理将能够确定数据流来自与 STUN 交换（先于媒体数据传输）相同的对端。因此，如果源传输地址发生变化，但媒体数据包来自同一对端代理，这不必须被视为 SSRC 冲突。

# 13. Extensibility Considerations | 13. 可扩展性考虑

This specification makes very specific choices about how both ICE agents in a session coordinate to arrive at the set of candidate pairs that are selected for data. It is anticipated that future specifications will want to alter these algorithms, whether they are simple changes like timer tweaks or larger changes like a revamp of the priority algorithm. When such a change is made, providing interoperability between the two agents in a session is critical.

本规范对会话中两个 ICE 代理如何协调以达成用于数据的候选者对集合做出了非常具体的选择。预计未来的规范会希望更改这些算法，无论是像定时器调整这样的简单更改，还是像优先级算法重新设计这样的大更改。当进行此类更改时，提供会话中两个代理之间的互操作性至关重要。

First, ICE provides the ICE option concept. Each extension or change to ICE is associated with an ICE option. When an agent supports such an extension or change, it provides the ICE option to the peer agent as part of the candidate exchange.

首先，ICE 提供了 ICE 选项概念。ICE 的每个扩展或更改都与一个 ICE 选项关联。当代理支持此类扩展或更改时，它在候选者交换过程中将 ICE 选项提供给对端代理。

One of the complications in achieving interoperability is that ICE relies on a distributed algorithm running on both agents to converge on an agreed set of candidate pairs. If the two agents run different algorithms, it can be difficult to guarantee convergence on the same candidate pairs. The nomination procedure described in [Section 8](#section-8) eliminates some of the need for tight coordination by delegating the selection algorithm completely to the controlling agent, and ICE will converge perfectly even when both agents use different pair prioritization algorithms. One of the keys to such convergence is triggered checks, which ensure that the nominated pair is validated by both agents.

实现互操作性的复杂性之一是 ICE 依赖于在两个代理上运行的分布式算法来就一组商定的候选者对达成一致。如果两个代理运行不同的算法，可能难以保证在相同候选者对上收敛。[第 8 节](#section-8) 中描述的提名过程通过将选择算法完全委托给控制代理来消除一些紧密协调的需要，并且即使两个代理使用不同的候选对优先级算法，ICE 也会完美收敛。这种收敛的关键之一是触发检查，它确保提名候选对被两个代理验证。

ICE is also extensible to other data streams beyond RTP and for transport protocols beyond UDP. Extensions to ICE for non-RTP data streams need to specify how many components they utilize and assign component IDs to them, starting at 1 for the most important component ID. Specifications for new transport protocols MUST define how, if at all, various steps in the ICE processing differ from UDP.

ICE 还可扩展到 RTP 以外的其他数据流以及 UDP 以外的传输协议。非 RTP 数据流的 ICE 扩展需要指定它们使用多少组件并为它们分配组件 ID，从最重要的组件 ID 开始为 1。新传输协议的规范必须定义 ICE 处理的各种步骤（如果有的话）如何与 UDP 不同。

# 14. Setting Ta and RTO | 14. 设置 Ta 和 RTO

## 14.1. General | 14.1. 概述

During the ICE gathering phase ([Section 5.1.1](#section-5.1.1)) and while ICE is performing connectivity checks ([Section 7](#section-7)), an ICE agent triggers STUN and TURN transactions. These transactions are paced at a rate indicated by Ta, and the retransmission interval for each transaction is calculated based on the retransmission timer for the STUN transactions (RTO) [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]].

在 ICE 收集阶段（[第 5.1.1 节](#section-5.1.1)）和 ICE 执行连通性检查期间（[第 7 节](#section-7)），ICE 代理触发 STUN 和 TURN 事务。这些事务以 Ta 指示的速率进行节奏控制，每个事务的重传间隔基于 STUN 事务的重传定时器 (RTO) [[RFC5389](./rfc5389 "\"Session Traversal Utilities for NAT (STUN)\"")]] 计算。

This section describes how the Ta and RTO values are computed during the ICE gathering phase and while ICE is performing connectivity checks.

本节描述在 ICE 收集阶段期间以及 ICE 执行连通性检查时如何计算 Ta 和 RTO 值。

> NOTE: Previously, in [RFC 5245](./rfc5245), different formulas were defined for computing Ta and RTO, depending on whether or not ICE was used for a real-time data stream (e.g., RTP).
> 注意：以前在 [RFC 5245](./rfc5245) 中，根据 ICE 是否用于实时数据流（例如 RTP）定义了不同的 Ta 和 RTO 计算公式。

The formulas below result in a behavior whereby an agent will send its first packet for every single connectivity check before performing a retransmit. This can be seen in the formulas for the RTO (which represents the retransmit interval). Those formulas scale with N, the number of checks to be performed. As a result of this, ICE maintains a nicely constant rate, but it becomes more sensitive to packet loss. The loss of the first single packet for any connectivity check is likely to cause that pair to take a long time to be validated, and instead, a lower-priority check (but one for which there was no packet loss) is much more likely to complete first. This results in ICE performing suboptimally, choosing lower-priority pairs over higher-priority pairs.

以下公式产生了一种行为，即代理在执行重传之前为每个单独的连通性检查发送其第一个数据包。这可以从 RTO 的公式中看出（它代表重传间隔）。这些公式随 N（要执行的检查数）缩放。因此，ICE 保持相当恒定的速率，但对数据包丢失变得更加敏感。任何连通性检查的第一个数据包的丢失可能导致该候选对需要很长时间才能被验证，而相反，较低优先级的检查（但没有数据包丢失的检查）更有可能首先完成。这导致 ICE 表现次优，选择较低优先级的候选对而不是较高优先级的候选对。

## 14.2. Ta

ICE agents SHOULD use a default Ta value, 50 ms, but MAY use another value based on the characteristics of the associated data.

ICE 代理应该使用默认 Ta 值 50 ms，但可以根据关联数据的特性使用其他值。

If an agent wants to use a Ta value other than the default value, the agent MUST indicate the proposed value to its peer during the establishment of the ICE session. Both agents MUST use the higher value of the proposed values. If an agent does not propose a value, the default value is used for that agent when comparing which value is higher.

如果代理希望使用默认值以外的 Ta 值，代理必须在 ICE 会话建立期间向其对端指示建议的值。两个代理必须使用建议值中的较高值。如果代理没有建议值，则在比较哪个值更高时，该代理使用默认值。

Regardless of the Ta value chosen for each agent, the combination of all transactions from all agents (if a given implementation runs several concurrent agents) MUST NOT be sent more often than once every 5 ms (as though there were one global Ta value for pacing all agents). See [Appendix B.1](#appendix-B.1) for the background of using a value of 5 ms with ICE.

无论为每个代理选择什么 Ta 值，来自所有代理的所有事务的组合（如果给定实现运行多个并发代理）不得以快于每 5 毫秒一次的频率发送（就像有一个全局 Ta 值来节奏控制所有代理一样）。关于使用 5 ms 值与 ICE 的背景，请参见 [附录 B.1](#appendix-B.1)。

> NOTE: [Appendix C](#appendix-C) shows examples of required bandwidth, using different Ta values.
> 注意：[附录 C](#appendix-C) 显示了使用不同 Ta 值的所需带宽示例。

## 14.3. RTO

During the ICE gathering phase, ICE agents SHOULD calculate the RTO value using the following formula:

在 ICE 收集阶段，ICE 代理应该使用以下公式计算 RTO 值：

```
RTO = MAX (500ms, Ta * (Num-Of-Cands))
```

During the ICE connectivity-check phase, ICE agents SHOULD calculate the RTO value using the following formula:

在 ICE 连通性检查阶段，ICE 代理应该使用以下公式计算 RTO 值：

```
RTO = MAX (500ms, Ta * (Num-Checks))
```

Where:

其中：

* Ta is the computed pacing value.
* Ta 是计算的节拍值。

* Num-Of-Cands is the number of candidate pairs for which the agent will be requesting bindings.
* Num-Of-Cands 是代理将请求绑定的候选者对数量。

* Num-Checks is the minimum of the number of candidate pairs in all checklists in the checklist set.
* Num-Checks 是检查列表集中所有检查列表中候选者对数量的最小值。

An agent SHOULD use RTO value MAX (500ms, Ta) during the ICE gathering phase if the value computed with the first formula results in a smaller value.

如果在 ICE 收集阶段第一个公式计算出的值导致更小的值，代理应该使用 RTO 值 MAX (500ms, Ta)。

# 15. Examples | 15. 示例

This section shows two ICE examples: one using IPv4 addresses and one using IPv6 addresses.

本节显示两个 ICE 示例：一个使用 IPv4 地址，一个使用 IPv6 地址。

To facilitate understanding, transport addresses are listed using variables that have mnemonic names. The format of the name is entity-type-seqno: "entity" refers to the entity whose IP address the transport address is on and is one of "L", "R", "STUN", or "NAT". The type is either "PUB" for transport addresses that are public or "PRIV" for transport addresses that are private [[RFC1918](./rfc1918 "\"Address Allocation for Private Internets\"")]. Finally, seq-no is a sequence number that is different for each transport address of the same type on a particular entity. Each variable has an IP address and port, denoted by varname.IP and varname.PORT, respectively, where varname is the name of the variable.

为便于理解，传输地址使用具有助记符名称的变量列出。名称格式为 entity-type-seqno："entity" 指传输地址所在的实体，可以是"L"、"R"、"STUN"或"NAT"之一。类型可以是"PUB"表示公共传输地址或"PRIV"表示私有传输地址 [[RFC1918](./rfc1918 "\"Address Allocation for Private Internets\"")]]。最后，seq-no 是一个序列号，对于特定实体上相同类型的每个传输地址是不同的。每个变量都有一个 IP 地址和端口，分别表示为 varname.IP 和 varname.PORT，其中 varname 是变量的名称。

In the call flow itself, STUN messages are annotated with several attributes. The "S=" attribute indicates the source transport address of the message. The "D=" attribute indicates the destination transport address of the message. The "MA=" attribute is used in STUN Binding response messages and refers to the mapped address. "USE-CAND" implies the presence of the USE-CANDIDATE attribute.

在呼叫流程本身中，STUN 消息带有多个属性注解。"S=" 属性表示消息的源传输地址。"D=" 属性表示消息的目的地传输地址。"MA=" 属性用于 STUN Binding 响应消息，指的是映射地址。"USE-CAND" 表示存在 USE-CANDIDATE 属性。

The call flow examples omit STUN authentication operations and focus on a single data stream between two full implementations.

呼叫流程示例省略了 STUN 身份验证操作，专注于两个完整实现之间的单个数据流。

# 17. Operational Considerations | 17. 操作考虑

## 17.1. NAT and Firewall Types | 17.1. NAT 和防火墙类型

ICE is designed to work with all types of NATs and firewalls. However, the operational characteristics of NATs and firewalls can vary. Some NATs have endpoint-independent mapping properties, while others have address-dependent mapping properties. Some firewalls allowUDP traffic, while others allow only TCP traffic.

ICE 旨在与所有类型的 NAT 和防火墙一起工作。然而，NAT 和防火墙的操作特性可能有所不同。有些 NAT 具有端点无关映射属性，而有些具有地址相关映射属性。有些防火墙允许 UDP 流量，而有些只允许 TCP 流量。

## 17.2. Bandwidth Requirements | 17.2. 带宽需求

### 17.2.1. STUN and TURN Server-Capacity Planning | 17.2.1. STUN 和 TURN 服务器容量规划

STUN servers require minimal bandwidth. TURN servers require more bandwidth due to relaying data.

STUN 服务器需要最少的带宽。TURN 服务器由于数据中继需要更多带宽。

### 17.2.2. Gathering and Connectivity Checks | 17.2.2. 收集和连通性检查

The bandwidth required for gathering and connectivity checks depends on the Ta value and the number of candidates.

收集和连通性检查所需的带宽取决于 Ta 值和候选者数量。

### 17.2.3. Keepalives | 17.2.3. 保活

Keepalives require minimal bandwidth (approximately 2 bytes every 15 seconds per selected pair).

保活需要最少的带宽（每个选定对大约每 15 秒 2 字节）。

## 17.3. ICE and ICE-Lite | 17.3. ICE 和 ICE-Lite

ICE-Lite is a lite implementation that only requires host candidates. It is designed for devices that are always connected to the public Internet.

ICE-Lite 是一种轻量级实现，只需要主机候选者。它专为始终连接到公共互联网的设备而设计。

## 17.4. Troubleshooting and Performance Management | 17.4. 故障排除和性能管理

When troubleshooting ICE, it is important to check candidate gathering, connectivity checks, and nomination processes. Performance can be affected by network conditions and NAT types.

排除 ICE 故障时，检查候选者收集、连通性检查和提名过程很重要。性能可能受网络条件和 NAT 类型影响。

## 17.5. Endpoint Configuration | 17.5. 端点配置

ICE endpoints should be configured with appropriate STUN and TURN servers. The configuration should consider network topology and security requirements.

ICE 端点应配置适当的 STUN 和 TURN 服务器。配置应考虑网络拓扑和安全要求。

# 19. Security Considerations | 19. 安全考虑

## 19.1. IP Address Privacy | 19.1. IP 地址隐私

ICE candidates may reveal IP addresses. This can be a privacy concern.

ICE 候选者可能泄露 IP 地址。这可能是一个隐私问题。

## 19.2. Attacks on Connectivity Checks | 19.2. 对连通性检查的攻击

Attackers may attempt to disrupt connectivity checks. ICE includes mechanisms to mitigate these attacks.

攻击者可能试图破坏连通性检查。ICE 包含缓解这些攻击的机制。

## 19.3. Attacks on Server-Reflexive Address Gathering | 19.3. 对服务器自反地址收集的攻击

Attackers may target STUN servers. Appropriate security measures should be in place.

攻击者可能以 STUN 服务器为目标。应采取适当的安全措施。

## 19.4. Attacks on Relayed Candidate Gathering | 19.4. 对中继候选者收集的攻击

TURN servers should be secured against unauthorized access.

TURN 服务器应防止未授权访问。

## 19.5. Insider Attacks | 19.5. 内部攻击

### 19.5.1. STUN Amplification Attack | 19.5.1. STUN 放大攻击

An attacker inside the network could amplify traffic. ICE limits the number of connectivity checks to mitigate this.

网络内部的攻击者可能会放大流量。ICE 限制连通性检查的数量以缓解此问题。
