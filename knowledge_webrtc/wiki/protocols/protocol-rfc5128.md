# RFC 5128 (P2P 跨 NAT 通信状态) 协议分析

## 一句话理解

**RFC 5128 是 P2P 穿越 NAT 的"全景地图"，系统性地分析了各种 NAT 穿透技术的原理、局限性和适用场景。**

---

## 语义层 (What - 说什么)

### 核心主题

| 主题 | 说明 |
|------|------|
| **NAT 类型分类** | 根据映射和过滤行为对 NAT 进行分类 |
| **P2P 通信方法** | 各种 NAT 穿透技术的原理和适用性 |
| **EIM-NAT 分析** | 端点无关映射 NAT 的打洞技术 |
| **EDM-NAT 分析** | 端点相关映射 NAT 的局限性 |
| **存活机制** | UDP 保活以维持 NAT 绑定 |

### 关键术语

| 术语                                     | 语义含义                      |
| -------------------------------------- | ------------------------- |
| **Endpoint-Independent Mapping (EIM)** | 端点无关映射，同一内部地址+端口映射到同一公网地址 |
| **Endpoint-Dependent Mapping (EDM)**   | 端点相关映射，映射结果受目标地址影响        |
| **Full Cone NAT**                      | 完全圆锥型 NAT，无限制接受入站包        |
| **Restricted Cone NAT**                | 受限圆锥型 NAT，只接受已访问过的 IP     |
| **Port-Restricted Cone NAT**           | 端口受限圆锥型 NAT，同时限制 IP 和端口   |
| **Symmetric NAT**                      | 对称型 NAT，每个(内部, 目标)对有不同映射  |
| **Hole Punching**                      | 打洞技术，利用 NAT 行为创建 P2P 通道   |
| **Hairpinning**                        | 回环通信，两个内部客户端通过 NAT 通信     |

## 语法层 (How - 怎么说)

### NAT 类型分类体系

```
                    NAT
                      │
          ┌───────────┴───────────┐
          │                       │
    Endpoint-Independent    Endpoint-Dependent
    Mapping (EIM)            Mapping (EDM)
          │                       │
    ┌─────┴─────┐                 │
    │           │           Symmetric NAT
 Full Cone    Restricted      (对称型 NAT)
(完全圆锥)    Port-Restricted   │
              (受限)           │
              │                │
         ┌────┴────┐           │
         │         │           │
    IP Restricted Port-Restricted
    (IP受限)   (端口受限)
```

### 打洞技术分类

| 技术 | 适用 NAT 类型 | 说明 |
|------|---------------|------|
| **UDP Hole Punching** | EIM-NAT (Full/Restricted/Port-Restricted) | 最通用的打洞方法 |
| **TCP Hole Punching** | 类似 UDP | 需要同步三次握手状态 |
| **Relaying** | 任意 NAT | TURN 方案，始终有效但有性能开销 |
| **Connection Reversal** | 一端在公网 | 简单场景的变通方案 |

## 时序层 (When - 何时说)

### UDP 打洞流程 (EIM-NAT 对 EIM-NAT)

```
Client A (10.0.0.1:4000)          Client B (10.0.0.2:4000)
     │                                  │
     │──────▶ 中继服务器 ◀────────────── │
     │         (帮助交换地址信息)         │
     │                                  │
     │◀───────────────────────────────  │
     │   A的公网地址: 1.2.3.4:60000      │
     │   B的公网地址: 5.6.7.8:55000      │
     │                                  │
     │                                  │
     ▼ 打洞开始                           ▼
     │                                  │
     │────── UDP 包 ───────────▶ B的NAT  │
     │    (创建 A→B 的映射)               │
     │                                   │
     │◀────── UDP 包 ◀────────── A的NAT  │
     │    (创建 B→A 的映射)               │
     │                                  │
     │======= P2P 直连建立 ===============│
```

### Hairpinning 场景 (两个内部客户端)

```
Client A ─────▶ NAT ─────▶ Client B
  10.0.0.1:4000    1.2.3.4   10.0.0.2:4000
       │                         │
       │──── A发包到 B的映射 ───▶  │
       │                         │
       │◀─── NAT 识别目标内部 ───  │
       │    转发给 B              │
       │                         │
       │◀═══════════════════════ │
       │   A 和 B 通信成功        │
```

### NAT 存活机制

```
时间线:  0 ── 30s ── 60s ── 90s ── 120s ── ...
         │    保活   保活   保活   保活
   
目的: 防止 NAT 绑定超时被清除
建议: 至少每 30 秒发送一次 UDP 保活
```

## NAT 类型对照表

| NAT 类型 | 映射规则 | 过滤规则 | 打洞难度 |
|----------|----------|----------|----------|
| **Full Cone** | 端点无关 | 无限制 | 最容易 |
| **Restricted Cone** | 端点无关 | 仅已访问 IP | 容易 |
| **Port-Restricted Cone** | 端点无关 | 仅已访问 IP:端口 | 中等 |
| **Symmetric NAT** | 端点相关 | 端点相关 | 困难/不可能 |

## EIM-NAT vs EDM-NAT 详解

### 一句话核心区别

| 概念 | 核心区别 |
|------|---------|
| **EIM** | 同一个内部地址发往**任何目标**，都映射到**同一个公网端口** |
| **EDM** | 同一个内部地址发往**不同目标**，可能映射到**不同的公网端口** |

### EIM 详解：宿舍分配手机号 🎓

#### 场景
大学宿舍里，你给**任何人**打电话，宿管都把你的名字登记为同一个号码 **88886666**。

```
内部主机 A (10.0.0.1:4000)

  发给 朋友B (1.2.3.4:5000)  ──→  NAT 映射为 ──→  6.6.6.6:60000
  发给 同学C (5.6.7.8:6000)  ──→  NAT 映射为 ──→  6.6.6.6:60000  ← 端口相同！
  发给 老师D (9.8.7.6:7000)  ──→  NAT 映射为 ──→  6.6.6.6:60000  ← 端口相同！
```

#### 特点
- **映射结果**：只看你从哪个房间（内部端口）打的，不看你打给谁
- **公网看到的**：你永远都是 `6.6.6.6:60000`
- **打洞效果**：✅ 简单，只要对方往这个地址发包就能收到

### EDM 详解：快递柜按收件人分配 📦

#### 场景
每个快递柜格口**专门给某个收件人**用，不同收件人用不同的格口。

```
内部主机 A (10.0.0.1:4000)

  发给 朋友B (1.2.3.4:5000)  ──→  NAT 映射为 ──→  6.6.6.6:60000
  发给 同学C (5.6.7.8:6000)  ──→  NAT 映射为 ──→  6.6.6.6:60001  ← 端口变了！
  发给 老师D (9.8.7.6:7000)  ──→  NAT 映射为 ──→  6.6.6.6:60002  ← 又变了！
```

#### 特点
- **映射结果**：看你从哪个房间（内部端口）**发给谁**（目标地址）
- **公网看到的**：每次发给不同人，显示不同的端口
- **打洞效果**：❌ 困难，你不知道下次发给对方会分配什么端口

### 生活类比

| 场景 | EIM | EDM |
|------|-----|-----|
| **酒店电话** | 打给谁都显示你的房间号 301 | 打给谁，显示的号码都不一样 |
| **快递柜** | 你是 1 号柜，给谁都从 1 号柜取 | 1 号柜专属于某收件人 |
| **公司总机** | 拨打外线都显示同一个总机号 | 不同部门显示不同外线号 |

> **记忆口诀**：EIM 是"**一视同仁**"，对谁都一样；EDM 是"**区别对待**"，因人而异。

### EIM vs EDM 通信示例

#### EIM 场景 ✅ 成功

```
Alice (NAT 后)                    Bob (NAT 后)
10.0.0.1:4000                   10.0.0.2:4000
    │                                │
    │─── 发给 STUN 服务器 ────▶       │
    │◀── 我的公网地址: 1.2.3.4:60000   │
    │                                │
    │                  ◀─── 发给 STUN 服务器 ───│
    │                  ───▶ 我的公网地址: 5.6.7.8:55000 │
    │                                │
    │◀═══════════════════════════════│
    │   Bob 发到 1.2.3.4:60000 成功！│
```

#### EDM 场景 ❌ 困难

```
Alice (对称型 NAT 后)              Bob (对称型 NAT 后)
10.0.0.1:4000                   10.0.0.2:4000
    │                                │
    │─── 发给 STUN ──▶               │
    │◀── 1.2.3.4:60000               │  (发给 STUN 的端口)
    │                                │
    │                  ◀─── 发给 STUN ───│
    │                  ───▶ 5.6.7.8:55000   │  (发给 STUN 的端口)
    │                                │
    │    问题：Alice 发给 Bob 时      │ 
    │    NAT 可能分配 60001 端口！     │
    │    而 Bob 期望的是 60000        │
    │    ──────────────────────────▶ │
    │         发到 5.6.7.8:55000     │
    │         但 Bob 只信任 55000     │
    │    NAT 过滤 ❌                 │
```

### EIM-NAT vs EDM-NAT 完整对比

| 对比维度 | EIM-NAT (圆锥型) | EDM-NAT (对称型) |
|----------|-----------------|-----------------|
| **分配规则** | 看"谁发的" | 看"发给谁" |
| **A→B 的映射** | `10.0.0.1:4000` → `6.6.6.6:60000` | `10.0.0.1:4000` → `6.6.6.6:60000` |
| **A→C 的映射** | `10.0.0.1:4000` → `6.6.6.6:60000` | `10.0.0.1:4000` → `6.6.6.6:60001` |
| **可预测性** | ✅ 固定 | ❌ 不固定 |
| **打洞支持** | ✅ 完整支持 | ❌ 无法可靠打洞 |
| **P2P 友好** | ✅ 友好 | ❌ 不友好 |
| **适用场景** | 大多数消费级 NAT | 企业网络、部分运营商 NAT |

## NAT 过滤规则详解

NAT 的过滤规则决定了**哪些入站数据包被允许通过**。这是 NAT 穿透打洞成功的关键因素。

### Full Cone NAT：无限制过滤 ✅

```
内部 A (10.0.0.1:4000) ──→ NAT ──→ 公网地址 6.6.6.6:60000

规则：谁往 6.6.6.6:60000 发包，我都接受
```

| 特点 | 说明 |
|------|------|
| **过滤条件** | 无限制，任何公网 IP:端口都能发 |
| **类比** | 公开邮箱，任何人都能投递 |
| **打洞难度** | 最容易 |

### Restricted Cone NAT：仅限制 IP ⚠️

```
内部 A (10.0.0.1:4000) ──→ NAT ──→ 公网地址 6.6.6.6:60000

规则：只有 A 访问过的 IP，才能往 6.6.6.6:60000 发包
```

#### 具体例子

```
步骤 1: A 先访问 B (1.2.3.4)
   A ──────────────────────────▶ 1.2.3.4:ANY
   
   结果：A 可以接收来自 1.2.3.4 的任何端口发来的包 ✅

步骤 2: C (5.6.7.8) 想给 A 发包
   C ──────────────────────────▶ 6.6.6.6:60000
   
   结果：NAT 拒绝 ❌（因为 A 没访问过 5.6.7.8）
```

#### 生活类比：手机通讯录白名单

```
你只接听通讯录里的人的电话
- 张三 (IP: 1.2.3.4) ──▶ 你接听 ✅
- 李四 (IP: 5.6.7.8) ──▶ 你不接 ❌（不在通讯录）
```

### Port-Restricted Cone NAT：限制 IP + 端口 ⚠️⚠️

```
内部 A (10.0.0.1:4000) ──→ NAT ──→ 公网地址 6.6.6.6:60000

规则：只有 A 访问过的 (IP:端口)，才能往 6.6.6.6:60000 发包
```

#### 具体例子

```
步骤 1: A 先访问 B (1.2.3.4:5000)
   A ──────────────────────────▶ 1.2.3.4:5000
   
   结果：A 只能接收来自 1.2.3.4:5000 的包 ✅
   
步骤 2: B 从不同端口 1.2.3.4:6000 想给 A 发包
   1.2.3.4:6000 ──────────────▶ 6.6.6.6:60000
   
   结果：NAT 拒绝 ❌（A 访问的是 1.2.3.4:5000，不是 6000）

步骤 3: C (5.6.7.8:5000) 想给 A 发包
   5.6.7.8:5000 ──────────────▶ 6.6.6.6:60000
   
   结果：NAT 拒绝 ❌（A 没访问过 5.6.7.8）
```

#### 生活类比：精确通讯录白名单

```
你只接听通讯录里的人从特定号码打来的电话
- 张三-手机 (1.2.3.4:5000) ──▶ 你接听 ✅
- 张三-座机 (1.2.3.4:6000) ──▶ 你不接 ❌（号码不对）
- 李四 (5.6.7.8:5000) ────────▶ 你不接 ❌（不是通讯录的人）
```

### 过滤规则总结对比

| NAT 类型 | 映射规则 | 过滤规则 | 灵活度 | 打洞难度 |
|----------|----------|----------|--------|----------|
| **Full Cone** | EIM | **无限制**<br>任何公网 IP:端口都能发 | 最高 | 最容易 |
| **Restricted Cone** | EIM | **仅限 IP**<br>必须是访问过的 IP | 中等 | 容易 |
| **Port-Restricted** | EIM | **限 IP + 端口**<br>必须是访问过的 IP:端口 | 较低 | 中等 |
| **Symmetric** | EDM | **端点相关**<br>每个目标有不同映射 | 无 | 困难 |

### 打洞场景中的实际影响

#### Restricted Cone NAT 打洞

```
Alice (受限 IP NAT 后)              Bob
10.0.0.1:4000                   5.6.7.8:ANY
    │                                │
    │─── 发给 Bob (5.6.7.8:ANY) ────▶│
    │    (创建 Alice 的映射)          │
    │                                │
    │◀── Bob 从任意端口发回 ───────│  ✅ 成功！(IP 对就行)
```

#### Port-Restricted Cone NAT 打洞

```
Alice (端口受限 NAT 后)            Bob
10.0.0.1:4000                   5.6.7.8:5000
    │                                │
    │─── 发给 Bob (5.6.7.8:5000) ───▶│
    │    (创建 Alice 的映射)          │
    │                                │
    │◀── Bob 必须从 5000 端口发回 ─│  ⚠️ 端口必须精确匹配！
    │    如果 Bob 从 5001 发          │
    │    NAT 丢弃 ❌                 │
```

### 过滤规则一句话总结

> **打洞关键**：发送方必须从**之前被 NAT 记录的那个地址**回复，否则 NAT 过滤掉！

| 类型 | 限制什么 | 灵活度 |
|------|---------|--------|
| **Restricted Cone** | 限制 IP，不限端口 | 中等 |
| **Port-Restricted** | 限制 IP + 限制端口 | 最低 |
| **Symmetric** | 映射都变了（最严格） | 无 |

## 穿透技术选择决策树

```
检测 NAT 类型
     │
     ├─ EIM-NAT ──────────────────▶ UDP Hole Punching
     │                                     │
     │                              成功？  │
     │                                ├─是─▶ 直连通信
     │                                └─否─▶ TURN 中继
     │
     └─ Symmetric NAT ─────────────▶ TURN 中继 (唯一可靠方案)
```

## 各技术对比

| 技术 | Full Cone | Restricted | Port-Restricted | Symmetric | 性能 |
|------|-----------|------------|-----------------|-----------|------|
| **UDP Hole Punching** | ✅ | ✅ | ✅ | ❌ | 高 |
| **TCP Hole Punching** | ✅ | ✅ | ✅ | ❌ | 中 |
| **Relaying (TURN)** | ✅ | ✅ | ✅ | ✅ | 低 |
| **Connection Reversal** | ✅ | ✅ | ✅ | ✅ | 高 |

## 与现代协议的关系

| 技术 | RFC | 关系 |
|------|-----|------|
| **STUN** | RFC 5389 | 基于 RFC 5128 的打洞原理实现 |
| **TURN** | RFC 5766 | 提供无法打洞时的中继方案 |
| **ICE** | RFC 8445 | 综合 STUN/TURN 的标准化方案 |

RFC 5128 的分析为这些协议的设计提供了理论基础。

---

## 一句话总结

> **RFC 5128 = NAT 类型分类 + 打洞技术分析 + 适用场景指南**
>
> **EIM-NAT 可打洞，Symmetric NAT 只能中继**
>
> **现代 P2P 方案 = ICE 统一协调 STUN + TURN**
