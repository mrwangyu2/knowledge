# A Google Congestion Control Algorithm for Real-Time Communication (GCC)

> **一句话**：GCC 是 WebRTC 中实际使用的拥塞控制算法，由**基于延迟的控制器**（Kalman 滤波 + 过载检测）和**基于丢包的控制器**两层组成，发送速率取两者中的较小值。

---

## 一句话理解

> **GCC = 延迟控制器（Kalman 滤波检测排队）+ 丢包控制器（丢包率调速率）。两个控制器独立运行，发送速率 = min(延迟估计, 丢包估计)。延迟探测"即将拥塞"，丢包处理"已经拥塞"。**

---

## 为什么实时通信需要专门的拥塞控制？

TCP 的拥塞控制（Reno/CUBIC/BBR）不适合实时音视频：

```
TCP 拥塞控制:
  "丢了包就降速，没丢就一直加" → AIMD 锯齿波

  问题在 RTC:
  ❌ 音视频编码器不能瞬间变码率（只能阶梯式切换）
  ❌ 不能重传（实时性不允许等待重传包）
  ❌ 锯齿波导致视频质量忽好忽坏，用户体验极差
  ❌ TCP 填满缓冲区 → 引入大量延迟 → 音视频通话不可用
```

**GCC 的方案：延迟先行，丢包兜底**

```
GCC:
  延迟控制器: "我感觉排队延迟在增长 → 快到瓶颈了 → 先降一点"
  丢包控制器: "丢包超过 10% → 已经堵死了 → 大幅降速"

  效果:
  ✅ 大多数情况在丢包前就降速（基于延迟，主动避让）
  ✅ 不会填满网络缓冲区（保持低延迟）
  ✅ 与 TCP 流公平共享瓶颈链路
```

## 系统模型

```
┌──────────────────────────────────────────────────────────────┐
│                     GCC 系统架构                               │
│                                                              │
│  ┌──────────┐    ┌───────────┐    ┌───────────┐              │
│  │ 编码器    │───>│  Pacer    │───>│  网络      │───> 接收端   │
│  │ (产生数据) │    │ (平滑发送) │    │           │              │
│  └──────────┘    └─────┬─────┘    └───────────┘              │
│                        │ burst_time=5ms                      │
│                        ▼                                     │
│               target_bitrate × burst_time                    │
│                                                              │
│  ┌──────────────────────────────────────────┐                │
│  │         发送端控制器                       │                │
│  │                                          │                │
│  │  ┌────────────────┐  ┌────────────────┐  │                │
│  │  │ 延迟控制器       │  │ 丢包控制器      │  │                │
│  │  │ (Kalman滤波)    │  │ (丢包率比例)    │  │                │
│  │  │ → A_hat        │  │ → As_hat       │  │                │
│  │  └───────┬────────┘  └───────┬────────┘  │                │
│  │          └────────┬──────────┘           │                │
│  │                   ▼                      │                │
│  │     target = min(A_hat, As_hat)          │                │
│  └──────────────────────────────────────────┘                │
│                                                              │
│  反馈通道: Transport-wide CC 或 REMB + RTCP RR                │
└──────────────────────────────────────────────────────────────┘
```

**Pacer（发送节奏控制）**：目标码率不是一次性灌入网络，而是每 5ms 发一小批包，模拟"匀速流"，避免突发造成自感拥塞。

## 延迟控制器 (Delay-based Controller)

> 核心思想：**排队延迟增长 = 即将拥塞的信号**。用 Kalman 滤波从噪声中提取真实的排队趋势。

### 四步流水线

```
RTP包到达时间序列
      │
      ▼
┌─────────────┐
│ 1. 预过滤    │  合并突发到达的包组 (同一 burst 内的包视为一组)
└──────┬──────┘
       │ 包组到达时间 t(i), 包组出发时间 T(i)
       ▼
┌─────────────┐
│ 2. Kalman   │  估计排队延迟趋势 m_hat(i)
│    滤波器    │  d(i) = t(i)-t(i-1) - (T(i)-T(i-1))
└──────┬──────┘  d(i) = m(i) + v(i)  (信号+噪声)
       │ m_hat(i)
       ▼
┌─────────────┐
│ 3. 过载检测  │  比较 m_hat(i) 与自适应阈值 del_var_th(i)
│             │  over-use:  m_hat > +threshold，持续 overuse_time_th
│             │  under-use: m_hat < -threshold
│             │  normal:    其他情况
└──────┬──────┘
       │ 状态信号
       ▼
┌─────────────┐
│ 4. 速率控制  │  状态机: Increase / Decrease / Hold
│             │  A_hat 目标的 AIMD 调整
└─────────────┘
```

### 关键公式

**包组间延迟变化 (inter-group delay variation)：**

```
d(i) = t(i) - t(i-1) - (T(i) - T(i-1))

  t(i): 第 i 组最后一个包的到达时间
  T(i): 第 i 组最后一个包的出发时间
  d(i) > 0 → 到达间隔 > 出发间隔 → 队列在增长
  d(i) < 0 → 到达间隔 < 出发间隔 → 队列在排空
```

**Kalman 滤波器**：从 d(i) 中估计真实的排队趋势 m_hat(i)

```
状态方程:  m(i+1) = m(i) + u(i)     (u ~ N(0, q), q=10^-3)
观测方程:  d(i) = m(i) + v(i)       (v ~ N(0, var_v))

递归更新:
  z(i) = d(i) - m_hat(i-1)               ← 观测残差
  m_hat(i) = m_hat(i-1) + z(i) × k(i)    ← Kalman 增益加权更新
  k(i) = (e(i-1)+q) / (var_v_hat + e(i-1)+q)
  e(i) = (1-k(i)) × (e(i-1)+q)           ← 估计误差协方差
```

**自适应过载阈值**：动态调整——防止被 TCP 流"饿死"

```
del_var_th(i) = del_var_th(i-1) + Δt × K × (|m(i)| - del_var_th(i-1))

  当 |m| > threshold → K=K_u=0.01 (快速提高门槛，容忍更多排队)
  当 |m| < threshold → K=K_d=0.00018 (缓慢降低门槛，追求低延迟)
  范围钳制: [6, 600] ms

设计哲学:
  有 TCP 竞争时 → 提高 threshold → 容忍排队 → 不被饿死
  没有竞争时    → 降低 threshold → 追求低延迟 → 更好体验
```

### 速率控制状态机

```
           +----+--------+-----------+------------+--------+
           |     \ State |   Hold    |  Increase  |Decrease|
           |      \      |           |            |        |
           | Signal\     |           |            |        |
           +--------+----+-----------+------------+--------+
           |  Over-use   | Decrease  |  Decrease  |        |
           +-------------+-----------+------------+--------+
           |  Normal     | Increase  |            |  Hold  |
           +-------------+-----------+------------+--------+
           |  Under-use  |           |   Hold     |  Hold  |
           +-------------+-----------+------------+--------+
```

**三种状态的策略：**

| 状态 | 触发条件 | 行为 |
|------|---------|------|
| **Increase** | Normal 信号，无拥塞 | 乘性增 (远离收敛) 或 加性增 (接近收敛)，最多 8%/s |
| **Decrease** | Over-use 信号 | A_hat = 0.85 × R_hat(i)，降至当前接收码率的 85% |
| **Hold** | Under-use 信号 | 保持 A_hat 不变，等队列排空 |

**自适应增加策略：**

```
乘性增加 (远离收敛):
  eta = 1.08^min(Δt/1000, 1.0)
  A_hat(i) = eta × A_hat(i-1)

加性增加 (接近收敛):
  response_time_ms = 100 + rtt_ms
  alpha = 0.5 × min(Δt/response_time_ms, 1.0)
  A_hat(i) = A_hat(i-1) + max(1000, alpha × expected_packet_size_bits)

限制: A_hat(i) < 1.5 × R_hat(i)  (不能脱离实际接收码率太远)
```

## 丢包控制器 (Loss-based Controller)

> 延迟控制器需要队列够大才能有效工作。当队列很浅（如某些 WiFi），拥塞直接表现为丢包。丢包控制器就是兜底。

```
基于 RTCP RR 或 transport-wide-cc 反馈的丢包率 p:

  如果 p < 2%:
    → As_hat(i) = 1.05 × As_hat(i-1)    (慢速增加)

  如果 2% ≤ p ≤ 10%:
    → As_hat(i) = As_hat(i-1)            (保持不变)

  如果 p > 10%:
    → As_hat(i) = As_hat(i-1) × (1 - 0.5p)   (按比例降低)

最终目标: target = min(A_hat, As_hat)
```

**为什么 2% 以下不管？** 无线网络本身可能有少量随机丢包，不是拥塞造成的，不应反应。

**为什么 10% 才大幅降速？** 如果丢包率不增长，说明不是"自感拥塞"（自己的流导致的拥塞）。只有丢包率持续上升时才是真正的拥塞信号。

## 推荐参数

| 参数 | 含义 | 推荐值 |
|------|------|:---:|
| **burst_time** | 包组识别的时间窗口 | 5 ms |
| **q** | Kalman 状态噪声协方差 | 10^-3 |
| **e(0)** | 初始误差协方差 | 0.1 |
| **chi** | 噪声方差滤波系数 | [0.1, 0.001] |
| **del_var_th(0)** | 初始过载检测阈值 | 12.5 ms |
| **overuse_time_th** | 触发 overuse 需持续的时间 | 10 ms |
| **K_u** | 阈值增加系数 | 0.01 |
| **K_d** | 阈值减少系数 | 0.00018 |
| **T** | 接收码率测量窗口 | [0.5, 1] s |
| **beta** | 降速因子 | 0.85 |

## 两种部署架构

### 架构 A：全发送端（推荐，WebRTC 主流）

```
接收端: 运行 transport-wide-cc 反馈 (每包到达时间发回)
发送端: 运行延迟控制器 + 丢包控制器
```

### 架构 B：分离式

```
接收端: 运行延迟控制器 → 输出目标码率 → REMB 消息
发送端: 运行丢包控制器，上限 = REMB 值
```

---

## 兼容性

如果接收端不支持这些扩展，发送端应降级为**仅丢包控制**：

```
发送端:
  延迟控制器: 禁用 ← 因为没有每包到达时间数据
  丢包控制器: 使用 RTCP RR 中的丢包率 + RTT
```

## 在 WebRTC 中的实际部署

```
Chrome M23 起内置 GCC
Google Hangouts 使用 GCC
开源 WebRTC 项目默认使用 GCC

实际遇到的问题及改进:
  • WiFi 拥塞/干扰场景 → 自适应阈值改进
  • 多人会议场景 → 与 SFU 配合，逐跳拥塞控制
  • TCP 竞争 → 自适应阈值避免被 TCP 饿死
```

---

## 核心要点

1. **两层控制**：延迟控制器（Kalman 滤波 + 自适应阈值）探测"即将拥塞"，丢包控制器兜底"已经拥塞"
2. **取最小值**：最终目标码率 = min(延迟估计 A_hat, 丢包估计 As_hat)
3. **自适应阈值**：del_var_th 动态调整——有竞争时提高避让被饿死，无竞争时降低追求低延迟
4. **Pacer 平滑**：5ms burst 避免自感拥塞，模拟匀速流
5. **AIMD 速率控制**：Increase 状态乘性/加性增长，Decrease 状态降到 85% 接收码率
6. **生产验证**：Chrome M23+ 默认启用，经 Hangouts 大规模验证
