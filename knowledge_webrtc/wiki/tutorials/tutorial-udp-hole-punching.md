# UDP 打洞流程详解

## 一句话理解

**UDP 打洞 = 两个 NAT 后的端点通过各自主动发包，"欺骗"双方的 NAT 创建互信的映射条目，从而建立直接的 P2P 通道。**

---

## 问题：为什么需要打洞？

### NAT 的"只出不进"原则

NAT 的核心行为是：**内部发出去的包，响应可以进来；外部主动发来的包，直接丢弃。**

```
┌─────────────────────────────────────────────────────────────┐
│  NAT 的默认过滤规则                                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  内部 → 外部:  ✅ 放行（创建映射条目）                          │
│  外部 → 内部:  ❌ 丢弃（除非已有映射条目匹配）                   │
│                                                             │
│  A (内网) ──────▶ B (公网)     NAT创建映射，放行              │
│  B (公网) ──────▶ A (内网)     NAT查映射，有则放行，无则丢弃    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 两端都在 NAT 后的问题

```
┌──────────────────────┐       ┌──────────────────────┐
│      NAT-A           │       │      NAT-B           │
│  公网: 1.2.3.4       │       │  公网: 5.6.7.8       │
│                      │       │                      │
│  Alice               │       │                 Bob  │
│  内网: 10.0.0.1:4000 │       │  内网: 10.0.0.2:5000 │
└──────────────────────┘       └──────────────────────┘

如果 Alice 直接发 UDP 到 5.6.7.8:5000：
  → 到达 NAT-B，但 NAT-B 从未见过 Alice 的地址
  → NAT-B 丢弃该包 ❌

如果 Bob 直接发 UDP 到 1.2.3.4:4000：
  → 到达 NAT-A，但 NAT-A 从未见过 Bob 的地址  
  → NAT-A 丢弃该包 ❌
```

**两个 NAT 互相不认识对方，会互相拦截对方的包。**

---

## 核心洞察：打洞为什么能工作？

### 关键原理

```
┌─────────────────────────────────────────────────────────────┐
│  打洞的核心洞察：                                            │
│                                                             │
│  当 Alice 向 Bob 发包时，虽然包被 NAT-B 丢弃了，              │
│  但 NAT-A 已经创建了映射条目：                                │
│                                                             │
│    Alice:10.0.0.1:4000 → 公网:1.2.3.4:60000                 │
│                                ↑                             │
│                        目标: 5.6.7.8:5000                    │
│                                                             │
│  与此同时，Bob 的包（发到 1.2.3.4:60000）到达 NAT-A 时，      │
│  NAT-A 查映射表发现已有该条目 → 放行！                        │
│                                                             │
│  一句话：先发制人 — 在自己这边开个洞，等对方钻进来。            │
└─────────────────────────────────────────────────────────────┘
```

### 为什么叫"打洞"？

```
类比：两个房间之间有一堵墙（NAT）

1. Alice 在墙上钻了一个小孔（发一个 UDP 包出去）
   → NAT-A 记录：这个孔通往 Alice 的房间
   
2. Bob 也在墙上钻了一个小孔（发一个 UDP 包出去）
   → NAT-B 记录：这个孔通往 Bob 的房间
   
3. 两个孔对齐后 → 数据可以双向流动

"打洞"不是真的在 NAT 上开端口，而是在 NAT 映射表里创建一条"允许通过"的记录。
```

## 完整流程：三步走

### 角色定义

| 角色 | 说明 | 类比 |
|------|------|------|
| **Alice** | NAT-A 后面的客户端 | 想通话的人 |
| **Bob** | NAT-B 后面的客户端 | 想通话的人 |
| **Rendezvous Server** | 公网上的中介服务器 | 帮忙传纸条的中间人 |

### 步骤一：Alice 和 Bob 分别向中介服务器报到

```
┌─────────────────────────────────────────────────────────────┐
│  步骤一：向中介报到，获取自己的公网地址                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Alice (10.0.0.1:4000)                                      │
│       │                                                     │
│       │──── STUN Binding Req ────▶ NAT-A ────▶              │
│       │                                          │          │
│       │                                     Rendezvous      │
│       │                                       Server        │
│       │                                     (公网)          │
│       │◀── STUN Binding Resp ─── NAT-A ◀────  │           │
│       │    "你的公网地址: 1.2.3.4:60000"                     │
│       │                                                     │
│  Bob (10.0.0.2:5000)                                        │
│       │──── STUN Binding Req ────▶ NAT-B ────▶             │
│       │◀── STUN Binding Resp ─── NAT-B ◀────               │
│            "你的公网地址: 5.6.7.8:55000"                     │
│                                                             │
│  双方得知自己的公网身份后，通过中介交换对方的地址                │
│                                                             │
│  Alice ◀──────────── Rendezvous ────────────▶ Bob           │
│     "Bob 在 5.6.7.8:55000"    "Alice 在 1.2.3.4:60000"      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**此时 NAT 映射表状态**：

```
NAT-A 映射表:
  10.0.0.1:4000 → 1.2.3.4:60000  (目标: Rendezvous Server)

NAT-B 映射表:
  10.0.0.2:5000 → 5.6.7.8:55000  (目标: Rendezvous Server)
```

**关键问题**：这个映射能用吗？

对于 **EIM-NAT** (端点无关映射，即 Cone NAT)：同一个内部端点 → 同一个公网端口，不管目标是谁。发到 Rendezvous Server 的映射和将来发到 Bob/Alice 的是**同一个端口**。✅

对于 **EDM-NAT** (端点相关映射，即 Symmetric NAT)：发给不同目标 → 不同公网端口。发给 Bob 会分配**新端口**。❌

### 步骤二：双方同时"打洞"

这是整个流程的核心。

```
┌─────────────────────────────────────────────────────────────┐
│  步骤二：双方同时向对方发包                                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  时间线 (假设几乎同时发生):                                    │
│                                                             │
│  Alice                                Bob                   │
│    │                                   │                    │
│    │──── UDP ────▶ NAT-A               │                    │
│    │  目标: 5.6.7.8:55000              │                    │
│    │                                   │                    │
│    │         NAT-A 创建/复用映射:        │                    │
│    │         10.0.0.1:4000              │                    │
│    │           → 1.2.3.4:60000          │                    │
│    │          (目标: 5.6.7.8:55000)     │                    │
│    │                                   │                    │
│    │              ┌──────────────────────┐                   │
│    │              │ 包到达 NAT-B         │                   │
│    │    ─────────▶│ NAT-B 查映射表...     │                   │
│    │              │ 没找到 1.2.3.4:60000  │                   │
│    │              │ → 丢弃！❌           │                   │
│    │              └──────────────────────┘                   │
│    │                                   │                    │
│    │              ┌──────────────────────┐                   │
│    │              │ 但与此同时...          │                   │
│    │              │                    UDP ◀────── NAT-B     │
│    │              │                    目标: 1.2.3.4:60000   │
│    │              └──────────────────────┘                   │
│    │                                   │                    │
│    │         NAT-A 收到来自 Bob 的包:    │                    │
│    │         查映射表 → 找到 1.2.3.4:60000                    │
│    │         对应 10.0.0.1:4000                              │
│    │         → 转发给 Alice！✅                                │
│    │◀──────────────────────────────    │                    │
│    │                                   │                    │
│    │    NAT-A: ✅ 洞已打通（可以收 Bob 的包）                   │
│    │                                   │                    │
│    │              ┌──────────────────────┐                   │
│    │              │ 接着 Bob 再发包...     │                   │
│    │    ─────────▶│ NAT-A 已有映射         │                   │
│    │              │ → 放行！✅            │                   │
│    │              │ → 转发给 Alice        │                   │
│    │              └──────────────────────┘                   │
│    │                                   │                    │
│    │    NAT-B: ✅ 洞也打通了（可以收 Alice 的包）               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**用一句话说**：Alice 发给 Bob 的包，在 NAT-B 被丢弃了，但它**在 NAT-A 上开了个洞**。Bob 的包正好从这个洞进来了。

### 步骤三：P2P 直连建立

```
┌─────────────────────────────────────────────────────────────┐
│  步骤三：P2P 直连建立                                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Alice (10.0.0.1:4000)    ←──────→    Bob (10.0.0.2:5000)   │
│       │                                    │                │
│    NAT-A                                 NAT-B              │
│    1.2.3.4:60000                      5.6.7.8:55000         │
│       │                                    │                │
│       └──────────── 互联网 ────────────────┘                │
│                                                             │
│  两个 NAT 的映射表已互相"认识"对方：                            │
│                                                             │
│  NAT-A:                                                     │
│    10.0.0.1:4000 → 1.2.3.4:60000                            │
│    允许来自 5.6.7.8:55000 的入站包                            │
│                                                             │
│  NAT-B:                                                     │
│    10.0.0.2:5000 → 5.6.7.8:55000                            │
│    允许来自 1.2.3.4:60000 的入站包                            │
│                                                             │
│  现在 Alice 和 Bob 可以直接通信，不需要中介！                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 深度拆解：NAT 映射表中的"洞"

### 映射条目的生命周期

```
┌─────────────────────────────────────────────────────────────┐
│  NAT 映射表条目                                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  内部地址     公网地址      目标地址        超时计时器           │
│  ─────────────────────────────────────────────                │
│  10.0.0.1    1.2.3.4      5.6.7.8        30s ←              │
│  :4000       :60000       :55000         倒计时              │
│                                                             │
│  每当有数据包匹配此条目时，计时器重置                            │
│  计时器到期 → 条目删除 → "洞"关闭                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 为什么需要同时发包？

```
场景：Alice 先发，Bob 后发（时间差较大）

  t=0ms:    Alice 发包 → NAT-A 开洞 → 包到达 NAT-B → 被丢弃
  t=5000ms: NAT-A 的洞还在 (超时一般为 30-120s)
  t=5000ms: Bob 发包 → NAT-B 开洞 → 包到达 NAT-A → 找到映射 → 放行！
  t=5001ms: Alice 再发包 → NAT-B 已有映射 → 放行！
  → ✅ 仍然成功！

但实际工程中：
  - 双方几乎同时发包（ICE 检查并行执行）
  - 时间窗口非常小（几毫秒到几十毫秒）
  - "同时"不是严格同步，而是双方都主动触发

当一方包先到并且被丢弃，另一方的包随后到达时：
  - 先到被丢弃的包 → 在自己 NAT 上开了洞
  - 随后到达的包 → 对方的洞已开，可以进来
  - 再重试一次 → 两边的洞都已开 → P2P 建立

这就是为什么连接性检查需要多次重试。
```

## 不同 NAT 类型下的打洞行为

### Full Cone NAT → 最容易打洞

```
NAT-A (Full Cone): 映射 10.0.0.1:4000 → 1.2.3.4:60000
  过滤规则：无（任何人发到这个端口都放行）

Alice 发包给 Bob → NAT-A 创建映射 → 洞已存在
Bob 发包给 1.2.3.4:60000 → NAT-A 无过滤 → 直接放行！
→ ✅ 单向发包即可打洞（甚至不需要 Bob 主动发包！）
```

### Restricted Cone NAT → 容易打洞

```
NAT-A (Restricted Cone): 映射 10.0.0.1:4000 → 1.2.3.4:60000
  过滤规则：只接受 Alice 发过的 IP 的入站包

1. Alice 发包给 Bob (5.6.7.8) → NAT-A 记录"Alice 访问过 5.6.7.8"
2. Bob 从 5.6.7.8:ANY_PORT 发到 1.2.3.4:60000
3. NAT-A 检查：5.6.7.8 在已访问列表中 → ✅ 放行！
→ ✅ 仍需双方发包，但 Bob 可以用任意端口回复
```

### Port-Restricted Cone NAT → 稍难但可行

```
NAT-A (Port-Restricted): 映射 10.0.0.1:4000 → 1.2.3.4:60000
  过滤规则：只接受 Alice 发过的 (IP:端口) 的入站包

1. Alice 发包给 Bob (5.6.7.8:55000) → NAT-A 记录"Alice 访问过 5.6.7.8:55000"
2. Bob 必须从 5.6.7.8:55000（注意：端口必须精确！）发到 1.2.3.4:60000
3. NAT-A 检查：5.6.7.8:55000 在已访问列表中 → ✅ 放行！
4. 如果 Bob 从 5.6.7.8:55001 发 → NAT-A 查无此端口 → ❌ 丢弃！
→ ⚠️ 需要精确端口匹配，这就是为什么必须通过中介交换端口信息
```

### Symmetric NAT → 打洞失败

```
NAT-A (Symmetric): 
  发给 Rendezvous → 映射为 1.2.3.4:60000
  发给 Bob → 映射为 1.2.3.4:60001（不同！）

问题：
  1. Alice 通过 Rendezvous 告诉 Bob："我在 1.2.3.4:60000"
  2. Bob 发包到 1.2.3.4:60000
  3. 但 Alice 发给 Bob 时，NAT-A 分配了新端口 60001
  4. NAT-A 中 60000 的映射只接受来自 Rendezvous 的包
  5. Bob 发到 60000 的包被当作"未授权入站" → ❌ 丢弃！

→ ❌ 无法可靠打洞，需要 TURN 中继
```

### 打洞成功率矩阵

```
              Bob
              Full Cone  Restricted  Port-Restr  Symmetric
Alice  ┌─────────────────────────────────────────────────┐
Full   │     ✅          ✅           ✅          ❌      │
Restr  │     ✅          ✅           ✅          ❌      │
Port-R │     ✅          ✅           ✅          ❌      │
Symm   │     ❌          ❌           ❌          ❌      │
       └─────────────────────────────────────────────────┘

规律：只要有一方是 Symmetric NAT，打洞就不可靠
      双方都非 Symmetric → 打洞可行
```

## 打洞过程中的四个"同时"问题

### 问题 1：包的时序竞争

```
┌─────────────────────────────────────────────────────────────┐
│  理想情况：双方包头碰头                                       │
│                                                             │
│  Alice ────▶ NAT-A ────▶ NAT-B ◀──── Bob                   │
│         ▲                         ▲                         │
│         └── Bob的包 ──── NAT-B ────┘                        │
│                                                             │
│  实际情况：总有一方先到达                                       │
│    先到方的包 → 在对方 NAT 被丢弃（对方还没开洞）                 │
│    但先到方的包 → 在自己的 NAT 上开了洞                         │
│    后到方的包 → 先到方的洞已开 → 成功到达！                      │
│                                                             │
│  对策：多次重试                                               │
│    第一次: Alice的包被NAT-B丢弃，但NAT-A开了洞                  │
│    第二次: Alice再发包 → NAT-B的洞可能已开（Bob发过包了）→ 成功   │
└─────────────────────────────────────────────────────────────┘
```

### 问题 2：映射端口的可预测性

```
EIM-NAT (Cone):
  Alice 发给 STUN → NAT-A 分配 60000
  Alice 发给 Bob  → NAT-A 复用 60000  ✅ 可预测
  
EDM-NAT (Symmetric):
  Alice 发给 STUN → NAT-A 分配 60000
  Alice 发给 Bob  → NAT-A 分配 60001  ❌ 不可预测
  
Bob 被告知 Alice 在 60000，但实际映射是 60001 → Bob 发到错误端口 → 被丢弃
```

### 问题 3：NAT 超时不够快

```
NAT 映射超时通常 30-120 秒，对于实时通信足够了。
但在打洞阶段，如果两次重试间隔太长，映射可能过期。

对策：打洞阶段使用快速重传（ICE 默认 RTO=500ms，后续指数退避）
```

### 问题 4：中介信息的时效性

```
Alice 通过 Rendezvous Server 获取：
  - Bob 的公网地址: 5.6.7.8:55000
  - 这个信息是 Bob 几分钟前上报的
  - 如果 Bob 的 NAT 映射已过期 → 端口可能变了 → 打洞失败
  
对策：在打洞前重新获取最新地址（ICE 的 candidate gathering 在连通性检查前完成）
```

## "中介"到底是谁？

在 UDP 打洞流程中，"中介"帮助两端交换地址信息。但**中介不是一个东西**，而是由三个不同角色共同承担：

### 中介的三重身份

```
┌─────────────────────────────────────────────────────────────┐
│  中介的三重身份                                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 地址发现者: STUN Server                                  │
│     "告诉我，我的公网地址是什么？"                              │
│                                                             │
│  2. 信息搬运工: Signaling Server                             │
│     "Alice 在 1.2.3.4:60000，Bob 在 5.6.7.8:55000，交换吧"    │
│                                                             │
│  3. 传输管道: Signaling Channel (WebSocket / SIP / HTTP)     │
│     "这条管道用来传 SDP/ICE 候选"                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 角色一：STUN Server — 告诉你"我是谁"

```
Alice (10.0.0.1:4000)
    │
    │── Binding Request ──▶ STUN Server (公网)
    │                       stun.l.google.com:19302
    │
    │◀─ Binding Response ──
    │   XOR-MAPPED-ADDRESS: 1.2.3.4:60000  ← Alice 的公网身份
    │
    │   "你在公网上长这样，记好了"
```

**STUN 服务器的特点**：

| 特点 | 说明 |
|------|------|
| **功能** | 回显客户端公网地址，不做其他事情 |
| **成本** | 极低，一个 UDP 包来一个 UDP 包回，几十字节 |
| **谁部署** | 用第三方免费的就行（Google 有公共 STUN） |
| **带宽** | 不中继数据，不存在带宽成本 |
| **公共 STUN** | `stun.l.google.com:19302`、`stun1.l.google.com:19302` |

> 你的 STUN Binding 请求本身就已经在 NAT 上创建了第一条映射记录。

### 角色二：Signaling Server — 帮你们交换"名片"

```
Alice                            Signaling Server                        Bob
  │                                    │                                  │
  │──── 我的 SDP (含候选列表) ────────▶│                                  │
  │  Host:    192.168.1.100:5000       │                                  │
  │  Srflx:   1.2.3.4:60000           │                                  │
  │  Relay:   198.51.100.5:30000       │                                  │
  │                                    │── Bob的SDP (含候选列表) ────────▶│
  │                                    │  Host:   10.0.0.2:5000           │
  │                                    │  Srflx:  5.6.7.8:55000           │
  │                                    │                                  │
  │◀── Bob的SDP (含候选列表) ──────────│                                  │
  │                                    │                                  │
  │         交换完毕，双方知道了对方的公网地址          交换完毕              │
```

**Signaling Server 的特点**：

| 特点 | 说明 |
|------|------|
| **功能** | 中继 SDP Offer/Answer 和 ICE 候选，不参与媒体传输 |
| **谁部署** | **应用开发者自己** — 因为业务逻辑（房间管理、鉴权、好友关系）是应用私有的 |
| **何时参与** | 只在连接建立前和 ICE 重启时参与，连上后可以离线 |
| **关键设计** | 它**不知道**音视频内容，只看得到候选地址列表 |

### 角色三：Signaling Channel — 传输管道

| 实现方式 | 适用场景 | 说明 |
|----------|---------|------|
| **WebSocket** | WebRTC 浏览器端 | 最常用，双向实时，浏览器原生支持 |
| **SIP** | VoIP 电话系统 | 电信级，配合 SIP Proxy/Registrar |
| **HTTP REST + SSE** | 简单 Web 应用 | 轮询或 Server-Sent Events |
| **XMPP** | 即时通讯 | Jabber/Google Talk 时代的方案 |
| **MQTT** | IoT 场景 | 轻量发布/订阅，适合嵌入式设备 |
| **自定义 TCP** | 游戏/嵌入式 | 资源受限或需要自定义协议 |

### 三者的协作全景

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  ① 报到阶段                                                        │
│     Alice ──▶ STUN Server ──▶ "你的公网地址: 1.2.3.4:60000"          │
│     Bob   ──▶ STUN Server ──▶ "你的公网地址: 5.6.7.8:55000"          │
│                                                                     │
│  ② 交换阶段                                                        │
│     Alice ──▶ Signaling Server ──▶ Bob 收到 Alice 的候选列表          │
│     Bob   ──▶ Signaling Server ──▶ Alice 收到 Bob 的候选列表          │
│                                                                     │
│  ③ 打洞+通信阶段 (Signaling 不再参与!)                                │
│     Alice ◀══════ UDP 直连 ═══════▶ Bob                             │
│                                                                     │
│  STUN Server:     只用了一次 (地址发现，几十字节)                      │
│  Signaling Server: 只用了一次 (交换候选，几 KB)                        │
│  真正通信:         Alice ↔ Bob，不再需要任何中介!                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 谁部署谁付费？

| 角色 | 谁部署 | 成本 | 为什么 |
|------|--------|------|--------|
| **STUN Server** | 第三方免费 ➕ 可自建 | $0（公共）/ 极低 | 只回几个字节的地址，无数据流量 |
| **Signaling Server** | **应用开发者自己** | 中等 | 业务逻辑私有的，但只传信令不传数据 |
| **TURN Server** | **应用开发者自己** | 高 | 中继所有音视频数据，带宽费用大头 |

> **一句话：STUN 可以白嫖 Google，Signaling 必须自己写（房间管理、鉴权、好友关系是应用私有的），TURN 得在自己服务器上跑（转发所有数据，带宽成本高）。**

## 候选者交换：不同场景的"邮递员"

ICE 只定义了**候选的格式**（SDP 里的 `a=candidate` 行），但没说**怎么送到对端**。不同场景选择了完全不同的"邮递员"。

### 全景对比

```
┌─────────────────────────────────────────────────────────────────────┐
│  场景                 交换方式               传输层      Trickle ICE  │
├─────────────────────────────────────────────────────────────────────┤
│  WebRTC 浏览器        WebSocket              TCP         ✅          │
│  WebRTC 简化版        HTTP REST + SSE        TCP         ⚠️ 折中     │
│  VoIP / SIP           SIP INVITE/200 OK      UDP/TCP     ✅          │
│  libnice (C 库)       IO Stream 抽象         ？           ✅          │
│  游戏 / 自定义         自定义协议              TCP/UDP     ✅          │
│  IoT / MQTT           MQTT Publish/Subscribe TCP         ✅          │
│  P2P 文件共享          DHT / Tracker         UDP         ❌          │
│  移动端离线             Push Notification     HTTP/2      ✅          │
└─────────────────────────────────────────────────────────────────────┘
```

### 场景一：WebRTC 浏览器 → WebSocket（最主流）

```
┌─────────────────────────────────────────────────────────────────────┐
│  WebRTC + WebSocket 候选交换                                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Alice (浏览器)                      Signaling Server       Bob (浏览器)
│       │          WebSocket 长连接          │     WebSocket 长连接   │
│       │═══════════════════════════════════│═══════════════════════  │
│       │                                   │                        │
│       │──── { type: "offer", sdp } ─────▶│                        │
│       │                                   │── { type: "offer" } ─▶│
│       │                                   │                        │
│       │                                   │◀─ { type: "answer" } ─│
│       │◀─ { type: "answer", sdp } ───────│                        │
│       │                                   │                        │
│       │──── { type: "candidate", ... } ──▶│── { type: "candidate"}▶│
│       │──── { type: "candidate", ... } ──▶│── { type: "candidate"}▶│
│       │      (Trickle ICE: 边收集边发)     │                        │
│       │                                   │                        │
│       │◀─ { type: "candidate", ... } ─────│◀─ { type: "candidate"}│
│                                                                     │
│  每条消息格式 (JSON):                                                │
│  {                                                                  │
│    "type": "candidate",                                             │
│    "sdpMid": "0",             ← 媒体流标识 (音频=0, 视频=1)           │
│    "sdpMLineIndex": 0,                                              │
│    "candidate": "candidate:1 1 UDP 2130706431 192.168.1.100 5000 ..."│
│  }                                                                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**为什么 WebSocket 是主流？**

| 优势 | 说明 |
|------|------|
| **双向实时** | 浏览器原生支持，一条连接双向推送 |
| **低延迟** | 长连接无需握手开销，候选到达立刻转发 |
| **穿防火墙** | WebSocket over HTTPS，443 端口无阻碍 |
| **Trickle ICE 友好** | 边收集边发，候选逐个推送，加速连接 |
| **生态成熟** | Socket.IO / ws / SignalR 等库开箱即用 |

**一个 WebSocket 连接的典型消息流**：

```
{ type: "join",   room: "abc123" }          ← 加入房间
{ type: "offer",  sdp: "v=0\r\n..." }       ← SDP Offer (含初始候选)
{ type: "candidate", candidate: "...", sdpMid: "0" }  ← Trickle ICE 候选
{ type: "candidate", candidate: "...", sdpMid: "0" }  ← 又一个候选...
{ type: "leave",  room: "abc123" }          ← 离开
```

### 场景三：VoIP / SIP → SIP 消息本身

这是**最经典的方式**——SIP 消息的 body 里直接携带 SDP，候选交换就是 SIP 信令过程的副产品。

```
┌─────────────────────────────────────────────────────────────────────┐
│  SIP 候选交换                                                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Alice (SIP UA)              SIP Proxy              Bob (SIP UA)    │
│       │                         │                         │          │
│       │── INVITE (body=SDP) ──▶│                         │          │
│       │  SDP 内含 ICE 候选:      │── INVITE ──────────────▶│          │
│       │  a=candidate:1 1 UDP    │                         │          │
│       │    2130706431           │                         │          │
│       │    192.168.1.100 5000   │◀── 180 Ringing ────────│          │
│       │    typ host             │                         │          │
│       │                         │◀── 200 OK (body=SDP) ──│          │
│       │◀── 200 OK (body=SDP) ──│  SDP 内含 Bob 的 ICE 候选 │          │
│       │       ICE 交换完成!      │                         │          │
│       │                         │                         │          │
│       │── ACK ─────────────────────────────────────────▶│          │
│       │                         │                         │          │
│       │══════════ RTP 媒体直连 ═══════════════════════════│          │
│                                                                     │
│  Trickle ICE 的 SIP 扩展:                                           │
│    - SIP INFO 消息携带新候选                                         │
│    - SIP UPDATE (RFC 3311) 在 200 OK 之前交换候选                     │
│                                                                     │
│  SDP 示例 (在 SIP INVITE body 中):                                   │
│  v=0                                                                │
│  o=alice 2890844526 2890844526 IN IP4 192.168.1.100                 │
│  s=                                                                 │
│  c=IN IP4 192.168.1.100                                             │
│  t=0 0                                                              │
│  m=audio 5000 RTP/AVP 0                                             │
│  a=rtpmap:0 PCMU/8000                                               │
│  a=candidate:1 1 UDP 2130706431 192.168.1.100 5000 typ host         │
│  a=candidate:2 1 UDP 1694498815 1.2.3.4 60000 typ srflx             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**SIP 候选交换的特点**：

| 特点 | 说明 |
|------|------|
| **无需额外信道** | 信令即候选交换，SIP 本身就会路由 SDP |
| **代理路由** | SIP Proxy 自动处理寻址、NAT 穿透、分叉呼叫 |
| **Trickle ICE** | RFC 8840 定义了 SIP INFO 携带 Trickle ICE 的方法 |
| **电信级可靠** | 重传、超时、故障转移都由 SIP 协议栈处理 |
| **部署成本** | 需要 SIP 基础设施 (Proxy, Registrar, PBX) |

### 场景四：libnice → IO Stream 抽象

`libnice` 是 GNOME 的 ICE 实现库，用于原生应用（非浏览器）。它的候选交换设计是**最大抽象**——给你一个 `NiceAgent`，你把候选字符串传到对端就行，怎么传的不关心。

```
┌─────────────────────────────────────────────────────────────────────┐
│  libnice 候选交换                                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  libnice 的哲学: "我只生成候选字符串，你怎么传给对面我不管"               │
│                                                                     │
│  ┌────────────────────────────────────────────────────┐            │
│  │  NiceAgent                                         │            │
│  │                                                    │            │
│  │  nice_agent_get_local_credentials()   ← 获取本地 ufrag/pwd       │
│  │  nice_agent_get_local_candidates()    ← 获取本地候选列表           │
│  │  nice_agent_set_remote_credentials()  ← 设置对端 ufrag/pwd       │
│  │  nice_agent_set_remote_candidates()   ← 设置对端候选列表           │
│  │                                                    │            │
│  │  所有参数都是字符串，你通过什么管道传都行:              │            │
│  │    → TCP Socket                                    │            │
│  │    → Unix Domain Socket                            │            │
│  │    → D-Bus                                         │            │
│  │    → 文件                                          │            │
│  │    → 剪贴板                                        │            │
│  │    → 任何你喜欢的方式                                │            │
│  └────────────────────────────────────────────────────┘            │
│                                                                     │
│  典型用法 (伪代码):                                                  │
│                                                                     │
│  // --- Alice 侧 ---                                                │
│  agent = nice_agent_new()                                           │
│  stream_id = nice_agent_add_stream(agent, 1)                         │
│  nice_agent_gather_candidates(agent, stream_id)                     │
│                                                                     │
│  // 等待候选收集完毕...                                              │
│  candidates = nice_agent_get_local_candidates(agent)                │
│  send_via_any_channel(candidates)  ← 发给 Bob，方式任意              │
│                                                                     │
│  // --- Bob 侧 ---                                                  │
│  remote_candidates = recv_via_any_channel()                         │
│  nice_agent_set_remote_candidates(agent, remote_candidates)         │
│  // ICE 开始打洞 → 连通!                                            │
│                                                                     │
│  常见使用 libnice 的项目:                                            │
│    - GStreamer (WebRTCBin)                  → D-Bus / GstBus        │
│    - Pidgin / libpurple                     → XMPP                  │
│    - Janus Gateway                           → 自定义 JSON over WS  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 场景五：游戏 / 自定义协议 → Matchmaking + 自定义传输

游戏场景的候选交换很"粗暴"——通常自定义二进制协议，直接嵌在 game protocol 里，不折腾 WebSocket/HTTP。

```
┌─────────────────────────────────────────────────────────────────────┐
│  游戏场景候选交换                                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌──────────────────────────────┐                                   │
│  │  Matchmaking Server          │                                   │
│  │  (配对 + 候选交换 + 房间管理)   │                                   │
│  └──────┬───────────────────────┘                                   │
│         │                                                           │
│    TCP 长连接 (自定义二进制协议)                                       │
│         │                                                           │
│  ┌──────┴──────┐                                          ┌──────┐  │
│  │ Player A    │                                          │Player│  │
│  │             │◀──── UDP P2P (ICE 打洞后) ──────────────▶│  B   │  │
│  └─────────────┘                                          └──────┘  │
│                                                                     │
│  典型做法:                                                           │
│    1. 玩家通过 TCP 连接 Matchmaking Server                           │
│    2. Server 配对 → 下发双方的候选                                    │
│    3. 双方同时开始打洞                                                │
│    4. 打洞成功 → TCP 断开 → 纯 UDP P2P                               │
│    5. 打洞失败 → 走游戏服务器的 Relay (类似 TURN)                      │
│                                                                     │
│  候选消息格式 (自定二进制):                                           │
│  ┌────────────┬────────┬──────────────────────┐                     │
│  │ MsgType=0x10│ Count  │ Candidate[0..N]      │                     │
│  │ (候选交换)   │ (候选数) │ 每个候选:              │                     │
│  │  1 byte     │ 1 byte │  - Type (host/srflx) │                     │
│  │            │        │  - IP (4 or 16 bytes) │                     │
│  │            │        │  - Port (2 bytes)     │                     │
│  │            │        │  - Priority (4 bytes)  │                     │
│  └────────────┴────────┴──────────────────────┘                     │
│                                                                     │
│  为什么不用 WebSocket?                                               │
│    - 游戏对延迟敏感，一条连接开销都要省                                 │
│    - 已有自定义 TCP 连接（登录、状态同步），复用即可                      │
│    - 不需要浏览器兼容性                                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 场景六：IoT / MQTT → Publish/Subscribe

MQTT 是物联网最常用的协议，利用其 **主题订阅** 机制实现候选交换。

```
┌─────────────────────────────────────────────────────────────────────┐
│  MQTT 候选交换                                                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│                         MQTT Broker                                  │
│                        (公网, 可 TLS)                                │
│                             │                                       │
│              ┌──────────────┼──────────────┐                        │
│              │              │              │                        │
│           Device A      Device B      Device C                       │
│                                                                     │
│  Topic 设计:                                                        │
│    webrtc/{device_id}/offer        ← 发布 Offer                      │
│    webrtc/{device_id}/answer       ← 发布 Answer                     │
│    webrtc/{device_id}/candidate    ← 发布 ICE 候选                    │
│    webrtc/{device_id}/hangup       ← 挂断                            │
│                                                                     │
│  流程:                                                              │
│  1. Device A 订阅 webrtc/A/#                                        │
│  2. Device A 发布 SDP Offer 到 webrtc/A/offer                       │
│  3. Device B 订阅了该 topic → 收到 Offer                            │
│  4. Device B 发布 Answer 到 webrtc/A/answer                         │
│  5. 双方通过 webrtc/{id}/candidate topic 交换 Trickle ICE 候选        │
│  6. P2P 或 TURN 直连建立                                            │
│                                                                     │
│  优点:                                                              │
│    - 零额外信道: IoT 设备已有 MQTT 连接                               │
│    - 天然解耦: 不需要设备知道彼此 IP                                  │
│    - QoS 可选: MQTT 支持 QoS 0/1/2，保证投递可靠                     │
│                                                                     │
│  缺点:                                                              │
│    - MQTT Broker 是单点（但可集群）                                  │
│    - Broker 可以看到所有信令（如果不用 E2E 加密）                      │
│    - 对低频、低功耗设备友好，高频率 Trickle ICE 可能不理想              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 场景七：P2P 文件共享 / 去中心化 → 不交换 ICE 候选

BitTorrent、IPFS 等去中心化场景通常**不使用 ICE/STUN/TURN**，而是使用自己的一套 NAT 穿透方案：

```
┌─────────────────────────────────────────────────────────────────────┐
│  P2P 去中心化场景: 不需要 Signaling Server                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  BitTorrent:                                                        │
│    - Tracker / DHT 发现 Peer 的 IP:Port                              │
│    - UDP 打洞 (与 ICE 类似的原理)                                     │
│    - 或 uTP (µTorrent Transport Protocol) over UDP                  │
│    - 没有 SDP、没有 ICE 候选格式，直接交换原始 IP:Port                 │
│                                                                     │
│  IPFS / libp2p:                                                     │
│    - 使用 multiaddr 格式: /ip4/1.2.3.4/tcp/5000                     │
│    - 通过 DHT 或 Bootstrap 节点发现对端地址                           │
│    - AutoNAT (自己写的 NAT 检测，不用 STUN)                           │
│    - Circuit Relay (自己的中继协议，不用 TURN)                        │
│                                                                     │
│  为什么不用 ICE?                                                     │
│    - ICE 设计时假设有信令服务器（SIP/WebSocket）                       │
│    - P2P 文件共享天然去中心化，没有"服务器"概念                        │
│    - libp2p 使用了类似原理（打洞+中继），但协议不同                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 场景八：移动端离线推送 → Push Notification + REST

移动 App 在后台时 WebSocket 可能被系统杀死，需要**推送唤醒 + 候选交换**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  移动端离线候选交换                                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Alice (在线)                 服务器                    Bob (离线)    │
│       │                         │                         │          │
│       │── POST /call (SDP) ──▶  │                         │          │
│       │                         │── FCM/APNs Push ──────▶ │          │
│       │                         │   "有来电! 唤醒处理"       │          │
│       │                         │                         │ 唤醒     │
│       │                         │◀── GET /pending ──────── │          │
│       │                         │   获取 Alice 的 SDP       │          │
│       │                         │── POST /answer ────────▶ │          │
│       │◀── Bob 的 Answer ────── │                         │          │
│       │                         │                         │          │
│       │══════════════ P2P 直连 ═════════════════════════════          │
│                                                                     │
│  关键:                                                              │
│    - 候选信息暂存服务器 (REST API)                                    │
│    - Push 通知只做唤醒，不带候选数据（Push 消息最大 4KB）               │
│    - 唤醒后 Bob 主动拉取 Alice 的候选（REST GET）                      │
│    - Trickle ICE 候选也用 REST POST 投递，服务器暂存                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 与 ICE 的关系

### ICE = 标准化的打洞框架

```
┌─────────────────────────────────────────────────────────────┐
│  UDP 打洞只是"技巧"，ICE 是把它变成标准化协议                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  原始 UDP 打洞:                                              │
│    需要: 中继服务器 + 两个客户端 + 运气                        │
│    问题: 手动协调、无标准、无法处理失败                         │
│                                                             │
│  ICE (RFC 8445):                                            │
│    标准化: 候选收集 → 候选交换 → 连通性检查 → 提名              │
│    自动化: 优先级排序、并行检查、自动降级到 TURN                │
│    可靠: 状态机、定时器、NAT 类型自适应                         │
│                                                             │
│  ICE 中的打洞对应关系:                                        │
│    - 候选收集 → 相当于"向中介报到获取公网地址"                   │
│    - 候选交换 → 相当于"通过中介交换地址信息"                    │
│    - 连通性检查 → 相当于"双方互相打洞+验证"                    │
│    - 提名 → 相当于"选定最优打洞路径"                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### ICE 连通性检查 = 标准化的打洞过程

```
ICE 中的连通性检查（打洞）本质：

1. Agent L 向 Agent R 的候选地址发 STUN Binding Request
   → L 的 NAT 创建映射（打洞）
   → 包到达 R 的 NAT（可能被过滤）

2. Agent R 同时向 Agent L 的候选地址发 STUN Binding Request
   → R 的 NAT 创建映射（打洞）
   → 包到达 L 的 NAT → L 的映射已存在 → 转发给 L

3. L 收到 R 的 Binding Request → 回复 Binding Response
   → R 收到 Response → 验证连通性 → Valid Pair
```

## EIM-NAT 打洞的完整时序

```
时间 │ Alice (10.0.0.1:4000)      NAT-A (1.2.3.4)           NAT-B (5.6.7.8)       Bob (10.0.0.2:5000)
─────┼─────────────────────────────────────────────────────────────────────────────────────────────────
     │
T0   │ ① Binding Req ────────▶    创建映射:
     │  目标: STUN Server       10.0.0.1:4000
     │                           → 1.2.3.4:60000
     │                           (目标: STUN)                                          ◀─── ② Binding Req
     │                                                                              创建映射:
     │                                                                            10.0.0.2:5000
     │                                                                            → 5.6.7.8:55000
     │                                                                            (目标: STUN)
     │
T1   │ Alice得到: "你公网是                                                 Bob得到: "你公网是
     │  1.2.3.4:60000"                                                       5.6.7.8:55000"
     │
     │ ③ 通过 STUN/Signaling 交换地址:
     │    Alice被告知: Bob = 5.6.7.8:55000
     │    Bob被告知: Alice = 1.2.3.4:60000
     │
T2   │ ④ 打洞包 ──────────────▶  复用映射:                                        
     │  目标: 5.6.7.8:55000     10.0.0.1:4000              包到达 ──▶ 查映射:
     │                           → 1.2.3.4:60000                     5.6.7.8:55000
     │                                                    目标不在映射表 → ❌ 丢弃!
     │
     │                    ⑤ Bob的打洞包到达 ▶                ◀──────────────── ⑥ 打洞包
     │  查映射:              目标: 1.2.3.4:60000            创建映射:          目标: 1.2.3.4:60000
     │  找到1.2.3.4:60000                                    10.0.0.2:5000
     │  → 转发给Alice! ✅                                     → 5.6.7.8:55000
     │                                                       (目标: 1.2.3.4:60000)
     │
T3   │ ◀── Bob的包 ─── NAT-A转发 ──────────────────────────────────────────── 来自Bob
     │    打洞成功! ✅
     │
     │ ⑦ 再发一个包 ──────────▶  NAT-A: 映射已存在            包到达 ──▶ 查映射:
     │  目标: 5.6.7.8:55000     直接转发              1.2.3.4:60000→5.6.7.8:55000
     │                                                    找到映射 → 转发给Bob ✅
     │                                                                       ──▶ Bob收到! ✅
     │                                                                        打洞成功!
     │
T4   │ ═══════════════════════ P2P 直连建立 ═════════════════════════════════════════
     │ Alice ◀════════ 双向通信 ═══════════▶ Bob
     │
```

---

## 一句话总结

> **UDP 打洞 = Alice 发包到 Bob 的 NAT（被丢弃但 Alice 的 NAT 开了洞） + Bob 发包到 Alice 的 NAT（从洞进来） + 重试确认双方洞都开了 = P2P 直连**
>
> **关键前提：双方都必须是 EIM-NAT（Cone NAT），任意一方 Symmetric → 打洞失败 → 降级 TURN**
>
> **ICE = UDP 打洞的标准化工程实现，自动化了候选收集→交换→打洞→验证→提名全流程**
